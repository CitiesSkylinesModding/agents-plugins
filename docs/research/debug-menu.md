# The developer menu

**Baseline.** Game version 1.6.0f1. Decompiled source read at that version under `src/`. The installed game read out of the same 1.6.0f1 install; UI-bundle line numbers cite a copy of `Cities2_Data/Content/Game/UI/index.js` reformatted with prettier at its defaults, at `DecompiledCitiesSkylines2/src-ui/source.js`, **135,021 lines** — check that count against your own copy before trusting a line number from it. Mod corpus read 2026-08-09 (22 repositories). Wiki fetched **live** 2026-08-09: `Developer mode`, `Launch Parameters` and `Debugging` all returned real article content, with no bot challenge on any of the three, so nothing here is cited through `survey-wiki-inventory.md`'s snapshot. The live half was run against a running 1.6.0f1 development build with `--developerMode --uiDeveloperMode`, a city loaded (11.7k population), through the gameface CDP tools and the unity SDB tools.

## Findings

### The boundary this topic draws, and the one it is drawn against

This topic owns the developer menu **as a surface**: what it already gives you, how to put your own material into it, and how to operate it on a running game. It owns the developer launch flag whole, because the `diagnostics` ticket was amended on 2026-08-04 to hand developer mode here rather than split it.

`diagnostics` owns the _question_ "why is my mod not working" — the order you check things in, and the log surfaces you check them on. This topic owns the _instrument_. The two meet at exactly one place and it is worth stating in both references: the menu's `Logs` tab (`src/Game/Game.Debug/LogsDebugUI.cs:18`) is a live view onto the same logger configuration `diagnostics` reads off disk, so a reader who has the menu open can change a logger's effectiveness there instead of relaunching with `--logsEffectiveness=`.

Building a player-facing panel is the UI skill's business and not this one's, even though both end at a React component: the developer menu takes no HTML, no CSS and no UI mod. A mod contributes to it by constructing C# widget objects, and the game's own React renders them. The one seam where a UI mod does touch this material is the other way round — the menu's widget components are registered modules a player-facing UI may import (finding "The menu's widgets are importable modules").

### `--developerMode` gates one key binding, and nothing else about the menu

**Ruled (2026-08-01, the setup-skill pass; conflicts.md).** Both `-developerMode` and `--developerMode` work, and the choice of spelling is a house convention rather than a fact about the game. The game parses its command line with `Mono.Options`, whose option pattern opens `^(?<flag>--|-|/)` (`src/Colossal.Core/Mono.Options/OptionSet.cs:134`) and whose `Parse` dispatches on the name alone (`:446`), so `-developerMode`, `--developerMode` and `/developerMode` are interchangeable. The wiki writes the single dash on its `Developer mode` page and the double dash on `Launch Parameters`; neither page is wrong. **What the reference owes:** it writes the double-dash form throughout, as every other shipped page in this plugin does, and it does not present the other spelling as an error a reader should correct — a reader who meets `-developerMode` elsewhere has met a variant. Option _names_ are matched case-sensitively (dictionary lookup at `OptionSet.cs:446`), so the camel case is load-bearing where the dash is not.

The flag itself sets one bool: `configuration.developerMode` (`src/Game/Game.SceneFlow/GameManager.cs:366-368`, description "Enable developer mode"). Three read sites across `src/`, in two areas, and the debug menu is neither:

- **Input bindings.** `InputManager.TryGetComposite` refuses to build any binding whose composite is marked developer-only when the flag is off: `if (compositeInstance.developerOnly && GameManager.instance != null && !GameManager.instance.configuration.developerMode) return false;` (`src/Game/Game.Input/InputManager.cs:1177`). The flag on a composite is `m_DeveloperOnly` (`src/Game/Game.Input/ValueInputBindingComposite.cs:18/48`, surfaced through `src/Game/Game.Input/CompositeInstance.cs:104-112` and `src/Game/Game.Input/ProxyBinding.cs:336-342`).
- **Settings.** A settings property carrying `SettingsUIDeveloperAttribute` is dropped from the options UI without the flag (`src/Game/Game.UI.Menu/AutomaticSettings.cs:751`), and the "About" tab is added only with it (`src/Game/Game.Settings/SharedSettings.cs:78-85`).
- Nothing else. `InputManager.cs:1177`, `SharedSettings.cs:78`, `AutomaticSettings.cs:751` are the complete set of `.developerMode` reads across `src/`; the only other occurrence is the write itself, `GameManager.cs:368`.

**Which bindings the flag actually gates was read live off the running game**, because the input action asset ships inside `Cities2_Data/resources.assets` and reading it offline needs the Unity serialized-file parser `docs/SOURCES.md` entry 5 describes. Method: `Game.Input.InputManager.instance.FindActionMap("Debug")` over SDB, then each action's first `ProxyBinding` and its source composite's `m_DeveloperOnly`. The `Debug` action map holds exactly three actions and all three composites are developer-only:

| Action              | Bindings                                    |
| ------------------- | ------------------------------------------- |
| `Debug UI`          | `<Keyboard>/tab`, `<Gamepad>/rightShoulder` |
| `Debug Prefab Tool` | `<Keyboard>/o`                              |
| `Debug Multiplier`  | `<Keyboard>/shift`                          |

`Rots:` the three action names, their bindings and the `Debug` map name — re-check by repeating that live read, or against the input action asset.

**So without the flag the menu is unreachable by keyboard and fully reachable by code.** `DebugUISystem.debugSystemEnabled` is the literal `true` (`src/Game/Game.UI.Debug/DebugUISystem.cs:136`), which is what the `debug.enabled` binding publishes (`:142`); `DebugUISystem` is registered into `SystemUpdatePhase.UIUpdate` unconditionally (`src/Game/Game.Common/SystemOrder.cs:900`); and `Show()` (`DebugUISystem.cs:181`) is a public method with no flag check. A mod can open the menu on a vanilla launch with `World.DefaultGameObjectInjectionWorld.GetOrCreateSystemManaged<DebugUISystem>().Show()`, and one corpus mod calls the sibling `Hide()` exactly that way (`CS2-Platter/Platter/Tests/Utils/TestUtils.cs:12/27`).

`Verdict:` the wiki says `--developerMode` "[allows] the debug menu to be opened ingame using TAB key" (https://cs2.paradoxwikis.com/Launch_Parameters), and its `Developer mode` page presents the flag as what enables developer mode as a whole. The decompile wins and narrows it: the flag enables the _binding_, and every other developer-menu capability is present without it. The wiki is not wrong about what a player experiences; it is wrong as a description of what a mod may rely on.

`Verdict:` the wiki's `Developer mode` page says **Home** opens the Add Object menu. The live game says the `Debug Prefab Tool` action is bound to `<Keyboard>/o`, single binding, no `Home`. The running game wins. Either the binding moved or the page always described a different build; the reference states `O` and does not repeat `Home`.

### The other developer launch flags, and which one costs performance

Every option the game registers is in one block, `GameManager.ParseOptions` (`src/Game/Game.SceneFlow/GameManager.cs:350-434`). Twenty options, of which the wiki's `Launch Parameters` page names four. Fifteen of the rest are named by no source at all — `cleanupSettings`, `saveAllSettings`, `duplicateLogToDefault`, `qaDeveloperMode`, `logTelemetry`, `help`, `disableThumbnails`, `disablePdxSdk`, `disableUserSection`, `startGame=`, `benchmark`, `noSplash`, `profile=`, `captureStdout=`, `continuelastsave` — and two more are registered outside `GameManager` entirely (`pdx-launcher-session-token=` at `src/Colossal.PSI.PdxSdk/Colossal.PSI.PdxSdk/PdxSdkPlatform.cs:961-964`; `pdxAccount=` and `pdxPassword=` at `src/Colossal.TestFramework/Colossal.TestFramework/AutomationClientSystem.cs:112-120`). The ones this topic's reader needs:

- `developerMode` (`:366`) — above.
- `uiDeveloperMode` (`:370`), described in the game's own help text as "Enable UI debugger and memory tracker". It reaches `new UIManager(configuration.uiDeveloperMode)` (`:1745`), which turns on `enableDebugger`, `enableMemoryTracking` **and `liveReload` together** (`src/Colossal.UI/Colossal.UI/UIManager.cs:185-190`). The port is 9444, the `UIManager` settings default (`src/Colossal.UI/Colossal.UI/UIManager.cs:93`), and the game path creates **one** UI system hosting the whole game UI (`GameManager.cs:1745-1750`), so boot, menu and in-game share the endpoint. `Verdict:` this pass first read `src/Game/Game.UI/UISystemBootstrapper.cs:90` (`settings2.debuggerPort = 9445`) as a second endpoint for the in-game view; the orchestrator's re-derivation overturned that — `settings2` belongs to the **fatal-error view** (`m_FatalUrl`, the `ErrorPage` block at `UISystemBootstrapper.cs:64-95`), the component's own `Awake` logs that it "is only meant for development purpose" (`:40`), `GameManager.cs:1693` (`developerMode: false`) is the `ShowFallbackUI` error path rather than the boot view, and the live 1.6.0f1 process under `--uiDeveloperMode` listened on 9444 alone. The decompile read past the confirming line wins. The maintainer ruled the port number not volatile (2026-08-09), so it ships unmarked.
- `qaDeveloperMode` (`:374`, "Enable tests and automation"). This is the flag that decides whether two whole tabs exist: `Test Scenarios` returns `null` without it (`src/Game/Game.Debug/TestsDebugUI.cs:15-18`) and so does `Platforms` (`src/Game/Game.Debug/DebugSystem.cs:7110-7113`), and part of the `Logs` tab is hidden without it (`src/Game/Game.Debug/LogsDebugUI.cs:60`). Confirmed live: with `qaDeveloperMode=False` the running game published 34 panels and neither of those two was among them.
- `logsEffectiveness=<level>` (`:358`) — a global logger override. `diagnostics` owns it; it is named here only because the menu's `Logs` tab is the live equivalent.
- `disableModding` (`:394`, which also sets `disableCodeModding`) and `disableCodeModding` (`:399`).

**`--burst-disable-compilation` is not a game option at all**, and the difference matters to a reader composing a command line. It is Unity Burst's own, parsed in a static constructor over the raw argument list with an **exact string compare** against `"--burst-disable-compilation"` (`src/Unity.Burst/Unity.Burst/BurstCompilerOptions.cs:683-697`). So the double dash is mandatory for this one flag and optional for every other, and the house convention of writing `--` everywhere happens to keep a reader out of that trap. The same block accepts `--burst-force-sync-compilation` (`:688`) and the environment variable `UNITY_BURST_DISABLE_COMPILATION` (`:703`, anything other than empty or `"0"`).

**This is the flag that costs performance**, and it is the only one any source warns about: the wiki's `Launch Parameters` page calls it "Not recommended for normal gameplay as it slows the game down massively, but useful for debugging native crashes" (https://cs2.paradoxwikis.com/Launch_Parameters). No first-party source contradicts that and the mechanism is obvious, so it ships on the wiki's authority, which `docs/SOURCES.md` entry 10 allows where nothing first-party covers the subject. What the reference should add on its own authority is _why a reader would ever want it_: with Burst compilation off, the game's own jobs are managed code and therefore visible to a Mono debugger, which is the only way to breakpoint them at all.

Of the developer flags proper, `developerMode` costs nothing by itself — three key bindings. **`uiDeveloperMode` does cost:** it opens the debugger socket and a memory tracker, adds live reload's OS file watchers (`UIManager.cs:185-190`, `UILiveReload` building `BufferedFileSystemWatcher`s per host location), and forces `Application.runInBackground` (`src/Colossal.UI/Colossal.UI/UISystem.cs:109-112`) — a process-wide Unity flag, so an unfocused game keeps running at full rate. (An earlier draft read the `runInBackground` write as UI-scoped and concluded no developer flag costs anything; the flag is global.) The menu being **open** costs separately, which is the cost-model finding below.

**There is a second, undocumented way to pass a flag, and it is worth one sentence in the reference** because it is the answer for a store install with no launch-options field. Before parsing, `GameManager` reads `<userDataPath>/runOnce.txt`, appends its contents to the command line, and **deletes the file** (`GameManager.cs:437-444`, merged through `MergeAdditionalCommandLineArguments` at `:326-337`, which de-duplicates through a `HashSet`). `kUserDataPath` is `Application.persistentDataPath` (`src/Colossal.PSI.Common/Colossal.PSI.Environment/EnvPath.cs:85`). `Rots:` the file name.

**There is no in-game text console.** `src/Game/Game.Debug/ConsoleWindow.cs` and `WinConsole.cs` are a Win32 stdout capture, constructed whenever `--captureStdout=` selects a capturing mode — `InitConsole` builds one for every mode except `None` and `Redirect`, and the `console` value only decides whether a Win32 console window is attached (`GameManager.cs:2024-2028`, mode parsing at `:339-348`). Nothing in the game reads a typed command. A reader arriving from a game that has one needs to be told plainly, because the absence is what sends them looking.

### What the menu is: a C# widget tree the game's own React renders

The menu is not an engine overlay and is not IMGUI. Three layers, and knowing where the seam is decides where a mod's code goes.

1. **The widget model is the render pipeline's.** `UnityEngine.Rendering.DebugUI` (`src/Unity.RenderPipelines.Core.Runtime/UnityEngine.Rendering/DebugUI.cs`, 972 lines) owns `Panel`, `Container`, `Foldout`, `Button`, `Value`, `Field<T>` and the rest. `DebugManager` (same namespace) owns the panel list. This is vendored Unity code the game did not write, which is why the extension API reads unlike the rest of the game.
2. **The game populates it.** `Game.Debug.DebugSystem` (`src/Game/Game.Debug/DebugSystem.cs`, 7,777 lines) reflects over attributes and registers panels with `DebugManager` (`:1026-1045`) — on every menu open rather than at startup, per the timing finding below.
3. **The game's own frontend renders it.** `Game.UI.Debug.DebugUISystem` (`src/Game/Game.UI.Debug/DebugUISystem.cs`) is a plain `UISystemBase` publishing a binding group named `debug`, and the React that consumes it is in the shipped bundle under `game-ui/debug/`. Between them, `Game.UI.Debug.DebugWidgetBuilders` (`src/Game/Game.UI.Debug/DebugWidgetBuilders.cs`) translates each `DebugUI.Widget` into a `Game.UI.Widgets.IWidget`, which is the _same_ widget layer the editor and the options screen use.

The `debug` group, complete (`DebugUISystem.cs:142-157`; the constant `kGroup` at `:75` is unused, every call passes the literal):

| Binding                                         | Kind                                                                           | Line       |
| ----------------------------------------------- | ------------------------------------------------------------------------------ | ---------- |
| `debug.enabled`                                 | `ValueBinding<bool>`, initial value the literal `true`                         | `:142`     |
| `debug.visible`                                 | `ValueBinding<bool>`, initial `false`                                          | `:143`     |
| `debug.panels`                                  | `GetterValueBinding<List<string>>` — the tab names, in order                   | `:144`     |
| `debug.selectedIndex`                           | `GetterValueBinding<int>`                                                      | `:145`     |

| `debug.children`                                | `RawValueBinding` inside `new WidgetBindings("debug")` — the whole widget tree | `:147`     |
| `debug.observedBinding`                         | `ValueBinding<IDebugBinding>`, nullable                                        | `:149`     |
| `debug.bindingTriggered`                        | `EventBinding<IDebugBinding>`                                                  | `:150`     |
| `debug.developerInfoVisible`                    | `GetterValueBinding<bool>`                                                     | `:151`     |

`m_WidgetBindings.AddDefaultBindings()` (`:148`) adds the shared widget action triggers into the same group (`src/Game/Game.UI.Widgets/WidgetBindings.cs:31-38`): `debug.invoke` (`InvokableBindings.cs:11`), `debug.setValue` (`SettableBindings.cs:11`), `debug.setExpanded` (`ExpandableBindings.cs:11`), the five list operations (`ListBindings.cs:11/23/35/47/59`) and `debug.setCurrentPageIndex` (`PagedBindings.cs:11`). `Rots:` every binding name in this table.

`Show()` (`DebugUISystem.cs:181-210`) is the whole open path, and it does three things: it sets `debug.visible`, it sets `DebugSystem.Enabled = true`, and it sets `PlatformManager.instance.achievementsEnabled = false`. Unless `"DebugMenu"` is already in `SharedSettings.instance.userInterface.dismissedConfirmations` **or** achievements are already off, it first raises a dismissible confirmation dialog (`Common.DIALOG_MESSAGE[DisableAchievements]`) and only does the last two on a yes. `Hide()` (`:212-220`) sets `visible` false and `DebugSystem.Enabled = false`, and never re-enables achievements. Confirmed live: after the menu had been opened, `PlatformManager.instance.achievementsEnabled` read `False`, `DebugSystem.Enabled` read `True`, and `dismissedConfirmations` did **not** contain `"DebugMenu"`.

**Ruled (2026-08-09, the maintainer; conflicts.md).** `DebugUISystem.Show()` ships as a plainly taught technique, with the confirmation dialog's mechanics — a first open can raise the dialog, the panels build only on its yes, a once-ticked "don't show again" skips it thereafter — and the reference states nothing about the achievements flag. The flag's behaviour stays recorded in this file and in `conflicts.md` as the pipeline's record, not as shipped teaching. (This supersedes the session's earlier delegated self-ruling, which had shipped the consequence set as facts beside the call.)

**Opening and closing the menu builds and tears down every panel it owns.** `DebugSystem.OnStartRunning` calls `RegisterDebug()` and `OnStopRunning` calls `UnregisterDebug()` (`DebugSystem.cs:911-926`), and those are the reflection scan and the panel removal. Measured live: with the menu visible, `debug.panels` held 34 names; after `engine.trigger("debug.hide")` it held **8** — `Display Stats`, `Material`, `Lighting`, `Rendering`, `Decals`, `Main Camera`, `Virtual Texturing`, `Volume` — and after `debug.show` it was 34 again with the previously selected panel restored. The 8 survivors are panels the rendering side registers with `DebugManager` independently of `DebugSystem`; every panel `DebugSystem` contributes to is gone while the menu is shut. This is the reason `SelectPanel` is a no-op unless `visible` (`DebugUISystem.cs:224`) and it is the first half of the cost model.

**What a running game shows is neither 29 nor a subset of it.** Live at 1.6.0f1 in a loaded city with `qaDeveloperMode` off, `debug.panels` held 34 names. The arithmetic: 29 declared tabs minus the two `qaDeveloperMode` ones is 27, plus **seven** panels the rendering stack registers on its own and the game never declares — `Display Stats`, `Material`, `Lighting`, `Rendering`, `Decals`, `Main Camera`, `Volume`. Returning `null` from a `[DebugTab]` method is the sanctioned way to say "no tab right now": `ExecuteMethod` skips `AddPanel` entirely when the list is null (`:1020-1023`).

### The two ECS surfaces, and what neither of them does

Two tabs answer a question about ECS state, and they answer different ones.

**`ECS Components` is an archetype and chunk census, not an entity view.** `ComponentDebugUtils.GetCommonComponents` (`src/Game/Game.Debug/ComponentDebugUtils.cs:26-105`) walks `EntityManager.GetAllArchetypes`, counts how many archetypes carry each component type, then walks `GetAllChunks` to sum entity counts and chunk capacities, and returns the **top 100 component types by archetype count** (`:101-104`). The tab's own widgets are a substring filter over the component's `FullName` (case-insensitive, `:107-110`), an "exclude used archetypes" toggle that keeps only archetypes with zero chunks, and a `Refresh` button — nothing recomputes until you press it (`DebugSystem.cs:733-803`). Each row's value is `"{archetypeCount}, {entityCount/chunkCapacity:F1}%"`, or the archetype count alone when the chunk capacity is zero (`:793`).

Read live in a loaded city: 432,759 entities, 11,393 chunks, 8,134 archetypes; the top rows were `Unity.Entities.Simulate` (8,134 archetypes, 67.2% chunk fill), `Prefabs.PrefabRef` (4,898, 76.5%), `Simulation.UpdateFrame` (3,579, 60.5%), `Common.Updated` (3,181, no percentage), `Rendering.CullingInfo` (3,160, 85.8%). Component names print with the leading `Game.` stripped (`:796`). The empty state is the three widgets and nothing else: the counts and the component list appear only after the first `Refresh`.

**`Search` finds entities and moves the camera to them.** `DebugSystemSearch` (`src/Game/Game.Debug/DebugSystemSearch.cs`) builds an `EntityQuery` from three component filters — All / Any / None, each a set the user adds to through foldouts, with `Buildings` / `Vehicles` / … one-click templates (`:181-200`) — then walks the result array matching a string against the prefab name, the localized prefab name, sub-mesh names, batch meshes and the citizen activity enum (`MatchSearch`, `:462-498`). `Must have transform` filters the result set (`AddToResults`, `:500-508`). With `Deep search` off it stops at the first match and remembers where it stopped, so pressing Apply again resumes the scan (`:562-571`); with it on it scans the whole array. Results page ten at a time as buttons (`ShowResults`, `:588-611`).

Clicking a result calls `FocusEntity` (`:625-645`), and that is a **write**: it sets `ToolSystem.selected`, points the orbit camera controller at the entity, sets the camera's rotation and zoom from the prefab's `ObjectGeometryData` bounds, and makes the orbit controller the active one. `Apply()` itself calls `FocusEntity(results[0])` (`:585`), so running a search moves the player's camera whether or not they click anything.

Driven live from outside: filling the search field with `PoliceStation` and pressing Apply returned `Results (1) (0-251766/432412)` and one button, `Entity(347093:1) PoliceStation02` — i.e. it scanned 251,766 of 432,412 entities before its first hit, and the camera moved.

**Neither tab, and nothing else in `Game.Debug`, enumerates the components of one entity.** `GetComponentTypes` appears twice in the whole of `src/Game/Game.Debug/` and both are `ComponentDebugUtils.cs:35` and `:89`, both over an `EntityArchetype` rather than an entity. There is no vanilla "inspect this entity" view. That absence is the single most useful thing this reference can tell a reader who is used to an ECS inspector, and it is why the `unity-devtools` route (`docs/SOURCES.md` entry 8) exists as the answer instead.

### What the menu tells you about one specific entity, and where it stops

The developer section of the selected-info panel. It is off by default and switched on from inside the menu — a `DebugUI.BoolField` labelled "Show developer info" on the `Gameplay` tab (`src/Game/Game.Debug/DebugSystem.cs:4764-4772`) writing `DebugUISystem.developerInfoVisible` (`src/Game/Game.UI.Debug/DebugUISystem.cs:122-132`). `SelectedInfoUISystem` checks that flag before updating the section (`src/Game/Game.UI.InGame/SelectedInfoUISystem.cs:509`) and before writing it to the `selectedInfo.developerSection` binding (`:906`, binding declared `:171`).

The content is **93 hand-written subsections**, all registered by `DeveloperInfoUISystem.OnCreate` (`src/Game/Game.UI.InGame/DeveloperInfoUISystem.cs:349-441`, 93 `AddDeveloperInfo` calls). Each is one of three helper types, and each decides for itself whether it applies to the selected entity:

- `GenericInfo(shouldDisplay, onUpdate)` — a label and a string value, plus an optional `target` entity that makes the row a link (`src/Game/Game.UI.InGame/GenericInfo.cs:19-52`).
- `InfoList(shouldDisplay, onUpdate)` — a label and a list of `Item { text, entity }` rows, each optionally a link (`src/Game/Game.UI.InGame/InfoList.cs:10-60`).
- `CapacityInfo(shouldDisplay, onUpdate)` — a label, a value and a max (`src/Game/Game.UI.InGame/CapacityInfo.cs:7-20`).

Read live for one police station, `selectedInfo.developerSection` returned thirteen subsections: `Entity` = `"PoliceStation02 347093"`, `Batches (8)` listing every LOD's mesh, `Address` = `"Street 375106 333"` with the road entity as a link target, `Pollution` = `"Ground: 0. Air: 0. Noise: 3200."`, `Garbage` = `"22 (+348 / day) homeless(0 * 25=0)"`, `Water Consuming`, `Efficiency` = `"114 %"`, `Electricity Consuming`, `Send Receive Mail`, `Arrested criminals` = 0/10, `Parking (1)`, `Vehicles availableVehicles:6`, `Employees (8)` with all eight citizen entities as links.

**Where it stops.** The `Entity` row is `NameSystem.GetDebugName(entity)` (`src/Game/Game.UI/NameSystem.cs:199`) — the prefab name and the entity index (`DeveloperInfoUISystem.cs:507-511`). That is the whole of the generic information. Everything else is a hand-written formatter for one domain, so a component nobody wrote a formatter for is invisible, and a **mod's own component is invisible by construction**. There is no component list, no raw field dump, and no buffer view.

### Adding a tab: the attribute route, which needs no patching

Two attributes, both public, both in `Game.Debug`:

```

```

`src/Game/Game.Debug/DebugContainerAttribute.cs:6-9`

```
[AttributeUsage(AttributeTargets.Method)]
public class DebugTabAttribute : PreserveAttribute {
    public readonly string name; public readonly int priority;
    public DebugTabAttribute(string name, int priority = 0) { … }
}
```

`src/Game/Game.Debug/DebugTabAttribute.cs:6-18`

Both derive from `UnityEngine.Scripting.PreserveAttribute`, which is what keeps a managed-code-stripping pass from removing the annotated member.

The scan is `DebugSystem.RegisterDebug` (`src/Game/Game.Debug/DebugSystem.cs:1026-1045`):

```
foreach (Type item in ReflectionUtils.GetAllConcreteTypesWithAttribute<DebugContainerAttribute>()) {
    object target = CreateDebugClass(item);
    foreach (var item2 in item.GetAllMethodsWithAttribute<DebugTabAttribute>()) {
        try { ExecuteMethod(item2.info, target, item2.attribute); }
        catch (Exception exception) { COSystemBase.baseLog.Error(exception, "Failed to register '" + item2.attribute.name + "' Debug UI"); }
    }
}
```

Four things about that scan a mod author has to know, and none of them is guessable:

1. **It sweeps every loaded non-Unity assembly, so a mod is found with no registration.** `GetAllConcreteTypesWithAttribute<T>` filters `GetAllAssemblyTypes(ignoreUnityAssemblies: true)` (`src/Colossal.Core/Colossal.Reflection/ReflectionUtils.cs:472-477`), and that helper skips assemblies whose `FullName` starts with `"Unity"` (`:515-535`). **A mod assembly named `Unity…` is invisible to the entire debug-menu extension surface** — and to every other `ReflectionUtils` sweep in the game.
2. **The type cache is invalidated on assembly load** (`ReflectionUtils.cs:20`, `:498-506`), so a mod loaded after the cache was first built is still found. But the scan itself runs once per menu-open, so timing still matters — see the timing finding.
3. **"Concrete" in the method name means only "not an interface".** The filter is `!t.IsInterface && t.HasAttribute<T>()` (`:475`). An abstract class carrying `[DebugContainer]` passes the filter and then `CreateDebugClass` returns `null` for it (`DebugSystem.cs:1057-1066`), so an instance tab method on it is invoked with no target and fails into the caught-and-logged path — while a static tab method takes the no-target branch (`:1013`) and works. `Verdict:` the first draft closed this on "put the attribute on a concrete class"; the verification pass overturned that generalisation, because a C# static class compiles as abstract-sealed and seven of the sixteen vanilla `[DebugContainer]` classes are `public static class` with working tabs (`AudioDebugUI.cs:11`, `CameraDebugUI.cs:12`, `LogsDebugUI.cs:11`, `ShadowDebugUI.cs:14`, `TestsDebugUI.cs:10`, `ThumbnailsDebugUI.cs:11`, `UIBindingDebugUI.cs:83`). The rule is per method: an instance tab method needs a concrete class; a static one works anywhere.
4. **Each tab's exception is caught and logged, not propagated** (`:1037-1040`). A mod whose tab throws loses that tab silently apart from one `Failed to register '<name>' Debug UI` line in the log. That line is the string to grep for, and it is the bridge to `diagnostics`.

**The declaration may take four shapes**, decided by `ExecuteMethod` (`DebugSystem.cs:996-1024`) from the method's parameter count and whether an instance was created:

| Shape                                                       | What the game does                                                                                                                                                                                                                            |
| ----------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Method, no parameters, on a plain concrete class            | `Activator.CreateInstance(type)` first (`CreateDebugClass`, `:1057-1066`), then invoke on the instance (`:1004`), static or not — the target is simply ignored for a static method. Needs a **public parameterless constructor**.             |
| Method, no parameters, on a `ComponentSystemBase`           | `World.GetOrCreateSystemManaged(method.DeclaringType)` and invoke on the system (`:1006-1010`). `CreateDebugClass` deliberately returns `null` for a system type so this branch is taken, and an instance method works here.                  |
| Static method, no parameters, on a static or abstract class | Invoked with no target (`:1013`) — the branch taken whenever no instance was created and the type is not a system.                                                                                                                            |
| Method taking one `World`                                   | Invoked with `base.World` (`:1016-1019`) — on the created instance for a plain concrete class, with no target otherwise, so on a system or abstract class it must be static or the null-target invoke throws into the caught-and-logged path. |

`Verdict:` the first draft keyed rows on static-versus-instance; the verification pass overturned that — `ExecuteMethod` dispatches on parameter count and `target != null` only, never on the method's own staticness. Every shape returns `List<DebugUI.Widget>`, returning `null` registers no tab, and a method with two or more parameters leaves the list `null` past both branches (`:1000/:1016`), registering nothing with no exception and no log line. **The method may be private**: every vanilla one is, because `GetAllMethodsWithAttribute` passes `BindingFlags.Instance | Static | Public | NonPublic` (`src/Colossal.Core/Colossal.Reflection/ReflectionUtils.cs:493-496`). Vanilla uses all four shapes: `AssetDatabaseDebugUI.BuildAssetDatabaseDebugUI()` is instance-on-a-plain-class (`src/Game/Game.Debug/AssetDatabaseDebugUI.cs:32-33`), `DebugSystem.BuildECSComponentsDebugUI()` is instance-on-a-system (`DebugSystem.cs:733-734`), `TestsDebugUI.BuildTestScenariosDebugUI()` is static (`src/Game/Game.Debug/TestsDebugUI.cs:12-13`), and `DebugSystem.BuildGizmosDebugUI(World)` is static-taking-`World` (`DebugSystem.cs:6708-6709`). `WatchersDebugUI.BuildWatchersDebugUI(World)` is the fifth combination, instance-on-a-plain-class taking `World` (`src/Game/Game.Debug/WatchersDebugUI.cs:23-24`), which the one-parameter branch handles alongside the static case.

A plain `[DebugContainer]` class implementing `IDisposable` gets disposed on menu close (`DisposeDebugClasses`, `:1068-1078`), which is where `WatchersDebugUI` turns its system off (`WatchersDebugUI.cs:18-21`).

**Rebuilding a tab from your own code** is `DebugSystem.Rebuild(Func<List<DebugUI.Widget>>)` or `Rebuild(Func<World, List<DebugUI.Widget>>)` (`:966-994`). It is `public static`, it looks the `DebugSystem` up in `World.DefaultGameObjectInjectionWorld` itself, and it throws `ArgumentException` if the delegate's method does not carry `[DebugTab]` — caught and logged in the same method. This is how a tab whose content depends on state redraws itself; the vanilla `ECS Components` `Refresh` button is exactly `Rebuild(BuildECSComponentsDebugUI)` (`:762`).

**No mod in the 22-repository corpus uses either attribute.** `DebugContainer`, `DebugTab`, `DebugSystem.Rebuild` and the four `DebugWatch*` attributes all return zero hits, including against git objects. The route is open and unused, so the decompile is the only witness and the reference is the first source to describe it.

### Adding a tab: the imperative route, which two mods actually take

`DebugUISystem` renders **every** panel registered with `DebugManager`, not only the ones `DebugSystem` created:

```
private static IEnumerable<DebugUI.Panel> visiblePanels =>
    DebugManager.instance.panels.Where(panel => !panel.isEditorOnly && panel.children.Any(x => !x.isEditorOnly));
```

`src/Game/Game.UI.Debug/DebugUISystem.cs:134`

So a mod can create a panel directly and it appears, with no attribute and no game type involved beyond `DebugManager`. Both corpus mods that add a panel do it this way:

- **AreaBucket** creates one root panel in `IMod.OnLoad`, unconditionally, and holds it in a static: `internal static DebugUI.Panel AreaBucketDebugUI;` (`AreaBucket/Mod.cs:28`) and `AreaBucketDebugUI = DebugManager.instance.GetPanel("Area Bucket", createIfNull: true, groupIndex: 0, overrideIfExist: true);` (`AreaBucket/Mod.cs:76`). Four systems then append a `Foldout` each from their own `OnCreate` — `AreaBucket/Systems/AreaBucketToolSystem/Debug.cs:39-42` and `:165-166` (called from `AreaBucket/Systems/AreaBucketToolSystem.cs:218`), `AreaBucket/Systems/SimpleHideAreaSystem.cs:51` and `:127-143`, `AreaBucket/Systems/AreaReplacementToolSystem/AreaReplacementToolSystem.cs:269-320`, `AreaBucket/Domain/SurfacePreview/SurfacePreviewSystem.cs:184-192`. Its own comment names the mechanism: "Here we borrow Unity's HDRP debug panel (also the CO developer panel) to shows our debug options" (`Debug.cs:39-42`).
- **Traffic** creates a panel named `Traffic_Debug` from a `BaseDebugSystem` subclass and rebuilds it wholesale each time (`Traffic/Code/Debug/LaneConnectorDebugSystem.cs:104-149`), with the whole registration behind `#if DEBUG_GIZMO` (`Traffic/Code/Mod.cs:70-72`) and the rebuild driven from the mod's own UI system (`Traffic/Code/UISystems/ModUISystem.cs:284`).

**The two routes differ in one way that decides which to teach.** A panel created imperatively is **not** torn down when the menu closes, because `DebugSystem.UnregisterDebug` only removes what it registered (`DebugSystem.cs:1047-1055`, `UnregisterDebugItems` at `:1080-1083`). Its getters therefore keep running whenever the frontend is subscribed, and its `DebugUI.Widget` objects live for the process. The attribute route's panels are rebuilt from scratch on every open, which is what lets a tab reflect state that changed while it was closed. The imperative route is the one to reach for when the panel must outlive the menu or must be built before `DebugSystem` exists; the attribute route is the default.

### A tab name that already exists merges instead of duplicating, and the match is case-insensitive

`DebugSystem.AddPanel` (`src/Game/Game.Debug/DebugSystem.cs:1085-1095`) calls `DebugManager.GetPanel(name, createIfNull: true, groupIndex, overrideIfExists: false)`. With `overrideIfExist` false, `GetPanel` **returns the existing panel** when one already carries that name (`src/Unity.RenderPipelines.Core.Runtime/UnityEngine.Rendering/DebugManager.cs`, `GetPanel` body: `if (panel != null) { if (!overrideIfExist) return panel; … }`), and the caller then adds its widgets to that panel's children. Name matching is `StringComparison.InvariantCultureIgnoreCase` (`DebugManager.cs:530`). But `AddPanel`'s own middle lines change the answer where two `[DebugTab]`s share an exact name: `m_Panels` — an ordinally keyed `Dictionary<string, List<DebugUI.Widget>>` (`DebugSystem.cs:253`) — is consulted first, and the widget list previously registered under that exact name is removed from the panel before the new list is added (`:1088-1093`).

Three consequences a mod author needs:

- `[DebugTab("Gizmos")]` on a mod method **collides ordinally and only one widget list survives** — `AddPanel` removes whichever list registered first, normally the vanilla one since a mod assembly is enumerated after `Game.dll`, but nothing fixes that order — while `[DebugTab("gizmos")]` misses the ordinal key, joins the case-insensitively matched panel, and **appends**. (An earlier draft of this finding read only the `GetPanel` half and recorded both spellings as appending; the `AddPanel` removal overturns the exact-name case.)
- The `groupIndex` — the `[DebugTab]` priority — is **ignored** when the panel already exists, because `GetPanel` only applies it on creation. A mod appending to an existing tab cannot move it.
- Tab order is `groupIndex` ascending: `DebugUI.Panel` implements `IComparable<Panel>` comparing `groupIndex` alone (`src/Unity.RenderPipelines.Core.Runtime/UnityEngine.Rendering/DebugUI.cs:963-969`), and `DebugManager` re-sorts on every panel add (`DebugManager.cs:391-394`). `List<T>.Sort` is not stable, so equal priorities give an arbitrary order — which is why the seven priority-0 vanilla tabs are not in declaration order.

Live evidence for the merge: while the menu was hidden, `Virtual Texturing` remained among the eight surviving panels even though `DebugSystem.cs:7544` declares a `[DebugTab("Virtual Texturing", -19)]`. The rendering side had already registered a panel of that name; the game's tab added its widgets to it, and `UnregisterDebug` removed only those widgets, leaving the panel standing. This witnesses the panel-level merge — a `[DebugTab]` joining a rendering-registered panel, which has no `m_Panels` entry to remove — and says nothing about two `[DebugTab]`s sharing a name.

### What a mod gets for free by annotating a field: the watch attributes

Four attributes, all public, all in `Game.Debug`:

| Attribute                                                                                      | Target                    | File                               |
| ---------------------------------------------------------------------------------------------- | ------------------------- | ---------------------------------- |
| `[DebugWatchValue]` with `color`, `updateInterval` (default −1), `historyLength` (default 128) | method, property or field | `DebugWatchValueAttribute.cs:5-13` |
| `[DebugWatchOption]`                                                                           | field                     | `DebugWatchOptionAttribute.cs:5-8` |
| `[DebugWatchDeps]`                                                                             | field                     | `DebugWatchDepsAttribute.cs:5-8`   |
| `[DebugWatchOnly]`                                                                             | class                     | `DebugWatchOnlyAttribute.cs:5-8`   |

They are collected by `DebugWatchSystem.BuildSystemFoldouts` (`src/Game/Game.Debug/DebugWatchSystem.cs:467-655`), which the `Watchers` tab calls (`src/Game/Game.Debug/WatchersDebugUI.cs:39`).

**The sweep is over `World.Systems`, not over types.** `foreach (ComponentSystemBase system in base.World.Systems)` (`:472`). So the attributes work on **any managed system already created in the world** — a mod's included — and on nothing else. A static class, a plain object, an unmanaged `ISystem`: none of them appear. Members are collected with `BindingFlags.Instance | Public | NonPublic` over fields, properties and methods (`GetWatchValueMembers`, `:657-662`), so a private field works.

**Which value types actually produce a graph.** `Watch.TryCreate` (`:47-90`) succeeds only on an accessor implementing `ITypedValueAccessor<T>` for `int`, `int2`, `int3`, `float`, `float2`, `float3`, `uint`, `uint2`, `uint3`, or `DebugWatchDistribution` — and which accessors are typed is decided one step earlier. `Verdict:` the first draft of this finding read the `TryCreate` list as the set a plain member may take; the verification pass overturned it. `CreateTypedAccessor` (`:665-721`) wraps a plain member's accessor into a typed `CastAccessor<T>` only for `int`, `uint` and `float`, and produces the vector forms only inside its `NativeValue<>` branch — a raw `FieldAccessor`/`PropertyAccessor` implements `IValueAccessor` alone — so a bare `int2`/`float3`-typed field, property or method falls through every `TryCreate` test to the blank row, and the vector forms graph only through `NativeValue<T>` (or as `NativeArray<T>` elements). One more accepted type sits outside the `TryCreate` list: a `NativePerThreadSumInt` field is special-cased into a property accessor over its `Count` (`src/Game/Game.Reflection/ValueAccessorUtils.cs:19-25`), which is an `int` and graphs. **Anything else yields a row whose getter returns the empty string** (`:522-527`) — not an error, not the value, a blank. That silent blank is the trap: a mod author annotating a `long`, a `double`, a `bool`, a bare vector type or a struct gets a labelled row with nothing in it.

A `NativeArray<T>` field is special-cased (`:529-559`): the tab adds a `Values` foldout with one row per element and a `Watches` foldout with one toggle per element, **capped at 100 elements** (`:532`). Element names come from `GetArrayItemName` (`:786-797`), which reads `[ResourceArray]` or `[EnumArray]` on the same member to name the indices, and otherwise prints the index.

**`updateInterval` must be a power of two.** The sampler tests `frameIndex & (updateInterval - 1)` (`HistoryWatch.Advance`, `:128-138`); any other value silently samples on a bit pattern rather than a period. The default, when the attribute leaves `updateInterval` at −1, is the system's own simulation cadence: `UpdateSystem.GetInterval(system, SystemUpdatePhase.GameSimulation, out var interval, out _)` (`:495`, applied `:501`). Sampling is driven from `DebugWatchSystem.OnUpdate` (`:429-444`) off `SimulationSystem.frameIndex`, so **a watch samples on simulation frames, not render frames**, and a system that runs rarely produces a nearly flat graph. Measured live: enabling the `Debug Birth` watch on `BirthSystem` produced exactly one non-zero sample in nine seconds of running simulation, at frame index 8,478,720.

`[DebugWatchOption]` renders **only for an enum field**; `CreateOptionWidget` returns `null` for anything else (`:737-784`) and the field is dropped without a message. `[DebugWatchDeps]` marks `JobHandle` fields (`GetWatchDepsFields`, `:723-728`, filtered to `f.FieldType == typeof(JobHandle)`) which the accessor completes before reading the watched value, so a watch on a field a job writes reads a settled value rather than a torn one. `[DebugWatchOnly]` on the system class makes the game **enable the system only while its foldout is open or one of its watches is active** (`:596-604` and `:431-434`) — that is how a debug-only system costs nothing when nobody is looking at it, and it is the attribute a mod author is most likely to want and least likely to find.

The list rebuilds only on the tab's `Refresh System List` button (`WatchersDebugUI.cs:29-33`), so a system created after the tab was built is missing until you press it.

Live: the `Watchers` tab listed **27** vanilla systems carrying these attributes — `AgingSystem`, `BirthSystem`, `CitizenHappinessSystem`, `CommercialDemandSystem`, `TripNeededSystem`, `WorkProviderSystem` and 21 more. `Rots:` that count.

### The gizmo tab cannot be joined, and why the base class is not the mechanism

`BaseDebugSystem` (`src/Game/Game.Debug/BaseDebugSystem.cs:8-63`) is a `GameSystemBase` with three things on it: a list of `Option { name, enabled }` populated by the protected `AddOption(displayName, defaultEnabled)` (`:32-37`), a `JobHandle OnUpdate(JobHandle)` override point (`:46-49`), and the pair `OnEnabled(DebugUI.Container)` / `OnDisabled(DebugUI.Container)` (`:51-57`) that let a system add extra widgets when it is switched on. Twenty-nine classes across `src/Game/` derive from it, and 31 systems are registered into `SystemUpdatePhase.DebugGizmos` (`src/Game/Game.Common/SystemOrder.cs:1027-…`), which `GameManager` drives after `LateUpdate` (`src/Game/Game.SceneFlow/GameManager.cs:2407`; the phase is `src/Game/Game/SystemUpdatePhase.cs:31`). **None of the three sets coincides**, which is the clearest proof that no registry connects them. The `Gizmos` tab's roster is a fourth list of 30 (`DebugSystem.cs:6717-6746`); two of those thirty are not `BaseDebugSystem` subclasses at all (`GroundWaterDebugSystem`, `SoilWaterDebugSystem`), which is why `AddSystemGizmoField<T>` is generic over `ComponentSystemBase` and tests `is BaseDebugSystem` at `:6661`; and one `BaseDebugSystem` subclass is on no gizmo row (`TradeCostDebugSystem`). Membership of each list is hand-maintained.

**But the `Gizmos` tab's roster is a hard-coded list, not a scan.** `BuildGizmosDebugUI` (`DebugSystem.cs:6709-6748`) is thirty literal `AddSystemGizmoField<T>(ref container, world, …)` calls, one per vanilla system, with no reflection anywhere. `AddSystemGizmoField<T>` (`:6643-6706`) is generic over `ComponentSystemBase`, adds one `DebugUI.EnumField` toggling `system.Enabled`, and then — only if the system is a `BaseDebugSystem` (`:6661-6664`) — renders one `EnumField` per `Option` and calls `OnEnabled(container)`.

So **deriving from `BaseDebugSystem` does not put a mod on the Gizmos tab, and nothing can**: there is no registry the base class writes itself into. What the base class buys is the option list, the enable/disable hooks and a `Dependency`-threading `OnUpdate` — the _content_ of a gizmo entry, with no route to the vanilla tab's display. A mod that wants that display renders it itself, and the corpus shows exactly that: **Traffic** hand-ports `AddSystemGizmoField`'s body into its own `InitGizmoFields` (`Traffic/Code/Debug/LaneConnectorDebugSystem.cs:104-149`), reproducing the `ToggleEnum`/`autoEnum` idiom and the `setIndex = delegate {}` no-op, and puts the result in its own `Traffic_Debug` panel.

Two routes are open to a mod and the reference should give both: render your own field into your own panel (what Traffic does), or declare a case-varied `[DebugTab("gizmos")]` and let `AddPanel` merge your widgets into the vanilla tab by name — case-varied because the exact spelling hits `m_Panels` and costs one of the two lists, by scan order (the collision finding above). The second is untried by anyone — nothing in the corpus does it — and follows from the merge semantics rather than from an observation, so it carries `Unconfirmed:` — settled by declaring a `[DebugTab("gizmos")]` in a test mod and reading `debug.children` with that tab selected.

Live shape of the tab, for a reference that wants to describe what a reader will see: 30 rows, each `<System Name Nicified>` with a `< Disabled >` / `< Enabled >` arrow control; switching one on rebuilds the panel in place and inserts that system's options directly beneath it (measured: 30 fields → 33 after enabling `Zone Debug System`, which added `Draw Pivots`, `Draw Grids`, `Vacant Lots`).

### Which widget kinds reach the frontend, and what happens to the rest

`DebugWidgetBuilders.TryBuildWidget` (`src/Game/Game.UI.Debug/DebugWidgetBuilders.cs:37-108`) is a chain of `is` tests. Seventeen `DebugUI` kinds match:

`Foldout` → `ExpandableGroup`; `Container` → `Group`; `ValueTuple` → `Group` of `ValueField`s; `Button` → `Button`; `Value` → `ValueField`; `BoolField` → `ToggleField`; `IntField` → `IntSliderField` or `IntArrowField`; `Game.Debug.IntInputField` → `IntInputField`; `UIntField` → `UIntSliderField` or `UIntArrowField`; `FloatField` → `FloatSliderField` or `FloatArrowField`; `Vector2Field` / `Vector3Field` / `Vector4Field` → `Float2/3/4SliderField`; `EnumField` → `EnumField`; `BitField` → `FlagsField`; `ColorField` → `ColorField`; `TextField` → `StringInputField`.

A numeric field becomes a **slider** only when both `min` and `max` are set away from the type's extremes, and an **arrow control** otherwise (`:168-190` for int, `:192-214` for uint, `:216-240` for float). That is the one place a mod's choice of `min`/`max` changes the control the reader gets.

Subclasses inherit their base's case, and the chain's order is what makes that work: `Foldout` is tested before `Container` (`:39` before `:43`) even though `Foldout : Container`, so `DebugUI.Table.Row : Foldout` renders as an expandable group. `HBox`, `VBox` and `Table` are all `Container` subclasses and all render as a flat `Group`, losing their layout intent. `ProgressBarValue : Value` renders as a plain value, losing its percentage formatting. `HistoryBoolField` and `HistoryEnumField` render as their non-history bases.

**Four kinds match nothing and are dropped in silence**: `DebugUI.ObjectField`, `DebugUI.ObjectListField`, `DebugUI.ObjectPopupField` and `DebugUI.MessageBox`. `TryBuildWidget` returns `null` and `BuildWidgets` simply skips it — no log line, no placeholder (`:24-31`). `CreateVolumeParameterWidget` would build an `ObjectListField` for an array-valued volume parameter (`DebugSystem.cs:542-547`), but no vanilla `OverrideablePropertiesComponent` declares one — the only array-typed `VolumeParameter` in the decompile is HDRP's diffusion-profile list, which the Climate stack never uses — so vanilla never takes that branch and the `Climate` tab renders without holes. (An earlier draft inferred "the Climate tab therefore has holes"; the sweep of the eight `OverrideablePropertiesComponent` subclasses' parameter types overturns it.)

**`isEditorOnly` and `isHiddenCallback` behave differently, and only one of them works.** A widget flagged editor-only is skipped at the top of `BuildWidgets` (`:20-23`) and a panel with no non-editor children is filtered out of `visiblePanels` (`DebugUISystem.cs:134`). But `DebugUI.Widget.isHiddenCallback` (`DebugUI.cs:301`, `:351`) is **never read by the translation** — `DebugWidgetBuilders` sets only `displayName` on the built widget and never wires `hidden`. So a `isHiddenCallback` returning true hides the widget in the render pipeline's own IMGUI renderer and does nothing at all in this game's menu.

**The frontend has one more layer of dropping, and it is loud rather than silent.** The React dispatches on `props.__Type`, the fully qualified C# type name (`src-ui/source.js:49807-49822`), against a 20-entry map `debugWidgetComponents` (`src-ui/source.js:69210-69230`). A `__Type` not in the map renders as a red box with yellow text reading `Unknown element type <name>` (`src-ui/source.js:49792-49796`) — it does not throw and does not warn. The map covers exactly what `DebugWidgetBuilders` can produce, so vanilla never shows one; a mod that reaches the widget layer another way can. Sixteen of the map's twenty entries name a `Game.UI.Widgets.*` kind and four name a debug-only one, so **37 of the 53 `Game.UI.Widgets.WidgetType` members are unmapped** (`src-ui/source.js:48588-48640` for the enum): `DropdownField`, `Label`, `MultilineText`, `Divider`, `PagedList`, `AnimationCurveField`, `Int2InputField` and the rest all exist in the shared widget layer, render in the editor, and would come out as red boxes here.

Four `__Type` values are debug-only (`src-ui/source.js:68282-68285`): `Game.UI.Debug.IntArrowField`, `UIntArrowField`, `FloatArrowField` and **`Game.UI.Debug.Image`**. That last one is a dead surface worth one line: `Game.UI.Debug.Image` is a real C# widget (`src/Game/Game.UI.Debug/Image.cs:6-31`, carrying a `uri`), the frontend maps it to a `BoundImage` component, and **nothing in the game constructs one** — it is unreachable from any `DebugUI.Widget`, so no mod can produce it through the supported route either.

### The tool enumeration a mod can crash, and the exact shape that crashes it

The `Simulation` tab builds an "Active tool" radio from every type assignable to `ToolBaseSystem`:

```
Type[] allTypesDerivedFromAsArray = ReflectionUtils.GetAllTypesDerivedFromAsArray<ToolBaseSystem>();
ToolBaseSystem[] array = new ToolBaseSystem[allTypesDerivedFromAsArray.Length];
GUIContent[] array2 = new GUIContent[allTypesDerivedFromAsArray.Length];
for (int i = 0; i < allTypesDerivedFromAsArray.Length; i++) {
    Type type = allTypesDerivedFromAsArray[i];
    array[i] = (ToolBaseSystem)base.World.GetOrCreateSystemManaged(type);   // ← DebugSystem.cs:1235
    array2[i] = new GUIContent(array[i].toolID);
}
```

`src/Game/Game.Debug/DebugSystem.cs:1229-1237`, feeding `RadioSelection` at `:1240-1246`.

`GetAllTypesDerivedFromAsArray<T>` filters on `typeof(T).IsAssignableFrom(t)` with **no abstract test** (`src/Colossal.Core/Colossal.Reflection/ReflectionUtils.cs:465-470`), and it sweeps every loaded non-Unity assembly. So the array contains abstract types, including the game's own `ToolBaseSystem` (`src/Game/Game.Tools/ToolBaseSystem.cs:28`) and `ObjectToolBaseSystem` (`src/Game/Game.Tools/ObjectToolBaseSystem.cs:25`).

**Why vanilla survives it, and this is the part that makes the failure mode predictable.** `World.GetOrCreateSystemManaged(Type)` resolves through `GetExistingSystemInternal(type) ?? CreateSystemInternal(type)` (`src/Unity.Entities/Unity.Entities/World.cs:400-408`), and `m_SystemLookup` maps **every base type in a created system's chain** back to that system: `AddTypeLookupInternal` walks `type = type.BaseType` up to `ComponentSystemBase`, registering each (`World.cs:275-285`, called from `AddSystem_Add_Internal` at `:292`). So once any concrete tool exists in the world, `typeof(ToolBaseSystem)` and `typeof(ObjectToolBaseSystem)` already have entries and never reach construction. Take the miss and you reach `TypeManager.ConstructSystem`, which ends in `Activator.CreateInstance(systemType)` (`src/Unity.Entities/Unity.Entities/TypeManager.cs:2989-2997`) — and that throws on an abstract type. `TypeManager.GetSystemTypeIndex` will happily add an abstract type to its tables first (`TypeManager.cs:3261-3275`), so nothing rejects it earlier.

**The shape that breaks it is therefore an abstract `ToolBaseSystem` descendant with no concrete descendant already created in the world at that moment.** The corpus supplies one: **CS2-NetworkTools** ships `public abstract partial class NT_BaseToolSystem : ToolBaseSystem` (`CS2-NetworkTools/NetworkTools.Mod/Systems/Tools/Base/BaseToolSystem.cs:61`) and a second intermediate layer, `public abstract partial class NT_PathSelectionToolSystem : NT_BaseToolSystem` (`.../Systems/Tools/PathSelection/PathSelectionToolSystem.cs:46`). Those are the only abstract tool bases in the corpus.

**The symptom** is that the whole `Simulation` tab disappears, with the same event logged under both names. `DebugSystem` itself carries `[DebugContainer]` (`DebugSystem.cs:68`) and `BuildSimulationDebugUI` carries `[DebugTab("Simulation", -1000)]` (`:1218`), so `RegisterDebug`'s attribute scan invokes it inside the catch that interpolates the tab name — `Failed to register 'Simulation' Debug UI` (`:1039`) — and the explicit `Rebuild(BuildSimulationDebugUI)` that follows (`:1043`) logs the method-name form (`:990-993`). A grep for `Simulation` finds the failure on either line, and the rebuild re-fires on active-tool changes and widget edits while the menu stays open (`:936-939`, `:1177`, `:1187`), so the method-name form repeats. (An earlier draft read the two paths as alternatives and concluded the tab name never reaches the log; the `[DebugContainer]` on `DebugSystem` itself overturns that.)

**A published mod exists whose only purpose is to survive this, and its source is not reachable from a plain clone.** The fix belongs to **CS2-WriteEverywhere**, in its `BelzontCommons` submodule (`CS2-WriteEverywhere/.gitmodules`, `[submodule "BelzontWE/Commons"] url = https://github.com/klyte45/CS2-BelzontCommons.git`, pinned at `3698b64`); `git submodule status` reports it and the repo's two other submodules uninitialised, so the directory is empty. What is visible is the repository's own change record, `CS2-WriteEverywhere/.klyte-kanban/Archive/Sprint_010/T_2_0096_DebugSystem-abstract-type-patch-pre-filter-array2-and-loop-safety.md`, which describes a Harmony transpiler that injects a `FilterAbstractTypes` call **immediately after** `GetAllTypesDerivedFromAsArray` stores into local 1 (`:32-34`), so that both parallel arrays size themselves from the filtered length; it records that an earlier in-loop design resized only one of the two arrays and left trailing nulls that null-reffed in `RadioSelection` (`:22`, `RadioSelection` being `DebugSystem.cs:1116`); and it records a conflict guard that matches all 24 opcodes of the unpatched loop and skips injection if they differ, assuming another mod already fixed it (`:32-34`). `Unconfirmed:` the transpiler's shape — the description is the mod's own prose and not read source; checking out that submodule would settle it.

**Live, at 1.6.0f1 with no mods loaded, the `Simulation` tab renders and its "Active tool" arrow control reads `<Default Tool>`** — confirming the base-type-lookup path rather than the throw.

### The cost model: what an open widget costs, and what it may therefore do

`DebugUISystem` is a `UISystemBase` in `SystemUpdatePhase.UIUpdate` (`src/Game/Game.Common/SystemOrder.cs:900`), driven once per rendered frame by `UIUpdateSystem` (`src/Game/Game.UI/UIUpdateSystem.cs:17-20`). `UISystemBase.OnUpdate` calls `Update()` on every update binding each time (`src/Game/Game.UI/UISystemBase.cs:39-46`), and `m_WidgetBindings` is one (`DebugUISystem.cs:147`).

`WidgetBindings.UpdateChildrenBinding` returns immediately unless `active` (`src/Game/Game.UI.Widgets/WidgetBindings.cs:65-84`), and `active` on an event binding is `observerCount > 0` (`src/Colossal.UI.Binding/Colossal.UI.Binding/EventBindingBase.cs:16`). So **nothing runs while nobody is subscribed to `debug.children`** — which is the case whenever the menu is closed or no panel is selected.

When it is active, `UpdateSubTree` walks the tree and calls `IWidget.Update()` on **every node** (`WidgetBindings.cs:86-112`). Four rules follow, and together they are what a mod author actually needs:

1. **An editable field's getter runs once per rendered frame.** `ReadonlyField<T>.Update` calls `GetValue()` unconditionally and compares (`src/Game/Game.UI.Widgets/ReadonlyField.cs:41-64`), and for a debug field that is `DebugFieldAccessor<T>.GetTypedValue()` → `DebugUI.Field<T>.GetValue()` → the mod's lambda (`src/Game/Game.UI.Debug/DebugFieldAccessor.cs:30-33`). Every `BoolField`, `IntField`, `FloatField`, `TextField`, `EnumField`, `BitField`, `ColorField` and `Vector*Field` is in this class.
2. **`DebugUI.Value` is the one throttled kind.** `Game.UI.Debug.ValueField.Update` counts a timer down by `Time.deltaTime` and calls the getter only when it expires, resetting to `m_DebugWidget.refreshRate` (`src/Game/Game.UI.Debug/ValueField.cs:24-38`). `refreshRate` defaults to `0.1f` (`src/Unity.RenderPipelines.Core.Runtime/UnityEngine.Rendering/DebugUI.cs:402`), i.e. 10 Hz, and is settable per widget. This is also the only kind whose `formatString` is honoured (`ValueField.cs:34` calling `DebugUI.Value.FormatString`, `DebugUI.cs:419-426`).
3. **A collapsed `Foldout` costs nothing at all.** `ExpandableGroup.visibleChildren` returns `Array.Empty<IWidget>()` when not expanded (`src/Game/Game.UI.Widgets/ExpandableGroup.cs:48-58`), so `UpdateSubTree` never descends and no child getter runs. A `Container` becomes a `Group`, whose `visibleChildren` is always `children` (`src/Game/Game.UI.Widgets/Group.cs:36`), so it costs its whole subtree unconditionally. **Put an expensive getter under a `Foldout`, never under a `Container`** is the actionable form.
4. A widget whose `hidden` callback returns true skips its own `Update()` (`src/Game/Game.UI.Widgets/Widget.cs:96-99`) — but nothing sets `hidden` on a debug widget, per the `isHiddenCallback` finding above, so this lever is not reachable from `DebugUI`.

So the rule for a getter: it is called at frame rate unless it is on a `DebugUI.Value`, and it must not allocate, must not complete a job handle, and must not run an `EntityQuery`. Vanilla obeys this by computing on a `Button` press and having the getters read a cached field — `BuildECSComponentsDebugUI` is the model (`DebugSystem.cs:756-800`: the `Refresh` button runs the census, the getters return captured locals).

Confirmed live by polling the DOM: the `Simulation` tab's `Smooth speed` and `Step Time (ms)` rows changed on every 250 ms sample (`0,4992363` → `0,4993685` → `0,4994762`, and `1,65125` → `0,97455` → `0,9568`), so a value does update in place and a poll observes it changing.

### When a mod's tab is registered, and what that timing forecloses

`RegisterDebug` runs from `DebugSystem.OnStartRunning` (`src/Game/Game.Debug/DebugSystem.cs:911-918`), and `DebugSystem` is enabled only by `DebugUISystem.Show()` (`src/Game/Game.UI.Debug/DebugUISystem.cs:199`/`:206`) — it starts disabled (`DebugSystem.OnCreate` sets `base.Enabled = false`, `DebugSystem.cs:816`). So **the scan happens the first time the menu is opened, and again on every subsequent open**, never at load.

`DebugSystem` also restarts itself on two lifecycle events, but only while already enabled: `OnGamePreload` when the mode is `MainMenu` (`DebugSystem.cs:949-956`) and `OnGameLoaded` (`:958-964`), both calling `Restart()` = `OnStopRunning(); OnStartRunning();` (`:943-947`). That is what rebuilds every tab when a save loads.

What this forecloses, and what it does not:

- **It does not foreclose late loading.** A mod whose assembly loads after the game started is still found, because the scan runs after it and `ReflectionUtils` invalidates its type cache on every `AssemblyLoad` (`ReflectionUtils.cs:20`, `:498-506`). There is no race to win, and no need to register anything in `OnLoad`.
- **It does foreclose one-shot side effects in the tab method.** The method runs again on every open and on every save load, so anything it does beyond building widgets happens repeatedly. `DebugSystemSearch.BuildSearchDebugUI` resets `m_SearchString`, `m_SelectedPage` and `m_SelectedEntity` on every call (`DebugSystemSearch.cs:86-88`), which is why a search does not survive closing the menu.
- **It does foreclose holding a widget reference across a close.** `UnregisterDebug` removes the widgets from the panel and disposes the container instances (`DebugSystem.cs:1047-1055` and `:1068-1078`), so a `DebugUI.Widget` a mod stashed in a static is orphaned after the first close and will never be rendered again.
- The **imperative** route sidesteps all of this, at the price named in that finding: an imperatively registered panel is never torn down and never rebuilt.

### Driving the menu from outside: what works, and the two traps

Everything below was established against the running game through the gameface CDP tools. The menu is **not** read-only from outside; every control responded.

**Reading a binding.** The route that works is the one `docs/SOURCES.md` entry 9 documents: `engine.on("debug.<name>.update", cb)` then `engine.trigger("debug.<name>.subscribe")`, with `engine.trigger("debug.<name>.unsubscribe")` to end it. Verified for `enabled` (`true`), `visible`, `panels` (34 strings), `selectedIndex`, `developerInfoVisible`, `children` (the whole widget tree, each node `{path, props:{__Type, …}, children}`) and `watches`. Reading `selectedInfo.developerSection` the same way returned the full developer subsection payload quoted earlier.

**Show, hide and select.** `engine.trigger("debug.show")`, `"debug.hide")` and `"debug.selectPanel", <index>)` all work. Selecting a panel from outside renders its content: `selectPanel(2)` produced `selectedIndex: 2`, `selectedPanel: {displayName: "Simulation"}` and the tab button carrying the class `selected`, with 13 widget rows beneath it. **The argument is a zero-based integer index into `debug.panels`, not a name** (`TriggerBinding<int>` at `DebugUISystem.cs:155`, `SelectPanel(int)` at `:222-229`). An out-of-range index yields a null panel and an empty tree rather than an error (`GetPanel`, `:301-309`).

**Trap one: `selectPanel` is a no-op while the menu is hidden** (`:224`), and worse, while hidden there is almost nothing to select — the panels are torn down. Measured: `hide`, then `selectPanel(2)`, gave `selectedIndex: -1`; `show` restored `selectedIndex: 9`, the panel that had been selected before. So the driving order is fixed: `debug.show`, let the binding round-trip, _then_ `debug.selectPanel`.

**Trap two: `game_fill` does not commit a text field.** The debug `StringInputField` component commits on **blur**, not on change: its `onChange` only updates local React state and its `onBlur` calls the `setValue` trigger (`src-ui/source.js:69070-69088`). Measured directly — after `game_fill` set the DOM input to `PoliceStation`, `debug.children` still reported the field's value as the _previous_ commit `FireStation`; dispatching a bubbling `focusout` on the input moved it to `PoliceStation`. So a driver must follow a fill with `el.dispatchEvent(new FocusEvent('focusout', {bubbles: true}))`. The same shape applies to `IntInputField` (`:69089-69109`).

**Clicks work everywhere else.** `game_click` on an arrow control's right button switched `Zone Debug System` from `Disabled` to `Enabled` and the panel rebuilt in place with that system's three options inserted; the left button switched it back. `game_click` on a toggle flipped `Show developer info` and the `debug.developerInfoVisible` binding followed. `game_click` on a `Button` ran its action (`Refresh` on `ECS Components` produced the census; `APPLY SEARCH` ran the search). `game_click` on a foldout header expanded it.

**Selectors, for a driver.** The root is `div.debugging_dvz` containing `div.debug-ui_M_y`; inside it `div.inspector_GbW` holds `div.tab-bar_b_c` (one `button.button_BNH` per tab, the active one also carrying the literal class `selected`) and a scrollable holding the widget tree; a second column `div.output-column_py9` holds the binding-observation and watch outputs. Every field is `div.field_vGA` with `div.label_KyX` and `div.control_b3l`; a plain value's control is `div.content_EQJ`, a toggle's is `div.toggle_x2y` (plus `checked`/`unchecked`), an arrow control is two `button.button__Wn` around `div.value_fMT`, a text input is `input.text-input_Y20`, a button is `button.button_hxl`, a foldout header is `.foldout-button_Ugi`, a group title is `div.title_Xkf`. `Rots:` every one of these class names — they are content-hashed and change on any UI rebuild. The class maps are in the bundle (`src-ui/source.js:69695-69709` for the menu shell, `:68433-68438` for the field layout, `:68270` for the tab theme).

**The menu survives a view reload, and that is what a UI mod rebuild causes.** After `location.reload()` the tab bar came back with 34 tabs, the previously selected panel (`Watchers`) still selected, and its 27 system foldouts rendered. Nothing is lost because the state lives in C#: the frontend re-subscribes to `debug.visible`, `debug.panels` and `debug.selectedPanel` and is handed the same values.

**A gizmo can be toggled from outside and cannot be captured through the UI screenshot.** Toggling `Zone Debug System` on and taking a `game_screenshot` showed the menu with the toggle Enabled and its three options, and nothing else: gizmos are drawn by the game's renderer into the 3D view, which never reaches the Cohtml view a CDP capture holds. `Unconfirmed:` that the Unity plugin's `UnityEngine.ScreenCapture.CaptureScreenshot`, which composites scene and UI, does capture one — this pass did not run it against an enabled gizmo, and that single call is what would settle it.

**A watch is readable from outside.** With one watch enabled, `debug.watches` returned `[{__Type: "debug.HistoryWatch", name: "Debug Birth", color: "#990000", history: [{__Type: "debug.WatchHistoryValue", x: <frameIndex>, y: <value>} × 128]}]` — the ring buffer, already rotated so index 0 is the oldest (`DebugWatchSystem.cs:149-170`). The other payload shape is `debug.DistributionWatch` with a `buckets` array (`:344-354`). Reading a **mod's** annotated field this way was not possible in this session and is `Unconfirmed:`: no mod in the corpus declares `[DebugWatchValue]`, so no loaded mod had one. What would settle it: a mod carrying `[DebugWatchValue]` on an `int` field of a `GameSystemBase` present in the world, then `Refresh System List` on the `Watchers` tab and a read of `debug.watches`.

**Two things this pass could not settle.** `Unconfirmed:` whether the frontend `debug.show` route flips the achievement flag the way the C# entry point does — it must, because the trigger is bound directly to `DebugUISystem.Show()` (`src/Game/Game.UI.Debug/DebugUISystem.cs:153`) and that method is the only implementation, but the flag was already false when this pass ran `debug.show`, so the transition was not observed; what would settle it is a fresh launch, a read of `PlatformManager.instance.achievementsEnabled`, then `engine.trigger("debug.show")` and a second read. `Unconfirmed:` whether the frontend route works with `--developerMode` off — everything in the code says yes (`debug.enabled` is a literal `true`, the system is registered unconditionally, `Show()` has no gate), but confirming it needs a restart without the flag.

### The module registry hands out dead accessors, and it is not about bindings

`window["cs2/modding"]` in the shipped build exposes exactly two functions, `findModule` and `getModule` (`src-ui/source.js:13366-13367`, installed on `window` at `:47076-47088`). There is no `getModuleRegistry` in this build — the pattern occurs zero times in the shipped `index.js` — and the registry object itself, with its `registry` Map, `add`, `override`, `extend` and `append`, is a module-private const (`:13370-13372`) unreachable from the page.

**The maintainer confirmed this finding's mechanism on 2026-08-09** — the dead-accessor explanation below stands, closing the gate the ticket set on shipping it.

`getModule` is a plain property read:

```
get(e, t) { const n = $.get(e); if (n && n[t]) return n[t]; throw `Module ${e}@${t} was not found.` }
```

`src-ui/source.js:13373-13377`

and `n[t]` evaluates an accessor. The registry entry for the debug bindings module is a hand-shaped accessor object:

```
Q.add("game-ui/debug/data-binding/debug-bindings.ts", {
  get enabled() { return enabled; },   set enabled(e) { enabled = e; },
  …
  get showDebugUI() { return s0; },     set showDebugUI(e) { s0 = e; },
  get DebugBindingType() { return WJ; },…
```

`src-ui/source.js:68166-68268`

The actual bindings live in the minified locals `YJ, $J, qJ, XJ, QJ, ZJ, JJ, e0, t0, n0` (`:68131-68140`). The ten accessors for them return the **pre-minification source names**, which no scope declares anywhere in the bundle. The five trigger functions and the two enums in the very same object return their correct minified locals and work.

Reproduced live, all seventeen exports of that module read through `getModule`:

| Export                                                                                                                                                      | Result                                  |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------- |
| `enabled`, `visible`, `panels`, `selectedIndex`, `selectedPanel`, `debugChildren`, `observedBinding`, `bindingTriggered`, `developerInfoVisible`, `watches` | `ReferenceError: <name> is not defined` |
| `showDebugUI`, `hideDebugUI`, `selectPreviousPanel`, `selectPanel`, `selectNextPanel`                                                                       | `function`                              |
| `DebugBindingType`, `DebugWatchType`                                                                                                                        | the enum object                         |

**The error text is the diagnosis.** `is not defined` is a free-variable miss, not the TDZ message `Cannot access 'X' before initialization`. There is no lazy module body and no circular-import stub: the declarations are plain `var … = bindValue(…)` evaluated eagerly at module-eval time. The setters are equally dead — assigning to an undeclared identifier in strict-mode module code is the same `ReferenceError`.

**It is bundle-wide and it has nothing to do with value bindings.** Counting the self-referential shape across the reformatted copy — `get X() { return X; }` — gives **581 occurrences over 561 distinct names**, against **3,044** registry getters in total across 1,386 `Q.add` calls — roughly one export in five. Intersecting the ~570 minified locals assigned from a binding factory against the identifiers that appear as an accessor _body_ leaves exactly eight, all in `game-ui/game/data-binding/taxation-bindings.ts` (`src-ui/source.js:45795-45808`, accessors `:45819-45898`). So one module in the whole bundle has its binding exports correctly wired into the registry, and every other data-binding module — including `game-ui/editor/data-binding/editor-bindings.ts`, whose `activeEditorScreen` accessor sits two lines from a correctly wired `setActiveEditorScreen` (`:69874-69879`) — hands out a dead accessor. This is a packaging defect in whatever generates the `Q.add` shim, not a property of bindings. `Rots:` the counts.

**The menu's own frontend never goes through the registry.** `DebugUIRenderer` and `DebugUI` close over the module locals lexically: `al(YJ)` and `al($J)` at `src-ui/source.js:69720-69721`, `al(qJ)`/`al(XJ)`/`al(QJ)`/`al(ZJ)` at `:69750-69753`. `al` is `useValue` (`:25352-25355`), which calls `binding.subscribe()` and re-renders on change; `Xr` is `bindValue` and returns `new ml("<group>.<name>")` (`:25323-25325`); `sl` is `trigger` (`:25346-25348`). The subscribe under `ml` is the same `engine.on`/`engine.trigger` pair an outside caller uses. So the bindings work perfectly and only their registry projection is dead, which is exactly what the observation looked like and exactly not what it implied.

**What an outside caller should do instead.** `findModule` is safe — it enumerates keys with `for…in` and never evaluates an accessor (`:13458-13471`) — so use it to discover paths and export names. To _read_ a binding, either use the engine route above, or rebuild the binding from `window["cs2/api"]`, which exports `bindValue`, `bindEvent`, `bindMap`, `bindTrigger`, `useValue` and friends (`src-ui/source.js:12396-12411`): `bindValue("debug", "visible", false).subscribe().value` reaches the same C# binding.

**No entry needs adding, and no other entry proved wrong.** The decompile, the install's UI bundle, the mod corpus and the two running-game plugins were all reachable exactly as their entries describe, at the paths the entries give; entry 8's warning that a live question can look unanswerable when it is merely unequipped is what the `[DebugWatchValue]` gap above is an instance of, and it held.
