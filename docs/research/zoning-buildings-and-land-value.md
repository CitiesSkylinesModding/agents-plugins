## Findings

### The vocabulary, in one pass

Six words carry this topic and the code uses them precisely. Getting them apart is the whole of the orientation.

- **Zone type** — an authored `ZonePrefab` (`src/Game/Game.Prefabs/ZonePrefab.cs:10`) plus its runtime data component `ZoneData` (`src/Game/Game.Prefabs/ZoneData.cs:7-20`). "Low Density Housing" is a zone type.
- **Area type** — the four-member enum `Game.Zones.AreaType { None, Residential, Commercial, Industrial }` (`src/Game/Game.Zones/AreaType.cs:3-9`). **There is no `Office` area type**: office is `AreaType.Industrial` plus the `ZoneFlags.Office` bit (`src/Game/Game.Prefabs/ZoneFlags.cs:11`, tested by `ZoneData.IsOffice()` at `ZoneData.cs:41-44`). Every `switch (areaType)` in the topic therefore has three real arms, and office rides inside the industrial one.
- **Zone block** — a `Block` entity (`src/Game/Game.Zones/Block.cs:8-14`: `m_Position`, `m_Direction`, `m_Size`) holding a `DynamicBuffer<Cell>`. Created off a road edge, not painted by the player.
- **Cell** — one 8 m × 8 m square, `Cell { m_State: CellFlags, m_Zone: ZoneType, m_Height: short }` (`src/Game/Game.Zones/Cell.cs:7-13`), `[InternalBufferCapacity(60)]` (`:6`). This is what the zoning tool paints.
- **Vacant lot** — a `VacantLot` buffer element on the block (`src/Game/Game.Zones/VacantLot.cs:9-17`): a rectangle of same-zoned cells (`m_Area` as `int4` min.x/max.x/min.y/max.y), its `m_Type`, a `m_Height` ceiling and `LotFlags` for corner-ness. Derived, not authored.
- **Spawnable building** — a `BuildingPrefab` carrying a `SpawnableBuilding` component (`src/Game/Game.Prefabs/SpawnableBuilding.cs:12`), which names a `ZonePrefab` and a level 1–5 and produces `SpawnableBuildingData { m_ZonePrefab, m_Level }` (`src/Game/Game.Prefabs/SpawnableBuildingData.cs:6-10`).

`Rots:` every component and field name in this file. Re-check against `src/Game/Game.Zones/`, `src/Game/Game.Buildings/`, `src/Game/Game.Prefabs/` (the `Zone*` and `Building*` files) and `src/Game/Game.Simulation/`.

### The three rulings that govern this file

**Ruled (2026-08-06, the citizens-and-households pass; conflicts.md).** No mechanics reference borrows a wiki stat table's numbers. First-party or nothing.
The `Service buildings` and `Signature buildings` catalogs this topic's ticket names ship as **the components that carry the values, never as numbers and never as a wiki link**. The wiki is a lead generator here and never a shipped citation.

**Ruled (2026-08-06, the citizens-and-households pass; conflicts.md; [ADR 0004](../adr/0004-a-mechanics-reference-names-the-component-not-the-balance-value.md)).** A prefab value ships as component and field, never as a number — widened from parameter singletons to **per-prefab components**, so a single building's upkeep is covered as squarely as a city-wide multiplier.
Three things are untouched and are the spine of what this topic ships: **C# constants ship as numbers** (a value compiled into the decompiled source, citable to a line); **formulas ship whole** (the expression a system evaluates, its baseline, its step functions); and **the map ships** — which component owns which family of numbers, with the access shape beside it, because a reader cannot write the call from a field name.
Two consequences bite this topic hard. A **derived ratio is a magnitude in disguise**, and so is an adverb carrying it: "high-density buildings spread a land-value rise over far more households than low-density ones" is the ratio `m_ResidentialProperties` between two prefabs, stated in prose. State the direction and name the field. And a **non-numeric prefab value is still a prefab value**: `ZonePropertiesData.m_IgnoreLandValue` is a `bool` that removes the land-value term from a zone's rent entirely (`ZonePropertiesData.cs:22`, consumed at `PropertyUtils.cs:399`), and it ships as the field to check before building against rent, with the reason to check it — never as a fact about low-rent housing.
Where this file records a magnitude below, it is evidence for the maintainer and for the next version's sweep. **The reference names component and field only.**

**Ruled (2026-08-08, the zoning-buildings-and-land-value pass; conflicts.md).** A field initializer on a prefab class ships as no number. `LandValuePrefab.m_LandValueBaseline = 10f` and its siblings are Unity-serialized defaults the shipped asset overrides — the operative value lives in the asset, so the literal at the cited line is not offline-checkable as a value, which is the property the C#-constant carve-out turns on. The test is what consumes the value: a `const` or `static readonly` the code reads ships as a number (`SignatureBuilding.kStatLevel = 5`); a field Unity deserialisation can replace is a prefab value whatever file declares it (`SignatureBuilding.m_XPReward`). Where the reference sends a reader into a file carrying such initializers, it states once, as a trap, that they are defaults the asset overrides, with nothing in the C# marking which survived.

For the read machinery: a parameter singleton needs no new prose, and a mechanics reference bridges to `ecs-in-this-game`'s `GetSingleton<T>` and stops. Everything else in this topic needs the access shape stated, and the shapes here are four:

| Where the value lives | How it is read |
| --- | --- |
| `LandValueParameterData`, `EconomyParameterData`, `DemandParameterData`, `ZonePreferenceData`, `BuildingConfigurationData` | singleton component on a settings-prefab entity, via a one-type `EntityQuery` and `GetSingleton<T>` (`LandValueSystem.cs:324/355`) |

(Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`, twice: `ZonePreferenceData` previously sat in both the singleton row and the per-zone-prefab row — it is the singleton — and this sentence previously read zone-first.)

### What the zone types and densities are, and where the lot dimensions actually live

**Zone types are authored prefabs, and their runtime index is assigned at load, not stored.**
`ZonePrefab` carries only four authored fields — `m_AreaType`, `m_Color`, `m_Edge`, `m_Office` (`ZonePrefab.cs:12-18`). `Game.Prefabs.ZoneSystem` walks every created prefab with a `ZoneData` and hands each a fresh `ZoneType.m_Index` from `GetNextIndex()`, starting at 1 and reusing holes left by removed zones (`src/Game/Game.Prefabs/ZoneSystem.cs:168-205`, `:212-226`). An `AreaType.None` prefab keeps index 0 and is given `ZoneFlags.SupportNarrow` and height limits of 1 (`:184-190`) — that is the "Remove Zoning" eraser.
**Nothing about that index is authored, and nothing about it is stable across sessions.**

`ZoneDensity` is a three-member enum (`src/Game/Game.Prefabs/ZoneDensity.cs:3-8`) that **no prefab carries**. It is computed from the zone's own data by `PropertyUtils.GetZoneDensity(ZoneData, ZonePropertiesData)` (`src/Game/Game.Buildings/PropertyUtils.cs:633-669`), and the rule differs per area type:

- Residential: `!m_ScaleResidentials` → Low; otherwise `m_ResidentialProperties < m_SpaceMultiplier` → Medium, else High.
- Commercial: `m_SpaceMultiplier > 1` → High, else Low.
- Industrial: office → `m_SpaceMultiplier < 10` ? Low : High; non-office industrial is always Low.
- `AreaType.None` trips an `Assert.IsTrue(false, ...)` and returns Low (`:667-668`).

So a mod that wants a "medium-density commercial" zone cannot have one: the commercial branch has two outcomes. And `ZoneProperties`' own tooltips state the same relations in the authors' words (`src/Game/Game.Prefabs/ZoneProperties.cs:14-21`).

**Lot dimensions belong to the building prefab, not to the zone.** `BuildingPrefab.m_LotWidth` and `m_LotDepth` (`BuildingPrefab.cs:24/27`, `lotSize => m_LotWidth * m_LotDepth` at `:29`) become `BuildingData.m_LotSize` (`int2`). The editor field caps both at 1500 (`src/Game/Game.UI.Editor/BuildingLotFieldBase.cs:13-15`) — a C# constant, and a much looser bound than the grid's.

**Verdict: the wiki's per-zone tile ranges are an aggregate over building prefabs, not a property of anything.** The `Zoning` page tabulates "4–24 tiles, 2×2 to 4×6" per zone type. The decompile has no field on `ZonePrefab`, `ZoneData` or `ZonePropertiesData` that could hold either bound, and the only lot dimensions in the game are per building prefab. First-party wins: the range is the observed spread of `BuildingData.m_LotSize` over the buildings whose `SpawnableBuildingData.m_ZonePrefab` names that zone. Under the ruling above the numbers do not ship either way; what this settles is that they were never a zone-type fact to begin with.

**The zone type's own flags and height limits are derived from its buildings, not authored.**
`BuildingInitializeSystem` writes back into `ZoneData` as it initialises each spawnable building prefab (`src/Game/Game.Prefabs/BuildingInitializeSystem.cs:1020-1061`):

- a level-1 building with `m_LotWidth == 1` sets `ZoneFlags.SupportNarrow` on the zone;
- `BuildingAccessType.LeftCorner` / `RightCorner` set `ZoneFlags.SupportLeftCorner` / `SupportRightCorner`;
- a level-1 front-access building no wider than 3 and no deeper than 2 lowers `m_MinOddHeight` (widths 1, 3) and `m_MinEvenHeight` (widths 1, 2) toward its own geometry height;
- every building raises `m_MaxHeight` toward its own height.

`ZoneSystem` seeds those three height fields at `ushort.MaxValue`, `ushort.MaxValue`, `0` (`ZoneSystem.cs:180-182`), so a zone with no registered buildings has nonsensical limits until the initializer runs.
The consumer is `CellOccupyJobs.cs:696`, which compares `max(m_MinOddHeight, m_MinEvenHeight)` against a cell's height headroom to decide whether the cell can be zoned at all.
`Unconfirmed:` whether a mod registering a zone prefab _after_ `BuildingInitializeSystem` has run for the buildings that reference it gets those flags at all. What would settle it: register a zone prefab and a matching level-1 building from a mod, then read `ZoneData.m_ZoneFlags` on the zone prefab entity through the sibling Unity plugin.

### The cell grid's declared limits, and why they look unused

`src/Game/Game.Zones/ZoneUtils.cs:8-16` declares five constants:

```
CELL_SIZE = 8f;  CELL_AREA = 64f;  MAX_ZONE_WIDTH = 10;  MAX_ZONE_DEPTH = 6;  MAX_ZONE_TYPES = 339;
```

**A grep for their names across `src/` returns only their own declaration, and that proves nothing.** They are C# `const`, so the compiler inlines them at every call site and the decompiler prints the literal: `ZoneUtils` itself writes `8f` and `4f` throughout (`:20-24`, `:34-39`, `:64`, `:152`). Reading the empty grep as "unused" is the mistake to avoid; this is the same trap [`empty-grep-read-as-proof-of-absence.md`](../solutions/empty-grep-read-as-proof-of-absence.md) is about, in its `const` form.
These are C# constants, so under the ruling they ship as numbers.
**Two shapes carry a compiled-in value in this codebase and both qualify, but only one is a `const`.** These five are `const`, inlined and invisible at their call sites. The `k`-prefixed values this file cites elsewhere — `kUpdatesPerDay`, `kMaterialUpkeep`, `kMaxFactorEffect`, `kTextureSize`, `kHomelessApartmentSize` — are `public static readonly int`, which the decompiler prints at the declaration _and_ leaves as a named reference at every use, so a grep finds those. Both are values the code itself consumes, compiled into the assembly and citable to a line, which is what the rulings turn on; the difference is only whether a search for the name finds the consumers.

**`MAX_ZONE_TYPES = 339` is contradicted by the shader array, and the shader array is the real cap.**
`ZoneSystem` allocates `m_FillColorArray` and `m_EdgeColorArray` as `Vector4[1023]` (`ZoneSystem.cs:94-95`) and pushes them with `Shader.SetGlobalVectorArray` (`:208-209`). `ZoneUtils.GetColorIndex` (`ZoneUtils.cs:141-148`) indexes them at `4 + m_Index * 4` plus 0–3 for the occupied/selected/highlight variants, and `UpdateZoneColors` writes all four (`ZoneSystem.cs:307-327`). The highest index that fits a 1023-element array is 1022, so the highest safe `m_Index` is 253 — well under 339. `Rots:` this arithmetic and both constants; re-check `ZoneUtils.cs` and `ZoneSystem.cs`'s array allocation together, since either moving alone changes the answer.
`Unconfirmed:` that a zone prefab at `m_Index` 254 actually throws. Nobody has registered that many; what would settle it is registering enough zone prefabs from a mod to push `m_Index` past 253 and watching for the index-out-of-range on load. Recorded because a mod pack adding zones en masse is the plausible way to reach it, and the failure would be at load, in rendering code, far from the mod.

### The zone index is remapped on every load, and a removed zone prefab erases zoning

`ZoneType.m_Index` is serialized into every `Cell` and every `VacantLot` (`Cell.cs:15-23`, `VacantLot.cs:29-39`), and it is a **runtime** index. `ResolvePrefabsSystem` therefore rebuilds a translation table on every load and rewrites both buffers:

- `FillZoneTypeArrayJob` (`src/Game/Game.Serialization/ResolvePrefabsSystem.cs:245-290`) maps each _loaded_ zone prefab's old index to the _actual_ prefab's new `ZoneType`, and writes `ZoneType.None` where the loaded prefab and the actual prefab are the same entity — the marker for a prefab that no longer resolves.
- `FixZoneTypeJob` (`:293-332`) walks every `Cell` and every `VacantLot` buffer through that table.
- Both are driven from `ResolvePrefabsSystem`'s load path at `:490-509`.

**So a save whose zone prefab has gone — a mod uninstalled, a DLC disabled — does not fail: every cell that carried that zone silently becomes unzoned.** That is the behaviour a mod shipping its own zone type has to plan for, and it is why zone indices must never be persisted by a mod in its own data.
`PrefabData` is an `IEnableableComponent` (`src/Game/Game.Prefabs/PrefabData.cs:6`) and `ResolvePrefabsSystem` disables it on obsolete loaded prefabs (`:511-512`, `:535`) — it marks _obsolescence_, not player-facing unlocking, which is a name that reads the other way. Both `ZoneCheckSystem.ValidateZoneBlocks` (`src/Game/Game.Buildings/ZoneCheckSystem.cs:337-340`) and `BuildingUpkeepSystem`'s level-up job (`src/Game/Game.Simulation/BuildingUpkeepSystem.cs:713-716`) gate on `IsComponentEnabled(zonePrefab)`.

### Where blocks come from, and the road's gate on zoning

Blocks are generated from road edges by `Game.Zones.BlockSystem` (`SystemUpdatePhase.Modification4`, `src/Game/Game.Common/SystemOrder.cs:156`).
The gate is one flag: `RoadFlags.EnableZoning` on the edge's `RoadComposition` (`src/Game/Game.Prefabs/RoadFlags.cs:8`, tested at `src/Game/Game.Zones/BlockSystem.cs:166`, `:292`, `:769`). No flag, no blocks — which is what makes highways unzonable, without any zoning code knowing what a highway is.
The block prefab comes from the road: `RoadPrefab.m_ZoneBlock` (`src/Game/Game.Prefabs/RoadPrefab.cs:20`) → `RoadData.m_ZoneBlockPrefab` (`RoadData.cs:8`) → `RoadComposition.m_ZoneBlockPrefab` (`RoadComposition.cs:7`), and `BlockSystem` instantiates `ZoneBlockData.m_Archetype` from it (`BlockSystem.cs:506-507`, `:987-988`).
`BlockSystem` creates a chain of blocks per side of an edge — segments split by curvature (`:828`) and again at 10 cells (`:954`) — plus node blocks only where the composition is a `Roundabout` (`:203`, `:214`); three suppressors fire before any block is made: an owner chain carrying `Building` (`:170-178`), an `Elevated`/`Tunnel` composition (`:180-183`), and a per-side `Raised`/`Lowered` flag (`:184-189`). `ZoneUtils.GetCellWidth(m_Width ∓ m_MiddleOffset * 2)` = `ceil(width/8 - 0.01)` (`ZoneUtils.cs:150-153`, the per-side argument at `BlockSystem.cs:195/200`) becomes the block row's lateral offset in metres (`:812-814`); a block's own `m_Size` is its segment length capped at 10, by 6 deep (`:965-966`). (Corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass: this file previously stated one block per side, corner blocks at every node, and `GetCellWidth` as the block width.)
`ZoneBlockPrefab` declares the block archetype in `LateInitialize` — `Block`, `CurvePosition`, `ValidArea`, `BuildOrder`, `Cell`, `CullingInfo`, `MeshBatch`, `Created`, `Updated` (`src/Game/Game.Prefabs/ZoneBlockPrefab.cs:31-59`).

**`NetZoneData` is dead at 1.6.0f1.** The struct exists (`src/Game/Game.Prefabs/NetZoneData.cs:6-8`, a serializable `m_BlockPrefab`) and a sweep of `src/` finds no producer and no consumer outside its own file. The live path is `RoadComposition.m_ZoneBlockPrefab`. Recorded because the ticket's starting points named `NetZoneData` and a reader would otherwise chase it.

### What decides a cell is vacant, and what the block owes the spawner

`Game.Zones.CellCheckSystem` (`SystemUpdatePhase.Modification5`, `SystemOrder.cs:215`) is the pipeline that turns painted cells into vacant lots. It short-circuits entirely unless one of five collect systems reports an update (`src/Game/Game.Zones/CellCheckSystem.cs:218-224`), and otherwise schedules eight jobs in a fixed chain (`:238-357`):

1. `CellBlockJobs.BlockCellsJob` — blocks cells against roads, areas and terrain, and writes `ValidArea`.
2. `CellCheckHelpers.FindOverlappingBlocksJob` → `GroupOverlappingBlocksJob` — finds and groups blocks that overlap.
3. `CellOccupyJobs.ZoneAndOccupyCellsJob` — marks cells occupied by existing objects, and it is the job that reads `ZoneData.m_MinOddHeight` / `m_MinEvenHeight` (`CellOccupyJobs.cs:696`).
4. `ZoneToggleJob` — sets only `CellFlags.Blocked`, for compositions carrying the `ZonesDisabled` side flag (`ZoneToggleJob.cs:57/69`); `leftHandTraffic` is only its tie-break for which side a block belongs to (`:50-56`). The direction bits are written in step 1 by `CellBlockJobs` (`CellBlockJobs.cs:197/205/551-553/621-628`). (Corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass: this file previously credited the direction bits to this job.)
5. `CellOverlapJobs.CheckBlockOverlapJob` — resolves the overlap groups, ordered by `BuildOrder.m_Order` (`src/Game/Game.Zones/BuildOrder.cs:6-8`).
6. `CellCheckHelpers.UpdateBlocksJob`, then `LotSizeJobs.UpdateLotSizeJob` — which is what writes the `VacantLot` buffer.
7. `LotSizeJobs.UpdateBoundsJob` — feeds the changed bounds back to `Game.Zones.UpdateCollectSystem`.

`CellFlags` (`src/Game/Game.Zones/CellFlags.cs:6-21`) is the whole state a cell can be in: `Blocked`, `Shared`, `Roadside`, `Visible`, `Overridden`, `Occupied`, `Selected`, `Redundant`, `Updating`, `RoadLeft`, `RoadRight`, `RoadBack`, `Highlight`. `Visible` is the one every consumer tests first.
`ZoneUtils.CanShareCells` and `IsNeighbor` (`ZoneUtils.cs:76-139`) are the geometry behind `Shared`, and both dispatch on `BuildOrder` so that the older block wins.

**A block must carry `Owner` pointing at a road edge before the spawner will look at it.** `ZoneSpawnSystem.m_LotQuery` requires `Block`, `Owner`, `CurvePosition` and `VacantLot`, and excludes `Temp` and `Deleted` (`src/Game/Game.Simulation/ZoneSpawnSystem.cs:1073-1088`).
**Corpus evidence, and it is the reason to state this as a hard requirement rather than as a query detail.** `lucarager/CS2-Platter` builds its own zone blocks under placeable "parcels" and manages `Owner` by hand: `CS2-Platter/Platter/Systems/Blocks/P_BlockToRoadReferenceSystem.cs:24-26` documents it as "what marks a block as a valid spawn location to the vanilla `ZoneSpawnSystem`", and `:103-108` removes `Owner` outright to stop a parcel spawning, with the author's own comment that a null owner "can crash when systems try to retrieve the Edge". The vanilla code agrees: `ZoneSpawnSystem.TryAddLot` returns early when the owner has no `ResourceAvailability` buffer (`ZoneSpawnSystem.cs:241-244`) but then indexes `m_LandValues[road]` with **no** `HasComponent` guard (`:270`). An owner that is not a road edge with a `LandValue` faults inside a Burst job.

### What drives demand, in both directions

Three systems produce six demand values, all in `SystemUpdatePhase.GameSimulation` at interval 16, on staggered offsets that `DemandUtils` names as constants (`src/Game/Game.Simulation/DemandUtils.cs:7-17`: `kUpdateInterval = 16`, count-companies at 1, commercial at 4, industrial at 7, residential at 10, zone spawn at 13). Those are C# constants and ship as numbers.

| System | Registered | Outputs |
| --- | --- | --- |
| `CountResidentialPropertySystem` | `SystemOrder.cs:387` | `ResidentialPropertyData { m_FreeProperties: int3, m_TotalProperties: int3 }` by density (`CountResidentialPropertySystem.cs:24-37`) |
| `ResidentialDemandSystem` | `:388` | `m_HouseholdDemand: int`, `m_BuildingDemand: int3` (low/medium/high) |
| `CommercialDemandSystem` | `:389` | `m_CompanyDemand`, `m_BuildingDemand`, plus per-resource arrays |
| `IndustrialDemandSystem` | `:391` | industrial, storage and office company and building demand |

**Residential demand is a sum of nine weighted terms, clamped, then split three ways.**
`ResidentialDemandSystem.UpdateResidentialDemandJob.Execute` (`src/Game/Game.Simulation/ResidentialDemandSystem.cs:81-192`) is the readable one and worth reading whole. Its shape:

1. It first builds a `bool3` of which residential densities are **unlocked**, by walking the unlocked zone prefabs and calling `PropertyUtils.GetZoneDensity` on each (`:83-103`). At the end, `m_BuildingDemand.value = math.select(default, value, test)` (`:185`) — **a density with no unlocked zone prefab gets zero demand, whatever the economics say.**
2. Nine factors, each a `float`: a population-decay term `20 - smoothstep(0, 20, population/20000)` (`:113`), happiness against `m_NeutralHappiness`, homelessness against `m_NeutralHomelessness` computed **twice from the same clamped ratio, once as `-m_HomelessEffect * r` and once as `+m_HomelessEffect * r`** (`:122-125`) — the first goes into `m_HouseholdDemand` (`:141`) and the second only into the high-density arm, as factor `[8]` and thence into that arm's sum (`:157`, `:165`) — the negative half reaches every density through `householdDemand / 2` at `:184`, high included, while the positive half reaches only the high sum; the average residential tax rate's deviation from 10 across five education levels, free simple and complex workplaces against `m_NeutralAvailableWorkplacePercentage`, study positions, and unemployment against `m_NeutralUnemployment` (`:113-131`).
3. Each of those nine goes through `GetFactorValue` (`:132-140`, the method at `:194-201`), which multiplies by `m_ResidentialDemandWeightsSelector.x` when negative and `.y` when positive — an **asymmetric weighting**, so the same magnitude does not push demand up and down equally.
4. `m_HouseholdDemand = min(200, sum)` (`:141`), where the workplace terms enter as `max(simple, complex)` rather than added.
5. Per density, a free-property pressure term `round(100 * (m_FreeResidentialRequirement[i] - free[i]) / m_FreeResidentialRequirement[i])` (`:142-144`), and the building demand is `clamp(householdDemand/2 + pressure + factorSum, 0, 100)` (`:184`).
6. `kMaxFactorEffect = 15` is a C# constant (`:224`) and ships.

**Demand falls by the same machinery that raises it, and there is no separate downward path.** Every factor is signed: happiness below `m_NeutralHappiness` is negative, unemployment above `m_NeutralUnemployment` is negative, a tax rate above 10 is negative, and the free-property pressure `100 * (requirement - free) / requirement` goes negative the moment free properties exceed the requirement. The clamps are what make the two directions asymmetric — the workplace terms are clamped to `[0, 40]` and `[0, 20]` and so can only ever push demand up (`:127`, `:129`), the positive homelessness term is clamped by `kMaxFactorEffect` (`:125`). Two guards that look like demand inputs are not: the no-workplaces guard (`:172-177`) and the zero-population guard (`:178-183`) rewrite only the reported factor arrays, after the per-density sums were taken at `:163-165`, so the demand arithmetic never sees them. Three shapes the arithmetic does carry, all read off the same lines: the low-density reported workplace slot is halved before the sum (`:146`), a negative pressure value zeroes that density's whole factor sum (`:163-165`), and the pressure term sits both inside the sum's `[13]` slot and as its own addend at `:184`, so it enters building demand twice when nonnegative. (Corrected 2026-08-08, the zoning-buildings-and-land-value orchestrator pass, re-derived from `ResidentialDemandSystem.cs:141-185`: this file previously stated the two reporting guards as zeroing the demand terms themselves.)

**The `DemandFactor` enum is the reported breakdown, and it is one enum for all six demand values.** `src/Game/Game.Simulation/DemandFactor.cs:3-25` — 20 members, the 19 factors plus a trailing `Count` sentinel: `StorageLevels`, `UneducatedWorkforce`, `EducatedWorkforce`, `CompanyWealth`, `LocalDemand`, `Unemployment`, `FreeWorkplaces`, `Happiness`, `Homelessness`, `TouristDemand`, `LocalInputs`, `Taxes`, `Students`, `EmptyBuildings`, `EmptyZones`, `PoorZoneLocation`, `PetrolLocalDemand`, `Warehouses`, `BuildingDemand`. That set ships as a set, because the game declares it in one enum.
**Trap:** the three demand systems index those arrays by **integer literal**, never by the enum member — `m_LowDemandFactors[7]`, `[6]`, `[5]`, `[11]`, `[13]`, `[18]` at `ResidentialDemandSystem.cs:145-162`, and the same pattern in `CommercialDemandSystem.cs:190-217`. Reading the code without the enum in the other hand tells a reader nothing. The `[EnumArray(typeof(DemandFactor))]` attributes on the fields (`ResidentialDemandSystem.cs:254-262`) are the only thing tying the two together.
A second trap in the same lines: `[13]` (`EmptyBuildings`) and `[18]` (`BuildingDemand`) are written twice — once for the running sum at `:163-165`, then **overwritten** at `:166-171` depending on whether that density has any total properties at all. The value the UI shows is the second write, and the value the demand arithmetic used is the first.

**Commercial demand is per resource, not per zone.**
`CommercialDemandSystem.UpdateCommercialDemandJob.Execute` (`src/Game/Game.Simulation/CommercialDemandSystem.cs:104-234`) iterates resources: for each commercial resource it computes a storage-shortfall term from `m_CommercialStorageEffect` and `m_CommercialStorageMinimum`, a tax term `-0.05 * (rate - 10) * m_TaxEffect.y`, and — only for `Resource.Lodging` — a tourism term comparing `m_HotelRoomPercentRequirement * currentTourists` against existing lodging (`:182-188`); the tax term also adds `m_CommercialTaxEffectDemandOffset`, latched from the loaded game mode in `OnGameLoaded` (`:181`, `:397-410`). The lodging slot is set to 100 on a shortfall and is otherwise the 0 the job wrote at the top of `Execute` — the opening `ResourceIterator` loop zeroes `m_ResourceDemands`, `m_BuildingDemands` and `m_FreeProperties` per resource (`:115-122`), while `:168-169` zero the totals besides — so the `(1 + tax)` scaling at `:191` scales a 0 on a no-shortfall pass and nothing carries over. (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously a carried-over, compounding slot, read from `:168-169` alone.) Building demand for a resource is non-zero **only when free properties minus propertyless companies is at or below zero** (`:197`), which is the "companies exist with nowhere to go" signal. Both totals divide by the count of resources with **company** demand (`:218`, `:232-233` — a resource with company demand and no building demand dilutes the building total), clamped to 0–100; building demand is zeroed outright if no commercial zone type is unlocked (`:106-114`, `:233`), and `m_UnlimitedDemand` then forces both to 100 (`:234-238`). (Corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass: the lodging else-arm, the averaging denominator and the debug override were previously wrong or missing.)

**Industrial demand carries three of everything.** `IndustrialDemandSystem` produces industrial, storage and office demand separately (`src/Game/Game.Simulation/IndustrialDemandSystem.cs:128-150`), splitting per resource inside the update job on `ResourceData.m_Weight == 0f` (`:370`) and routing office **totals** into `m_OfficeCompanyDemand`/`m_OfficeBuildingDemand` (`:435`, `:466`) while the per-resource values land in the shared `m_IndustrialCompanyDemands`/`m_IndustrialBuildingDemands` arrays the spawner reads (`:433-434`, `:452`) — there is no office per-resource array. Per-resource building demand is 50-or-0 for a weightless or processed resource, gated on free properties minus propertyless companies at or below zero, and a flat ungated 1 for a material resource with company demand (`:448-461`). Storage building demand gets a final `ceil(pow(20 * value, 0.75))` while storage company demand stays a raw sum (`:520`, `:384`); the industrial building total is `2 * sum / resource count` then clamped, the office company total squares itself through `*= 2 * value / count` and is never clamped, the office building total is clamped and never scaled (`:521-524`), and `m_UnlimitedDemand` forces the building totals to 100 after the clamps (`:525-529`). (Corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass: previously split on `EconomyUtils.IsOfficeResource`, per-resource office routing, and a uniform scaled-then-clamped description.)

**Verdict: the wiki's demand loop is right in direction and silent on the mechanism, and the mechanism is what a modder needs.**
`https://cs2.paradoxwikis.com/Zoning` (fetched 2026-08-08) describes residential demand rising "with new citizens seeking housing", commercial demand depending on "manufacturing output and citizen purchasing power", and so on. Every one of those is a real term in the code. What it never says is that demand is computed per **density** for residential and per **resource** for commercial and industrial, that a locked density is forced to zero regardless, or that the negative and positive weights differ. The decompile owns all four. First-party wins with no contest; the wiki set the agenda correctly and answered nothing a mod could act on.

### How a demand value becomes a building

`ZoneSpawnSystem` (`SystemOrder.cs:544`, interval 16, offset 13 — `ZoneSpawnSystem.cs:1047-1055`) is the whole of it, and it is stricter than it looks.

**Four booleans gate the whole update** (`:1101-1104`): residential spawns only when the mean of the three residential building demands exceeds zero; commercial when its building demand does; industrial when the mean of industrial and office demand does; storage on storage demand. `debugFastSpawn` forces all four and sets `m_MinDemand = 0` (`:1125`).

**`EvaluateSpawnAreas` picks at most one best lot per area type per chunk** (`:162-231`), keeping three running bests and enqueuing each into its own queue. Per vacant lot it:

- resolves the zone prefab through `ZonePrefabs[lot.m_Type]` — an indexed accessor over a `NativeArray<Entity>` (`src/Game/Game.Prefabs/ZonePrefabs.cs:7-11`), which is where the runtime zone index is spent;
- masks off `LotFlags.CornerLeft` / `CornerRight` the zone does not support (`:245-252`);
- refuses the lot if the owner road has no `ResourceAvailability` buffer (`:241-244`);
- samples ground, noise and air pollution at the lot position and the road edge's `LandValue` (`:267-270`).

**`SelectBuilding` (`:279-370`) is the selection rule**, and every clause matters:

- Candidates come from chunks whose `BuildingSpawnGroupData` shared component matches the lot's `ZoneType` (`:288`) — a `ISharedComponentData` keyed on zone type (`src/Game/Game.Prefabs/BuildingSpawnGroupData.cs:6-8`), which is how the chunk filter does the work a query could not.
- Warehouse chunks are taken only for storage and never for normal, and vice versa (`:292-296`).
- **Only level 1 spawns.** `if (nativeArray3[j].m_Level != 1) continue;` (`:304-307`). Every building in the city starts at level 1 and climbs; nothing spawns above it.
- The lot must fit (`lotSize <= availableArea`) and the prefab's `ObjectGeometryData.m_Size.y` must clear the cell height ceiling (`:312-315`).
- `EvaluateDemandAndAvailability` (`:372-419`) returns the demand for this candidate: for residential, the density's slot in the `int3`; for commercial and industrial, the **sum over every resource the prefab's `BuildingPropertyData` allows** — `m_AllowedSold`, `m_AllowedManufactured` or `m_AllowedStored`. The candidate is dropped unless that is at least `m_MinDemand` (`:319`).
- The priority is a lot-fit score: the fraction of the vacant area the building covers, jittered per term (`random.NextFloat(1f, 1.05f)` for the building itself, `0.95–1.0` for the leftover strip beside it, `0.55–0.6` for the strip behind it), scaled by `(demand + 1)` and by a corner-flag match term `csum(select(0.01f, 0.5f, lotCorners == buildingAccess))` (`:323-329`).
- That is then multiplied by `ZoneEvaluationUtils.GetScore` (`:344`), the suitability score, unless the candidate is an extractor.
- The winner's lot rectangle is shrunk to the building's footprint, anchored left or right depending on its access flags with a coin flip when it has neither (`:356-366`).

**`SpawnBuildingJob` is an `IJobParallelFor` scheduled over exactly three indices** — `IJobParallelForExtensions.Schedule(jobData2, 3, 1, ...)` at `:1188`, with `Execute(int index)` switching on 0, 1 and 2 and returning on anything else (`:570-598`) — residential, commercial, industrial, each dequeuing every candidate and keeping the single highest priority (`:600-612`). **So at most three buildings are created per update, one per area type**, and storage rides inside industrial. That is the growth throttle, and no parameter tunes it.

**The spawn goes through the placement pipeline rather than creating an entity.** `Spawn` (`:614-666`) writes a `CreationDefinition` with `CreationFlags.Permanent | CreationFlags.Construction` and an `ObjectDefinition` into a four-component archetype declared at `:1090` (`CreationDefinition`, `ObjectDefinition`, `Updated`, `Deleted`), and lets the definition machinery build the entity. Position and rotation come from `ZoneUtils.GetPosition(block, min, max)` and `GetRotation(block)` (`ZoneUtils.cs:18-30`), the ground height from `TerrainUtils.SampleHeight` at the lot's front position, and the final `y` is clamped under the cell height ceiling minus the building's own height minus 0.1 (`:648-655`). This is the join to `placement-definitions`.

**`ZoneEvaluationUtils` is where zone suitability lives, and it is one file.**
`src/Game/Game.Simulation/ZoneEvaluationUtils.cs` carries both halves: `GetFactors` (`:53-148`) produces the per-factor breakdown the suitability infoview shows, and `GetScore` (`:242-278`) produces the single number the spawner multiplies by. The factor enum is `ZoningEvaluationFactor { None, Workplaces, Services, Competitors, Customers, OutsideConnections, Inputs, Pollution, LandValue, Employees, Count }` (`:16-29`), and `ZoningEvaluationResult.CompareTo` sorts by **absolute** score descending, then by sign (`:37-45`) — so the biggest problem and the biggest advantage rank together.
The scores are built from `NetUtils.GetAvailability(availabilities, resource, curvePos)` on the road edge, four of the five arms wrapping it as `GetFactor = min(20, 0.2 / availability)` (`:48-51`) — an inverse, so scarcity reads high.
Per area type (`:242-278`), each returns a `555f` baseline plus signed terms:

- Residential (`:221-227`): the one arm built **without** `GetFactor` — `-m_ResidentialSignificanceServices / max(0.1, services availability) - m_ResidentialSignificanceWorkplaces / max(0.1, workplaces availability)`, raw and uncapped — plus `dot(m_ResidentialSignificancePollution, pollution)`, plus `m_ResidentialSignificanceLandValue * (landValue - m_ResidentialNeutralLandValue)`. (Corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass: previously implied every arm used the wrapper.)
- Commercial (`:229-240`): `max(consumers term, workplaces term)`, plus a **competitors** term that is _positive_ in service scarcity (`-0.4 + serviceFactor`), plus the land-value deviation. `GetScore` blends two calls, 0.9 non-lodging and 0.1 lodging (`:249`) — and at 1.6.0f1 the `lodging` parameter is accepted and never read inside `GetCommercialScore`, so the blend is 1.0 of the same number.
- Industrial non-office (`:274`): `m_IndustrialSignificanceInput * GetTransportScore(...)` plus the land-value deviation **and a further `- 0.5f * landValue`**, which is a second, unparameterised land-value penalty that exists nowhere else.
- Office (`:268-273`): educated-citizen and services scarcity, with the coefficients `0.25 - 5*factor` and `0.25 - 2*factor` rather than the `0.2 - factor` the `GetFactors` breakdown uses (`:136-143`) — **the infoview's factor and the spawner's score are not the same expression.** That is worth a trap in the reference: a player or a mod reading the suitability overlay is not reading what decided the spawn.
- Storage (`:251-266`): the minimum over allowed resources with nonzero demand of **both** `GetStorageScore` and `0.05 / max(0.1, supply availability)` (`:262-263`), then `max(0, 555 - 10 * that)`; no such resource leaves the minimum at `+inf` and the score at 0.

The coefficients are all `ZonePreferenceData` fields (`src/Game/Game.Prefabs/ZonePreferenceData.cs:6-39`), read as a singleton.

### How land value, rent and upkeep combine into the level-up loop

This is the chain the topic is named for, and it is five systems in a fixed order inside `SystemUpdatePhase.GameSimulation`: `PropertyProcessingSystem` (`SystemOrder.cs:399`), `LandValueSystem` (`:420`), `BuildingUpkeepSystem` (`:492`), `RentAdjustSystem` (`:496`), `PropertyRenterSystem` (`:497`).

**Land value is two things with the same name, and the cell map is derived from the per-road-edge one.**
`LandValueSystem : CellMapSystem<LandValueCell>` (`src/Game/Game.Simulation/LandValueSystem.cs:24`) writes both:

1. A **128 × 128 cell map** of `LandValueCell { m_LandValue: float }` (`src/Game/Game.Simulation/LandValueCell.cs:5-7`), `kTextureSize = 128`, `kUpdatesPerDay = 32`, interval `262144 / 32` (`:258-260`, `:292-295`). This is what the rendered overlay (`src/Game/Game.Rendering/OverlayInfomodeSystem.cs:927`) and the hover tooltip (`src/Game/Game.UI.Tooltip/LandValueTooltipSystem.cs:61`, `:260`) read; the land-value infoview panel's headline average does not, taking the per-edge component through `Building.m_RoadEdge` instead (`src/Game/Game.UI.InGame/LandValueInfoviewUISystem.cs:36-39`). `GetCellIndex(float3)` at `:302-306` is how a mod samples it. Corrected 2026-08-10 against the earlier "infoview layer" gloss.
2. A **per-road-edge `Game.Net.LandValue { m_LandValue, m_Weight }`** (`src/Game/Game.Net/LandValue.cs:6-10`). **This is the one rent reads.**

`EdgeUpdateJob` (`:151-221`) computes the edge value from six terms on the edge's own buffers, and the indices are magic numbers with no named constant behind them: `ServiceCoverage[0]` × health multiplier, `[5]` × education, `[2]` × police (`:183-192`); `ResourceAvailability[1]` × commercial-service, `[31]` × bus, `[32]` × tram/subway (`:196-205`). The sum is floored at zero and the edge value is lerped 60% toward it, and only when it differs by at least 0.1 (`:207-213`). `Rots:` those six buffer indices most of all — re-check `src/Game/Game.Net/ServiceCoverage.cs` and the `AvailableResource` enum, since nothing in `LandValueSystem` names them.

`LandValueMapUpdateJob` (`:103-147`) computes the cell map differently: water deeper than 1 m gets the baseline flat (`:106-113`); otherwise it averages the `LandValue` of the road edges inside a box 1.5 cells either side whose value is positive — a zero-value edge leaves numerator and denominator alike (`:48`, `:114-129`) — adds attractiveness and telecom bonuses each capped at `m_CommonFactorMaxBonus` (`:130-132`), adds a terrain-attractiveness bonus **only when there is no water pollution and no ground pollution** (`:135-139`), subtracts the three pollution penalties (`:140`), and lands on `max(m_LandValueBaseline, m_LandValueBaseline + that sum)` — the baseline is an addend as well as the floor (`:141`) — then lerps 40% behind the same `>= 0.1` difference guard as the edge (`:142-145`).

Every coefficient is `LandValueParameterData` (`src/Game/Game.Prefabs/LandValueParameterData.cs:5-34`), a singleton. **Under the ruling the reference names the component and these fourteen fields and states no magnitude.**

**Rent is one formula and it is small.** `PropertyUtils.GetRentPricePerRenter` (`src/Game/Game.Buildings/PropertyUtils.cs:384-402`):

```
base      = m_RentPriceBuildingZoneTypeBase[areaType]      // .x res, .y com, .z ind
lvMod     = m_LandValueModifier[areaType]
asked     = ignoreLandValue
            ? base * level * lotSize * m_SpaceMultiplier
            : (landValue * lvMod + base * level) * lotSize * m_SpaceMultiplier
renters   = IsMixedBuilding ? round(m_ResidentialProperties / (1 - m_MixedBuildingCompanyRentPercentage))
                            : CountProperties()
rent      = round(asked / renters)
```

`areaType` selects both `float3` components by the same switch (`:388-398`), `landValue` is the road edge's, `level` is `SpawnableBuildingData.m_Level` via `GetBuildingLevel` (`:685-692`, defaulting to 1 when there is no spawnable data), `lotSize` is `m_LotSize.x * m_LotSize.y`, and `ignoreLandValue` is `ZonePropertiesData.m_IgnoreLandValue`.
The game ships its own commentary on this formula: `GetRentPriceDebugInfo` (`:404-432`) labels the four terms A–D in plain English. That is the clearest single artefact for the reference to point at.
`BuildingPropertyData.CountProperties(AreaType)` (`src/Game/Game.Prefabs/BuildingPropertyData.cs:22-52`) is the renter count: residential returns `m_ResidentialProperties`; commercial returns 1 if anything is sellable; industrial returns 1 if anything is storable or manufacturable; and `CountProperties()` sums all three, which is how a mixed building counts.
`IsMixedBuilding` is `m_ResidentialProperties > 0 && (m_AllowedSold != NoResource || m_AllowedManufactured != NoResource)` (`:694-705`).

**Upkeep is a different formula on the same inputs.** `PropertyRenterSystem.GetUpkeep` (`src/Game/Game.Simulation/PropertyRenterSystem.cs:226-245`): `round(pow(level, exponent) * baseUpkeep * lotSize)`, with a per-area-type exponent (`m_ResidentialUpkeepLevelExponent`, `m_CommercialUpkeepLevelExponent`, `m_IndustrialUpkeepLevelExponent` on `EconomyParameterData`), `baseUpkeep` from the **zone's** `ZoneServiceConsumptionData.m_Upkeep`, and a flat halving for storage buildings. It is called once, at prefab initialisation, to write `ConsumptionData.m_Upkeep` on each building prefab (`src/Game/Game.Prefabs/BuildingInitializeSystem.cs:1066-1077`) — **so upkeep is baked per prefab per level and never recomputed at runtime**, and a mod changing the parameters after initialisation changes nothing already written.
One override sits inside that block and is easy to miss: a prefab carrying `SignatureBuildingData` has its upkeep computed at `level = 2` (`:1070-1073`, the flag set from the chunk's `SignatureBuildingData` handle at `:843` and `:794`) — **even though `SignatureBuilding` writes `SpawnableBuildingData.m_Level = 5`**, so a signature building's rent is computed at level 5 and its upkeep at level 2.
Note the asymmetry with `ZoneServiceConsumption.GetBuildingConsumptionData` (`src/Game/Game.Prefabs/ZoneServiceConsumption.cs:63-73`), which writes `m_Upkeep = 0` — the initializer overwrites it afterwards.

**`BuildingCondition` is the level-up bar, and it goes both ways.**
`BuildingCondition { m_Condition: int }` (`src/Game/Game.Buildings/BuildingCondition.cs:6-8`) accumulates in `BuildingUpkeepSystem.BuildingUpkeepJob` (`src/Game/Game.Simulation/BuildingUpkeepSystem.cs:170-292`), `kUpdatesPerDay = 16` (`:1014`), interval `262144 / (16 * 16)` (`:1064-1067`). Per tick, per building:

1. `levelingCost = BuildingUtils.GetLevelingCost(areaType, propertyData, level, cityEffects)` (`src/Game/Game.Buildings/BuildingUtils.cs:293-319`) — `CountProperties() * round(pow(2, 2 * level) * 40)` for residential, `* 160` for commercial and industrial with a further `* 4` when the building stores anything, then `CityModifierType.BuildingLevelingCost` applied. At level 5 and above it returns `1073741823`, so level 5 can never level again.
2. `abandonCost = GetAbandonCost(...)` (`:332-340`) — the leveling cost, except at level 5 where it is level 4's, and for multi-apartment residential divided as `round(cost * (6 - level) / sqrt(m_ResidentialProperties))`.
3. The tick's upkeep is `ConsumptionData.m_Upkeep / kUpdatesPerDay` (`:189`), less a `/ kMaterialUpkeep` share (a C# constant, `= 4`, `:1016`) that is computed into `num2` at `:190` and read only at `:191` to form the remainder `num3`, never spent on anything — only `num3` reaches the comparison at `:214` and the renter charge at `:221`, so the charge is three quarters of the slice. Level-up materials come from the `LevelUpResourceData` / `ZoneLevelUpResourceData` delivery path in step 6 instead, so nothing deducts materials from upkeep. Corrected 2026-08-10 against the earlier "split into a materials and a money share" reading.
4. The renters' total worth is summed — money for a household, `EconomyUtils.GetCompanyTotalWorth` for a company, including its owned vehicles (`:193-212`).
5. **If the renters cannot cover that remainder, condition falls** by `m_BuildingConditionDecrement * pow(2, level) * max(1, renterCount)` (`:214-217`). Otherwise it rises by `GetBuildingConditionChange(areaType, config)` — `BuildingConfigurationData.m_BuildingConditionIncrement` indexed `.x`/`.y`/`.z` by area type (`BuildingUtils.cs:321-330`) — times the same `pow(2, level) * max(1, renterCount)`, and each renter is charged its equal share (`:218-230`).
6. At or above the leveling cost the building requests level-up **materials** and gains `ResourceNeeding` and `GuestVehicle` buffers (`:239-277`). The material list is looked up in three places in order: `LevelUpResourceData` on the **building** prefab, then `ZoneLevelUpResourceData` on the **zone** prefab filtered to the current level, then the `ZoneLevelUpResourceData` buffer on the `BuildingConfigurationData` singleton entity as the fallback (`:250-276`).
7. At or below `-abandonCost` the building is queued for level-**down**, and its condition is credited back by the leveling cost (`:278-289`).
8. **`BuildingFlags.Historical` freezes both ends** (`src/Game/Game.Buildings/BuildingFlags.cs:10`): a historical building has its condition pinned at the leveling cost and never levels (`:241-246`), and pinned at `-abandonCost` and never abandons (`:280-283`). A building whose prefab has `SignatureBuildingData` never abandons at all (`:278`).

`ResourceNeedingUpkeepJob` (`:301-369`) waits for every `ResourceNeeding` to reach `ResourceNeedingFlags.Delivered`, then removes the buffer, clears the notification, zeroes the condition and enqueues the level-up.

**Level-up replaces the prefab; it does not mutate the building.** `LevelupJob.SelectSpawnableBuilding` (`:761-795`) looks for a prefab at `level + 1` in the same `BuildingSpawnGroupData` zone chunk that matches on **all** of: identical `m_LotSize`, height under the cell ceiling, identical left/right access flags, `m_ResidentialProperties` at least the current one, and identical `m_AllowedManufactured`, `m_AllowedInput`, `m_AllowedSold` and `m_AllowedStored`. Every match gets weight 100 and one is picked by reservoir sampling (`:785-790`). The winner is written as `UnderConstruction { m_NewPrefab, m_Progress = 255 }` (`:726-730`) — so the construction machinery does the swap.
`GetMaxHeight` (`:797-819`) re-reads the zone cells under the building's footprint through the zone search tree and takes the minimum `Cell.m_Height` of the visible ones, minus the building's own `y` — **so a zone height limit painted after the building was built can stop it levelling up.**
Level-up also fires a `TriggerAction` per area type present in the property data (`:731-749`) and enqueues a `ZoneBuiltLevelUpdate { m_Zone, m_FromLevel, m_ToLevel, m_Squares }` (`:750-756`).

**Level-down is abandonment, and it strips components.** `LeveldownJob` (`:412-559`) adds `Abandoned { m_AbandonmentTime = frame }`, removes `ElectricityConsumer`, `WaterConsumer`, `GarbageProducer` and `MailProducer`, **doubles** `CrimeProducer.m_Crime`, and removes `PropertyRenter` from every renter while emptying the `Renter` buffer (`:481-529`). The road edge is queued for update so the utility connections rebuild.
**Corpus evidence for the exact inverse, and it is the best documentation of that component set anywhere.** `algernon-A/PlopTheGrowables` un-abandons buildings by hand: `PlopTheGrowables/Code/Systems/ExistingBuildingSystem.cs:64-110` removes `Abandoned`, adds `PropertyToBeOnMarket` and drops `PropertyOnMarket`, resets `BuildingCondition.m_Condition` to 0, re-adds `GarbageProducer`, `MailProducer`, `ElectricityConsumer` and `WaterConsumer` each with an explicit "removed when abandoned" comment, clears the notification, and adds `Updated` to `Building.m_RoadEdge` to refresh utilities. Read beside `LeveldownJob` the two are a matched pair.

**Rent is re-derived and re-applied every tick, and a renter that cannot pay starts looking.**
`RentAdjustSystem` (`kUpdatesPerDay = 16`, interval `262144 / (16 * 16)`, `src/Game/Game.Simulation/RentAdjustSystem.cs:571`, `:623-626`) runs `AdjustRentJob` over `Building` + `UpdateFrame` + `Renter`, excluding `StorageProperty` (`:645`). Per building (`:226-357`): it recomputes the asked rent (`:267`), writes it into `PropertyOnMarket.m_AskingRent` if listed (`:268-273`), and writes it into **every** renter's `PropertyRenter.m_Rent` (`:307`) — rent is not negotiated and not grandfathered.
Affordability is then compared against income: a household's is `EconomyUtils.GetHouseholdIncome(...) + max(0, money)`; a company's is `GetCompanyMaxProfitPerDay(...)` when nonnegative and `GetCompanyTotalWorth(...)` only as the fallback (`:289-306` — the local is 0 at the test, so this is a fallback, not a max: profit 5 beats worth 10000; corrected 2026-08-08, the zoning-buildings-and-land-value mechanical pass, from `max(...)`). **A company that cannot afford it gets `PropertySeeker` enabled and starts hunting** (`:309-312`); a household does not — that is `citizens-and-households`' side of the line.
`BuildingFlags.HighRentWarning` is raised when more than 70% of renters are over budget **and** `CanDisplayHighRentWarnIcon` finds no competing company or workforce notification and takes the LAST household renter's liveness verdict — its loop resets `result` per household and only the inner citizen loop breaks (`:184-224`, `:325-336`). (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously "at least one living citizen".) The 0.7 is a bare literal in the job.

**`PropertyRenterSystem` is the collection pass** (`kUpdatesPerDay = 16`, `PropertyRenterSystem.cs:207`). `PayRentJob` (`:72-129`) deducts `RoundToIntRandom(rent / kUpdatesPerDay)` per renter — stochastic rounding, so the daily total is right in expectation and no tick is — except a `StorageCompany`, which is drained of **all** its money (`:93`). It also drops renters whose `PropertyRenter` is gone, adds `PropertyToBeOnMarket` when the building has spare capacity and is neither abandoned nor destroyed nor a `Signature` (`:108-111`), evicts from the end of the buffer when the building is abandoned, destroyed or over capacity (`:113-122`), and raises a `RentersUpdated` event entity when anything changed (`:123-127`).

**`PropertyProcessingSystem` is what puts a property on the market** (`SystemOrder.cs:399`, interval 16). `PutPropertyOnMarketJob` (`src/Game/Game.Simulation/PropertyProcessingSystem.cs:106-190`) drops `PropertyToBeOnMarket` from anything abandoned, recomputes the asking rent, and swaps `PropertyToBeOnMarket` for `PropertyOnMarket { m_AskingRent }`. For a `Signature` building it also **manufactures the company itself**, creating an entity from the matching company prefab's `ArchetypeData` (`:136-176`) — signature buildings do not wait for a company to find them.

### What a building gains at each level

**Nothing intrinsic.** A level is a different prefab (see `SelectSpawnableBuilding` above), so everything a level "gains" is either a field on that other prefab or a term in a formula that reads `SpawnableBuildingData.m_Level`. The complete set of level-dependent expressions at 1.6.0f1:

| What changes with level | Where |
| --- | --- |
| Rent asked, linearly in `level` | `PropertyUtils.cs:399` |
| Upkeep, as `pow(level, exponent)` | `PropertyRenterSystem.cs:226-245` |
| Leveling cost, as `pow(2, 2 * level)` | `BuildingUtils.cs:304-312` |
| Condition change per tick, as `pow(2, level)` | `BuildingUpkeepSystem.cs:216`, `:220` |
| Abandon cost, as `(6 - level)` for multi-apartment residential | `BuildingUtils.cs:335-338` |
| Apartment count, as `(1 + 0.25 * (level - 1)) * lotSize * m_ResidentialProperties`, **only when `m_ScaleResidentials`** | `ZoneProperties.cs:111-123` |
| Apartment wellbeing, as `+4 * (level - 1)` inside `0.8 * (...)` | `CitizenHappinessSystem.cs:1050-1053` |
| Level-up material list, selected by level | `BuildingUpkeepSystem.cs:257-276` |
| The prefab's own `ConsumptionData`, `PollutionData`, workplaces and geometry | per-prefab, authored |

`ZoneProperties.GetBuildingPropertyData` (`ZoneProperties.cs:111-123`) is the one place the apartment scaling lives, and it runs at prefab initialisation for each level, not at runtime.
The three coefficients in it — `1f`, `0.25f`, and `4f`/`0.8f` in the wellbeing curve — are literals in C# and ship as part of the formula.

**Verdict: the wiki's "residential buildings gain apartments at levels 3 and 5" is a per-prefab observation, not a rule.**
`https://cs2.paradoxwikis.com/Zoning` states apartment availability increases "at levels 3 and 5". The code has no level-3 or level-5 branch anywhere: `m_ScaleResidentials` scales the count continuously at `1 + 0.25 * (level - 1)`, and `math.round` at `ZoneProperties.cs:116` is what makes the count jump at some levels and not others for a given `lotSize * m_ResidentialProperties`. First-party wins on the mechanism: whether a particular building family appears to gain apartments at 3 and 5 is arithmetic over its own `lotSize * m_ResidentialProperties`, so it is a per-prefab observation and not a rule the simulation applies.
A neighbouring observation from the install, offered as suggestive rather than as proof: the shipped locale key set at `Cities2_Data/Content/Game/Locale.cok` carries the mixed-storefront sub-object family at levels 1, 3 and 5 only (`Assets.NAME[EU_MixedStorefront01_L1_1x1]` through `..._L5_6x1`), while ordinary zoned building prefabs exist at all five (`Assets.NAME[EU_CommercialGasStation01_L1_2x2]` … `_L5_4x6`). That is a fact about which art was authored at which level and nothing more; it does not establish where the wiki's sentence came from, and this pass did not try to.

### Theme-based zoning, and what "unthemed" means in components

**A theme is a prefab with an empty marker component**, and the whole mechanism is one buffer element.
`ThemePrefab : PrefabBase` carries an `assetPrefix` string and adds `ThemeData` — a zero-size marker (`src/Game/Game.Prefabs/ThemePrefab.cs:8-16`, `src/Game/Game.Prefabs/ThemeData.cs:6-9`).
`ThemeObject` is the `ComponentBase` that binds a prefab to a theme (`src/Game/Game.Prefabs/ThemeObject.cs:16-57`). Its `[ComponentMenu]` lists the six prefab kinds it may sit on: `ZonePrefab`, `ObjectPrefab`, `NetPrefab`, `AreaPrefab`, `RoutePrefab`, `NetLanePrefab` (`:7-15`). What it does is add **one** `ObjectRequirementElement(themeEntity, group, ObjectRequirementType.IgnoreExplicit)` to the prefab's requirement buffer (`:56`), each in its own group. It also yields the theme's name as a mod tag (`:20-33`).

**So "themed" and "unthemed" are not two systems. A zone prefab is themed iff it carries a `ThemeObject`, and unthemed iff it does not.** There is no flag and no enum; the absence of a buffer element is the whole of it.
The city's chosen theme is `CityConfigurationSystem.defaultTheme` (`src/Game/Game.City/CityConfigurationSystem.cs:77`), resolved on load: null falls back to the first `ThemeData` entity that is not `Locked` (`:202-212`), and an `overrideThemeName` string can name one by prefab name (`:213-220`). A theme change forces every `SubLane` to `Updated` (`:229-232`).
`ObjectRequirementType.IgnoreExplicit` is one of two flags (`src/Game/Game.Prefabs/ObjectRequirementType.cs:6-11`, the other being `SelectOnly`), and `VehicleSelectRequirementData` shows how it is read: a requirement is satisfied when it is the default theme, **or** when `ignoreTheme` is set and the requirement is any `ThemeData` at all (`src/Game/Game.Prefabs/VehicleSelectRequirementData.cs:63`).

**`ThemeRequirementData` is declared and never used.** `src/Game/Game.Prefabs/ThemeRequirementData.cs:7-9` is a zero-size marker, and a sweep of `src/` finds no producer and no consumer. Do not send a reader to it.

**First-party evidence for the themed/unthemed split, from the install rather than from the wiki.** The decoded locale package (`Cities2_Data/Content/Game/Locale.cok`, `en-US`) carries every zone prefab's display name under `Assets.NAME[...]`. Themed zone prefabs come in `EU ` / `NA ` pairs — `EU Residential Low` / `NA Residential Low`, `… Low Waterfront`, `… Medium`, `… Medium Row`, `… High`, `… Mixed`, `… Mixed Old Town`, `EU Commercial Low` / `NA Commercial Low`, `EU Commercial High` / `NA Commercial High`. Unthemed ones exist exactly once: `Industrial Manufacturing`, `Office Low`, `Office High`, `Residential LowRent`.
That matches the wiki's split exactly (`https://cs2.paradoxwikis.com/Zoning`, fetched 2026-08-08: theme-based rows for the housing and business families, an unthemed table for low-rent housing, industrial manufacturing and the two office densities), so this is one of the places the wiki is simply correct — but it is now stated on the install's authority rather than the wiki's, which is the point.
Verdict: confirmed live (2026-08-08, the sibling Unity plugin against the running 1.6.0f1 game, after the discovery pass). The `EU Residential Low` zone prefab entity carries exactly one `ObjectRequirementElement { m_Requirement = <the European theme entity, carrying ThemeData>, m_Group = 0, m_Type = IgnoreExplicit }`, resolved by name through `PrefabSystem.TryGetPrefab(PrefabID)`; the unthemed `Residential LowRent` prefab entity has no `ObjectRequirementElement` buffer at all. The mechanism claim and the absence-is-the-difference claim both hold as `ThemeObject.cs` states them.

**Themes reach unlock requirements too.** `ZoneBuiltRequirementData { m_RequiredTheme, m_RequiredZone, m_MinimumSquares, m_MinimumCount, m_RequiredType, m_MinimumLevel }` (`src/Game/Game.Prefabs/ZoneBuiltRequirementData.cs:6-19`) is evaluated by `ZoneBuiltRequirementSystem` (`SystemOrder.cs:195`, `Modification5`) in three mutually exclusive branches (`src/Game/Game.Prefabs/ZoneBuiltRequirementSystem.cs:180-235`): by named zone at or above a level; by **theme**, walking each built zone's `ObjectRequirementElement` buffer for a `ThemeData` requirement matching the required theme; or by area type. The tally comes from a map of `ZoneBuiltDataKey { m_Zone, m_Level }` → `ZoneBuiltDataValue { m_Squares, m_Count }` (`ZoneBuiltDataKey.cs:6-11`, `ZoneBuiltDataValue.cs:3-7`), fed primarily by a chunk pass over buildings with `Created`/`Deleted`, with the `ZoneBuiltLevelUpdate` records level-up emits covering only level transitions (`ZoneBuiltRequirementSystem.cs:60-92`). (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously attributed the whole feed to the level-up records.)

### Specialized industry is an area, not a zone

This is where the wiki's vocabulary and the game's part company, and getting it wrong sends a modder to the wrong namespace.

**In the toolbar it is a zone sub-service.** The shipped locale package carries `SubServices.NAME[ZonesExtractors] = "Specialized Industry"` beside `ZonesResidential`, `ZonesCommercial`, `ZonesIndustrial`, `ZonesOffice`, `ZonesSignatures` and `ZonesDefault` ("Remove Zoning"). So the game's own UI files it under Zones.

**In the simulation it is `Game.Areas`.** There is no `ZonePrefab` for forestry or mining. What the player paints is an **area**:

- `LotPrefab : AreaPrefab` (`src/Game/Game.Prefabs/LotPrefab.cs:12-40`) — `m_MaxRadius`, `m_RangeColor`, `m_OnWater`, `m_AllowOverlap`, `m_AllowEditing`, producing `LotData` (`LotData.cs:7-13`) and an archetype of `Lot`, `Geometry`, `SubObject`, `PseudoRandomSeed`.
- `ExtractorArea : ComponentBase` on that lot prefab (`src/Game/Game.Prefabs/ExtractorArea.cs:11-53`) — `m_MapFeature`, `m_ObjectSpawnFactor`, `m_MaxObjectArea`, `m_RequireNaturalResource`, `m_WorkAmountFactor` — producing `ExtractorAreaData` (`ExtractorAreaData.cs:7-17`) and adding `Extractor`, `OwnedVehicle`, and `WoodResource` when the feature is `Forest` (`:33-38`).
- `Game.Areas.Extractor` on the instance (`src/Game/Game.Areas/Extractor.cs:7-21`) — `m_ResourceAmount`, `m_MaxConcentration`, `m_ExtractedAmount`, `m_WorkAmount`, `m_HarvestedAmount`, `m_TotalExtracted`, `m_WorkType`.
- `MapFeature` is the resource layer the area sits on (`src/Game/Game.Areas/MapFeature.cs:3-15`): `None, Area, BuildableLand, FertileLand, Forest, Oil, Ore, SurfaceWater, GroundWater, Fish, Count`.
- The building that runs the area is a `Game.Buildings.ExtractorFacility { m_Flags: ExtractorFlags, m_Timer, m_MainBuildingFlags }` (`src/Game/Game.Buildings/ExtractorFacility.cs:6-10`), with `ExtractorFacilityData { m_RotationRange, m_HeightOffset, m_Requirements: ExtractorRequirementFlags }` on its prefab (`ExtractorFacilityData.cs:7-13`); `ExtractorRequirementFlags` is `{ None, RouteConnect = 1, NetConnect = 2 }`.
- The lot's `ExtractorProperty` marker (`src/Game/Game.Buildings/ExtractorProperty.cs`) exempts it from the high-rent warning (`RentAdjustSystem.cs:277`, `:331`).

The install's own naming confirms the shape: `Assets.NAME[Ore Area Placeholder - Coal] = "Coal Mining"`, `[... - Ore] = "Ore Mining"`, `[... - Stone] = "Stone Mining"`, `[Oil Area Placeholder] = "Oil Drilling"`, `[Forestry Area Placeholder] = "Forestry"`, beside `[Industrial Ore] = "Mining Area Hub"`, `[Industrial Oil] = "Oil Drilling Area Hub"`, `[Industrial Forestry] = "Forestry Area Hub"` and `[Extractor Lot] = "Specialized Industry Area Tool"` — a placeholder area prefab per specialisation, a hub building per family, and one area tool. The hub buildings exist at five levels (`IndustrialOreHub01_L1` … `_L5`), so specialized industry levels like anything else.

**The pollution tiers do not exist as a tier.** The wiki (fetched 2026-08-08) sorts the eight specialisations into "low pollution" — livestock, grain, vegetable and textile-fibre farming, forestry — and "medium pollution" — stone, coal and ore mining, oil drilling. The decompile has no tier enum, no band and no threshold: pollution is three floats per prefab. For a _zoned_ building they come from `ZonePollution` on the zone prefab (`src/Game/Game.Prefabs/ZonePollution.cs:9-18`: `m_GroundPollution`, `m_AirPollution`, `m_NoisePollution`), multiplied by the building's `lotSize` into `PollutionData` at initialisation (`:58-67`). For an extractor's hub building they are that building prefab's own `Pollution` component.
**Verdict: the wiki's tiers are a two-bucket summary of eight per-prefab float triples, and the ruling puts them out of reach anyway.** First-party wins with no contest — the buckets are a reader aid the game does not model — and the ruling on prefab values means the reference names `ZonePollution` / `PollutionData` and their three fields, says pollution scales with lot size, and states no bucket and no magnitude. Saying "mining pollutes more than farming" would be the ratio in prose the ruling names.
The wiki's other claim here — that livestock and stone mining need no natural resource — **is** modelled: `ExtractorArea.m_RequireNaturalResource` is a per-prefab `bool` (`ExtractorArea.cs:22`) and ships as the field to check, not as a list of which two.

### What a district scopes, and how

A district is an `AreaPrefab` subclass with a name colour and nothing else authored (`src/Game/Game.Prefabs/DistrictPrefab.cs:11-40`), producing `DistrictData` (an empty marker) and an archetype of `District`, `Geometry`, `LabelExtents`, `LabelVertex`, `DistrictModifier` and `Policy`.

**The district itself holds two things.**

- `District { m_OptionMask: uint }` (`src/Game/Game.Areas/District.cs:6-8`), a bitmask over `DistrictOption { PaidParking, ForbidCombustionEngines, ForbidTransitTraffic, ForbidHeavyTraffic, ForbidBicycles }` (`src/Game/Game.Areas/DistrictOption.cs:3-10`), tested by `AreaUtils.CheckOption` as `(m_OptionMask & (1 << (int)option)) != 0` (`src/Game/Game.Areas/AreaUtils.cs:124-127`).
- A `DynamicBuffer<DistrictModifier>` of `float2 m_Delta` (`src/Game/Game.Areas/DistrictModifier.cs:8-10`), **indexed positionally by `DistrictModifierType`** (`src/Game/Game.Areas/DistrictModifierType.cs:3-19`): `GarbageProduction, ProductConsumption, ParkingFee, BuildingFireHazard, BuildingFireResponseTime, BuildingUpkeep, LowCommercialTax, Wellbeing, CrimeAccumulation, StreetSpeedLimit, StreetTrafficSafety, EnergyConsumptionAwareness, CarReserveProbability, BikeProbability`. `AreaUtils.ApplyModifier` (`:129-137`) guards on `modifiers.Length > (int)type` and applies `value += delta.x; value += value * delta.y` — an additive and a multiplicative half in one struct. **A short buffer silently means no modifier**, which is what makes the enum's order a save-compatibility surface.

Policies supply both: `DistrictModifiers` and `DistrictOptions` are `ComponentBase` subclasses on a `PolicyPrefab` (`src/Game/Game.Prefabs/DistrictModifiers.cs`, `src/Game/Game.Prefabs/DistrictOptions.cs`), producing a `DistrictModifierData` buffer of `{ m_Type, m_Mode: ModifierValueMode, m_Range: Bounds1 }` and a `DistrictOptionData { m_OptionMask }`.

**Membership is by position, recomputed, not stored on the district.**
`BuildingPrefab` puts `CurrentDistrict` in every building's archetype (`src/Game/Game.Prefabs/BuildingPrefab.cs:46`), and `CurrentDistrictSystem` (`SystemOrder.cs:222`, `Modification5`) resolves it by testing the entity's `Transform.m_Position.xz` against the area search tree and taking the first area carrying a `District` (`src/Game/Game.Areas/CurrentDistrictSystem.cs:151-215`, `:340-360`). Roads carry `BorderDistrict { m_Left, m_Right }` instead (`src/Game/Game.Areas/BorderDistrict.cs:6-9`), and `AreaUtils.CheckOption(BorderDistrict, ...)` accumulates both sides and returns `x & !y` — a side with the option set and no existing side with it unset (`AreaUtils.cs:678-704`). (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously "reads either side", the service-scoping grain — the shipped reference had it right.)

**Service scoping is a buffer on the service building, and its default is the whole city.**
`ServiceDistrict { m_District }` (`src/Game/Game.Areas/ServiceDistrict.cs:6-9`) is a buffer added to a service building's archetype by the service prefab component that wants it — `Hospital`, `FireStation`, `PoliceStation`, `School`, `GarbageFacility`, `PostFacility`, `DeathcareFacility`, `Prison`, `EmergencyShelter`, `TransportDepot`, `AdministrationBuilding` and `WelfareOffice` each add it under their own condition (`src/Game/Game.Prefabs/Hospital.cs:54`, `FireStation.cs:46`, `PoliceStation.cs:47`, `School.cs:45`, `GarbageFacility.cs:56`, `PostFacility.cs:59`, `DeathcareFacility.cs:44`, `Prison.cs:45`, `EmergencyShelter.cs:45`, `TransportDepot.cs:50`, `AdministrationBuilding.cs:33`, `WelfareOffice.cs:33`).

`AreaUtils.CheckServiceDistrict` has three overloads and **all three return `true` when the buffer is missing or empty** (`AreaUtils.cs:144-190`):

```
no buffer          -> true   (serves everywhere)
buffer empty       -> true   (serves everywhere)
district is null   -> false  (a building outside every district is not served by a scoped service)
otherwise          -> membership test
```

That is the wiki's rule — "services that have not been assigned to any districts will service the entire city" (`https://cs2.paradoxwikis.com/Districts`, fetched 2026-08-08) — stated as the code states it, and the third line is the part the wiki does not have: **a target that lies in no district at all is invisible to any scoped service.**
The consumers are the pathfinding setups: `CitizenPathfindSetup.cs:237`, `FirePathfindSetup.cs:101` and their siblings. The AI-side citations previously listed here (`AmbulanceAISystem.cs:544-546`, `EvacuationDispatchSystem.cs:320`) read `CurrentDistrict`, not `ServiceDistrict` — they are the caller side supplying the district a pathfind setup then checks; `GarbageTruckAISystem` is the one AI reading the buffer directly (`:184`, `:774`, `:851`, `:912`). (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`.)
`ServiceDistrictSystem` (`SystemOrder.cs:223`, `Modification5`) does one job: when a district is deleted it strips that district from every `ServiceDistrict` buffer in the world (`src/Game/Game.Areas/ServiceDistrictSystem.cs`).

**Verdict: both halves of the wiki's coverage-versus-vehicle distinction resolve in the decompile.** The `Districts` page states that a building assigned to multiple districts keeps "passive coverage only in immediate neighbourhoods" while its "active simulated services (vehicles) operate across all assigned districts". The vehicle half is exactly what the pathfinding setups do. The passive half is settled too: `ServiceCoverageSystem.ProcessCoverageJob` reads the `ServiceDistrict` buffer itself (`ServiceCoverageSystem.cs:189`, `:217-231`) and gates per edge on `BorderDistrict` membership — an edge in no assigned district is skipped, one straddling an assigned and an unassigned district takes a 0.5 density factor (`:242-260`) — with no `AreaUtils` involvement, and `ResourceAvailabilitySystem` scopes taxi availability the same way (`:546`, `:569`, `:596`). (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously recorded as an unread lead for `city-services-and-coverage`, off an empty grep of `AreaUtils` alone.)

### What a placed building is, in components

`BuildingPrefab : StaticObjectPrefab` (`src/Game/Game.Prefabs/BuildingPrefab.cs:19`) declares the archetype, and reading `GetArchetypeComponents` (`:40-56`) is the fastest way to answer this question: `Building`, `CitizenPresence`, `SpawnLocationElement`, `CurrentDistrict`, `UpdateFrame`, `Game.Objects.Color`, `Game.Objects.Surface`, `BuildingModifier`, `Policy`, `Game.Net.SubLane`, `Game.Objects.SubObject`, `Game.Buildings.Lot`, `EnabledEffect` — on top of whatever `StaticObjectPrefab` contributes. `RefreshArchetype` (`:58-80`) is where the archetype is actually built, folding in every `ComponentBase` on the prefab plus `Created` and `Updated`, and adding `InstalledUpgrade`, `SubNet` and `SubRoute` when the prefab has a `BuildingUpgradeElement` buffer.

The instance's own state:

- `Building { m_RoadEdge, m_CurvePosition, m_OptionMask, m_Flags: BuildingFlags }` (`src/Game/Game.Buildings/Building.cs:6-12`). **`m_RoadEdge` is the join to almost everything**: land value, service coverage, resource availability and the address are all read off it.
- `BuildingFlags { None, HighRentWarning, StreetLightsOff, LowEfficiency, Illuminated, Historical }` (`src/Game/Game.Buildings/BuildingFlags.cs:6-14`) — a byte flags enum, and `Historical` is the level lock.

- `Game.Buildings.Lot { m_FrontHeights, m_RightHeights, m_BackHeights, m_LeftHeights }`, four `float3` of terraformed edge heights (`src/Game/Game.Buildings/Lot.cs`).
- The property markers, one per kind and mostly empty: `ResidentialProperty` (empty), `CommercialProperty { m_Resources }`, `IndustrialProperty { m_Resources }`, `OfficeProperty` (empty), `StorageProperty` (empty), `ExtractorProperty` (empty), `Signature` (empty).
- The rental state: `Renter { m_Renter }` buffer on the property, `PropertyRenter { m_Property, m_Rent }` on the renter, `PropertyOnMarket { m_AskingRent }`, `PropertyToBeOnMarket` (empty), `RentersUpdated { m_Property }` as an event.
- The distress states: `Abandoned { m_AbandonmentTime }`, `Condemned` (empty), `Destroyed`.
- `BuildingCondition { m_Condition }`.

**A `Signature` building is a spawnable building that was plopped.** `SignatureBuilding : ComponentBase` (`src/Game/Game.Prefabs/SignatureBuilding.cs:12`) names a `ZonePrefab` (`:16`) and `const int kStatLevel = 5` (`:14`), and it writes `SpawnableBuildingData { m_Level = 5, m_ZonePrefab }` (`:69-82`), asks the zone for the same building components a growable would get at level 5 (`:37`, `:48`), and adds `Signature`, `UniqueObject` (`:44-45`) and `PlacementFlags.Unique` (`:52-62`). The reference names those and never a table. (Corrected 2026-08-08, the zoning-buildings-and-land-value pass's `/review-gate`: previously also listed `WorkplaceData`, which only a prefab authoring the `Workplace` component carries — asset data, not part of the zone flow.)

### The zone check: what condemns a building

`ZoneCheckSystem` (`SystemOrder.cs:258`, `SystemUpdatePhase.ModificationEnd`) is the system that adds and removes `Condemned`, and it is the one the corpus forks.
It runs in three stages (`src/Game/Game.Buildings/ZoneCheckSystem.cs`):

1. `FindSpawnableBuildingsJob` (`:26-93`) — over the updated zone bounds, collect every object that has a `Building`, whose prefab has `SpawnableBuildingData` and **not** `SignatureBuildingData` (`:52`).
2. `CollectEntitiesJob` (`:96-141`) — sort and dedupe.
3. `CheckBuildingZonesJob` (`:144-369`) — validate each, and add or remove `Condemned` plus the `m_CondemnedNotification` icon (`:299-315`).

Validation is two chances (`:290-298`). `ValidateAttachedParent` (`:317-332`) passes a building attached to a parent whose prefab has `PlaceholderBuildingData` naming the **same** zone prefab. Otherwise `ValidateZoneBlocks` (`:334-368`) walks the building's footprint through the zone search tree and requires **every** cell under it to be `Visible` and to carry that exact `ZoneType`, **and** the lot's front row to meet a road — `:361` tests only the `Roadside` bit of the accumulated directions, and `Roadside` is masked in only for the front row (`:209-214`). Its opening short-circuit returns `false` only when all three hold: the zone prefab has `ZoneData`, its `ZoneType` is not `None`, and its `PrefabData` is **disabled** (`:337-340` — the obsolete-prefab case; every other combination falls through to the cell walk). (Corrected 2026-08-08 twice, the zoning-buildings-and-land-value mechanical pass then its `/review-gate`: previously "at least one cell Roadside", then an inverted rendering of this guard as a three-way precondition for proceeding.) Editor mode passes everything (`:290`).

**Corpus evidence: the substitution is exact and its shape is the point.** `algernon-A/PlopTheGrowables` disables the vanilla system outright and re-registers its own fork in the same phase: `PlopTheGrowables/Code/Mod.cs:74` sets `World.GetOrCreateSystemManaged<ZoneCheckSystem>().Enabled = false`, and `:79-82` registers `PloppedBuildingSystem` at `ModificationEnd` followed by `SelectiveZoneCheckSystem` after it. The fork (`Code/Systems/SelectiveZoneCheckSystem.cs`) copies the same three jobs with the same lookups (`:93-119`, `:353-378`, `:390-421`) and adds one exclusion. What it tags with is the mechanics fact: its query for buildings the mod owns is `WithAll<Building>().WithAny<ResidentialProperty, IndustrialProperty, CommercialProperty>().WithNone<Temp, Deleted, Signature, UnderConstruction, SpawnedBuilding, PloppedBuilding, ExtractorProperty>()` (`Code/Systems/PloppedBuildingSystem.cs:52`) — which is a working enumeration of what "a growable the player did not plop" means in components, arrived at by someone who had to make it work. It sets `Building.m_Flags |= BuildingFlags.Historical` to lock the level (`:75`), which is the vanilla flag `BuildingUpkeepSystem` already honours rather than a parallel lock.

## Bridge

**Techniques a change in this area needs.**

- **`prefabs-and-assets`** — everything authored here is a prefab, and three of this topic's mechanisms are prefab-lifecycle mechanisms rather than simulation ones. `ZoneProperties`, `ZonePollution`, `ZoneServiceConsumption` and `GroupAmbience` (`src/Game/Game.Prefabs/GroupAmbience.cs:9`) implement `IZoneBuildingComponent` (`src/Game/Game.Prefabs/IZoneBuildingComponent.cs:6-13`), whose three methods — `GetBuildingPrefabComponents`, `GetBuildingArchetypeComponents`, `InitializeBuilding` — let a _zone_ prefab contribute components and data to a _building_ prefab at initialisation, dispatched by `ZonePrefab` over whatever implementors the prefab carries (`ZonePrefab.cs:48-89`). A mod adding a zone type implements it or its buildings get no property, pollution or consumption data at all. `ZoneBlockPrefab.LateInitialize` building an `EntityArchetype` into `ZoneBlockData` (`ZoneBlockPrefab.cs:42-59`) is the archetype-declaration pattern. And `BuildingInitializeSystem` writing back into `ZoneData` (`BuildingInitializeSystem.cs:1020-1061`) is the case where prefab initialisation order between two prefabs matters.
- **`placement-definitions`** — a growable is not created; it is _defined_. `ZoneSpawnSystem.Spawn` writes `CreationDefinition` + `ObjectDefinition` into a four-component archetype (`ZoneSpawnSystem.cs:623-666`, the archetype at `:1090`) with `CreationFlags.Permanent | CreationFlags.Construction`, and the definition machinery builds the entity. A mod that wants to change what spawns, or where, works on definitions rather than on entities. Level-up is the same story one step removed: `UnderConstruction { m_NewPrefab, m_Progress }` (`BuildingUpkeepSystem.cs:726-730`) hands the prefab swap to the construction pipeline.
- **`ecs-in-this-game`** — every parameter component in this topic is read with `GetSingleton<T>` off a one-type query (`LandValueSystem.cs:324/355`), which is the only route to a parameter component and needs no prose here. Two shapes this topic leans on harder than most: `BuildingSpawnGroupData` as an `ISharedComponentData` used as a **chunk filter** on zone type (`ZoneSpawnSystem.cs:288`, `BuildingUpkeepSystem.cs:768`), which is how the spawner avoids a per-entity zone test; and `UpdateFrame` as a shared component sharding the rent and upkeep passes across ticks (`PropertyRenterSystem.cs:74`, `RentAdjustSystem.cs:228`, both against `SimulationUtils.GetUpdateFrame(frameIndex, kUpdatesPerDay, 16)`), so a system's stated interval is not how often a given building is touched.
- **`save-serialization`** is not on this topic's bridge list but is where the zone-index remap belongs if any reference states it: `Cell` and `VacantLot` carry a runtime index that `ResolvePrefabsSystem` rewrites on every load (`ResolvePrefabsSystem.cs:245-332`, driven at `:490-509`), and both structs are versioned (`Version.cornerBuildings`, `Version.zoneHeightLimit` at `Cell.cs:27/39`, `VacantLot.cs:47/56`). **The parameter-prefab field initializers are a trap and are not the values.**
`LandValuePrefab` (`src/Game/Game.Prefabs/LandValuePrefab.cs:14-38`) and `ZonePreferencePrefab` (`src/Game/Game.Prefabs/ZonePreferencePrefab.cs:12-43`) declare every field with a C# initializer — `m_LandValueBaseline = 10f`, `m_TramSubwayBonusMultiplier = 50f`, `m_ResidentialSignificanceServices = 100f`, and so on. These are compiled into the decompiled source and are citable to a line, which makes them look exactly like the C# constants the ruling permits.
**They are not.** `PrefabBase : ComponentBase : ScriptableObject` (`src/Game/Game.Prefabs/PrefabBase.cs:16`, `src/Game/Game.Prefabs/ComponentBase.cs:13`), so Unity deserialisation overwrites every serialized field the shipped asset carries a value for, and the initializer survives only where the asset wrote nothing. A reader who cites one has stated a prefab value on the authority of a default.
Verdict: settled live (2026-08-08, the sibling Unity plugin against the running 1.6.0f1 game, after the discovery pass) — many initializers do **not** survive the asset, and neither component survives intact. `LandValueParameterData` read as a singleton: baseline 10, telecom 20, bus 5, tram/subway 50, cap 100 and ground penalty 10 match their initializers, but the health, education and police coverage multipliers are 2 against an initialized 5, attractiveness 5 against 3, commercial service 5 against 10. `ZonePreferenceData`: nine of sixteen fields differ — `m_ResidentialSignificanceServices` 6 against 100, `m_ResidentialSignificanceWorkplaces` 3 against 50, `m_ResidentialSignificancePollution` (−0.1, −0.1, −0.1) against (−100, −100, −100), `m_ResidentialNeutralLandValue` 100 against 10, `m_CommercialSignificanceCompetitors` 50 against 200, `m_CommercialNeutralLandValue` 100 against 20, `m_IndustrialNeutralLandValue` 40 against 5, both land-value significances −0.5 against −1. A caveat the read cannot remove: these are the values in one loaded save, so a mode class or a mod may sit between asset and reading — which changes nothing for the ruling, since either way the initializer is not the number. **Ruled (2026-08-08, the zoning-buildings-and-land-value pass; conflicts.md).**
