## Findings

### 1. What the build produces, and where it installs

**The scaffold's webpack config is the whole build, and it writes straight into the installed mod folder.**
`OUTPUT_DIR = ${CSII_USERDATAPATH}\\Mods\\${MOD.id}` (`create-csii-ui-mod/template/webpack.config.js:14`), used as `output.path` at `:88`. There is no intermediate `dist/`: `npm run build` installs.
The config throws before webpack starts if `CSII_USERDATAPATH` is unset (`:10-12`), with the message *"CSII_USERDATAPATH environment variable is not set, ensure the CSII Modding Toolchain is installed correctly"*.

**Four kinds of file come out, and their names are all load-bearing.** Read off the maintainer's own built mod at `%CSII_LOCALMODSPATH%/HallOfFame/`, which holds `HallOfFame.mjs`, `HallOfFame.css`, `HallOfFame.mjs.LICENSE.txt` and `images/` beside the C# half's `HallOfFame.dll`:

- **`<id>.mjs`** — the entry bundle. The name is `[name].mjs` where `[name]` is the entry key, and the entry key is `MOD.id` (`webpack.config.js:28-30`). Nothing in the config sets `output.filename`; the `.mjs` extension is webpack's default when `output.module` is true, and `output.module` is derived from `experiments.outputModule` (`:104-106`) — `ExtraDetailingTools/UI/node_modules/webpack/lib/config/defaults.js:938` sets `output.module` from that experiment and `:1037` sets `filename` to `[name].mjs` when it is. Those two are read out of the corpus checkout's only installed `node_modules`, at webpack 5.97.1, which is the version the template pins (`create-csii-ui-mod/template/package.json:35`).
  The extension is what makes the file a UI module at all: `DefaultAssetFactory` maps `.mjs` to `UIModuleAsset` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/DefaultAssetFactory.cs:257`), and `UIModuleAsset.kExtension` is the literal `".mjs"` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/UIModuleAsset.cs:27`).
- **`<id>.css`**, only when the mod imported any style. `MiniCssExtractPlugin` is instantiated with no options (`webpack.config.js:108`), so its filename is `[name].css` — the same entry key.
- **`images/<name><ext><query>`** — every `.png`, `.jpe?g`, `.gif` and `.svg` imported from the source, emitted as `asset/resource` (`:71-77`).
- **`<id>.mjs.LICENSE.txt`** — Terser's extracted-comments file (`:97-101`). It holds the third-party licence banners lifted out of the bundle; the mod's own manifest banner is *not* in it, it is prepended to the `.mjs`. Verified on the built artefact: `HallOfFame.mjs.LICENSE.txt` holds only the `classnames` and React notices, while `HallOfFame.mjs`'s first eight lines are the `Cities: Skylines II UI Module` banner.

`Rots:` the produced file set and their names. Re-check `create-csii-ui-mod/template/webpack.config.js` (`entry`, `output`, the `asset/resource` generator) and `UIModuleAsset.kExtension`.

**The game reaches the bundle through one flat host, and the file name is the whole address.**
`ModManager.InitializeUIModules` walks every `UIModuleAsset` in the global database and calls `UIManager.defaultUISystem.AddHostLocation("ui-mods", Path.GetDirectoryName(asset.path), asset.isLocal)` for each, then hands the list of `couiPath`s to the app bindings (`src/Game/Game.Modding/ModManager.cs:461-473`). `couiPath` is `"coui://ui-mods/" + Path.GetFileName(path)` (`UIModuleAsset.cs:41`).
So **every** mod's directory is registered under the single host name `ui-mods`, and `coui://ui-mods/<file>` is resolved by walking those directories.

**1a. The `.mjs` is safe from collision and everything beside it is not.**
`DefaultResourceHandler` looks the host up once and then tries each registered location in list order, returning the first that answers (`src/Colossal.UI/Colossal.UI/DefaultResourceHandler.cs:607-622`, and the identical stream path at `:632-647`). The list is kept sorted by an integer priority (`src/Colossal.UI/Colossal.UI/UISystem.cs:254-273`, comparer at `:155`), and `ModManager` passes no priority, so every mod is inserted at 0 and the order among them is whatever `List.BinarySearch` returned for an equal key — unspecified.
The `.mjs` and `.css` carry the mod id in their names, so they never collide. `images/` does: the scaffold emits `images/[name][ext][query]` and `publicPath` is `coui://ui-mods/` (`webpack.config.js:75`, `:92`), so an imported icon resolves to `coui://ui-mods/images/<name>.svg` for **every** mod. Confirmed in the built artefact: the bundle carries `t.p="coui://ui-mods/"` and concatenates `t.p+"images/…"` at each use site (`%CSII_LOCALMODSPATH%/HallOfFame/HallOfFame.mjs`, the `t.p=` assignment and the `+"images/` sites).
Two mods each shipping `images/icon.svg` therefore both request the same URL, and which file answers is not determined by anything the mod controls.
**Settled live.** With three UI mods loaded, four `coui://ui-mods/images/<name>` requests resolved into **three different mods' folders**, chosen by nothing but the file name: `trophy.svg` (655 bytes, HallOfFame's), `city.svg` (2,360, FindIt's), `Magnifier.svg` (3,130, FindIt's) and `skyve.png` (18,283, Skyve Mod's) all returned 200 from the one prefix. A name none of them ships, `images/nope.svg`, returned **404**.
**One corpus author has already hit this and fixed it in the build**: Traffic renames the output directory to `traffic-images/` (`Traffic/UI/webpack.config.js:76`, against the scaffold's `images/`) and adds a `copy-webpack-plugin` pattern targeting the same folder (`:110-114`). It is the only divergence of its kind in the corpus.
`Unconfirmed:` which of two identically-named files wins. No installed pair collides, so producing one means writing a file into the user's mods folder — which also trips the live reload in finding 5 — and that is theirs to authorise. The decompiled resolution order above says the answer is unspecified; the experiment would say which way it fell on one machine, which is weaker than the reading.

**1b. A UI module does not have to sit at the root of the mod folder.**
The host location is `Path.GetDirectoryName(asset.path)` — whatever directory holds the `.mjs`. WriteEverywhere puts its bundle in a subdirectory, `OUTPUT_DIR = ${CSII_USERDATAPATH}\\Mods\\BelzontWE\\UI` (`CS2-WriteEverywhere/_Frontends/UI/k45-we-vuio/webpack.config.js:14`), and the game registers that subdirectory as a `ui-mods` location like any other.

### 2. The externals contract

**The game defines its shared modules as properties on `window`, and the externals map is the mirror of that list.**
`Object.defineProperties(window, { React, ReactDOM, ReactDOMClient, "cs2/api", "cs2/bindings", "cs2/l10n", "cs2/ui", "cs2/utils", "cs2/input", "cs2/modding", "cohtml/cohtml", "chart.js" })` (`source.js:47076-47089`). The scaffold sets `externalsType: "window"` and maps ten import specifiers onto those names (`create-csii-ui-mod/template/webpack.config.js:31-43`).
`Object.defineProperties` with a bare `value` descriptor leaves `writable`, `enumerable` and `configurable` at `false`, so a mod cannot replace `window.React` or any of the others.
**Settled live.** `Object.getOwnPropertyNames(window)` shows all twelve names present, in the declaration order of the block above — a presence check over those twelve, not a census of `window`'s own properties — and `Object.getOwnPropertyDescriptor(window, "React")` reads `{ writable: false, enumerable: false, configurable: false }`.

**The corpus does not touch this list.** Every one of the 19 webpack configs in the checkout carries the same ten mappings, two of them re-indented and otherwise identical; ten of them are **byte-identical to the current scaffold config in its entirety** (`Anarchy/Anarchy/UI`, `BetterBulldozer/BetterBulldozer/UI`, `CS2-MoveIt/UI`, `FindIt-CSII/FindIt/UI`, `LineTool-CS2/UI`, `NodeController/NodeController/UI`, `Recolor/Recolor/UI`, `RoadBuilder-CSII/RoadBuilder/UI`, `Tree_Controller/Tree_Controller/UI`, `Water_Features/Water_Features/UI`, each `webpack.config.js` diffing empty against `create-csii-ui-mod/template/webpack.config.js`). The nine that diverge change output paths, plugins, loaders or formatting — never the externals.

**Two of the game's `window` modules are not in the scaffold's externals, and one of them a corpus mod pays for.**
`ReactDOMClient` and `chart.js` are exposed by the game (`source.js:47079` and `:47088`) and absent from the template's map. InfoLoom imports `chart.js` and five chart plugins as ordinary dependencies (`InfoLoom/InfoLoom/UI/package.json:24-28`) with the stock externals list unchanged (`InfoLoom/InfoLoom/UI/webpack.config.js:32-42`), so it bundles a second copy of Chart.js into its `.mjs` rather than using the game's.
**Settled live: the game ships Chart.js 4.0.1.** `window["chart.js"].Chart.version` reads `"4.0.1"`, and the namespace exports the full public surface (`Chart`, the controllers, the scales, `Legend`, `Filler`, `Decimation`, `DomPlatform` and the rest — 25 names read off the first slice). InfoLoom pins `^4.4.4`, four minors ahead of what it could have had for free. No first-party artefact states the version statically: `source.js` carries only the library's internals (`_chartjs`, `$chartjs` at `:13715`, `:18436`) and a grep for a version banner returned nothing, so the running game is the only source for it.
`Rots:` the Chart.js version. Re-check `window["chart.js"].Chart.version` against a running game.
`Unconfirmed:` whether declaring `"chart.js": "chart.js"` as an external and importing it actually resolves at build time — the window property is there and the version is known, but no mod in the corpus does it, so the webpack side is unexercised. Building a mod that externalises it and loading it would settle it.

**The scaffold's own type declarations depend on a package the scaffold does not install.**
`types/bindings.d.ts:2` opens `import { ChartDataset } from 'chart.js';`, and `chart.js` appears in neither `dependencies` nor `devDependencies` of `create-csii-ui-mod/template/package.json:17-37`. The build survives because the template's tsconfig sets `skipLibCheck: true` (`create-csii-ui-mod/template/tsconfig.json:12`); turning that off surfaces an unresolved import in a first-party declaration file the mod author did not write.

`Rots:` the `window` module list and the externals map. Re-check `source.js`'s `Object.defineProperties(window, …)` block against `create-csii-ui-mod/template/webpack.config.js`'s `externals`.

### 3. The manifest, and the identity it shares with the C# half

**`mod.json` is four keys and the webpack config is what turns them into a manifest.**
The template ships `{ "id": "", "author": "", "version": "1.0.0", "dependencies": [] }` (`create-csii-ui-mod/template/mod.json`). The config interpolates them into a comment banner carrying the **capitalised** keys `Id`, `Author`, `Version`, `Dependencies` (`create-csii-ui-mod/template/webpack.config.js:16-23`), and that banner reaches the bundle through Terser's `extractComments.banner` (`:97-101`) rather than through a banner plugin — which is where to look when a built module carries no manifest.
The game's parser reads it back: `UIModuleAsset.ParseModuleInfo` scans for the first line starting `/*`, then reads `*`-prefixed lines until one ends `*/` (`UIModuleAsset.cs:45-73`), and `ProcessLine` handles each: a blank line is skipped (`:77-81`), a line *starting* `Cities: Skylines II UI Module` passes only when it equals the sentinel exactly — `line.StartsWith(...)` followed by `return line == ...`, so extra text on that line stops the parse (`:82-85`) — and any other line without a `:` stops it (`:86-90`). **The sentinel is not required**: the identifier gate fires only for a line that already starts with it, so a comment block carrying only `* Id: Foo` produces a valid module (`:37`, `isValidModule` on `m_ModuleId` alone). Recognised keys are `Id`, `Author`, `Version`, `Dependencies` (`:93-108`); an unrecognised `Key: value` line falls through the switch and is ignored, the parse continuing.
`isValidModule` turns on `m_ModuleId != null` alone (`:37`), so a mod with an unparsable version is still a valid module.

**Two manifest fields do less than they look.**
`Version` goes through `System.Version.TryParse` (`UIModuleAsset.cs:102`), which takes only numeric `major.minor[.build[.revision]]`; a semver pre-release string parses to null and is dropped silently. Verified on the maintainer's install: `Modding.log` records `"m_ModuleVersion":{"Major":2026,"Minor":3,"Build":0,"Revision":-1,…}` for `HallOfFame`, whose `mod.json` version is `2026.3.0`.
`Dependencies` is **inert**. `PostCreate` splits it and passes the result to `AddTags` (`:112-124`, the call at `:123`), and a repository-wide grep of the decompile for `m_UIModuleDependencies` returns that write and no reader. Nothing orders module loading by it. An empty `dependencies: []` renders as an empty string in the banner and comes back as the one-element array `[""]` — visible in the same log line.

**The identity the two halves must share is one string, and three independent derivations have to agree on it.**
- The C# deploy directory is `$(LocalModsPath)\$(TargetName)` (`%CSII_TOOLPATH%/Mod.targets:52`), with `LocalModsPath` read from the **user-scope** `CSII_LOCALMODSPATH` (`%CSII_TOOLPATH%/Mod.props:34`).
- The UI output directory is `${CSII_USERDATAPATH}\Mods\${MOD.id}` (`webpack.config.js:14`), read from the **process** environment.
- The bundle's own URL is `coui://ui-mods/<filename>` with the filename `<MOD.id>.mjs`.

So `mod.json`'s `id` must equal the csproj's `TargetName`, and the two paths must land in the same folder. They are not the same variable: the toolchain writes `CSII_LOCALMODSPATH` as `<user data>\Mods` and webpack composes that path itself, so a user who repoints `CSII_LOCALMODSPATH` moves the C# half and leaves the UI half behind. On the maintainer's machine the two agree (`CSII_LOCALMODSPATH` = `C:\Users\Morgan\AppData\LocalLow\Colossal Order\Cities Skylines II\Mods`, `CSII_USERDATAPATH` = its parent).

**The scaffold makes the id the directory name, which is how the mismatch happens.**
`createModProject` prompts for a project name, validates it against `/^[a-zA-Z0-9_-]+$/`, creates a directory of exactly that name, then writes it into `mod.json` as `id` (`create-csii-ui-mod/utils/create-mod-project.js:9-11`, `:61-73`). Scaffolding a folder called `UI` inside the C# project gives a mod whose id is `UI`. Every corpus repository has a `UI/` directory and an `id` that is not `UI`, so each author renamed the directory or edited `mod.json` afterwards — the scaffold offers no way to get both in one step.

**The mod id is also the binding group name, by convention rather than by mechanism.**
16 of the 19 UI repositories import `mod.json` into their TypeScript and pass `mod.id` as the binding group: 98 source files import the manifest and 193 lines pass `mod.id`. Traffic is the clearest single site (`Traffic/UI/src/bindings/index.ts:2`, `:6-13`). Nothing in the game requires it — the group name is a free string on both sides — but a mod that does this cannot get the two halves out of step.
The counts are a corpus measurement, not a version-volatile fact; they re-derive from a grep for `mod.id`.

**A mod id containing a space works, though the scaffold forbids one.** `createModProject`'s validator rejects a space, but a published mod ships as `Skyve Mod` from `Skyve Mod.mjs` (`Modding.log`, its registration line). **Settled live**: `coui://ui-mods/Skyve Mod.mjs` returns 200 with its manifest banner intact — the unencoded space in the URL is no obstacle to the resource handler, and the module is one of the three registered in the session. So the scaffold's character class is the scaffold's rule, not the game's.

### 4. Refreshing the type declarations after a game update

**The scaffold on the machine is a junction into the game install, so it moves with the game.**
`NpxModProjectDependency` installs the template by running `npm link` with the working directory set to `<install>/Cities2_Data/Content/Game/.ModdingToolchain/npx-create-csii-ui-mod` (`src/Game/Game.Modding.Toolchain.Dependencies/NpxModProjectDependency.cs:20`, `:116`). Verified on the maintainer's machine: `~/AppData/Roaming/npm/node_modules/@colossalorder/create-csii-ui-mod` is a **junction** whose target is that install path, and `diff -rq` between the two returns nothing.
So the globally installed package is not a copy that ages — it is the game's own files under another name, and a game patch that ships new `types/*.d.ts` changes what `npx create-csii-ui-mod` hands out immediately, with no npm step.

**The project's own copy does age, and only one command refreshes it.**
`npm run update` is `npx create-csii-ui-mod update` (`create-csii-ui-mod/template/package.json:10`). `updateModTemplate` requires `mod.json`, `package.json`, `tsconfig.json` and `types/` all to exist, then copies the template's `tsconfig.json`, `types/`, `tools/` and `webpack.config.js` over the project's (`create-csii-ui-mod/utils/update-mod-template.js:17-34`), deletes the renamed `declarations.d.ts` if present (`:36-47`), rewrites the pinned dependency versions and the `scripts` block into the project's `package.json` (`:49-75`), and runs `npm install` (`:87`).
`copyAsync` overwrites file by file and never deletes (`create-csii-ui-mod/utils/copy-async.js:10-30`), so a declaration file removed from a later template survives in the project — the hard-coded `declarations.d.ts` deletion at `:36-47` is the toolchain's own acknowledgement of that, and it is the only such entry.
**The update also overwrites `webpack.config.js` and `tsconfig.json`.** A mod that edited either loses the edit on the next `npm run update`.

**Every vendored `types/` directory in the corpus is stale, and nothing tells the author.**
Against the current scaffold's `types/` (11 files; `bindings.d.ts` 3,646 lines, `ui.d.ts` 707, `input.d.ts` 812, `modding.d.ts` 46, `l10n.d.ts` 213, `cohtml.d.ts` 194, `api.d.ts` 87, `utils.d.ts` 25, `react.d.ts` 7, `assets.d.ts` 5, plus `validateTypes.ts`), all 18 vendored copies differ, at 8 or 9 of the 11 files each (17 repositories; Time2Work carries two copies, `Time2WorkUI/types/` and `Time2WorkUI/src/types/`). Their `bindings.d.ts` ranges from 3,028 lines (`AreaBucket/UI/area-bucket/types`, `Time2Work/NightShift/Time2WorkUI/types`) to 3,625 (`Anarchy`, `CS2-MoveIt`, `ExtraDetailingTools`, `Tree_Controller`). `modding.d.ts` is 45 lines in 14 of them and 46 in four — the one-line difference is the seventh append-hook anchor the sibling topic's conflict entry records as recent growth.
The failure is silent: the mod compiles against whatever it vendored, and a binding payload that changed shape in the game reads as the old shape with no error.

**One corpus author took the declarations out of the repository entirely.** Hall of Fame drops the vendored `types/` folder and adds a versioned npm package to its tsconfig `include` instead: `"include": ["src/**/*", "../../node_modules/@csmodding/urbandevkit/cs2-types"]` (`HallOfFame/HallOfFame/UI/tsconfig.json:2`). The refresh then becomes an ordinary dependency bump with a reviewable diff.

`Rots:` the scaffold's file layout — the `types/` file set, their sizes, and the `update` subcommand's copy list. Re-check `create-csii-ui-mod/template/types/` and `create-csii-ui-mod/utils/update-mod-template.js:25-34`.

**`clean` deletes the C# half too.** `cleanInstalledLocalMod` does `fs.rmSync(<CSII_USERDATAPATH>/Mods/<id>, { recursive: true, force: true })` (`create-csii-ui-mod/utils/clean-installed-local-mod.js:6-14`), and that directory is the shared deploy folder — the `.dll`, the Burst libraries and the `.pdb` go with the bundle. It throws `Local installation of <id> not found. Already deleted?` when the folder is absent.

### 5. The inspector port, how it opens, and what the dev loop actually does

**One launch flag turns on three things at once.**
`GameManager.ParseOptions` registers `uiDeveloperMode` with the description *"Enable UI debugger and memory tracker"* (`src/Game/Game.SceneFlow/GameManager.cs:370-373`), and its only consumer is `m_UIManager = new UIManager(configuration.uiDeveloperMode)` (`:1745`). That constructor sets three settings from the one boolean: `enableDebugger`, `enableMemoryTracking` and **`liveReload`** (`src/Colossal.UI/Colossal.UI/UIManager.cs:177`, the initialiser at `:185-190`).
So the inspector and the file-watching reload are the same switch.

**The port is 9444 and it is a constant.**
`UIManager.Settings.SetDefault` sets `debuggerPort = 9444` and `enableDebugger = liveReload = false` (`UIManager.cs:79-94`, the port at `:93`); the constructor's object initialiser overrides the two booleans and leaves the port alone. `CohtmlSystemSettings.DefaultDebuggerPort` is the same 9444 (`src/Cohtml.Runtime/cohtml/CohtmlSystemSettings.cs:13`, field default at `:22`).
Turning the debugger on also forces the process to keep running unfocused: `UISystem.Settings.ToNativeSettings` sets `Application.runInBackground = true` and logs *"Cohtml DevTools debugger forced to run in the background at port {0}"* (`src/Colossal.UI/Colossal.UI/UISystem.cs:99-114`), reached because `UISystem.Settings.New` copies `enableDebugger` straight off `UIManager.instance.settings` (`:29-31`). That is what makes a CDP session survive alt-tabbing.
Confirmed on the maintainer's install. `Logs/SceneFlow.log:3-6` records the full command line — `Cities2.exe`, `dowser.exe`, `--developerMode`, `--uiDeveloperMode` — and `Logs/UI.log:7` reads `Inspector initialized. Remote debugging available on port: 9444`, with `Logs/UI.log:9` `UIView 0 url set to assetdb://gameui/index.html`.
`Rots:` the port and the flag name. Re-check `CohtmlSystemSettings.DefaultDebuggerPort`, `UIManager.Settings.SetDefault`, and `GameManager.ParseOptions`.

**Flag spelling.** Both `-uiDeveloperMode` and `--uiDeveloperMode` parse, for the reason `conflicts.md`'s ruled entry *"Launch flags: `-developerMode` or `--developerMode`"* gives: `Mono.Options`' pattern opens `^(?<flag>--|-|/)` and dispatches on the name alone (`src/Colossal.Core/Mono.Options/OptionSet.cs:134`, `:446`). That entry's ruling — the double-dash form throughout shipped prose — governs this flag identically. The wiki writes `--uiDeveloperMode`, *"Lauches the game in ui developer mode, allowing to access localhost:9444 for UI inspection and debugging"* (https://cs2.paradoxwikis.com/Launch_Parameters, fetched 2026-08-24, its typo).

**A second debugger port, 9445, exists only in a development harness the shipped game never runs.** `UISystemBootstrapper` sets `enableDebugger = true` and `debuggerPort = 9445` (`src/Game/Game.UI/UISystemBootstrapper.cs:89-90`), but the component is a `MonoBehaviour` nothing in the boot path instantiates, its `Awake` logs that it "is only meant for development purpose" (`:40`), and the fatal-UI block sits behind `if (!m_EnableFatalUI) return;` (`:60-63`). The retail crash screen is `GameManager.ShowFallbackUI`, whose UI system is created with `developerMode: false` and `enableDebugger = false` (`src/Game/Game.SceneFlow/GameManager.cs:1693`, `:1717`), so the shipped game serves no 9445 at all. The `debug-menu` pass had already established this (`debug-menu.md:48`); this pass first re-read the assignment as unconditional — a read that stopped at the confirming line — and the shipped reference carries no 9445 claim.

**`liveReload` is a real file watcher, and it is what makes `npm run dev` a dev loop.**
`UIView` copies `liveReload` from the manager's settings and sets `liveReloadUrl = "assetdb://gameui/Static/reload.html"` and `devServerPort = 9000` (`src/Colossal.UI/Colossal.UI/UIView.cs:54-56`); when the flag is on the view constructs a `UILiveReload` (`:260-262`) and drives it from `Update` (`:320`).
`UILiveReload.Create` builds a `BufferedFileSystemWatcher` per host location of the **view's own URL host** (`src/Colossal.UI/Colossal.UI/UILiveReload.cs:62-207`, the `coui` branch at `:73-105`) — that is `gameui`, the game's own UI directory. Mods are reached by the second route: it subscribes to `onHostLocationAdded` and creates a watcher for any location registered later, **if that registration asked to be watched** (`:209-233`).
`ModManager.InitializeUIModules` passes `asset.isLocal` as that flag (`ModManager.cs:468`). So a mod under `%CSII_LOCALMODSPATH%` is watched and a mod downloaded from Paradox Mods is not. That is the mechanism behind "rebuild and it reloads" and it applies only to what you built yourself.

**What a rebuild triggers depends on the extension, and `.mjs` is not on the list you would expect.**
`OnChanged` classifies a change with `IsPageFileExtension`, which returns true for exactly `.js`, `.css` and `.html` (`UILiveReload.cs:289-296`). A page-classified change sets a 1-second debounce and ends in `m_Target.View.Reload()`; anything else — **including `.mjs`** — is classified Media, with a 0.5-second debounce (`:260-287`).
The Media path is not a lesser reload. `Update` navigates the view to `liveReloadUrl` first, waits out the delay, calls `uiSystem.ClearCachedUnusedImages()` and clears the pending state (`:333-345`, the sweep at `:342`); the next frame falls through to `UpdateURL(m_Target.url)` and navigates back (`:367`), which is a fresh load of `index.html`. So a mod rebuild costs a full document teardown and reload plus an image-cache sweep, and a stylesheet-only change costs a plain `View.Reload()` without the sweep.
Observed twice on the maintainer's install, in two different sessions, with the same signature in `UI.log`: a run of *"…hasn't been loaded yet when view with id 0 unloaded its document"* font messages (the teardown), then `Reloading media 0`, then the document's CSS-parse messages again (the fresh load). The first time was a `.mjs` rewritten by `npm run build` at 09:59:16 with the game open; the second was the mod's whole deploy folder being emptied by `DeployWIP` at 10:49:53. **To reproduce:** with the game running under `--uiDeveloperMode`, write any file in a local mod's folder and read `UI.log` — the line is `Reloading media <viewId>` for anything but `.js`/`.css`/`.html`, and `Reloading page <viewId>` for those (`UILiveReload.cs:341`, `:373`).
Two things the second occurrence adds. **A deletion is a change like any other**, so wiping the folder triggers the same reload as writing to it. And **a mixed batch takes the Media path**: the wipe removed the `.css` along with the `.mjs`, `.dll` and `.pdb`, and Media won, because `OnChanged` refuses to upgrade a pending Media to Page (`if (m_Reloading != ReloadType.Media && IsPageFileExtension(extension))`, `UILiveReload.cs:276`).
`Rots:` the extension list in `IsPageFileExtension`, the two debounce constants (`kPageReloadDelay = 1f` at `:26`, `kMediaReloadDelay = 0.5f` at `:28`), and `liveReloadUrl`. Re-check `UILiveReload.cs` and `UIView.cs:54-56`. `Static/reload.html` exists in the 1.6.0f1 install at `Cities2_Data/Content/Game/UI/Static/reload.html`.

**Verdict: the watcher is event-driven, not a poll, and this repo's own shipped prose said otherwise until this ticket's gate corrected it (2026-08-24).**
`plugins/coherent-gameface/skills/gameface-driving/SKILL.md:72` described the mod-file watcher as "a slow coalescing mtime poll (~15-20s period, jittery)" whose triggers "coalesce into ONE reload" and fire "exactly two context swaps ~530ms apart"; the line now states the event-driven mechanism and the holding-page hold below.
The decompile settles the mechanism against it. `UILiveReload` constructs each watcher with `Polling = BufferedFileSystemWatcher.PollingMode.FileSystemWatcher` (`UILiveReload.cs:95`, `:218`), and that enum is `[Flags]` with `OnFocus = 1`, `Interval = 2`, `FileSystemWatcher = 4` (`src/Colossal.IO/Colossal.IO.FileSystem/BufferedFileSystemWatcher.cs:23-28`) — so the interval and focus polls are both off, `StartPollingIfNeeded` has nothing to start (`:835`, gated at `:199`), and events come from a native `FileSystemWatcher`. They are handed to a `BlockingCollection` drained by a background task with no delay (`:655-681`). The 15-second constant that would explain the number, `m_ReconcileWindow` (`:114`), gates `ShouldSuppress` (`:565-617`), which **only inserts into its recent-event index on the non-native path** (`:600-604`); with no poll running, the index stays empty and no native event is ever suppressed. While the watch root exists, the only delays in the chain are `UILiveReload`'s own 1-second and 0.5-second debounces; a deleted root is the second delay source — `EnterMissingAndProbe` cancels the buffered-event consumer and re-arms by a probe backing off from 500ms toward a 5000ms cap (`BufferedFileSystemWatcher.cs:719-750`, `:752-797`), and writes landing while it probes are dropped, a window `DeployWIP`'s `RemoveDir` of the watched deploy folder opens on every C# build (`Mod.targets:111`).
The observation the skill records is still real, and the two swaps ~530ms apart are exactly the Media path this file describes — navigate to `reload.html`, wait `kMediaReloadDelay`, navigate back — which is what makes a reload count go up by two. What the mechanism does not support is the latency: a rebuild-to-live measurement includes `npm run build`, which on the scaffold's production config is most of a webpack run.
`Unconfirmed:` the true watcher-to-first-swap latency. Measuring it needs a write into a watched mod folder timed against `game_status`, which was not available in this pass's window. `FileSystem.log` is the instrument on the game's side: the buffer's consumer logs `Event '<type>' detected with <path> while watching <dir>` at Debug for every event it dispatches (`BufferedFileSystemWatcher.cs:681`).

**There is a webpack-dev-server mode, and a mod cannot reach it.**
`UILiveReload` looks for a `.dev-server-active` marker file and a listener on TCP port 9000, and on finding both switches the view to `http://localhost:<devServerPort><path>` (`UILiveReload.cs:24`, `:193-202`, `:316-323`), registering `webpackOk` and `webpackClose` view events to hold or drop that mode (`:256-257`, `:306-313`).
`m_DevServerActivePath` is only ever assigned inside `Create`, from the host location in which the view's **own main document** was found (`:81-86` for `coui`, with the assignment at `:85`; `:127-133` for `assetdb`, at `:131`). The game's view is `assetdb://gameui/index.html`, so the marker path lands in the game's own UI directory and no mod host location can set it. This is Colossal's loop for developing the game UI itself, not one a mod author can enter.
`Rots:` port 9000 and the `.dev-server-active` name.

**The persisted-settings route to the same switches exists and is unexercised.**
The manager loads `AssetDatabase.global.LoadSettings("UIManager Settings", m_Settings, m_Settings)` **after** applying the flag (`UIManager.cs:191`), and `Settings` carries `enableDebugger`, `debuggerPort` and `liveReload` as ordinary properties (`:44-72`). `Unconfirmed:` whether writing a `UIManager Settings.coc` opens the port without the launch flag. No such file exists on the maintainer's install (the `%CSII_USERDATAPATH%` root holds 20 `.coc` files and none of them is it), so nothing ever writes one; what would settle it is producing that file in the game's settings format and launching without `--uiDeveloperMode`.

**What the discovery workflow does with the port.** The sibling `coherent-gameface` plugin's `game_*` tools are a direct CDP client against `http://localhost:9444`, which is the same endpoint the wiki tells a modder to open in Chrome — *"When the game is started with --uiDeveloperMode, you can connect the Chrome Debugger using http://localhost:9444"* (https://cs2.paradoxwikis.com/Modding_Toolchain, fetched 2026-08-24). **Settled live:** the endpoint reports one page target, id `0`, url `assetdb://gameui/index.html`, engine `Cohtml/1.64.0.7` — the same single view the game logs creating at startup (`UI.log`, `View Id: 0 created.` then `UIView 0 url set to assetdb://gameui/index.html`). `frontend-and-injection.md` records what it reaches: the live DOM, `engine`-based binding reads, and `window["cs2/modding"].findModule` for the registry (`frontend-and-injection.md`, its "Soft pointer, not a bridge slug" paragraph).

**The bundle ships no source maps.** The template sets `mode: "production"` (`webpack.config.js:26`) and never sets `devtool`, whose production default is `false`, so the `.mjs` an author debugs in the inspector is minified with no mapping back. One corpus mod fixes this: Time2Work sets `devtool: false` explicitly and adds `new webpack.EvalSourceMapDevToolPlugin({})` (`Time2Work/NightShift/Time2WorkUI/webpack.config.js:26`, `:111`).

### 7. Where this topic meets `cs2-mod-project`

The seam is the MSBuild hook, and both sides already exist in shipped prose. `cs2-mod-project` owns everything up to and including the `Exec`; this topic owns what the `Exec` runs.

- `plugins/cs2-modding/skills/cs2-mod-project/SKILL.md:41-56` owns: the `npx create-csii-ui-mod` invocation and its `--name`/`--author` flags, the `update` and `clean` subcommands as one-liners, the rule that `mod.json`'s `id` equals the assembly name, the `npm run build`/`npm run dev` pair, and the `AfterTargets="DeployWIP"` hook.
- `plugins/cs2-modding/skills/cs2-mod-project/references/build-pipeline.md`'s "Hooking into the build" section owns the three supported moves in `Mod.targets` and names `AfterTargets="DeployWIP"` as where a UI build belongs. Its "The environment variables" section already carries the fact that the UI build reads the inherited process environment while the C# side reads the user scope.

**What this topic adds at the seam, and what a reference on this side owes.**

`Mod.targets` documents the pattern itself in its own header comment — a target `AfterTargets="DeployWIP"` copying `AdditionalFilesToDeploy` into `$(DeployDir)` (`%CSII_TOOLPATH%/Mod.targets:12-19`) — and `DeployWIP` is `RemoveDir $(DeployDir)` followed by the copy (`:106-113`). The scaffold's webpack writes *into* `$(DeployDir)`, so the wipe is what a UI build has to land after.
**Seen happening.** Mid-pass the maintainer started a rebuild of a mod the running game had loaded, and the deploy folder went from `.mjs` + `.css` + `.mjs.LICENSE.txt` + `images/` + `.dll` + `.pdb` + the Burst library down to the Burst library alone. That is the window a UI build hooked too early lands in, and nothing reports it: the file watcher reloaded the view, the game logged a 404 for the now-missing bundle, and the build carried on reporting success.

**The corpus splits three ways, and the majority pattern is correct only by accident.**

- **`AfterTargets="AfterBuild"`, webpack writing straight into the mods folder** — ten repositories, e.g. `Anarchy/Anarchy/Anarchy.csproj:201-202`, `Traffic/Code/Traffic.csproj:164-166`, `AreaBucket/AreaBucket.csproj:112-113`.
- **`AfterTargets="DeployWIP"`, webpack writing straight into the mods folder** — Move It, with the reason written down beside it: *"Mod.targets DeployWIP deletes and recreates $(DeployDir). Building UI earlier can leave UI files missing after DeployWIP runs."* (`CS2-MoveIt/Code/MoveIt/MoveIt.csproj:168-172`, target at `:174-207`).
- **webpack writing to a local directory, with a separate copy after DeployWIP** — Extra Detailing Tools builds at `BeforeTargets="AfterBuild"` into `..\bin\UI` (`ExtraDetailingTools/ExtraDetailingTools.csproj:79-80`, its config's `OUTPUT_DIR` overridden at `ExtraDetailingTools/UI/webpack.config.js:14`) and copies into `$(DeployDir)` at `AfterTargets="DeployWIP"` (`:90-94`). This is the shape `Mod.targets`' own header demonstrates.

**Established by experiment: `AfterTargets` on a shared anchor runs in declaration order, so the majority pattern depends on where the import sits.**
Method, since the artefact was throwaway: two `.csproj` files were built with `dotnet build -v:m`, each importing a `common.targets` declaring `DeployWIP` with `AfterTargets="AfterBuild"` and each declaring its own `InstallUI` with the same `AfterTargets`, differing only in whether `InstallUI` was declared before or after the `<Import>`. With the import first the run order was `DeployWIP`, `InstallUI`; with the import last it was `InstallUI`, `DeployWIP`.
Every corpus csproj places the two toolchain imports immediately after the first `PropertyGroup` — the "Imports must be after PropertyGroup block" comment appears verbatim in several — and declares its UI target further down, which is why `AfterTargets="AfterBuild"` has worked for ten authors. The comment is first-party: the official C# template ships it above its two imports, immediately after the first property group (`ColossalOrder.ModTemplate.1.0.0.nupkg` under `Cities2_Data/Content/Game/.ModdingToolchain/`, `content/ModTemplate.csproj:10-12`). Move an import to the bottom of the file and the same target runs before `DeployWIP` and its output is deleted, with the build still reporting success.

**Move It's target is the corpus's best build engineering on this seam**: three MSBuild switches (`RunMoveItUIBuild`, `RunMoveItNpmCi`, `MoveItForceNpmCiAlways`, documented at `MoveIt.csproj:29-50` and defaulted at `:52-58`), a `node_modules/.moveit-npmci.stamp` so `npm ci` runs only when `package-lock.json` changed (`:65`, `:137-163`), 900-second timeouts on both `Exec`s (`:68-69`), and fail-hard on any configuration but Debug where it warns instead (`:189-195`).

### 8. Two scaffold behaviours a reference has to state, because getting them wrong is silent

**8a. `hasCSS` is a named export the game reads, and the scaffold's own comment says it does not exist.**
The frontend's mod loader reads *two* things off each imported module: `a.push(t.default)` and `t.hasCSS` (`source.js:134933`). When `hasCSS` is truthy it derives the stylesheet URL by string replacement — `e.replace(".mjs", ".css")` (`:134935`) — and loads it through `loadCss` (`:134936`, the function at `:47090-47106`, registered into the module registry as `game-ui/modding/utils/load-css.tsx` at `:47107-47114`).
The scaffold's `types/validateTypes.ts:4` states the opposite: *"only default export is processed by the UI, any named exports will be ignored."*
**Verdict:** the bundle wins. `../SOURCES.md:10-12` gives the game authority over what the game does and the scaffold authority over what a mod may import; this is a claim about what the game does with a built module. `hasCSS` is read, and the scaffold's own `CSSPresencePlugin` exists solely to emit it — the comment describes an earlier contract. A reference must not repeat it.

**8b. The `hasCSS` injection is a text substitution that only works before minification, and its failure mode takes down every mod.**
`CSSPresencePlugin` taps `processAssets` passing `stage: compilation.PROCESS_ASSETS_STAGE_ADDITIONS` (`create-csii-ui-mod/template/tools/css-presence.js:9`) — an instance access of a `Compilation` static, so it evaluates to `undefined` and the tap lands at tapable's default stage 0 rather than the constant's -100 — finds whether any emitted asset ends `.css` (`:12-15`), then for each chunk file ending `.mjs` replaces the first occurrence of the literal `"export {"` with `` `const hasCSS = ${hasCSS}; export { hasCSS, ` `` (`:20-26`).
That literal only exists before Terser runs. `terser-webpack-plugin` taps at `PROCESS_ASSETS_STAGE_OPTIMIZE_SIZE`, `400` (`ExtraDetailingTools/UI/node_modules/webpack/lib/Compilation.js:5734`; `ExtraDetailingTools/UI/node_modules/terser-webpack-plugin/dist/index.js:674`, the same installed copy), so the plugin's stage 0 still sits ahead of it, the injection lands on unminified output, and Terser renames the constant afterwards. The built artefact ends `export{As as default,Ps as hasCSS}` — note the minified `export{` with no space, which is what the plugin would fail to match if the stages were the other way round.
**The consequence of getting the CSS wrong is not a missing stylesheet, it is a dead UI.** In the loader, `s` starts at the mod count and is incremented once per mod that reports `hasCSS` (`source.js:134921`, `:134934`); the completion callback `o` fires `pR(a)` — the call that runs every mod's registrar — only when `t === s` (`:134925-134927`). `loadCss` invokes its callback only from the `<link>`'s `onload`, and only after an XHR returned status 200 (`:47094`, `:47100-47102`); a 404 does nothing at all, with no timeout and no error path. So a module exporting `hasCSS: true` whose `<id>.css` is missing or differently named leaves the counter one short forever, `pR` never runs, and **no mod's registrar runs** — the whole modded UI, not just that mod's.
This is why the two names have to match: the stylesheet must be `<id>.css` beside `<id>.mjs`, which is what `MiniCssExtractPlugin`'s default `[name].css` gives you and what a custom `filename` takes away.
**Settled live, both halves of the premise.** A missing `coui://ui-mods/` resource returns a clean **404** rather than erroring the request, so `loadCss`'s `200 === n.status` gate is simply never entered and its callback never fires. And the success path is visible in the document: `document.querySelectorAll('link[rel="stylesheet"]')` returns the game's own `assetdb://gameui/index.css` plus one `<link>` per CSS-carrying mod, each with `id` set to the file name minus `.css` and `href` set to the `coui://ui-mods/<id>.css` URL — `FindIt` and `HallOfFame` in the first session read.

**A missing `.mjs` is the benign case, and it was observed.** Mid-pass the maintainer rebuilt one of the loaded mods; `DeployWIP` emptied its deploy folder and the C# build had not yet refilled it, so a registered UI module's bundle was simply gone. The game logged `ResourceHandler: HTTP/1.1 404 Not Found / URL: coui://ui-mods/HallOfFame.mjs (Id: 121)` at ERROR with a `DefaultResourceHandler.CheckForFailedRequest` stack — **`UI.log` names the exact failing `coui://` URL**, which is the diagnostic for every missing-artefact case in this file. And the UI came up normally: the app root rendered and the other mod's stylesheet was attached, because a rejected `import()` is caught and counted (`source.js:134940-134942`). So the counter completes when a module fails to load, and hangs only on the CSS branch, which has no catch.
`Unconfirmed:` the whole-UI symptom itself. Producing it means renaming a built `<id>.css` in the user's mods folder, which is a change to their install and would also trip the live reload; `frontend-and-injection.md`'s finding that one throwing registrar silences every later mod is the neighbouring case already established, and this is the same counter reached from the other side.

**One corpus mod replaces the plugin with a hand-written export.** Hall of Fame removes `CSSPresencePlugin` — the removal is listed in its config's header (`HallOfFame/HallOfFame/UI/webpack.config.js:1-12`) and its plugin list is `[new MiniCssExtractPlugin()]` (`:132`) — and writes `export const hasCSS = true;` in the entry module instead (`HallOfFame/HallOfFame/UI/src/index.tsx:30`). Its built `.mjs` carries `Ps as hasCSS` exactly as the plugin's would.

### 9. Two more build knobs the corpus reached for, and what they are for

**Prefixing the CSS-module class names.** The scaffold sets `localIdentName: "[local]_[hash:base64:3]"` (`webpack.config.js:64`). Every mod's stylesheet is injected into the **same document** as the game's and as every other mod's, and a three-character base64 hash is a small space. Hall of Fame prefixes its own — `localIdentName: 'hof-[local]_[hash:base64:3]'` (`HallOfFame/HallOfFame/UI/webpack.config.js:87`) — with the stated reason that it helps debugging and lets other mods target its classes. It is the corpus's only divergence on this option.

**Keeping the game's own asset URLs out of css-loader's resolver.** A stylesheet referencing one of the game's shipped images with `url(Media/…)` makes css-loader try to resolve it as a module and fail the build. Hall of Fame passes `url: { filter: url => !url.startsWith('Media') }` to leave those alone (`HallOfFame/HallOfFame/UI/webpack.config.js:75-82`), against the scaffold's plain `url: true` (`create-csii-ui-mod/template/webpack.config.js:59`).

**`ts-loader` means a type error fails the build.** The template compiles `.tsx?` through `ts-loader` with no `transpileOnly` (`webpack.config.js:46-50`), so `npm run build` type-checks. `swc-loader` sits in `devDependencies` (`template/package.json:30`) and no rule uses it.
The template's tsconfig sets `typeRoots: ["./types"]` (`template/tsconfig.json:13`), which disables the automatic inclusion of `node_modules/@types` globals; the `cs2/*` declarations are picked up as ordinary project files instead, and `@types/react` still resolves because it is reached through module resolution rather than through `typeRoots`.

- **`binding-layer`** gets the identity chain that decides the group name. `mod.json`'s `id` is imported into the frontend by 16 of the 19 UI repositories and passed as the binding group (98 files importing the manifest, 193 `mod.id` sites; `Traffic/UI/src/bindings/index.ts:2`, `:6-13`), so the string a `ValueBinding` is constructed with on the C# side and the string `bindValue` is called with on the frontend side are the same manifest field, and the same field names the folder both halves deploy into. And it gets the one route in the corpus that generates the frontend's payload types from the C# rather than restating them (finding 6), which is the answer to "how do the two sides stay in step" that no other topic can supply.

**Trunk techniques.**

- **`mod-lifecycle-and-ordering`** — a UI module has a lifecycle of its own and it is not the C# one. `UIModuleAsset` is created by the asset factory from the `.mjs` extension (`DefaultAssetFactory.cs:257`), the module is registered when the mod manager initialises (`ModManager.cs:461-473`), and it can be added or removed **mid-session** when a playset entry is toggled (`ModManager.AddUIModule`/`RemoveUIModule` at `:475-493`, driven from `src/Game/Game.SceneFlow/GameManager.cs:1518-1633`). A mod whose C# failed to load can still have its UI module registered, because the two are separate assets in the same folder.
- **`mod-compatibility`** — three build-side collision surfaces, all of them consequences of one flat host and one document: the `images/` namespace (finding 1a), the three-character CSS-module hash (finding 9), and the loader's shared completion counter, where one mod's missing stylesheet silences every mod (finding 8b).
- **`settings-and-input`** and **`localization`** — both reach the frontend through the same bundle, so both inherit the identity rule in finding 3 and the staleness measurement in finding 4: a mod's `cs2/l10n` or `cs2/input` surface is whatever its vendored `types/` folder last copied, and every vendored copy in the corpus is behind.
- **`diagnostics`** — `UI.log` is where this topic's evidence lives: the inspector port line, the view URL, every `Reloading media`/`Reloading page` line, and — the one a modder acts on — `ResourceHandler: HTTP/1.1 404 Not Found` with the failing `coui://` URL on the next line, which is how a missing or misnamed build artefact announces itself. The module registrations and their `coui://` paths are in `Modding.log` and the launch flags in `SceneFlow.log`. All three truncate per session, so the run that shows the problem is the run you have to read.

**Mechanics topics this technique exercises.** None directly: this topic is the build, and a build has no simulation subject. What it does is decide whether any of the mechanics-facing UI work in `frontend-and-injection`, `binding-layer` and `settings-and-input` reaches the screen at all — a wrong `id`, a missing `hasCSS` or a UI build hooked before `DeployWIP` all present as "the panel is not there", with nothing in either half's source to look at.

**Soft pointer, not a bridge slug.** The sibling `coherent-gameface` plugin is the discovery workflow at the far end of finding 5's port: its `game_*` tools connect to the same `http://localhost:9444` the wiki hands a modder for Chrome DevTools, opened by the same `--uiDeveloperMode` flag, against the same single page target. The plugin is application-agnostic and this file is the CS2-specific half — which flag, which port, and what else that flag turns on (the file watcher, and `Application.runInBackground`, which is why a CDP session survives alt-tabbing).
