# City state and progression

**Baseline.** Game version 1.6.0f1, established against the decompiled C# under `DecompiledCitiesSkylines2/src/` (decompiled 2026-06-24) and against the user's running city — a debug-patched development build, read live over the sibling `unity-devtools` plugin — on 2026-08-21. Wiki pages fetched 2026-08-21. The mod corpus at `cs2-third-party-mods` was read on 2026-08-21 (22 repositories).
**The live save is not a naturally progressed city and every live number below has to be read with that in mind.** `CityConfigurationSystem` reports `unlimitedMoney=True unlockAll=True unlockMapTiles=True` on it, so its milestone level, owned-tile count and unlocked-prefab set are the result of the unlock-all path (`src/Game/Game.Prefabs/UnlockAllSystem.cs:47-61`) rather than of accumulated XP. **Prefab data read live is unaffected by this** — milestone rewards, dev-node costs, policy components and notification-icon rosters are authored asset data and read the same either way — and it is prefab data that carries this topic.

**Ruled (2026-08-06, the citizens-and-households pass; conflicts.md), governing every finding in this file.** A shipped reference states **no prefab value**. It names the component and the field, with the access shape, and that is the whole of what it says about the magnitude. Three things are untouched and are the spine of the topic: **C# constants ship, as numbers** — a `const` or `static readonly` the consuming code compiled in, offline-checkable and citable to a line; **formulas ship whole** — the expression a system evaluates, its baseline, its step functions and the shape of its randomisation are invariant structure rather than balance; and **the component-to-number-family map ships whole**, because an agent cannot perform the read without it, and it carries the access shape beside each component since a reader cannot write the call from a field name. Two consequences bind this topic: **a derived ratio is a magnitude wearing a mechanism's clothes** (where the ratio is the point, the reference states the direction and names the field), and **an adverb carrying the same magnitude counts** — "far more", "roughly twice", "an order of magnitude" are the ratio in prose. A non-numeric prefab value is still a prefab value.
The bite here is unusual in shape. This topic's balance is **not** on parameter singletons: it is on twenty `MilestoneData` prefabs, seventy-one `DevTreeNodeData` prefabs, two `MapTilePrefab` assets and twenty-three policy prefabs' `CityModifierData` / `DistrictModifierData` / `BuildingModifierData` / `RouteModifierData` buffers. **So the whole milestone table, the whole dev-node cost table and every policy's modifier range are barred as numbers**, and what ships is the field map plus the formulas — of which this topic has several that are genuine invariant structure (the modifier composition, the tile-cost expression, the statistic collection modes, the unlock predicate). This file records the live numbers freely; the reference will not.

**Ruled (2026-08-08, the zoning-buildings-and-land-value pass; conflicts.md), governing this file's prefab classes.** A field initializer on a prefab class is a Unity-serialized default the shipped asset overrides. It ships as **the field, never as the figure**, and a reference whose map or traps send a reader into a file carrying them states once, as a trap, that these are Unity-serialized defaults the shipped asset overrides, with nothing in the C# marking which survived. The test is what consumes the value: a `const` or `static readonly` the code compiled in ships as a number; a public field on a `ScriptableObject`-derived class does not, whatever file declares it.
Four classes in this topic carry the shape. `MilestonePrefab` initializes three `Color` fields (`src/Game/Game.Prefabs/MilestonePrefab.cs:27-31`); `MapTilePrefab.m_PurchaseCostFactor = 2500f` (`src/Game/Game.Prefabs/MapTilePrefab.cs:20`); `PolicySliderPrefab` initializes `m_SliderRange = new Bounds1(0f, 1f)`, `m_SliderDefault = 0.5f`, `m_SliderStep = 0.1f`, `m_Unit = PolicySliderUnit.integer` (`src/Game/Game.Prefabs/PolicySliderPrefab.cs:11-17`); `NotificationIconPrefab` initializes `m_DisplaySize = new Bounds1(3f, 3f)`, `m_PulsateAmplitude = new Bounds1(0.01f, 0.1f)`, `m_EnabledByDefault = true` (`src/Game/Game.Prefabs/NotificationIconPrefab.cs:20-24`). `MapTilePrefab`'s initializer **does** survive on the base-game `Map Tile` asset — read live, `TilePurchaseCostFactor.m_Amount = 2500`, matching the initializer exactly — and that is precisely why the trap is needed: a reader who checks one and finds it right will trust the next. Three of the four requirement prefabs also initialize a threshold (`CitizenRequirementPrefab.m_MinimumPopulation = 100`, `ObjectBuiltRequirementPrefab.m_MinimumCount = 1`, `ZoneBuiltRequirementPrefab.m_MinimumSquares = 2500` / `m_MinimumLevel = 1`, `ProcessingRequirementPrefab.m_MinimumProducedAmount = 10000`), and those are authored per requirement asset, so the initializer is a template rather than a value.

**Ruled (2026-08-06, the citizens-and-households pass; conflicts.md), governing this file's use of the wiki.** No mechanics reference borrows a wiki stat table's numbers **at all** — first-party or nothing.
This topic is the ruling's hardest case, because the wiki's `Progression` page is essentially one large stat table and it is the page a reader would reach for first. **Every number on it is barred**: the twenty-row milestone table (money, development points, expansion permits, loan limit), the nested `Milestones || Before || After` money table inside the collapsed *Changes to Milestone in Version 1.1.5f1* block, the dev-tree tier costs, and the four per-resource tile-cost rates (`per ton of Wood or Ore`, `per kg of Oil`, `per m³ of Groundwater`, `per m² of Fertile Land`). The before/after table is the exact artifact the ruling was made about and it is doubly barred: its "Before" column is a build nobody can reach and its "After" column is stamped 1.1.5f1 while the game is on 1.6.0f1. The reference states the field — `MilestoneData.m_Reward`, `m_DevTreePoints`, `m_MapTiles`, `m_LoanLimit`, `m_XpRequried` — and the read shape, and says nothing about the magnitudes. What the wiki *is* used for below is the agenda, the vocabulary and the player-facing names, and where it is wrong the verdict says so.

## Findings

### The city is one entity, and its component list is the whole of what "the city tracks"

`CitySystem` (`src/Game/Game.Simulation/CitySystem.cs:15`, registered at `SystemUpdatePhase.Modification1`, `src/Game/Game.Common/SystemOrder.cs:105`) holds a single `Entity m_City` and exposes it as `City` (`CitySystem.cs:29`). It is not a `GetSingleton<T>` target — **the state is a set of ordinary components and buffers on one entity**, and the read shape is `EntityManager.GetComponentData<T>(citySystem.City)` or `GetBuffer<T>(citySystem.City)`. `CitySystem` itself serializes only that entity reference (`CitySystem.cs:54-63`), so the entity index moves between saves and must never be cached.

`PostDeserialize` builds it on a new game and is the authoritative roster of what the city carries (`CitySystem.cs:71-153`): `Game.City.City`, `MilestoneLevel`, `XP`, `DevTreePoints`, a `Policy` buffer, a `CityModifier` buffer, `Loan`, `Creditworthiness`, `DangerLevel`, a `TradeCost` buffer, a `ServiceFee` buffer seeded from `ServiceFeeParameterData.GetDefaultFees()`, `PlayerMoney(economyParameters.m_PlayerStartMoney)`, a `SpecializationBonus` buffer, `Population` and `Tourism`.

Read live at 1.6.0f1, `ecs_list_components` on the city entity returns exactly sixteen entries and confirms the roster: the fifteen above plus `Unity.Entities.Simulate`. **`Game.City.TaxRates` is not among them** — see the dead-types finding.

`CitySystem.OnUpdate` caches two scalars off it every frame, `moneyAmount` and `XP` (`CitySystem.cs:45-52`), and those two properties are what the rest of the simulation reads rather than the components.

Live values on the user's city (`unlockAll` save, so treat the milestone level as forced): `XP { m_XP=173368, m_MaximumPopulation=41849, m_MaximumIncome=2627145, m_XPRewardRecord=ElectricityGridBuilt }`, `MilestoneLevel { m_AchievedMilestone=20 }`, `DevTreePoints { m_Points=0 }`, `Population { m_Population=41856, m_PopulationWithMoveIn=42209, m_AverageHappiness=85, m_AverageHealth=50 }`, `Tourism { m_CurrentTourists=976, m_AverageTourists=734, m_Attractiveness=70 }`, `City { m_OptionMask=2 }`, `Creditworthiness { m_Amount=26100000 }`.

`Rots:` every component, system, field and binding name in this file. Re-check against `src/Game/Game.City/`, `src/Game/Game.Policies/`, `src/Game/Game.Notifications/`, `src/Game/Game.Areas/`, `src/Game/Game.Prefabs/`, `src/Game/Game.Simulation/`, `src/Game/Game.UI.InGame/` and `src/Game/Game.Common/SystemOrder.cs`, at the files cited beside each claim.

### `City.m_OptionMask` is a bitmask over a three-member enum, and both the read and the write are one-liners

`Game.City.City` carries nothing but `uint m_OptionMask` (`src/Game/Game.City/City.cs:6-8`). `CityOption` has three members — `UnlimitedHighwaySpeed`, `PaidTaxiStart`, `ImportOutsideServices` (`src/Game/Game.City/CityOption.cs:3-8`) — and `CityUtils.CheckOption(city, option)` is `(m_OptionMask & (1u << (int)option)) != 0` (`src/Game/Game.City/CityUtils.cs:12-15`). The mask is **rebuilt from scratch** out of the active policies every time it is refreshed (`RefreshCityOptions`, `src/Game/Game.Simulation/CityModifierUpdateSystem.cs:93-105`): `city.m_OptionMask = 0u`, then OR in `CityOptionData.m_OptionMask` for each active `Policy` whose prefab carries one. **So writing the mask directly is pointless** — it is derived state, and the next `ModifiedSystem` or `CityModifierUpdateSystem` pass overwrites it. Live value 2 = `PaidTaxiStart`.
The district and building equivalents are `DistrictOptionData` / `BuildingOptionData` with the same one-bit-per-enum-member construction (`src/Game/Game.Prefabs/DistrictOptions.cs`, `src/Game/Game.Prefabs/BuildingOptions.cs`).

### City statistics: an append-only sample buffer per statistic, three collection modes, and a hash-map lookup that is the only way in

`CityStatisticsSystem` (`src/Game/Game.Simulation/CityStatisticsSystem.cs:22`, `SystemUpdatePhase.GameSimulation`, `SystemOrder.cs:418`) runs every `8192` frames (`GetUpdateInterval`, `:393-396`) with `public const int kUpdatesPerDay = 32` (`:357`) — `262144 / 32 = 8192`, so the constant and the literal agree, and one sample is a thirty-second of an in-game day. `GetUpdateOffset` returns 0 (`:398-401`).

**A statistic is an entity, not a field.** Each `StatisticsPrefab` (`src/Game/Game.Prefabs/StatisticsPrefab.cs:10`) declares `StatisticsData { m_Category, m_Group, m_StatisticType, m_CollectionType, m_UnitType, m_Color, m_Stacked }` as its prefab component and `CityStatistic` as an **archetype** component, so its instances carry the sample buffer (`:26-36`). `StatisticsPrefab.CreateInstance` builds one instance per parameter value (`:57-73`). 69 `StatisticsData` prefabs exist live at 1.6.0f1.

**The address of a statistic is `(StatisticType, int parameter)`**, wrapped in `CityStatisticsSystem.StatisticsKey` (`CityStatisticsSystem.cs:24-62`, hash `((int)type * 311 + parameter)`), and the key-to-entity map is `NativeParallelHashMap<StatisticsKey, Entity>` exposed by `GetLookup()` (`CityStatisticsSystem.cs:403-406`). `InitializeLookup` builds it lazily on the first update (`CityStatisticsSystem.cs:709-845`): every `StatisticsData` prefab contributes either one key per `StatisticParameterData` buffer element or the single key `(type, 0)` when it has no buffer. **`StatisticType` has 62 real members plus `Invalid = -1` and `Count`** (`src/Game/Game.City/StatisticType.cs:3-68`) — that is a declared set and ships as one.

**Parameterisation is a small class hierarchy, and each subclass names the enum its parameter indexes.** `ParametricStatistic : StatisticsPrefab` adds the `StatisticParameterData` buffer to the prefab and `StatisticParameter` to the archetype (`src/Game/Game.Prefabs/ParametricStatistic.cs:9-34`); the nine concrete subclasses and their parameter enums are `ResourceStatistic` → `Resource` index, `IncomeStatistic` → `IncomeSource`, `ExpenseStatistic` → `ExpenseSource`, `EducationStatistic` → `CitizenEducationLevel`, `AgeStatistic` → `CitizenAge`, `LevelStatistic` → a raw int, `PassengerStatistic` → `PassengerType`, `CityServiceStatistic` → `CityService`, `MoveAwayStatistic` → `MoveAwayReason` (each file in `src/Game/Game.Prefabs/`, `GetParameterName` naming the enum). That mapping is the thing an agent cannot reconstruct from `StatisticType` alone, and it ships.

**The sample buffer and the three collection modes** are `ResetEntityJob` (`CityStatisticsSystem.cs:265-333`), which appends one element per update:

```
last = buffer[^1]
Cumulative: append { m_TotalValue = last.m_TotalValue + last.m_Value, m_Value = 0 }
Point:      append { m_TotalValue = last.m_Value,                    m_Value = 0 }
Daily:      old = buffer.Length >= 32 ? buffer[^32].m_Value : 0
            append { m_TotalValue = last.m_TotalValue + last.m_Value - old, m_Value = 0 }
```

so `Daily` is a rolling sum over the last 32 samples — one in-game day, exactly `kUpdatesPerDay` — `Point` is that sample's own delta, and `Cumulative` is the running total. `StatisticCollectionType` is the declared three-member set (`src/Game/Game.City/StatisticCollectionType.cs`), `StatisticUnitType` is `None, Money, Percent, Weight` (`src/Game/Game.City/StatisticUnitType.cs`).

`CityStatistic { double m_Value, double m_TotalValue }` (`src/Game/Game.City/CityStatistic.cs:6-11`) is `double` **only since two save-format versions ago**: `Deserialize` reads two `int`s below `Version.statisticOverflowFix`, two `long`s below `Version.statisticPrecisionFix`, and two `double`s above (`:20-43`). `StatisticsEvent.m_Change` took the same `int` → `float` widening (`src/Game/Game.City/StatisticsEvent.cs:30-39`), and the struct carries `[FormerlySerializedAs("Game.City.StatisticsEvent2, Game")]` (`:5`).

**Reading a statistic** comes in three shapes, all funnelling into `GetStatisticValueDouble`, which returns `Math.Round(buffer[^1].m_TotalValue, MidpointRounding.AwayFromZero)` and **0.0 for an unknown key or an empty buffer** (`CityStatisticsSystem.cs:506-523`) — an unregistered `StatisticType` reads as zero rather than throwing. The static forms take `(lookup, BufferLookup<CityStatistic>, type, parameter)` and are Burst-callable (`CityStatisticsSystem.cs:478-490`, `CityStatisticsSystem.cs:492-504`); the instance forms complete the writer chain first (`CityStatisticsSystem.cs:553-566`). `ICityStatisticsSystem` (`src/Game/Game.Simulation/ICityStatisticsSystem.cs`) is the full public surface and includes `GetStatisticDataArray`/`…Long` for the whole series, `sampleCount`, `GetSampleFrameIndex(index)` (`CityStatisticsSystem.cs:703-707`, `(sampleCount - index - 1) * 8192` back from `m_LastSampleFrameIndex`) and the `eventStatisticsUpdated` action.

### Writing a statistic is a queue protocol, and 24 systems join it

The queue is `NativeQueue<StatisticsEvent>` and the handshake is `GetStatisticsEventQueue(out JobHandle deps)` / `AddWriter(JobHandle)` (`CityStatisticsSystem.cs:847`), the same reader/writer shape `ecs-in-this-game` describes for other shared containers. `ProcessStatisticsJob` drains it (`CityStatisticsSystem.cs:217-262`), and `OnUpdate` chains the three jobs as `CityStatisticsJob` → `ProcessStatisticsJob` → `ResetEntityJob` (`CityStatisticsSystem.cs:441-465`), so the drain lands on the current sample *before* the roll-over appends the next one: an event with `m_Statistic == StatisticType.Count` is dropped, a key not in the lookup is dropped, and otherwise `buffer[^1].m_Value += m_Change`. **So a mod's own `StatisticType` value is silently ignored unless a `StatisticsPrefab` declaring it exists.**

`SafeStatisticQueue` (`CityStatisticsSystem.cs:64-79`) is the wrapper the game passes into jobs: it holds `m_StatisticsEnabled` and drops every enqueue when false, with `[NativeDisableContainerSafetyRestriction]` on the writer.

**24 files call `GetStatisticsEventQueue`**, and they are the complete producer set: `HouseholdInitializeSystem`, `AddHealthProblemSystem`, `BirthSystem`, `BudgetApplySystem`, `CitizenHappinessSystem`, `CitizenTravelPurposeSystem`, `CityServiceStatisticsSystem`, `CompanyStatisticsSystem`, `CrimeCheckSystem`, `CrimeStatisticsSystem`, `CriminalSystem`, `DeathCheckSystem`, `DeliveryTruckAISystem`, `HealthProblemSystem`, `HouseholdMoveAwaySystem`, `LoanUpdateSystem`, `PostVanAISystem`, `PropertyProcessingSystem`, `ResidentAISystem`, `TaxSystem`, `TradeSystem`, `TransportBoardingHelpers`, `WealthStatisticsSystem`, `WorkProviderStatisticsSystem` (sweep result; re-derive with one grep for `GetStatisticsEventQueue` over `src/Game/`). Fourteen `StatisticType`s bypass the queue and are pushed by `CityStatisticsJob` from the main system itself, derived from the city entity and the household counts — `Money`, `LodgingTotal`, `LodgingUsed`, `HouseholdCount`, `TouristCount`, `AdultsCount`, `WorkerCount`, `Unemployed`, `Population`, `Age` (one per `CitizenAge` parameter), `Wellbeing`, `Health`, `EducationCount` (one per education level), `HomelessCount` (`CityStatisticsSystem.cs:82-216`; re-derive by listing `StatisticType.` inside the job).

**One trap in the reset path.** `ResetEntityJob` seeds an empty buffer with `m_Value = money` for `StatisticType.Money` and 0 for everything else (`CityStatisticsSystem.cs:293-300`), and `ProcessStatisticsJob` re-seeds `m_TotalValue = m_Change` on the *first* Money element only (`CityStatisticsSystem.cs:253-256`). Money is therefore the one statistic whose series starts from an absolute rather than from zero.

### The statistic trigger system, and one branch that does integer division where its three siblings do not

`StatisticTriggerSystem` (`src/Game/Game.Simulation/StatisticTriggerSystem.cs`) runs immediately after `CityStatisticsSystem` (`SystemOrder.cs:419`) and turns a statistic series into a `TriggerType.StatisticsValue` action. `StatisticTriggerData { m_Type, m_StatisticEntity, m_StatisticParameter, m_NormalizeWithPrefab, m_NormalizeWithParameter, m_TimeFrame, m_MinSamples }` (`src/Game/Game.Prefabs/StatisticTriggerData.cs`) with `StatisticTriggerType = TotalValue | AverageValue | AbsoluteChange | RelativeChange` (`src/Game/Game.Prefabs/StatisticTriggerType.cs`).

Two structural facts ship. First, a trigger whose statistic (or normaliser) is `Daily` has its minimum-sample floor raised at authoring time to `max(m_MinSamples, 32 + max(0, m_TimeFrame - 1))` (`src/Game/Game.Prefabs/StatisticTriggerPrefab.cs`, in `LateInitialize`) — because a `Daily` series is meaningless before its own 32-sample window has filled. Second, **a locked statistic suppresses its trigger**: the job skips when `m_Locked.HasEnabledComponent(m_StatisticEntity)` (`StatisticTriggerSystem.cs:59`, `StatisticTriggerSystem.cs:112`).

**The defect.** The normalised branches compute their ratio as `(float)a[i] / (float)b[i]` for `TotalValue` (`StatisticTriggerSystem.cs:70`), `AverageValue` (`StatisticTriggerSystem.cs:83`) and `AbsoluteChange` (`StatisticTriggerSystem.cs:93-94`), (the last two also guarded on both normaliser endpoints being non-zero, `StatisticTriggerSystem.cs:91`, `StatisticTriggerSystem.cs:99`), but `RelativeChange` writes `float num6 = statisticDataArray[…] / statisticDataArray2[…]` with no cast (`StatisticTriggerSystem.cs:101-102`) — both operands are `int`, so the quotient truncates before the float assignment and the branch reports 0 for every ratio below 1. Recorded as observed arithmetic; whether shipped prose may characterise it is the ruled question in `conflicts.md` under *Two first-party expressions in the service code look like arithmetic defects*, and its ruling — behaviour flat, arithmetic stated, no word on intent — is what this claim would ship under.

### XP: four producers, one queue, and one enum member nothing produces

`XP { m_XP, m_MaximumPopulation, m_MaximumIncome, m_XPRewardRecord }` on the city entity (`src/Game/Game.City/XP.cs:6-14`); `XPRewardFlags` has exactly one member, `ElectricityGridBuilt = 1` (`src/Game/Game.City/XPRewardFlags.cs`).

`XPSystem` (`src/Game/Game.Simulation/XPSystem.cs:12`, `SystemUpdatePhase.ModificationEnd`, `SystemOrder.cs:274`) owns a persistent `NativeQueue<XPGain>` behind the same `GetQueue(out deps)` / `AddQueueWriter(handle)` handshake (`:77-86`), and `XPQueueProcessJob` adds every non-zero gain to `XP.m_XP` and mirrors it into a `NativeQueue<XPMessage>` for the UI (`:28-41`). `TransferMessages(IXPMessageHandler)` drains that second queue on the main thread (`:67-75`), and `MilestoneUISystem` is the handler.

`XPGain { Entity entity, int amount, XPReason reason }` (`src/Game/Game.Simulation/XPGain.cs`). `XPReason` declares 14 members plus `Count` (`src/Game/Game.Simulation/XPReason.cs`). **Sweeping every `XPGain` enqueue in `src/Game/` returns four producers and one orphan reason:**

- `XPAccumulationSystem` (`src/Game/Game.Simulation/XPAccumulationSystem.cs:18`, `SystemUpdatePhase.GameSimulation`, `SystemOrder.cs:417`, `public static readonly int kUpdatesPerDay = 32`, interval `262144 / 32`) enqueues `Population` and `Happiness` gains, **and only when `population.m_Population >= 10`** (`:45`). Population XP is paid on *new maximum* population, not on population: `num = max(0, pop - value.m_MaximumPopulation)`, then `m_MaximumPopulation = max(m_MaximumPopulation, pop)` (`:48-49`), so a city that shrinks and regrows earns nothing until it passes its old peak. Both gains are `Mathf.FloorToInt(param * quantity / kUpdatesPerDay)`, where `param` is `XPParameterData.m_XPPerPopulation` / `m_XPPerHappiness` (`src/Game/Game.Prefabs/XPParameterData.cs`), a parameter singleton read at `XPAccumulationSystem.cs:134` that `XPParametersMode` (`src/Game/Game.Prefabs.Modes/XPParametersMode.cs`) can rewrite on load — the one parameter singleton in this topic, and its values are barred like any other.
- `XPBuiltSystem` (`src/Game/Game.Simulation/XPBuiltSystem.cs`, `SystemOrder.cs:272`) pays `PlaceableObjectData.m_XPReward` as `ServiceBuilding` and `ServiceUpgradeData.m_XPReward` as `ServiceUpgrade` over the `Created`-without-`Temp` query (`:52-81`), and a one-shot `kElectricityGridXPBonus` (a `private static readonly int`, `:172`) as `ElectricityNetwork` the first time any `ElectricityConsumer` has `m_FulfilledConsumption > 0` (`:105-123`), latching `XPRewardFlags.ElectricityGridBuilt` so it cannot repeat (`:118`, gate at `:211`). A **signature** building pays once ever: the job stamps `PlacedSignatureBuildingData` **onto the prefab entity** and skips any prefab carrying it (`:52`, `:64-67`). The whole system is gated on `m_ToolSystem.actionMode.IsGame()` (`:192`).
- `NetXPSystem` (`src/Game/Game.Simulation/NetXPSystem.cs`, `SystemOrder.cs:273`) pays for network edges. Per created edge: `(PlaceableNetData.m_XPReward + elevationBonus) * Curve.m_Length / kXPRewardLength`, with `private static readonly float kXPRewardLength = 112f` (`:254`) and `elevationBonus` a flat `1f` when the prefab is a road and either endpoint node has `Elevation.m_Elevation.x > 0 && .y > 0` (`:60-67`, `:80`). Deleted edges are counted the same way and **subtracted** (`:120-123`). The per-update totals are accumulated into seven separate buckets — roads, train, tram, subway, waterway, pipes, power lines (`NetXPs`, `:138-214`) — and then **only the single largest bucket is awarded**, through `GetMaxValue`, with the other six discarded (`:124-134`). One `XPGain` per update, never seven. Unlike `XPBuiltSystem` it has no `actionMode.IsGame()` gate.
- `DebugSystem` enqueues `XPReason.Unknown` twice from the developer menu (`src/Game/Game.Debug/DebugSystem.cs:4974`, `:5003`).

**`XPReason.Income` has no producer anywhere in `src/`** — the four systems above cover thirteen of the fourteen members and nothing enqueues that one. `XP.m_MaximumIncome`, the field it would have been paid from, is written by `XPAccumulationSystem` (`XPAccumulationSystem.cs:60-61`) and read by nothing else in the decompile. Both are dead at 1.6.0f1.

**A second defect in the same job.** `XPAccumulationSystem`'s income tally opens with `for (int i = 0; i < 5; i++) { num2 = GetStatisticValue(…, ResidentialTaxableIncome, i); }` — a plain assignment inside the loop rather than `+=` (`XPAccumulationSystem.cs:51-54`), so four of the five residential education brackets are discarded and only bracket 4 survives into `num2`. The commercial/industrial/office loop immediately below uses `+=` correctly (`XPAccumulationSystem.cs:58`). Since the result feeds only `m_MaximumIncome`, which has no reader, nothing observable depends on it.

### Milestones: six fields, one event, and a reward path that writes two components directly

`MilestoneData { m_Index, m_Reward, m_DevTreePoints, m_MapTiles, m_LoanLimit, m_XpRequried, bool m_Major, bool m_IsVictory }` (`src/Game/Game.Prefabs/MilestoneData.cs`) is copied verbatim from `MilestonePrefab` in `Initialize` (`src/Game/Game.Prefabs/MilestonePrefab.cs:44-58`); the prefab additionally carries `m_Image` and three colours the data component does not. The field name is misspelled `m_XpRequried` in both — spell it exactly.

`MilestoneSystem` (`src/Game/Game.Simulation/MilestoneSystem.cs:15`, `SystemUpdatePhase.ModificationEnd`, `SystemOrder.cs:275`) is 176 lines and the whole of the mechanism:

1. **It does nothing while the intro tutorial is unfinished** — `if (m_TutorialSystem.tutorialIntroUnfinished) return;` is the first line of `OnUpdate` (`:73-76`).
2. `m_LastRequired` = the achieved milestone's `m_XpRequried`, or 0 when `TryGetMilestone` fails (`:79`).
3. If milestone `achieved + 1` exists and `m_CitySystem.XP >= its m_XpRequried`, increment `MilestoneLevel.m_AchievedMilestone`, write the singleton back, and call `NextMilestone` (`:80-89`).
4. `NextMilestone` creates **two** event entities on `ModificationEndBarrier` — one `MilestoneReachedEvent(milestoneEntity, index)` and one `Unlock(milestoneEntity)` — then writes `PlayerMoney.Add(m_Reward)` and `Creditworthiness.m_Amount += m_LoanLimit` **directly on the city entity, outside the command buffer** (`:96-109`). When the milestone entity is missing it still emits a `MilestoneReachedEvent(Entity.Null, index)` and logs `"Warning: did not find data for milestone N"` (`:112-114`).
5. `TryGetMilestone(index)` is a **linear scan over the whole `MilestoneData` query with two `Allocator.TempJob` arrays allocated and disposed per call** (`:118-142`), and `OnUpdate` calls it twice per update. There is no index.

So the reward paid at a milestone is: `m_Reward` into `PlayerMoney`, `m_LoanLimit` into `Creditworthiness`, `m_DevTreePoints` into `DevTreePoints` (via `DevTreeSystem`, below), `m_MapTiles` into the expansion-permit budget (via `MapTilePurchaseSystem.GetAvailableTiles`, below), and an `Unlock` event on the milestone prefab entity, which cascades through `UnlockSystem`.

`m_Major` reaches only the UI (`milestone.Milestone.major`, `src/Game/Game.UI.InGame/MilestoneUISystem.cs:451-452`). `m_IsVictory` is console-only — see below.

**Live roster, 1.6.0f1: exactly 20 milestone prefabs, named `Milestone 1` … `Milestone 20`, with `m_Index` running 1..20.** There is no index 0, so `MilestoneLevel.m_AchievedMilestone = 0` on a new city means "before the first milestone" and `TryGetMilestone(0)` deliberately fails. **Ruled (2026-08-21, the city-state-and-progression pass under the maintainer's delegated authority; conflicts.md).** The entry asking whether ADR 0004's substitution holds where the mechanism *is* the number — a milestone's reward being five integers with no arithmetic around them — is ruled **hold the line**. No milestone figure ships: not the table, not its endpoints, and not a shape that is the values in other words. The deciding evidence is the wiki's own before/after table: this exact table was retuned at 1.1.5f1, so it is the one prefab table in the plugin with a documented history of moving, which is ADR 0004's rot-rate ground stated by the game's history. What the reference owes instead is the reward as **mechanism**: `m_Reward` into `PlayerMoney` and `m_LoanLimit` into `Creditworthiness`, written directly outside the command buffer; `m_DevTreePoints` into `DevTreePoints` through the `MilestoneReachedEvent`; `m_MapTiles` into a permit budget recomputed from the unlocked milestone set on every ask; and an `Unlock` event on the milestone prefab that cascades through `UnlockSystem`'s fixpoint loop. The `MilestoneData` row carries its `ecs_query` read, and a milestone is named through `Progression.MILESTONE_NAME:N` rather than by any wiki name. **Verdict: the wiki's milestone table is structurally right and numerically stale, and its dev-point column disagrees with the game.** `https://cs2.paradoxwikis.com/Progression` (stamped `{{Version|1.1.5f1}}`, in `Category:Potentially outdated`) lists twenty milestones with money, development points, expansion permits and loan limit, and the money, permit and loan columns match the live `MilestoneData` exactly. Its development-point column reads `…+21, +25 (Total 202), +30 (Total 232)` for milestones 18–20 where the game has 21, **24**, **27** — two of twenty rows are wrong, and its stated totals (202, 232) are wrong with them. The decompile plus the live prefab data win outright, and under the wiki-table ruling none of these numbers ships anyway. The wiki also **states no XP or population threshold for any milestone at all**, which is the one column a reader most wants and the one only the game has.
**Verdict: the wiki's milestone *names* are not worth taking either, because the game ships them.** The prefab names are `Milestone 1`…`Milestone 20` and carry no player-facing name; the names live in the compiled locale data as the indexed key family `Progression.MILESTONE_NAME:0` … `:20`, established by decoding the install's own `en-US.loc` (see the locale finding below). So a reference that needs to name a milestone names the **key** and the reader resolves it in their own install at their own version — which is both first-party and translated, where the wiki is neither.

### Past the last milestone, `MilestoneSystem`'s public properties go negative and the UI still renders a percentage

`m_NextRequired` is only assigned inside the `TryGetMilestone(achieved + 1)` branch (`MilestoneSystem.cs:80-82`). At `m_AchievedMilestone == 20` that branch never runs, so the field keeps whatever it last held — 0 in a session that loaded at max. `m_Progress` is then `XP - max(0, m_LastRequired)` with `m_LastRequired` = milestone 20's requirement, and `progress` is `m_Progress / requiredXP` where `requiredXP = nextRequiredXP - max(0, lastRequiredXP)`.

Read live on a max-milestone city: `currentXP=-498332 requiredXP=-671700 lastRequiredXP=671700 nextRequiredXP=0 progress=0.7418967 nextMilestone=21`. **Two negatives divide into a plausible 74% — on this `unlockAll` save only, whose XP sits below the last requirement; a city that earned its milestones has `m_Progress >= 0` and gets a non-positive `progress` when it loaded at max, or a division by zero when it crossed the last milestone in-session**, and `nextMilestone` names a milestone that does not exist. `MilestoneUISystem` publishes `achievedMilestoneXP` from `lastRequiredXP` and `nextMilestoneXP` from `nextRequiredXP` (`src/Game/Game.UI.InGame/MilestoneUISystem.cs:388-396`), so the binding carries those values straight to the frontend; what saves the player-visible panel is the separate `maxMilestoneReached` binding, computed as `m_LockedMilestoneQuery.IsEmpty` (`:383-386`), which the UI is expected to branch on first. **A mod reading `MilestoneSystem.progress` without checking that flag gets a number that looks fine and is meaningless.**

### Development points and the dev tree: one currency, 71 nodes, and a purchase gate with four conditions

`DevTreePoints { int m_Points }` on the city entity (`src/Game/Game.City/DevTreePoints.cs`). `DevTreeSystem` (`src/Game/Game.City/DevTreeSystem.cs:16`, `updateSystem.UpdateAfter<DevTreeSystem>(SystemUpdatePhase.ModificationEnd)`, `SystemOrder.cs:297`) does two things and nothing else.

**Accrual.** `AppendPointsJob` runs only when `MilestoneReachedEvent` entities exist and adds `MilestoneData.m_DevTreePoints` for each (`:31-43`). When the event carries `Entity.Null` — the missing-milestone path from `MilestoneSystem` — it falls back to `GetDefaultPoints(level)`: `0` for `level <= 0`, `10` for `level >= 19`, otherwise `(level + 1) / 2 + 1` (`:45-56`). **That fallback is a genuine C# formula and it disagrees with the shipped data at nearly every index** (it yields 2,2,3,3,4,… against the assets' 1,2,3,4,…), so it is a degradation path rather than a description of the reward curve. It ships as a formula; it must not be described as what a milestone grants.

**Purchase.** `DevTreeSystem.Purchase(Entity node)` and its `DevTreeNodePrefab` overload (`:148-175`) are public and are the entry point a mod uses. The gate is a single conjunction (`:165`): `m_Cost <= points`, **and** the node is still `Locked` (enabled), **and** `CheckService` — the node's `m_Service` entity is `Entity.Null` or not locked (`:194-201`), **and** `CheckRequirements` — the node has no `DevTreeNodeRequirement` buffer, or **at least one** listed node is unlocked (`:177-192`). On success it debits `points`, creates an `Unlock(node)` event on `EndFrameBarrier`, and calls `Telemetry.DevNodePurchased` (`:167-172`).

**The requirement semantics differ from the general unlock system's**: `CheckRequirements` is *any*, while `UnlockSystem`'s `UnlockRequirement` buffer defaults to *all*. That is what lets a tree branch — the wiki's `Progression#Development` describes exactly this ("you need to purchase the previous Nodes on a branch to unlock the next one, you do not need to purchase everything in a Tier") and the decompile confirms it.

`DevTreeNodeData { int m_Cost, Entity m_Service }` (`src/Game/Game.Prefabs/DevTreeNodeData.cs`) is written in `LateInitialize` alongside the `DevTreeNodeRequirement` buffer (`src/Game/Game.Prefabs/DevTreeNodePrefab.cs:59-86`). The prefab class is `[RequireComponent(typeof(ManualUnlockable))]` (`:7`) — which is what puts a self-referencing `UnlockRequirement(entity, RequireAll)` on the node so that `UnlockSystem` can never unlock it on its own (`src/Game/Game.Prefabs/ManualUnlockable.cs:14-18`). It also carries `m_HorizontalPosition`, `m_VerticalPosition`, `m_IconPath` and `m_IconPrefab`, which are layout data the UI reads.

**`DevTreeNodeAutoUnlock` is added to any node whose `m_Cost == 0` (`DevTreeNodePrefab.cs:53-56`) and has no reader anywhere in `src/`** — two hits total, both the declaration and that one add. A zero-cost node is instead unlocked by the ordinary `Purchase` path (`0 <= points` is always true), or by the milestone that unlocks its service.

**Live at 1.6.0f1: 71 `DevTreeNodeData` prefabs, 11 of which carry `DevTreeNodeAutoUnlock`** — `BasicCommunicationsNode`, `BasicEducationNode`, `BasicElectricityNode`, `BasicFire&RescueNode`, `BasicGarbageManagementNode`, `BasicHealthcareNode`, `BasicParks&RecreationNode`, `BasicPolice&AdministrationNode`, `BasicRoadServiceNode`, `BasicTransportationNode`, `BasicWater&SewageNode`. One per service, and `CityService` declares exactly those eleven plus `Districts`, `Landscaping`, `Zones` (`src/Game/Game.City/CityService.cs:3-19`). **Verdict: the wiki's "eleven development trees" is right** (`https://cs2.paradoxwikis.com/Development_Tree`, an eleven-image gallery with an empty `== Development Trees ==` section), and its "Tier 1 nodes cost 1 point, tier 2 nodes cost 2 points, tier 3 nodes cost 4 points and tier 4 nodes cost 8 points" is confirmed in shape: a sample of fifteen consecutive node prefabs read live returns costs drawn only from {1, 2, 4, 8}. **Ruled (2026-08-21, the city-state-and-progression pass under the maintainer's delegated authority; conflicts.md).** The node costs are barred under the same ruling as the milestone table — hold the line. The reference names `DevTreeNodeData.m_Cost` with its `ecs_query` read and states the purchase gate as mechanism (cost compared against `DevTreePoints.m_Points`, debited on success, `Locked` and `CheckService` and the any-of `DevTreeNodeRequirement` all required); it states no cost, no tier-to-cost mapping, and not "powers of two", which is the values in three words. The wiki's tier sentence is therefore not a claim the reference restates in any form.

`ServicePrefab` is what a node's `m_Service` points at: it carries `ServiceData { CityService m_Service, bool m_BudgetAdjustable }`, a `CollectedCityServiceBudgetData` and `CollectedCityServiceUpkeepData` component, and a `CollectedCityServiceFeeData` buffer when it declares `PlayerResource[] m_CityResources` (`src/Game/Game.Prefabs/ServicePrefab.cs`).

### Unlocking is one enableable component, one buffer, and a fixpoint loop

**`Locked` is an empty, enableable, `IEmptySerializable` tag** (`src/Game/Game.Prefabs/Locked.cs`). Unlocking is `SetComponentEnabled<Locked>(entity, false)` — the component stays on the entity forever. **`HasComponent<Locked>` is therefore always the wrong read; `HasEnabledComponent<Locked>` is the right one.** Three independent mods in the corpus get this right and it is the single most repeated fact in the sweep (`Time2Work/NightShift/Systems/Time2WorkStatisticsUISystem.cs:427`, `RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderToolSystem.cs:206`, `Anarchy/Anarchy/Patches/ToolbarUISystemActivatePrefabToolPatch.cs:29`). It is also why `ecs_query` on `Locked` under-reports: the engine's default filtering drops entities whose queried enableable component is disabled, so a query for locked prefabs returns only the still-locked ones — which is usually what you want and is a silent trap when it is not.

**Who gets `Locked`.** `PrefabSystem.AddPrefab` adds `UnlockRequirement` **and** `Locked` to the prefab entity exactly when `IsUnlockable(prefab)` (`src/Game/Game.Prefabs/PrefabSystem.cs:137-142`), and the same pair is re-added on prefab replacement, preserving the current enabled state (`:790-803`). `IsUnlockable` is cached in a `Dictionary<PrefabBase, bool>` (`:54`, `:522-538`) and is **transitive**: a prefab is unlockable if it is a `UnlockRequirementPrefab`, or carries any `UnlockableBase` component, or **any of its dependencies is** (`IsUnlockableImpl`, `:540-599`). The recursion honours `prefab.canIgnoreUnlockDependencies` together with each component's `ignoreUnlockDependencies` (`:547`, `:556`). So attaching `Unlockable` to one prefab silently makes everything that references it unlockable too.

**The predicate.** `UnlockSystem.CheckUnlockRequirementsJob` (`src/Game/Game.Prefabs/UnlockSystem.cs:20-71`) walks the `UnlockRequirement` buffer of every locked entity and computes three booleans:

```
blockedAll  |= requirementLocked && (flags & RequireAll)
blockedAny  |= requirementLocked && (flags & RequireAny)
satisfiedAny|= !requirementLocked && (flags & RequireAny)
unlock when  !blockedAll && (satisfiedAny || !blockedAny)
```

with an early `break` once `blockedAll` is set (`:47-50`). An empty buffer, or one with no `RequireAny` entries at all, unlocks — `!blockedAny` is vacuously true.

**The loop.** `OnUpdate` runs the job, drains the queue, unlocks, and **repeats until the queue comes back empty** (`:150-176`), scheduling `ScheduleParallel(...).Complete()` inside a `while (true)`. So an unlock cascade of any depth resolves in one frame, at the cost of one full parallel pass per level. It runs at `SystemUpdatePhase.MainLoop` (`SystemOrder.cs:61`) and only in a game: `OnGamePreload` sets `base.Enabled = mode.IsGame()` (`:121-125`). Its entry conditions are: a pending `Unlock` event, the first update after `OnGameLoaded`, or a non-empty `Locked + UnlockRequirement + Updated` query (`:146-149`).

`Unlock { Entity m_Prefab }` (`src/Game/Game.Prefabs/Unlock.cs`) is an event component; the archetype is `Event + Unlock` and is created independently by `MilestoneSystem`, `UnlockSystem`, `DevTreeSystem`, `ObjectBuiltRequirementSystem`, `CountHouseholdDataSystem`, `UnlockAllSystem` and the other requirement systems. `ProcessEvents` unlocks each named prefab **without** re-emitting an event (`UnlockSystem.cs:179-204`), which is what stops the loop from feeding itself.

`UnlockFlags` is a two-member `[Flags] uint` — `RequireAll = 1, RequireAny = 2` (`src/Game/Game.Prefabs/UnlockFlags.cs`).

### The unlock-requirement family: eight condition kinds, and each one adds itself to its own requirement buffer

`UnlockRequirementPrefab : PrefabBase` is abstract, carries a `string m_LabelID` and adds `UnlockRequirementData { int m_Progress }` (`src/Game/Game.Prefabs/UnlockRequirementPrefab.cs`, `src/Game/Game.Prefabs/UnlockRequirementData.cs`). `m_Progress` is display-only: nothing gates on it.

**Every concrete subclass does the same thing in `LateInitialize` — `GetBuffer<UnlockRequirement>(entity).Add(new UnlockRequirement(entity, UnlockFlags.RequireAll))`.** The requirement prefab makes *itself* a require-all prerequisite of itself, which under the predicate above means `UnlockSystem` can never unlock it (`blockedAll` is set on the first pass). It stays locked until its own condition system emits an explicit `Unlock` event for it.
The eight condition kinds, each with the component it writes, the system that evaluates it, and its update shape. **Seven are `UnlockRequirementPrefab` subclasses and the eighth, `MilestonePrefab`, is not** — it derives straight from `PrefabBase` and is unlockable only because `PrefabSystem.IsUnlockable` returns true for anything a `UnlockRequirementPrefab` depends on. **`ObjectBuiltRequirementSystem` is the exemplar and carries two things worth reading closely** (`:44-70`). ### How a mod adds an unlock requirement — the two supported routes, and the one that fails silently

**Route one, the public API.** `PrefabSystem.AddUnlockRequirement(PrefabBase unlocker, PrefabBase unlocked)` and its array overload (`src/Game/Game.Prefabs/PrefabSystem.cs:601-641`) append `new UnlockRequirement(GetEntity(unlocker), UnlockFlags.RequireAll)` to the unlocked prefab's buffer. **Both sides must already be unlockable**: the method logs `"{0} is trying to add unlock requirements, but is non-unlockable"` when the unlocker is not, and `"{0} is trying to add unlock requirement to non-unlockable prefab {1}"` when the target is not, and in both cases does nothing (`:610-616`, `:631-639`). Since `IsUnlockable` is cached the moment it is first asked, **calling this after the target prefab has already been added to `PrefabSystem` is too late**: the entity was created without a `Locked` or `UnlockRequirement` component and `GetBuffer<UnlockRequirement>` throws.

**Route two, authoring the component.** Attach `Unlockable` (`[ComponentMenu("Prefabs/Unlocking/")]`, `src/Game/Game.Prefabs/Unlockable.cs:8`) with `m_RequireAll`, `m_RequireAny` and `m_IgnoreDependencies`. Its `LateInitialize` (`:43-85`) adds a `RequireAll` entry for **every unlockable prefab in the dependency list** unless `m_IgnoreDependencies`, then the explicit `m_RequireAll` and `m_RequireAny` arrays, skipping any entry that is not itself unlockable. `UnlockableBase.DefaultLateInitialize` is the same dependency sweep on its own (`src/Game/Game.Prefabs/UnlockableBase.cs:21-34`).

The corpus has exactly one worked example and it is worth reading: `RoadBuilder` indexes every requirement prefab in the game by name with a single query — `WithAny<FeatureData, DevTreeNodeData, ObjectBuiltRequirementData, StrictObjectBuiltRequirementData, ZoneBuiltRequirementData>()` (`RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderGenerationDataSystem.cs:176`, resolved back to `PrefabBase` at `:183`) — then attaches `Unlockable.m_RequireAll` from that index and `UnlockOnBuild.m_Unlocks` cast to `ObjectBuiltRequirementPrefab`, yielding the component only when the array is non-empty (`RoadBuilder-CSII/RoadBuilder/Utilities/NetworkPrefabGenerationUtil.cs:613-628`). The requirement names are hard-coded string literals selected by road category and computed width (`:759-820`), which is the fragile half. It also sets `PlaceableNet.m_XPReward = 2` to match a vanilla road (`:545`).

**`UIGroupPrefab` unlocks on ANY member, and that is the only place `RequireAny` is used structurally.** `UIGroupPrefab.GetPrefabComponents` adds `UIGroupElement`, `UnlockRequirement` and `Locked` unconditionally; `LateInitialize` adds a self-referencing `UnlockRequirement(entity, RequireAny)`, and `AddElement` adds `UnlockRequirement(element, RequireAny)` alongside the `UIGroupElement` (`src/Game/Game.Prefabs/UIGroupPrefab.cs:10-29`). Under the predicate: with only the self-entry, `blockedAny` is true and `satisfiedAny` false, so the group stays locked; the moment any member unlocks, `satisfiedAny` flips and the group unlocks. **A mod adding a toolbar entry to a vanilla group must call `AddElement` rather than writing the buffers itself**, or the group's unlock condition will not see it.

`ProgressionUtils.CollectSubRequirements` / `GetRequiredMilestone` (`src/Game/Game.UI.InGame/ProgressionUtils.cs`) is the read side: it walks the requirement graph recursively and returns the highest `MilestoneData.m_Index` reachable through `RequireAll` edges. It short-circuits on the self-referencing entry (`:22`) — which is exactly the entry every requirement prefab adds — and that is what makes the walk terminate. It is public and static and is the supported way to ask *"what milestone does this prefab need"*.

### Map tiles: 529 area entities, and `Native` means "not yours"

A map tile is an ordinary `Game.Areas` area. `MapTilePrefab : AreaPrefab` adds `MapTileData`, a `MapFeatureData` buffer, `AreaGeometryData` and `TilePurchaseCostFactor` as prefab components, and `MapTile`, a `MapFeatureElement` buffer and `Geometry` as archetype components (`src/Game/Game.Prefabs/MapTilePrefab.cs:24-39`). `MapTile` and `MapTileData` are both empty `IEmptySerializable` tags.

**Ownership is the absence of `Game.Common.Native`.** `MapTilePurchaseSystem.UnlockTile` is three lines: remove `Native`, add `Updated` (`src/Game/Game.Simulation/MapTilePurchaseSystem.cs:346-353`). The owned-tile query is `[MapTile, Exclude<Native>]` (`:161`) and the purchasable query is `[MapTile, Native, Area]` (`:162`).

**Generation.** `MapTileSystem.LegacyGenerateMapTiles` (`src/Game/Game.Areas/MapTileSystem.cs:188-228`) destroys any existing tiles, creates `529` entities from the `MapTilePrefab`'s archetype, marks them all `Native` outside the editor, and hands nine of them to the player: `AddOwner` on the 3×3 block from `(10,10)` to `(12,12)`, indexed `tile.y * 23 + tile.x` (`:206-214`, `:230-235`). `GenerateMapTilesJob` lays them out on a 23×23 grid with `private const int LEGACY_GRID_WIDTH = 23`, `LEGACY_GRID_LENGTH = 23`, `private const float LEGACY_CELL_SIZE = 623.3043f` (`:76-80`), centred on the world origin (`:46-55`).

**Modern maps do not run that path.** `PostDeserialize` uses it only when `context.version < Version.editorMapTiles` on a new game, or on `Purpose.NewMap`; otherwise it takes the editor-authored `m_StartTiles` list, drops nulls, and removes `Native` from the rest (`:127-154`). `m_StartTiles` is a `NativeList<Entity>` the system serializes itself (`:161-186`) and prunes on tile deletion (`:110-125`); `GetStartTiles()` is public (`:156-159`) and is used by the purchase system for both the free-tile floor and the cost exclusion.

`MapTileSystem` runs at `SystemUpdatePhase.PostTool` (`SystemOrder.cs:725`).

**Live at 1.6.0f1: 529 `MapTile` entities, 0 of them `Native`** (this save has `unlockMapTiles`). Two `MapTileData` prefabs exist — `Map Tile` and `Water Tile`.

Its per-tile area is right — `623.3043²` m² ≈ 0.3885 km². Its "9 tiles will start purchased" matches `kAutoUnlockedTiles` and the 3×3 legacy block. The 441 figure is cited on that page to a **1.0.12f1 decompile from 2 November 2023**, and the section still carries an unresolved `{{Verification needed|Exact numbers need source code deep dive validation}}` from that date.
### Tile cost: expansion permits are a milestone budget, and money scales with how many tiles you already own

**Permits.** `GetAvailableTiles()` (`MapTilePurchaseSystem.cs:255-273`) is `max(0, budget - owned)` where `budget = max(kAutoUnlockedTiles, startTiles.Length) + Σ m_MapTiles over every *unlocked* milestone` — the query is `[MilestoneData, Exclude<Locked>]` (`MapTilePurchaseSystem.cs:163`), so a milestone contributes its permits the moment its prefab unlocks. `private static readonly int kAutoUnlockedTiles = 9` (`MapTilePurchaseSystem.cs:52`) is a C# constant and ships. There is no permit component and no permit currency: **the budget is recomputed from the milestone set every time it is asked.** The UI binding is `mapTiles.expansionPermits` → `GetAvailableTiles()` (`src/Game/Game.UI.InGame/MapTilesUISystem.cs:104`), and `mapTiles.expansionPermitCost` → `GetSelectedTileCount()` (`MapTilesUISystem.cs:105`), which is the whole of "one permit per tile".

**Money.** The per-tile intrinsic value, computed identically in `UpdateStatus` (`MapTilePurchaseSystem.cs:226-236`) and `CalculateOwnedTilesCost` (`MapTilePurchaseSystem.cs:402-420`), is

```
tileValue = Σ over map feature j of
    MapFeatureElement[j].m_Amount           // the tile's endowment
  * baselineModifier(j)                     // kMapFeatureBaselineModifiers[j], else 1.0
  * 10.0
  * MapFeatureData[j].m_Cost                // per-feature rate, on the tile prefab
  * TilePurchaseCostFactor.m_Amount         // one scalar, on the tile prefab
```

and the purchase price of a multi-tile selection is (`MapTilePurchaseSystem.cs:238-242`)

```
sort the per-tile values ascending
cost = Σ over k of  values[len - 1 - k] * (ownedTiles + k)
```

**So the price is linear in the number of tiles you already own, and the sort deliberately pairs the most valuable selected tile with the lowest multiplier.**
The baseline modifiers are three `private static readonly` doubles and an array (`MapTilePurchaseSystem.cs:48-54`): `kMapTileSizeModifier = 1.0 / Math.Pow(623.304347826087, 2.0)` — the reciprocal of the tile's own area, so the `Area` and `BuildableLand` terms are normalised to a fraction of a tile — `kResourceModifier = 8.0718994140625E-07`, and `kMapFeatureBaselineModifiers = { size, size, resource, resource, resource, resource, 1.0, resource }`.
**`MapFeature` has nine members and the modifier array has eight.** `MapFeature = Area, BuildableLand, FertileLand, Forest, Oil, Ore, SurfaceWater, GroundWater, Fish` (indices 0–8, `src/Game/Game.Areas/MapFeature.cs`), and `GetBaselineModifier` returns `1.0` for any index outside the array (`MapTilePurchaseSystem.cs:288-295`). So `Fish` is multiplied by 1.0 where `Ore` and `Oil` are multiplied by 8.07e-07 — a factor of roughly 1.2 million. **At 1.6.0f1 this is inert because the base `Map Tile` prefab's fish rate is zero**: read live, `MapFeatureData` on `Map Tile` is `[0.03, 0.05, 0.06, 0.06, 0.1, 0.1, 0.04, 0.1, 0]` and `TilePurchaseCostFactor.m_Amount = 2500`. A sampled tile's `MapFeatureElement` amounts confirm fish is endowed (120766 on one tile) while its rate is 0. **A mod that gives fish a non-zero rate gets a tile price dominated by fish alone**, and nothing in the code will complain. `m_FeatureAmounts` is allocated at length 9 (`MapTilePurchaseSystem.cs:166`) against the 8-entry modifier array, which is where the mismatch is visible.

`GetFeatureAmount(MapFeature)` is public and converts `FertileLand` through `NaturalResourceSystem.ResourceAmountToArea` before returning it (`MapTilePurchaseSystem.cs:430-438`); every other feature is returned raw. That is what the `mapTiles.resources` binding renders (`MapTilesUISystem.cs:113-136`), with fixed unit tags `area` / `weight` / `volume` per feature.

**`TilePurchaseErrorFlags` is the declared status set** — `None, NoCurrentlyAvailable, NoAvailable, NoSelection, InsufficientFunds, InsufficientPermits` (`src/Game/Game.Simulation/TilePurchaseErrorFlags.cs`) — and it is a `[Flags]` enum used as a scalar in two of its branches: the no-permits and no-selection branches **assign** rather than OR and return early (`MapTilePurchaseSystem.cs:189-198`), while `InsufficientPermits` and `InsufficientFunds` are OR-ed and can coexist (`MapTilePurchaseSystem.cs:245-252`). `NoCurrentlyAvailable` vs `NoAvailable` is decided by `IsMilestonesLeft()` — whether any `MilestoneData` prefab is still `Locked` (`MapTilePurchaseSystem.cs:275-286`).

**Two arithmetic shapes in `UpdateStatus` a reader should verify before trusting the upkeep figure.** `CalculateOwnedTilesCost(includeSelection: true)` does not include the owned tiles at all — when the selection is non-empty it iterates *only* the selection (`MapTilePurchaseSystem.cs:389-400`), so `num3` is the selection's value despite the method's name. `num5` is then initialised to `num3` and the loop at `MapTilePurchaseSystem.cs:210-237` adds the same per-feature terms a second time, making `num5` twice the selection value; `m_Upkeep = num5 * mult(owned + selected) - num3 * mult(owned)` (`MapTilePurchaseSystem.cs:244`). The same double pass runs over `m_FeatureAmounts` (`MapTilePurchaseSystem.cs:230` after `MapTilePurchaseSystem.cs:415`), so `GetFeatureAmount` reports each selected tile's endowment twice while a selection is active. Both are recorded as observed arithmetic under the `conflicts.md` ruling on first-party expressions that look like defects; neither is characterised here as intent. `CalculateOwnedTilesUpkeep()` takes `includeSelection: false` and is unaffected (`MapTilePurchaseSystem.cs:425-428`).

**Upkeep is a curve on `EconomyParameterData`, not a per-tile cost.** `GetMapTileUpkeepCostMultiplier(tileCount)` returns 0 at or below `kAutoUnlockedTiles` and otherwise `EconomyParameterData.m_MapTileUpkeepCostMultiplier.Evaluate(tileCount)` — an `AnimationCurve` (`MapTilePurchaseSystem.cs:121-128`). `GetMapTileUpkeepEnabled()` is a **sampling probe rather than a flag**: it returns false when `unlockMapTiles` is set, and otherwise samples the curve at `0, 10, 20, … 100` and returns true on the first positive sample (`MapTilePurchaseSystem.cs:130-147`). `CityServiceBudgetSystem` folds `CalculateOwnedTilesUpkeep()` into the budget, zeroed when `unlockMapTiles` (`src/Game/Game.Simulation/CityServiceBudgetSystem.cs:891`).

**The permit budget does not reach every tile, and that is a structural fact only prefab values state.** The whole milestone track grants `Σ m_MapTiles = 432` permits, and the floor is `max(kAutoUnlockedTiles, startTiles.Length)`, so a city on a map with the default nine start tiles can buy at most **441** of the **529** tiles the grid contains — 88 are unreachable without `CityConfigurationSystem.unlockMapTiles`. The derivation is: sum `MilestoneData.m_MapTiles` over the twenty milestone prefabs, add `kAutoUnlockedTiles`, and compare against the `MapTile` entity count. Re-derive with `ecs_query` on `Game.Prefabs.MilestoneData` plus a batched read of `m_MapTiles`, and `ecs_query` on `Game.Areas.MapTile` for the denominator. Confirmed live at 1.6.0f1 on this install; the milestone roster is one install's prefab set, so a content pack adding a milestone would move the numerator. **How a fact of this shape ships is not this file's to decide** — the standing rule for a structural fact read off prefab values is the 2026-08-11 ruling in `conflicts.md`, which ships it as the shape with the reproducing derivation attached rather than as a bare figure, and the derivation is recorded here for that reason. The wiki states the 432 total and the 441 tile count without noticing that they meet exactly, and it gets the denominator wrong.

**Verdict: the wiki's tile-cost rates are stale, unsourceable and barred.** `Progression#Map Tiles` gives four per-resource money rates and a flat "+125 per map tile unlocked", all cited to a 1.0.12f1 decompile and all flagged `{{Verification needed}}` by their own author. Its "+125 per tile" is not the shape of the formula at all: the per-tile increment is the tile's own value, which varies per tile and per map. The `=== Map Tiles Upkeep ===` subsection is an empty `{{stub|section}}` — the wiki documents no tile upkeep whatsoever.

**`MapTilePurchaseSystem` is not registered in `SystemOrder.cs`, and that is deliberate.** Grepping the file for the type returns nothing; only `MapTileSystem` (PostTool) and `MapTilesUISystem` (UIUpdate) are registered. `MapTilesUISystem.OnUpdate` calls `m_MapTileSystem.Update()` by hand, and only when the map-tile view is open (`src/Game/Game.UI.InGame/MapTilesUISystem.cs:139-148`). **So `cost`, `upkeep`, `status` and `GetFeatureAmount` are stale except while that view is active**; `PurchaseSelection()` re-runs `UpdateStatus()` itself before spending (`MapTilePurchaseSystem.cs:311-313`). The other callers reach it through `World.GetOrCreateSystemManaged<MapTilePurchaseSystem>()` and call its methods directly: `CityServiceBudgetSystem`, `SelectionToolSystem` (which refuses map-tile selection when `GetAvailableTiles() == 0`, `src/Game/Game.Tools/SelectionToolSystem.cs:605`, `SelectionToolSystem.cs:991`, `SelectionToolSystem.cs:1001`), `TutorialSystem` (three `UnlockMapTiles()` calls) and the editor's `MapPanelSystem`.

Selection itself is the generic tool: `MapTilePurchaseSystem.selecting` sets `SelectionToolSystem.selectionType = SelectionType.MapTiles` and makes it the active tool (`MapTilePurchaseSystem.cs:92-115`), and the selection lives in a `SelectionElement` buffer on a singleton (`MapTilePurchaseSystem.cs:355-367`).

### Policies: four scopes, decided by which component the policy prefab happens to carry

`Policy { Entity m_Policy, PolicyFlags m_Flags, float m_Adjustment }` is an `[InternalBufferCapacity(0)]` buffer element (`src/Game/Game.Policies/Policy.cs`), and `PolicyFlags` has one member, `Active = 1` (`src/Game/Game.Policies/PolicyFlags.cs`). **A policy is stored on whatever entity it applies to** — the city entity, a `District`, a `Building`, a `Route` — and the scope is not declared anywhere: `ModifiedSystem.GetPolicyRange` derives it by testing eight component pairs in order and returning `PolicyRange.District | Building | City | Route | None` (`src/Game/Game.Policies/ModifiedSystem.cs:213-248`). `PolicyRange` is a nested public enum on `ModifiedSystem` (`:26-33`), which is the only place the four scopes are named as a set.

The authoring surface is eight `ComponentBase` classes, all `[ComponentMenu("Policies/", typeof(PolicyPrefab))]`, each turning an authored array into a prefab-side buffer or mask: `CityModifiers` → `CityModifierData` buffer, `DistrictModifiers` → `DistrictModifierData`, `BuildingModifiers` → `BuildingModifierData`, `CityOptions` → `CityOptionData.m_OptionMask`, `DistrictOptions` → `DistrictOptionData`, `BuildingOptions` → `BuildingOptionData` (each in `src/Game/Game.Prefabs/`). `RouteModifiers` → `RouteModifierData` and `RouteOptions` → `RouteOptionData` are the route pair. **The modifier element shape is identical across the four scopes**: `{ TypeEnum m_Type, ModifierValueMode m_Mode, Bounds1 m_Range }` (`src/Game/Game.Prefabs/CityModifierData.cs` and siblings).

`PolicyPrefab : PrefabBase` is abstract, carries `PolicyVisibility m_Visibility` and `PolicyCategory m_Category`, and adds `PolicyData { int m_Visibility }` (`src/Game/Game.Prefabs/PolicyPrefab.cs`). Two concrete subclasses: `PolicyTogglePrefab` (empty) and `PolicySliderPrefab`, which adds `PolicySliderData { Bounds1 m_Range, float m_Default, float m_Step, int m_Unit }` (`src/Game/Game.Prefabs/PolicySliderPrefab.cs`). `PolicyCategory = None, CityPlanning, Budget, Traffic, Culture, Services`; `PolicyVisibility = Default, HideFromPolicyList`; `PolicySliderUnit = money, percentage, integer` — three declared sets.

**Live at 1.6.0f1: 23 `PolicyData` prefabs**, and the scope breakdown is the sweep that answers the ticket's question. By which component each carries:

- **City modifiers (5)**: `Taxi Starting Fee`, `High-Speed Highways`, `Advanced Pollution Management`, `PreRelease Programs`, `City Promotion`.
- **City options (3)**: `Paid Outside Services`, `Taxi Starting Fee`, `High-Speed Highways`.
- **District modifiers (6)**: `Gated Community`, `Roadside Parking Fee`, `Recycling`, `Speed Bumps`, `Energy Consumption Awareness`, `Urban Cycling Initiative`.
- **District options (5)**: `Gated Community`, `Combustion Engine Ban`, `Heavy Traffic Ban`, `Bicycle Traffic Restriction`, `Roadside Parking Fee`.
- **Building modifiers (1)**: `Lot Parking Fee`. **Building options (3)**: `Empty`, `Out of Service`, `Lot Parking Fee`.
- **Route modifiers (2)**: `Route Ticket Price`, `Route Vehicle Count`. **Route options (4)**: `Route Ticket Price`, `Day Route`, `Night Route`, `Route Out of Service`.
- **Sliders (5)**: `Taxi Starting Fee`, `Route Ticket Price`, `Route Vehicle Count`, `Lot Parking Fee`, `Roadside Parking Fee`.

A policy can be in more than one row: `Taxi Starting Fee` carries a city modifier, a city option and a slider; `Roadside Parking Fee` is a district modifier, a district option and a slider. Two policies sit at entity indices three orders of magnitude above the rest (`Bicycle Traffic Restriction` at 20648, `Urban Cycling Initiative` at 20650, against 142–162 for the other twenty-one), which is what a later-loaded content pack looks like; `Unconfirmed:` that they are one, since the index is suggestive rather than probative and the cheap check is the `Prefabs*.cok` route. **Either way the roster is one install's set, not a fact about the base game.**

**Verdict: the wiki's policy page is a subset less than two-thirds the size, and its three-way scope split is the game's four-way one with routes missing.** `https://cs2.paradoxwikis.com/Policies` (`{{Version|1.0}}`, in `Category:Potentially outdated`) opens *"Cities: Skylines II features three types of policies: city policies, district policies and building policies"* and documents 14: six city, seven district, one building. The decompile has a fourth scope — `PolicyRange.Route`, backed by `RouteModifierData` / `RouteOptionData` and four live policies — and the live roster has 23. The wiki also assigns `Roadside Parking Fee` and `Combustion Engine Ban` to districts, which the components confirm, and its `Import City Services` corresponds to `Paid Outside Services` (`CityOption.ImportOutsideServices`), a name mismatch worth knowing. **The decompile settles the policy set; the page settles nothing and its `Required milestone` column is the only thing on it the game does not state directly.**

### Applying a policy: an event component, one job, and a full rebuild of the target's modifier buffer

The write path is uniform and short. Something creates an `Event + Modify` entity carrying `Modify { m_Entity, m_Policy, m_Flags, m_Adjustment }` (`src/Game/Game.Policies/Modify.cs`); `ModifiedSystem` (`src/Game/Game.Policies/ModifiedSystem.cs:24`, `SystemUpdatePhase.Modification4`, `SystemOrder.cs:146`) consumes it. **There are exactly two producers in the game**: `PoliciesUISystem.ModifyPolicy` (`src/Game/Game.UI.InGame/PoliciesUISystem.cs:237-242`, archetype at `:157`) and `DebugSystem` (`src/Game/Game.Debug/DebugSystem.cs:858`, `:3481`). The UI exposes it as two triggers, `policies.setPolicy` and `policies.setCityPolicy`, both `TriggerBinding<Entity, bool, float>` (`PoliciesUISystem.cs:161-162`). **So a mod applies a policy by creating that event entity, not by editing the `Policy` buffer** — editing the buffer skips the modifier refresh entirely.

`ModifyPolicyJob.Execute` (`ModifiedSystem.cs:103-195`) walks the target's `Policy` buffer for a matching `m_Policy` and:

- **Deactivating a toggle policy** (no `PolicySliderData`) removes the buffer entry (`ModifiedSystem.cs:125-136`).
- **Deactivating a slider policy** removes the entry **only when the adjustment equals `PolicySliderData.m_Default`**; otherwise it falls through and merely rewrites the flags and adjustment (`ModifiedSystem.cs:137-148`). So a slider left off-default stays in the buffer as an inactive entry.
- **Any other case** overwrites `m_Flags` and `m_Adjustment` in place (`ModifiedSystem.cs:150-153`).
- **No match and `Active` set** appends a new `Policy`, and *only this path* fires `TriggerType.PolicyActivated` (`ModifiedSystem.cs:159-170`).

Every branch calls `RefreshEffects`; only the two remove branches (`ModifiedSystem.cs:129`, `ModifiedSystem.cs:141`) and the append branch (`ModifiedSystem.cs:164`) enqueue a `PolicyEventInfo { m_Activated, m_Entity, m_PolicyRange }` — the off-default-slider fall-through and the in-place overwrite do not. `RefreshEffects` (`ModifiedSystem.cs:250-299`) tests the same eight component pairs as `GetPolicyRange` and calls the matching refresh, then `AddComponent<Updated>(entity)`.

Two side paths in the same job: a `Modify` whose target is an `Extension` and whose policy carries `BuildingOption.Inactive` toggles `ExtensionFlags.Disabled` instead (`ModifiedSystem.cs:174-186`), and a `Modify` on a `ServiceUpgrade` marks the owner `Updated` (`ModifiedSystem.cs:187-194`). One special-case trigger: deactivating the ticket-price policy fires `TriggerType.FreePublicTransport` (`ModifiedSystem.cs:198-211`).

### Modifier composition is the formula the whole policy system reduces to

`CityModifierUpdateSystem.CityModifierRefreshData.RefreshCityModifiers` (`src/Game/Game.Simulation/CityModifierUpdateSystem.cs:107-193`) is called both from `ModifiedSystem` and from `CityModifierUpdateSystem` itself, which runs at `SystemUpdatePhase.GameSimulation` with `GetUpdateInterval` returning **256** (`:257-260`). It **clears the buffer and rebuilds it** every time (`:109`), from two sources:

**Active policies** (`:110-136`). For each active `Policy` whose prefab has a `CityModifierData` buffer, and for each element in it:

```
if the policy has PolicySliderData:
    t     = saturate((adjustment - slider.min) / (slider.max - slider.min))   // 0 when min == max
    delta = lerp(modifier.m_Range.min, modifier.m_Range.max, t)
else:
    delta = modifier.m_Range.min
```

**A toggle policy therefore uses `m_Range.min`, not `max`.**

**City effect providers** (`:137-192`) — buildings and upgrades carrying `CityEffectProvider`, from the `[CityEffectProvider, Exclude<Deleted>, Exclude<Destroyed>, Exclude<Temp>]` query at `:268`. The branch is `if (!hasSignature && efficiencyAccessor.Length != 0)` (`:140-144`): a non-signature provider with an `Efficiency` buffer contributes `lerp(range.min, range.max, efficiency)` (`:165`); **every other provider — a `Signature` building, or any provider without an `Efficiency` buffer — contributes `range.max` flat** (`:171-191`). Installed upgrades are folded in through `AddToTempList`, skipping any carrying `BuildingOption.Inactive` (`:195-205`).

**Accumulation** is `AddModifier` (`:207-228`), which grows the buffer to the modifier's type index and then, by `ModifierValueMode`:

```
Relative:        y = y * (1 + delta) + delta          // i.e. (1+y') = (1+y)(1+delta)
Absolute:        x += delta
InverseRelative: delta = 1/max(0.001, 1 + delta) - 1; then as Relative
```

and **application** is `CityUtils.ApplyModifier` (`src/Game/Game.City/CityUtils.cs:17-25`): `value += delta.x; value += value * delta.y;` — absolute first, then relative, with a silent no-op when the buffer is shorter than the type index. `CityUtils.GetModifier` returns the raw `float2` and `default` for a missing index (`:27-34`). **Both are public statics and are the supported read**; `Time2Work` uses `ApplyModifier` rather than reimplementing it (`Time2Work/NightShift/Systems/Time2WorkTourismSystem.cs:265-266`, `Time2Work/NightShift/Systems/Time2WorkDeathCheckSystem.cs:313`, `:397`) and `Info Loom` hands the live buffer to the game's own evaluator (`InfoLoom/InfoLoom/Systems/InfoviewUISystems/ILEducationInfoviewUISystem.cs:462`, `:465`).

**Because the buffer is indexed by the enum value, its length is `max(usedType) + 1` and not the enum's member count.** `CityModifierType` declares 40 members with explicit values spanning `0..40` and a hole at 2 (`src/Game/Game.City/CityModifierType.cs`) — `Attractiveness = 0`, `CrimeAccumulation = 1`, then `DisasterWarningTime = 3`. There is no member with value 2, so index 2 of a live `CityModifier` buffer is permanently `default`. `DistrictModifierType` declares 14 contiguous members (`src/Game/Game.Areas/DistrictModifierType.cs`). Both are declared sets and ship.

`CityModifier` and `DistrictModifier` are `[InternalBufferCapacity(0)]` `float2 m_Delta` elements whose `Deserialize` reads only `m_Delta.y` below `Version.modifierRefactoring` (`src/Game/Game.City/CityModifier.cs:17-29`) — the absolute channel is the newer half.

**`CityEffects` is the building-side authoring component** and it constructs a one-sided range: `new Bounds1(0f, cityEffectInfo.m_Delta)` (`src/Game/Game.Prefabs/CityEffects.cs`), so a building's effect at zero efficiency is zero. It adds `CityEffectProvider` to the archetype unless the prefab is a `ServiceUpgrade`, in which case `GetUpgradeComponents` adds it to the upgrade instead.

### Default policies are seeded twice, by two different code paths

`DefaultPoliciesSystem` (`src/Game/Game.Policies/DefaultPoliciesSystem.cs`, `SystemUpdatePhase.Modification3`, `SystemOrder.cs:135`) runs `AddDefaultPoliciesJob` over `[Created, ReadWrite<Policy>, PrefabRef, Exclude<Temp>]`: for each created entity whose prefab carries a `DefaultPolicyData` buffer, append every listed policy as `Active`, with `PolicySliderData.m_Default` as the adjustment when the policy is a slider and `0f` otherwise (`:35-61`). That is how a newly placed building or district gets its policies.

`PostDeserialize` does the same for the **city** entity, reading `DefaultPolicyData` off the `ServiceFeeParameterData` singleton entity, and only on `Purpose.NewGame` or on a load below `Version.taxiFee` (`:124-149`). So the city's default policy set is authored on a settings prefab rather than on the city.

### Notifications: 160 icon prefabs, three families, and one command buffer that is the whole mod-facing API

**The icon prefab.** `NotificationIconPrefab : PrefabBase` (`src/Game/Game.Prefabs/NotificationIconPrefab.cs`) carries `m_Icon`, `m_Description`, `m_TargetDescription`, `m_DisplaySize`, `m_PulsateAmplitude`, `m_EnabledByDefault`, and adds `NotificationIconData { EntityArchetype m_Archetype }` plus `NotificationIconDisplayData` as prefab components and `Icon` to the archetype. `RefreshArchetype` builds the icon-entity archetype in `LateInitialize` from the prefab's own archetype components plus `Created` and `Updated` (`:48-68`), which is what makes an icon a real entity. `Initialize` disables `NotificationIconDisplayData` when `m_EnabledByDefault` is false (`:33-40`) — that component is `IEnableableComponent, ISerializeAsEnabled`, and `ComponentSerializerLibrary.Initialize` routes an `ISerializeAsEnabled` type to the plain `ComponentDataSerializer<>`, so the enabled bit is session state the save neither carries nor restores.

**The icon instance.** `Icon { float3 m_Location, IconPriority m_Priority, IconClusterLayer m_ClusterLayer, IconFlags m_Flags, int m_ClusterIndex }` (`src/Game/Game.Notifications/Icon.cs`) — `m_ClusterIndex` is runtime-only and not serialized (`:18-42`). The owning entity gets an `IconElement { Entity m_Icon }` buffer entry, `[InternalBufferCapacity(4)]` and `IEmptySerializable` (`src/Game/Game.Notifications/IconElement.cs`).

Three declared sets ship: `IconPriority : byte = Min 0, Info 10, Problem 50, Warning 100, MajorProblem 150, Error 200, FatalProblem 250, Max 255` (`src/Game/Game.Notifications/IconPriority.cs`); `IconFlags : byte = Unique 1, IgnoreTarget 2, TargetLocation 4, OnTop 8, SecondaryLocation 0x10, CustomLocation 0x20` (`src/Game/Game.Notifications/IconFlags.cs`); `IconClusterLayer : byte = Default, Marker, Transaction` with the parallel `IconLayerMask : uint = None, Default 1, Marker 2, Transaction 4` used by raycasts (`src/Game/Game.Notifications/IconClusterLayer.cs`, `src/Game/Game.Notifications/IconLayerMask.cs`).

**The API.** `IconCommandBuffer` (`src/Game/Game.Notifications/IconCommandBuffer.cs`) is a 120-line struct with five methods and is the entire supported surface:

- `Add(owner, prefab, priority = Info, clusterLayer = Default, flags = 0, target = default, isTemp = false, isHidden = false, disallowCluster = false, delay = 0f)` (`:54-68`) — **strips `IconFlags.CustomLocation`**.
- `Add(owner, prefab, float3 location, priority = Info, clusterLayer = Default, flags = IgnoreTarget, …)` (`:70-85`) — **adds `IconFlags.CustomLocation`**. Note the two overloads have different `flags` defaults.
- `Remove(owner, prefab, target = default, flags = 0)` (`:87-98`).
- `Remove(owner, IconPriority priority)` (`:100-109`) — sets `CommandFlags.Remove | All`, removing every icon on the owner at that priority.
- `Update(owner)` (`:111-119`) — re-evaluates positions.

The handshake is `IconCommandSystem.CreateCommandBuffer()` / `AddCommandBufferWriter(JobHandle)` (`src/Game/Game.Notifications/IconCommandSystem.cs:727-737`). `CreateCommandBuffer` allocates a fresh `NativeQueue` per call and hands out a monotonically increasing `m_BufferIndex` (`:731`), which becomes the command's tie-break in `Command.CompareTo` (`:43-47`) — commands sort by owner index first, then by "has a prefab", then by buffer index, so **the order in which two systems obtained their command buffers decides which of their commands wins on the same owner in the same frame.**

`IconCommandSystem` runs at `SystemUpdatePhase.ModificationEnd` (`SystemOrder.cs:271`). `OnUpdate` completes the writers, concatenates every queue into one array, disposes them all, sorts, and plays back one owner at a time in a single non-parallel `IJob` (`:740-803`, `Execute` at `:107`). The command buffers are **per-frame**: `m_Queues` is cleared every update and on `OnStopRunning`, so a buffer obtained in one frame must be filled and its writer registered in that frame.

The sibling systems are `IconClusterSystem` (clustering, runs after `ModificationEnd`, `SystemOrder.cs:299`), `IconAnimationSystem` and `IconDeletedSystem` (both `Modification5`, `SystemOrder.cs:240-241`), and `MarkerCreateSystem` (`ModificationEnd`, `SystemOrder.cs:256`). `Animation { m_Timer, m_Duration, AnimationType m_Type }` with `AnimationType : byte = MarkerAppear, MarkerDisappear, WarningAppear, WarningResolve, Transaction` (`src/Game/Game.Notifications/AnimationType.cs`) is the declared animation set, and `IconCommandSystem` maps `IconClusterLayer.Transaction → AnimationType.Transaction` (`IconCommandSystem.cs:439`). `DisallowCluster` is an empty tag on the icon entity.

### The notification set is not the complete failure surface, and the split that says why is `SimulationWarning` against `ToolError`

**Live at 1.6.0f1, 160 entities carry `NotificationIconData`.** They are three different things wearing one prefab type:

- **30 are placement/tool errors.** Querying `[NotificationIconData, ToolErrorData]` returns exactly 30, and `Game.Tools.ErrorType` declares exactly 30 real members between `None` and `Count` (`src/Game/Game.Tools/ErrorType.cs`) — equal counts. `Unconfirmed:` the bijection, since no per-member sweep was run; a `m_Error` read over the 30 prefabs settles it. `ToolError` is the authoring component (`[ComponentMenu("Notifications/", typeof(NotificationIconPrefab))]`) and writes `ToolErrorData { ErrorType m_Error, ToolErrorFlags m_Flags }` with `ToolErrorFlags = TemporaryOnly | DisableInGame | DisableInEditor` (`src/Game/Game.Prefabs/ToolError.cs`, `src/Game/Game.Prefabs/ToolErrorFlags.cs`). These are raised by `Game.Tools.ValidationSystem`, not by the simulation; `ToolFeedbackSystem` raises feedback icons named on `FeedbackConfigurationData` (`src/Game/Game.Tools/ToolFeedbackSystem.cs:350`, `:361`, `:667-700`), not `ErrorType` errors.
- **A subset are simulation warnings**, marked by the `SimulationWarning` component — also `[ComponentMenu("Notifications/", typeof(NotificationIconPrefab))]`, contributing **no ECS component of its own** and instead OR-ing `1 << (int)category` into `NotificationIconDisplayData.m_CategoryMask` for each entry of its `IconCategory[] m_Categories` (`src/Game/Game.Prefabs/SimulationWarning.cs`). `IconCategory` is a 16-member declared set: `Healthcare, FireRescue, Police, Water, Electricity, Garbage, Road, Track, Transport, Disaster, Zoning, AirPollution, NoisePollution, GroundPollution, LandValue, Level` (`src/Game/Game.Prefabs/IconCategory.cs`).
- **The rest are markers**: transport stops, vehicles, service buildings, outside connections, `Selected`, `Followed`, `Happy Face`, `Sad Face`, `ValentineHeart`. `MarkerCreateSystem` adds them at `IconPriority.Info` on `IconClusterLayer.Marker` with `IconFlags.Unique`, driven by `TransportStopMarkerData`, `BuildingMarkerData`, `VehicleMarkerData`, `InfoviewMarkerData` and `MarkerMarkerData` on the owning prefab (`src/Game/Game.Notifications/MarkerCreateSystem.cs:415`, `:465`, `:473`).

**`NotificationIconPrefabSystem` is what distinguishes the second family from the third at runtime**, with one line: `value.m_CategoryMask = math.select(2147483648u, value.m_CategoryMask, value.m_CategoryMask != 0)` (`src/Game/Game.Prefabs/NotificationIconPrefabSystem.cs:84`). Bit 31 is outside `IconCategory`'s 0–15 range and is the "uncategorised" sentinel; `NotificationIconDisplayData.Deserialize` writes the same value (`src/Game/Game.Prefabs/NotificationIconDisplayData.cs:27`). Read live: `Abandoned` = 1024 (`Zoning`), `Air Pollution` = 2048 (`AirPollution`), `Crime Scene` = 4 (`Police`), `Rent Too High` = 17408 (`LandValue | Zoning`); `Bus Stop`, `Steep Slope`, `Selected` and `Building Level Up` all = 2147483648. **`Building Level Up` carrying the sentinel despite `IconCategory.Level` existing is the one live reading that does not fit the pattern**, and it is why the category mask cannot be used as a clean warning/marker test on its own.

**So the answer to "is the notification list the complete set of failure states the simulation can report" is no, and the correction is precise**: the icon-prefab family is the complete set of *map-marker icons*, of which simulation failures are one of three subfamilies, tool errors are a second (a closed enum of 30 the simulation never raises), and markers are a third. The complete failure surface is not enumerable from the icon set alone; it is the set of icon prefabs carrying `SimulationWarning`, and since that component contributes no ECS type, **enumerating it needs the authoring assets or an inference from `m_CategoryMask != 1<<31`** — and the `Building Level Up` reading above shows that inference is not sound.

**One live count difference is itself a trap worth shipping.** `ecs_query` on `NotificationIconData` alone returns 160; the same query with `NotificationIconDisplayData` added returns 159. `NotificationIconDisplayData` is enableable, so the engine's default query filtering silently drops the one prefab shipping with `m_EnabledByDefault = false`. **A query that includes an enableable component under-counts by exactly the disabled entities, with no error.**

**The infoview does not filter icons; it dims them.** `NotificationIconBufferSystem` computes, per icon, `math.select(1f, new float2(0.5f, 0f), (displayData.m_CategoryMask & m_CategoryMask) == 0 && !cluster.isTemp)` (`src/Game/Game.Rendering/NotificationIconBufferSystem.cs:222`, and again at `:287` and `:327` without the temp exemption), where `m_CategoryMask` is the active infoview's, built from `InfoviewPrefab.m_WarningCategories` (`src/Game/Game.Prefabs/InfoviewPrefab.cs:25`). An out-of-category icon is drawn at half scale and zero alpha rather than skipped.

`NotificationIconPrefabSystem` also assigns `m_IconIndex` by walking chunks and incrementing from 1 (`NotificationIconPrefabSystem.cs:66-86`), so **the icon index is a per-session ordering rather than a stable id** and must not be persisted.

**Verdict: the wiki's notification page is a partial, unstamped hand-transcription and its own tier list is self-hedged.** `https://cs2.paradoxwikis.com/Notifications` carries **81** detail rows, not the "90+" the ticket assumed, against 160 icon prefabs live — and its rows are entirely simulation warnings and placement errors, with no markers. It carries **no `{{Version}}` stamp at all** and so is absent from `Category:Potentially outdated` for the wrong reason. Its seven-tier list is transcribed from `IconPriority` and its own footnote admits *"Unclear if error & fatal problem exist in-game or are developer only or the assessed notification types are wrong"* — the decompile settles it: all eight members exist, `Min` is spelled `Min` and not `Minimal`, and `FatalProblem` is used in the wild (`PlopTheGrowables/Code/Systems/SelectiveZoneCheckSystem.cs:378`). Its `Leveled up` row is typed `Problem`, which the live `Building Level Up` prefab contradicts — that icon is added at `IconPriority.Info` on the `Transaction` cluster layer (`src/Game/Game.Simulation/BuildingUpkeepSystem.cs:757`). Its `Poor electricity flow` and `Not enough electricity` rows carry identical description text. **The page is a lead generator for vocabulary and nothing else.**

### Removing a notification means removing it twice, and the corpus has the worked example

An icon exists in two places: as an entry in the owner's `IconElement` buffer, and as a standalone entity carrying `Owner + Icon + PrefabRef`. `Water Features` reverses both after disabling a vanilla system: it locates the prefab by `new PrefabID(nameof(NotificationIconPrefab), "Water Damage")` through `PrefabSystem.TryGetPrefab`/`TryGetEntity` with an `is not NotificationIconPrefab` guard (`Water_Features/Water_Features/Systems/RemoveFloodedSystem.cs:32`, `:58-64`), removes the whole `IconElement` buffer when the target is its only element and otherwise rebuilds it minus the matching entries (`:80-101`), and separately deletes every entity matching `WithAll<Owner, Icon, PrefabRef>()` whose `PrefabRef.m_Prefab` is that icon (`:47-50`, `:107-122`). **Disabling the system that raised a notification does not clear the notifications it already raised** — that is the general lesson and it generalises past icons.

Proposed amendment to entry 10, after the `Map Creation:` sentence: *An unflagged page is not a current one. `Category:Potentially outdated` is populated by the `{{Version}}` template, so a page that never claimed a version is absent from the category for the wrong reason — `Notifications`, `Development Tree` and `Achievements` are all unstamped and all unverified. Read the stamp, not the category.*

Second amendment, same entry: the entry's MediaWiki-API paragraph should note that **titles differ by the case of the second word**, since `Development Points`, `Development Tree`, `Expansion Permits` and `Map Tiles` exist while `Development points`, `Development tree`, `Expansion permits` and `Map tiles` all report `missing`. Four wasted fetches on one topic.

No gap found in entries 1, 4, 8 or 11, all four of which this pass leaned on heavily. Neither entry 4 nor the method file says that, and it is the cheapest cross-check on a swept prefab roster this pipeline has found. Entry 8's `ecs_query` guidance held: the prefab families in this topic (`MilestoneData`, `PolicyData`, `DevTreeNodeData`, `NotificationIconData`, `StatisticsData`, `UnlockRequirementData`, `MapTileData`) all enumerate directly with `PrefabSystem.GetPrefabName` as the label. Its note that **no established route builds an `EntityQuery` inside `eval`** was confirmed the hard way: `em.CreateEntityQuery(ComponentType, ComponentType)` fails overload matching because `params` expansion is unsupported, and the message names the pointer overload. `ecs_query` is the substitute and it takes the component list directly.

## Bridge

**`prefabs-and-assets`** is the technique this whole topic is built on and a mechanics reference here bridges rather than restates it. Everything in this file is prefab data: `MilestoneData` from `MilestonePrefab.Initialize`, `DevTreeNodeData` and the `DevTreeNodeRequirement` buffer from `DevTreeNodePrefab.LateInitialize`, the four modifier buffers from the six `Policies/` `ComponentBase` classes, `NotificationIconData`'s archetype from `NotificationIconPrefab.RefreshArchetype`, `StatisticsData` from `StatisticsPrefab.LateInitialize`. The specific mechanisms this topic needs from there are: **`Initialize` versus `LateInitialize`**, because every requirement prefab writes its self-referencing `UnlockRequirement` in `LateInitialize` and every one of them resolves another prefab's entity through `PrefabSystem.GetEntity` while doing it; **`GetPrefabComponents` versus `GetArchetypeComponents`**, which is the whole distinction between `StatisticsData` (on the prefab) and `CityStatistic` (on the instance), and between `NotificationIconData` (prefab) and `Icon` (instance); and **`PrefabSystem.GetPrefab<T>(entity)`**, which is how `DevTreeSystem` and `MilestoneUISystem` reach the managed prefab for telemetry and layout. **The one thing this topic adds that `prefabs-and-assets` does not carry is `PrefabSystem.IsUnlockable`** and its transitive, cached dependency walk (`src/Game/Game.Prefabs/PrefabSystem.cs:522-599`), because it decides at add time whether a prefab gets `Locked` and `UnlockRequirement` at all — and a mod that asks for the buffer on a prefab that never qualified gets an exception rather than a warning.

**`ecs-in-this-game`** owns the read shapes and this topic uses four of them, three of which are not `GetSingleton<T>`. The city's state is `GetComponentData<T>(citySystem.City)` / `GetBuffer<T>(citySystem.City)` on an entity whose index is serialized and moves. A statistic is a `BufferLookup<CityStatistic>` indexed through a `NativeParallelHashMap` the owning system hands out. Two systems publish a queue plus a `JobHandle` and expect a writer registration back — `XPSystem.GetQueue`/`AddQueueWriter` and `CityStatisticsSystem.GetStatisticsEventQueue`/`AddWriter` — the same asymmetric protocol `environment-and-pollution` found on `CellMapSystem<T>`, and `IconCommandSystem.CreateCommandBuffer`/`AddCommandBufferWriter` is a third instance with a per-frame lifetime the other two do not have. **The enableable-component half is where this topic bites hardest**: `Locked`, `NotificationIconDisplayData` and `Simulate` are all enableable, `HasComponent` is the wrong read for all three, and an `EntityQuery` naming one of them silently drops the disabled entities — which is the mechanism behind both the 160-versus-159 icon count above and the reason a query for locked prefabs cannot find the unlocked ones.

**`save-serialization`** is bridged by seventeen types in this topic, and by six version gates a mod will hit. `MilestoneLevel`, `XP`, `DevTreePoints`, `PlayerMoney`, `Population`, `Tourism`, `City`, `CityStatistic`, `StatisticsEvent`, `CityModifier`, `DistrictModifier`, `Policy`, `ServiceFee`, `SpecializationBonus`, `MapFeatureElement`, `Icon` and `Animation` all implement `ISerializable`, and three of them implement `IDefaultSerializable` with a `SetDefaults` that is not all-zero (`Population.m_AverageHappiness = 50`, `m_AverageHealth = 50`). Two systems implement `IPostDeserialize` and build state that exists nowhere else: `CitySystem.PostDeserialize` creates the city entity on a new game, and `MapTileSystem.PostDeserialize` chooses between the editor-authored start tiles and the legacy 23×23 generation on a `Version.editorMapTiles` test. **The widening migrations are the shipped detail**: `CityStatistic` read `int`, then `long`, then `double` across `Version.statisticOverflowFix` and `Version.statisticPrecisionFix`; `CityModifier`/`DistrictModifier` read only the relative channel below `Version.modifierRefactoring`; `XP` gained `m_MaximumPopulation`/`m_MaximumIncome` at `Version.xpMaximumStats` and `m_XPRewardRecord` at `Version.xpRewardRecord`; `Icon` gained its cluster layer and flags at `Version.iconClusteringData`. `MapTileSystem` and `TaxSystem` serialize themselves rather than components, which is that reference's system-state case.

**`binding-layer`** owns the six binding groups enumerated above and the `GetterValueBinding` / `RawValueBinding` / `RawMapBinding<Entity>` / `TriggerBinding<T…>` shapes they use; this topic's contribution is which groups exist and which values each carries. Two crossings matter beyond the list. `PrefabUtils.HasUnlockedPrefab<T>(EntityManager, unlockQuery)` is the standard "did anything of this kind unlock this frame" test and both `PoliciesUISystem` (`PoliciesUISystem.cs:175`) and a corpus fork use it, paired with `EntityManager.GetComponentOrderVersion<UnlockRequirementData>()` as the second half (`Time2Work/NightShift/Systems/Time2WorkStatisticsUISystem.cs:70`, `:332-339`). And `PrefabUISystem.BindPrefabRequirements` is the supported way to write a prefab's unlock requirements into a binding without walking the graph.

**`frontend-and-injection`** is the bridge for changing what the progression panels *show*, since `ProgressionPanel`, `StatisticsPanel`, `NotificationsPanel`, `CityInfoPanel` and `UIPolicy`/`UIPolicySlider` are the C# halves of React components a UI mod replaces. The corpus's one worked case is a wholesale fork — `StatisticsUISystem.Enabled = false` plus a replacement registered on the same `"statistics"` group (`Time2Work/NightShift/Mod.cs:106`, `:153`) — which is the expensive route that reference exists to make unnecessary.

**`city-services-and-coverage`** is joined at two seams. `ServicePrefab` / `ServiceData` is the object a dev-tree node gates (`DevTreeNodeData.m_Service`), so **which buildings a service offers is that topic's and whether the service is reachable at all is this one's**; `CityService` is the shared enum and this file's copy is the declared one. The second seam is the notification family: every service failure a building can report is an icon prefab named on a configuration prefab in the 66-field table above, and that topic owns what each failure *means* while this one owns how it is raised, cleared, prioritised and clustered. `CityUtils.GetCityServiceWorkplaceMaxWorkers` (`src/Game/Game.City/CityUtils.cs:41-78`) sits in `Game.City` and belongs to that topic: it folds installed upgrades' `m_MinimumWorkersLimit` and `m_MaxWorkers` together and then, for a school, lerps the result against `SchoolData.m_StudentCapacity`.

**`economy-and-companies`** owns everything a milestone *pays into*. `PlayerMoney` (`const int kMaxMoney = 2000000000`, clamped both ways, and `money` returning the cap unconditionally when `m_Unlimited`), `Creditworthiness`, `Loan`, `ServiceFee`, `TaxRate`/`TaxSystem`, `TradeCost` and `SpecializationBonus` all live on the city entity and are read there, but their behaviour is that topic's. The crossing this topic must state is the direction of causation: **a milestone writes `PlayerMoney` and `Creditworthiness` directly and outside a command buffer** (`MilestoneSystem.cs:103-108`), and `Creditworthiness.m_Amount` is a running sum of every unlocked milestone's `m_LoanLimit` rather than a per-milestone cap — read live at 26,100,000 on a max-milestone city, which is the sum of all twenty increments. Six `CityModifierType` members are that topic's levers (`ImportCost`, `ExportCost`, `LoanInterest`, `BuildingLevelingCost`, `CityServiceImportCost`, `CityServiceBuildingBaseUpkeepCost`) and `ProcessingRequirementData` gates unlocks on cumulative production, which is its output.

**`citizens-and-households`** owns `Population` and `Tourism`'s contents; this topic owns that they sit on the city entity and that `CountHouseholdDataSystem` is what writes them and, in the same system, what evaluates `CitizenRequirementData`. The two-phase progress value in that evaluator (population, then happiness) is the crossing point.

**`localization`** owns the key grammar and the namespace table; this topic supplies four families that sit inside it and that a reference here names rather than restates: `Progression.*` (320 keys, the requirement-label vocabulary and the indexed `MILESTONE_NAME:N` / `MILESTONE_DESCRIPTION:N` families), `Policy.TITLE[…]` / `Policy.DESCRIPTION[…]`, `Notifications.DESCRIPTION[…]`, and `MapTilePurchase.*`. The crossing that matters beyond the list is **`UnlockRequirementPrefab.m_LabelID`, which is a localization key rather than a display string**, resolved by the frontend from the `labelId` property `PrefabUISystem` writes — so a mod adding a requirement kind ships a locale entry, not a label. `method-decoding-shipped-locale-data.md` is the recipe that produced every count above and the copyright boundary that keeps the strings out.

**`simulation-time-and-units`** owns what `kUpdatesPerDay = 32` means in real time, which is what makes `StatisticCollectionType.Daily`'s 32-sample window a day and `GetSampleFrameIndex`'s `* 8192` a date. It is also where the duplicated `updatesPerDay` literal in the statistics binding belongs as a trap.

**`diagnostics`** is the bridge for two log lines a modder will see and misread: `"Warning: did not find data for milestone N"` from `MilestoneSystem` when a milestone index has no prefab, and `"Prefab unlocked: {0}"` / `"Prefab locked: {0}"` from the `"Unlocking"` logger (`src/Game/Game.Prefabs/UnlockSystem.cs:118`, `:217`, `:222`; `PrefabSystem.cs:141`), which is the cheapest way to watch an unlock cascade. `"Could not find victory milestone."` and `"Population goal is not set for platform …"` go to the `"Platforms"` logger and only ever appear on a console build.

**`debug-menu`** is where `UnlockAllSystem`, `MilestoneSystem.UnlockAllMilestones`, `MapTilePurchaseSystem.UnlockMapTiles` and `DebugSystem`'s two XP grants are reachable from, and it is the reason a research read of a live save has to check `CityConfigurationSystem.unlockAll` before believing a milestone level.
