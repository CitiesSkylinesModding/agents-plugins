**Ruled (2026-08-06, the citizens-and-households pass; conflicts.md), governing every finding in this file.** A shipped reference states **no prefab value**. It names the component and the field, with the access shape, and that is the whole of what it says about the magnitude. Three things are untouched and are the spine of the topic: **C# constants ship, as numbers** — a `const` or `static readonly` the consuming code compiled in, offline-checkable and citable to a line; **formulas ship whole** — the expression a system evaluates, its baseline, its step functions and the shape of its randomisation are invariant structure rather than balance; and **the component-to-number-family map ships whole**, because an agent cannot perform the read without it, and it carries the access shape beside each component since a reader cannot write the call from a field name. Two consequences bind this topic hard: **a derived ratio is a magnitude wearing a mechanism's clothes** (where the ratio is the point, the reference states the direction and names the field), and **an adverb carrying the same magnitude counts** — "far more", "roughly twice", "an order of magnitude" are the ratio in prose. A non-numeric prefab value is still a prefab value. This file records the live numbers freely; the reference will not. The bite here is total: every per-mode figure a reader would want — vehicle capacity, vehicle speed, default headway, stop duration, maintenance range, depot vehicle capacity, cargo capacity, outside-connection storage limit — is a prefab value on a `*Data` component, and none of them ships.

## Findings

### A route is four entity kinds, and only two of them are things the player sees

`RouteType` is a two-member closed enum plus sentinels — `None = -1`, `TransportLine`, `WorkRoute`, `Count` (`src/Game/Game.Routes/RouteType.cs:3-9`). Every route in the game is one of those two, and the second is the resource-extraction work route rather than transit.

The four entity kinds are declared as four archetypes on one prefab component. `RoutePrefab.LateInitialize` builds `RouteData { m_RouteArchetype, m_WaypointArchetype, m_ConnectedArchetype, m_SegmentArchetype }` by running every attached `ComponentBase.GetArchetypeComponents` four times, once with a seed set containing `Route`, once with `Waypoint`, once with `Waypoint + Connected`, once with `Segment` (`src/Game/Game.Prefabs/RoutePrefab.cs:54-89`, the component at `src/Game/Game.Prefabs/RouteData.cs:8-27`). **That four-way seed switch is the whole mechanism by which one prefab describes four different entity archetypes**, and it is why `TransportLinePrefab.GetArchetypeComponents` reads as a chain of `components.Contains(...)` tests rather than as a list (`src/Game/Game.Prefabs/TransportLinePrefab.cs:60-99`).

- **The route** carries `Route { m_Flags, m_OptionMask }` (`src/Game/Game.Routes/Route.cs:6-11`), where `RouteFlags` has exactly one member, `Complete = 1` (`src/Game/Game.Routes/RouteFlags.cs:6-9`). Plus the `RouteWaypoint` and `RouteSegment` buffers, `Game.Routes.Color`, and `RouteBufferIndex` (`RoutePrefab.cs:35-41`).
- **The waypoint** is a numbered node on the line: `Waypoint { m_Index }` (`src/Game/Game.Routes/Waypoint.cs:6-9`) plus `Position { m_Position }` and `Owner` (`RoutePrefab.cs:42-46`). A waypoint that sits at a stop also carries `Connected { m_Connected }` naming the stop object (`src/Game/Game.Routes/Connected.cs:6-9`) — that is the fourth archetype, and it is what `m_ConnectedArchetype` exists for.
- **The segment** is the stretch between waypoint *i* and waypoint *i+1*: `Segment { m_Index }` (`src/Game/Game.Routes/Segment.cs:6-9`), a `CurveElement` buffer of `Bezier4x3` (`src/Game/Game.Routes/CurveElement.cs:7-11`) and `Owner`. A transport-line segment additionally carries `PathTargets`, `RouteInfo`, and its own `PathElement` buffer and `PathInformation` (`TransportLinePrefab.cs:92-98`) — **each segment of a transit line is its own pathfinding request**.
- **The stop** is not a route entity at all. It is an ordinary world object carrying `Game.Routes.TransportStop`, and it is reached from the waypoint through `Connected`, and back through the stop's own `ConnectedRoute` buffer (`src/Game/Game.Routes/ConnectedRoute.cs:8-11`, holding `m_Waypoint`). `WaypointConnectionSystem` maintains both directions (`src/Game/Game.Routes/WaypointConnectionSystem.cs:78-131`) and snaps a waypoint to a stop within `maxDistance = 10f` (`:607`).

The line's own buffers: `RouteWaypoint { m_Waypoint }` and `RouteSegment { m_Segment }`, both `[InternalBufferCapacity(0)]` and both `IEmptySerializable` — **rebuilt on load rather than saved** (`src/Game/Game.Routes/RouteWaypoint.cs:6-10`, `src/Game/Game.Routes/RouteSegment.cs:6-10`). `SubRoute { m_Route }` (`src/Game/Game.Routes/SubRoute.cs:8-11`) is how a building owns routes. `HiddenRoute` is a tag added to a route no segment of which resolved a path (`src/Game/Game.Routes/HiddenRoute.cs:7-11`, added at `src/Game/Game.Routes/RoutePathReadySystem.cs:193` and removed at `:197`).

`Rots:` every component and field name in this file. Re-check against `src/Game/Game.Routes/`, `src/Game/Game.Vehicles/`, `src/Game/Game.Prefabs/`, `src/Game/Game.Simulation/`, `src/Game/Game.Buildings/`, `src/Game/Game.Companies/` and `src/Game/Game.Pathfind/`, at the files cited beside each claim.

### The stop is the world object and the waypoint is the line's node at it, and they carry different halves of the state

**On the stop object** (`TransportStop.GetArchetypeComponents`, `src/Game/Game.Prefabs/TransportStop.cs:50-122`): `Game.Routes.TransportStop { m_AccessRestriction, m_ComfortFactor, m_LoadingFactor, m_Flags }` (`src/Game/Game.Routes/TransportStop.cs:6-15`), `Game.Objects.Color`, the `ConnectedRoute` buffer, `BoardingVehicle { m_Vehicle, m_Testing }` (`src/Game/Game.Routes/BoardingVehicle.cs:6-11`), and one per-mode tag — `BusStop`, `TramStop`, `TrainStop`, `SubwayStop`, `ShipStop`, `FerryStop`, `AirplaneStop`, all zero-size `IEmptySerializable` structs (`src/Game/Game.Routes/BusStop.cs` and siblings). `StopFlags` has two members, `Active = 1` and `AllowEnter = 2` (`src/Game/Game.Routes/StopFlags.cs:6-10`).

**On the waypoint** (`TransportLinePrefab.cs:73-91`): `AccessLane { m_Lane, m_CurvePos }` when the prefab declares an access connection (`src/Game/Game.Routes/AccessLane.cs:7-12`), `RouteLane { m_StartLane, m_EndLane, m_StartCurvePos, m_EndCurvePos }` when it declares a route connection (`src/Game/Game.Routes/RouteLane.cs:7-16`), `VehicleTiming { m_LastDepartureFrame, m_AverageTravelTime }` when it is a `Connected` waypoint (`src/Game/Game.Routes/VehicleTiming.cs:6-11`), and **`WaitingPassengers` when and only when the line prefab's `m_PassengerTransport` is true** (`TransportLinePrefab.cs:87-90`).

So: **`WaitingPassengers` lives on the waypoint, never on the stop.** Read live at 1.6.0f1, a placed `NA Bus Stop Shelter` carries `TransportStop`, `BoardingVehicle`, `ConnectedRoute`, the `BusStop` tag, `Attached { m_Parent = <road edge> }` and `SpawnLocation`, and carries no `WaitingPassengers` at all. A reader who queries the stop for a passenger count gets nothing; the count is per line, on that line's waypoint at that stop, which is also why two lines sharing a stop have two independent queues.

**The taxi stand is the exception that proves the split.** `TransportType.Taxi` is the one case in `TransportStop.GetArchetypeComponents` that puts the *waypoint's* components onto the stop object: `AccessLane`, `RouteLane`, `WaitingPassengers`, plus `RouteVehicle`, `TaxiStand` and `DispatchedRequest` (`TransportStop.cs:66-83`). A taxi stand is a stop with no line behind it, so it has to carry the line's half itself.

### Instance state on a stop is derived every tick, and the prefab value is only the seed

`TransportStopSystem` (registered at `SystemUpdatePhase.GameSimulation`, `src/Game/Game.Common/SystemOrder.cs:593`, `GetUpdateInterval` returns 256 at `src/Game/Game.Simulation/TransportStopSystem.cs:194-197`) recomputes three fields of every `Game.Routes.TransportStop` from the prefab and from the owning station:

```
comfort = saturate(TransportStopData.m_ComfortFactor)
loading = max(0, 1 + TransportStopData.m_LoadingFactor)
if a TransportStation owns the stop:
    comfort = saturate(comfort + (1 - comfort) * station.m_ComfortFactor)
    loading = max(0, loading * station.m_LoadingFactor)
    active  = station has TransportStationFlags.TransportStopsActive
else
    active  = true
```
(`src/Game/Game.Simulation/TransportStopSystem.cs:69-79`, `:85-107`; the station walk at `:112-135`, which takes the first `Owner` carrying a station and steps exactly one hop further when that station's own owner is also one — one extra hop, not a continued climb; corrected 2026-08-16, the mechanical pass.)

**Comfort composes as a diminishing blend and loading composes as a product** — that shape is the mechanism and it ships; the magnitudes do not. When any of the three changes, the system stamps `Game.Common.PathfindUpdated` on the taxi stand itself and on **every waypoint in the stop's `ConnectedRoute` buffer** (`:88-98`), which is the cheap re-derivation trigger `roads-and-traffic` records for lanes, used here for transit edges.

Live at 1.6.0f1 the shape is visible in one read: `Integrated Cargo Ship Stop`'s prefab `TransportStopData.m_LoadingFactor` is `0` while the placed instance's `TransportStop.m_LoadingFactor` is `1.5199962` and its flags are `Active | AllowEnter` — the instance value is derived, not copied. A reader who reads `TransportStopData` expecting the operative number has read the seed.

The station half comes from `TransportStationAISystem` (`SystemOrder.cs:521`, interval 256 at `src/Game/Game.Simulation/TransportStationAISystem.cs:171-174`):

```
station.m_ComfortFactor = saturate(prefab.m_ComfortFactor * efficiency)
station.m_LoadingFactor = max(0, (1 + prefab.m_LoadingFactor) * efficiency)
efficiency > 0 ? copy the four refuel masks and set TransportStopsActive
               : zero the four masks and clear it
```
(`src/Game/Game.Simulation/TransportStationAISystem.cs:82-100`), with the prefab data first combined over installed upgrades through `UpgradeUtils.CombineStats` (`:71-74`).

**Then one more gate, and it is a trap.** A station that is active *and* offers any refuelling has `TransportStopsActive` **cleared again when `BuildingUtils.GetNumberOfConnectedLines` returns zero** (`:101-110`). So a refuelling station with no line through it deactivates its own stops. Stated flat: connect a line before expecting a station's stops to work.

### The per-mode mechanism table, and the query that reproduces it

The C# mechanism beside it ships flat, as it always did. A prefab name appears only as a cited worked example, at most one per claim. ### What distinguishes passenger from cargo, mechanically — three switches and nothing else

**One: `m_AccessConnectionType`.** A passenger line declares `RouteConnectionType.Pedestrian`, a cargo route declares `RouteConnectionType.Cargo` (the table above; `TransportLinePrefab.cs:15`). That decides how the payload reaches the stop, and it decides the archetype: the access lane is a pedestrian lane on one and a cargo lane on the other.

**Two: the `m_PassengerTransport` / `m_CargoTransport` boolean pair**, carried identically on `TransportLineData` (`src/Game/Game.Prefabs/TransportLineData.cs:21-23`) and on `TransportStopData` (`src/Game/Game.Prefabs/TransportStopData.cs:18-20`). They do exactly four things (the fourth added 2026-08-16, the review gate):

- `m_PassengerTransport` on the line prefab is what adds `WaitingPassengers` to the waypoint archetype (`TransportLinePrefab.cs:87-90`).
- In `PathUtils.GetTransportStopSpecification`, `m_PassengerTransport` adds `PathMethod.PublicTransportDay | PathMethod.PublicTransportNight` to the stop edge and `m_CargoTransport` adds `PathMethod.CargoTransport` (`src/Game/Game.Pathfind/PathUtils.cs:1552-1559`). The same pair does the same on the line edge in `GetTransportLineSpecification` (`:1786-1799`).
- In `TransportLineSystem.RefreshLineSegments`, `m_PassengerTransport` feeds the line's speed into the passenger slot of `m_MaxTransportSpeed` and `m_CargoTransport` into the cargo slot (`src/Game/Game.Simulation/TransportLineSystem.cs:498-527`).
- `Game.Routes.InitializeSystem` turns the pair into the `PublicTransportPurpose`, cargo `Resource` and passenger/cargo capacity ranges that `TransportVehicleSelectData.SelectVehicle` picks the line's `VehicleModel` from (`src/Game/Game.Routes/InitializeSystem.cs:144-149`) — so flipping the pair also changes which vehicle prefab the line gets.

**Three: which payload component the vehicle carries.** A passenger vehicle prefab has `PublicTransport` and gets `Game.Vehicles.PublicTransport`, a `Passenger` buffer and an `Odometer` (`src/Game/Game.Prefabs/PublicTransport.cs:47-57`); a cargo vehicle prefab has `CargoTransport` and gets `Game.Vehicles.CargoTransport`, an `Economy.Resources` buffer, a `LoadingResources` buffer and an `Odometer` (`src/Game/Game.Prefabs/CargoTransport.cs:28-39`). **Both add `PathInformation` and `ServiceDispatch` under the same condition** — the prefab is `Moving` and is either not a `Controller` or is a `LayoutElement` — which is the multi-unit train case (`PublicTransport.cs:52-56`, `CargoTransport.cs:34-38`).

**The two vehicle state components are near-twins and that is the point.** `PublicTransport { m_TargetRequest, m_State, m_DepartureFrame, m_RequestCount, m_PathElementTime, m_MaxBoardingDistance, m_MinWaitingDistance }` (`src/Game/Game.Vehicles/PublicTransport.cs:8-20`) against `CargoTransport { m_TargetRequest, m_State, m_DepartureFrame, m_RequestCount, m_PathElementTime }` (`src/Game/Game.Vehicles/CargoTransport.cs:8-16`) — the cargo one lacks only the two boarding-distance fields, which exist so a passenger can be refused at a door too far away. **Their flag enums share twelve members and `PublicTransportFlags` adds exactly six** — `Launched`, `Evacuating`, `PrisonerTransport`, `StopLeft`, `StopRight`, `Full` — every one of which is about carrying people. The bit values of the shared members line up only through `Arriving` — `Returning = 1`, `EnRoute = 2`, `Boarding = 4`, `Arriving = 8` on both — and diverge from `RequiresMaintenance` on (`0x80` against `0x10` — a 3-bit offset that holds through `DummyTraffic`, widening to 5 bits at `Disabled` once `StopLeft` and `StopRight` are inserted ahead of it; `Full`, `StopLeft` and `StopRight` have no cargo counterpart), so a mod that casts one enum to the other silently reads the wrong flag (corrected 2026-08-16, the mechanical pass: the original said all twelve diverge; the offset shape corrected 2026-08-16, the review gate). Full sets:

- `PublicTransportFlags` (`uint`, eighteen members): `Returning`, `EnRoute`, `Boarding`, `Arriving`, `Launched`, `Evacuating`, `PrisonerTransport`, `RequiresMaintenance`, `Refueling`, `AbandonRoute`, `RouteSource`, `Testing`, `RequireStop`, `DummyTraffic`, `StopLeft`, `StopRight`, `Disabled`, `Full` (`src/Game/Game.Vehicles/PublicTransportFlags.cs:8-25`).
- `CargoTransportFlags` (`uint`, twelve members): `Returning`, `EnRoute`, `Boarding`, `Arriving`, `RequiresMaintenance`, `Refueling`, `AbandonRoute`, `RouteSource`, `Testing`, `RequireStop`, `DummyTraffic`, `Disabled` (`src/Game/Game.Vehicles/CargoTransportFlags.cs:8-19`).

Almost every consumer tests both, defaulting the absent one to zero — `TransportLineSystem.CheckVehicles` is the canonical shape (`TransportLineSystem.cs:281-305`). **A mod that handles only one of the two has silently dropped half the fleet.**

`Game.Vehicles.PassengerTransport` is a bare tag with no fields (`src/Game/Game.Vehicles/PassengerTransport.cs:7-11`); it marks the vehicle and carries nothing.

### A line's own state, its options and its policies

`TransportLine { m_VehicleRequest, m_VehicleInterval, m_UnbunchingFactor, m_Flags, m_TicketPrice }` sits on the route entity (`src/Game/Game.Routes/TransportLine.cs:7-18`). Note the field initializers: `m_VehicleInterval` and `m_UnbunchingFactor` are seeded from `TransportLineData`'s defaults through the primary constructor (`:11-13`) — this is a plain `IComponentData` rather than a `ScriptableObject`, so those are ordinary C# defaults rather than the serialized kind the ruling below covers. `TransportLineFlags` has two members, `RequireVehicles = 1` and `NotEnoughVehicles = 2` (`src/Game/Game.Routes/TransportLineFlags.cs:8-9`).

**Line options are a bitmask over a four-member enum**, and the enum is the whole player-facing option set: `RouteOption` = `Day`, `Night`, `Inactive`, `PaidTicket` (`src/Game/Game.Routes/RouteOption.cs:3-9`), read through `RouteUtils.CheckOption(route, option) => (route.m_OptionMask & (1 << (int)option)) != 0` (`src/Game/Game.Routes/RouteUtils.cs:542-545`). `Route.m_OptionMask` is only deserialized from `Version.routePolicies` onward (`Route.cs:24-28`), so it is a comparatively recent addition.

**Options arrive as policies.** `RouteOptions : ComponentBase` sits on a `PolicyPrefab` and ORs its authored `RouteOption[]` into `RouteOptionData.m_OptionMask` (`src/Game/Game.Prefabs/RouteOptions.cs:9-34`, the component at `src/Game/Game.Prefabs/RouteOptionData.cs:5-8`). So **a line option is a policy applied to the route entity**, which is why `TransportLinePrefab` puts `Game.Policies.Policy` on the route archetype (`TransportLinePrefab.cs:71`). A reader looking for "where the day/night toggle lives" finds a policy prefab, not a field.

**Numeric line adjustments are modifiers, and there are exactly two.** `RouteModifierType` = `TicketPrice`, `VehicleInterval` (`src/Game/Game.Routes/RouteModifierType.cs:3-7`), carried as a `RouteModifier { m_Delta }` buffer indexed **by enum value** (`src/Game/Game.Routes/RouteModifier.cs:7-11`) and applied by

```
ApplyModifier(ref value, modifiers, type):
    if (modifiers.Length > (int)type):
        value += modifiers[(int)type].m_Delta.x
        value += value * modifiers[(int)type].m_Delta.y
```
(`RouteUtils.cs:552-560`, body at `:554-559`) — an additive term then a multiplicative one, the ordinary `ModifierValueMode` shape. The authoring side is `RouteModifiers : ComponentBase` on a policy prefab, filling a `RouteModifierData { m_Type, m_Mode, m_Range }` buffer (`src/Game/Game.Prefabs/RouteModifiers.cs:8-33`, `src/Game/Game.Prefabs/RouteModifierData.cs:8-15`). **The buffer is positional: index 0 is ticket price and index 1 is vehicle interval, and the length test is what makes a short buffer mean "no modifier" rather than an out-of-range read.**

**Day and night are a time-of-day window, and its two bounds appear as literals at three sites.** `TransportLineSystem.OnUpdate` computes `isNight = normalizedTime < 0.25f || normalizedTime >= 11f / 12f` (`TransportLineSystem.cs:824`) and `RouteUtils.GetPublicTransportMethods` computes the complement, returning `PathMethod.PublicTransportDay` inside `[0.25, 11/12)` and `PathMethod.PublicTransportNight` outside it, after offsetting the query time by a `predictionOffset` defaulting to `1f/48f` (`RouteUtils.cs:571-579` and the resident overload at `:581-593`). The window's two ends and the prediction offset are `RouteUtils.TRANSPORT_DAY_START_TIME`, `TRANSPORT_DAY_END_TIME` and `DEFAULT_TRAVEL_TIME` — see the const-inlining finding below for why the decompile shows literals rather than the names.

The activity decision is a `bool3` — is the line running now, does it run by day, does it run by night:

```
inactive option set                       -> false
no active building on the line            -> false
Day option set                            -> (not isNight, true, false)
Night option set                          -> (isNight, false, true)
otherwise                                 -> true
```
(`TransportLineSystem.cs:187`). The `.yz` become `RouteInfoFlags.InactiveDay` / `InactiveNight` on every segment (`:428-436`, the enum at `src/Game/Game.Routes/RouteInfoFlags.cs:3-7`), and `GetTransportLineSpecification` turns those into the presence or absence of the two `PublicTransport*` path methods on the line edge (`PathUtils.cs:1786-1795`). **So a day-only line is not switched off at night: it loses the night path method, and a citizen planning a night trip simply cannot route over it.**

**"No active building on the line" is a real gate and it is easy to miss.** `CheckIfIsThereAnyActiveBuildingsOnTheLine` walks every waypoint's `Connected` stop up its `Owner` chain to the top owner and asks whether any of them is a `Building` without `BuildingOption.Inactive`; it returns true when *no* waypoint resolves to a building at all, and false when they all resolve to inactive ones (`TransportLineSystem.cs:562-586`). A line whose every station the player has switched off stops running.

### Vehicle count comes out of two public static formulas, and the reference can ship both

`TransportLineSystem` runs in `SystemUpdatePhase.GameSimulation` (`src/Game/Game.Common/SystemOrder.cs:587`), `GetUpdateInterval` returns `256` (`TransportLineSystem.cs:790-793`) and the class also declares `public const uint UPDATE_INTERVAL = 256u` (`:772`) — the same unreferenced-constant-beside-a-literal shape `roads-and-traffic` records for `RoadSafetySystem`, and the const-inlining finding below is why that reads the way it does.

Two `public static` methods on the system are the whole of the fleet-sizing model, and they are formulas under the ruling — they ship whole:

```
CalculateVehicleCount(vehicleInterval, lineDuration) = max(1, round(lineDuration / max(1, vehicleInterval)))
CalculateVehicleInterval(lineDuration, vehicleCount) = lineDuration / max(1, vehicleCount)
```
(`TransportLineSystem.cs:906-914`.)

Per tick, per line (`:177-247`):

1. `interval = TransportLineData.m_DefaultVehicleInterval`, then `ApplyModifier(..., VehicleInterval)` (`:178-179`).
2. `ticketPrice = clamp(round(ApplyModifier(0, ..., TicketPrice)), 0, 65535)` **only when the `PaidTicket` option is set** (`:181-186`) — with the option off the price is forced to zero regardless of the modifier.
3. `RefreshLineSegments` produces `lineDuration` and `stableDuration` (`:188`).
4. `targetCount = CalculateVehicleCount(interval, stableDuration)` (`:189`).
5. `m_VehicleInterval = min(interval * 10, CalculateVehicleInterval(lineDuration, targetCount))` (`:190`) — **the operative headway is capped at ten times the requested one**, which is what stops a broken or enormously long line reporting an absurd interval.
6. When the interval moved by at least 1, or the ticket price changed at all, stamp `PathfindUpdated` on every waypoint that has `VehicleTiming` (the `abs(new - old) >= 1f` threshold at `:192`, the stamp at `:202-205`, `:254-264`).
7. `targetCount` is forced to `0` when the line is not currently active (`:207`).

**The two durations differ and the difference is the mechanism.** `stableDuration` sums each segment's raw `PathInformation.m_Duration` plus `TransportLineData.m_StopDuration` per stop — planned time, congestion-blind. `lineDuration` sums, per stop, `max(segment durations since the last stop, VehicleTiming.m_AverageTravelTime) + GetStopDuration(...)` — **measured time, floored by the plan** (`TransportLineSystem.cs:446-470`). So the fleet is sized on the plan and the reported headway is computed from what the vehicles actually achieved.

`GetStopDuration(lineData, stop) = lineData.m_StopDuration / max(0.25f, stop.m_LoadingFactor)` (`RouteUtils.cs:490-493`, body at `:492`) — **the `0.25` floor is a C# constant and it caps the dwell penalty at four times the base**, and because loading factor rises with the station's own loading factor, a better station shortens the stop.

Each segment's `RouteInfo` is rewritten in the same pass:

```
RouteInfo.m_Duration = PathInformation.m_Duration * max(1, timeSinceLastStop / max(1, plannedSinceLastStop))
RouteInfo.m_Distance = PathInformation.m_Distance
RouteInfo.m_Flags    = the InactiveDay/InactiveNight pair
```
and when any of the three moved by more than a rounding step, `PathfindUpdated` goes on the segment (`TransportLineSystem.cs:471-490`). **That scale factor is how measured congestion reaches the routing graph for transit** — the segment path itself was planned with flow ignored (see the routing finding below), and this multiplier is the correction.

`RouteInfo { m_Duration, m_Distance, m_Flags }` is `src/Game/Game.Routes/RouteInfo.cs:6-13`, and the flags half only deserializes from `Version.transportLinePolicies` (`:30-34`).

### Requesting, abandoning and unbunching vehicles

`CheckVehicles` walks the `RouteVehicle` buffer, drops any entry whose vehicle no longer has `CurrentRoute { m_Route }` pointing back at this line (`src/Game/Game.Routes/CurrentRoute.cs:6-9`; the drop at `TransportLineSystem.cs:307-310`), and splits the rest into `totalCount` and `continuingCount` — the latter excluding anything already flagged `AbandonRoute` or whose prefab no longer matches the line's `VehicleModel` buffer (`:266-312`).

**`VehicleModel { m_PrimaryPrefab, m_SecondaryPrefab }`, `[InternalBufferCapacity(4)]`, is the per-line vehicle-model selection** (`src/Game/Game.Routes/VehicleModel.cs:6-12`). An empty buffer, or a buffer whose entries are all `Entity.Null`, means "any model"; `RouteUtils.CheckVehicleModel` returns true unless a non-null primary is declared and this prefab is not one of them, and correspondingly for secondaries (`RouteUtils.cs:595-651`). **Primary is the engine and secondary is the carriage**, and a multiple-unit train satisfies the secondary test by carrying `MultipleUnitTrainData` at all, while any other consist satisfies it when at least one `LayoutElement` car is a listed secondary — the walk stops at the first match (`:614-651`, the MU clear at `:622-624`, the car walk at `:634-648`; corrected 2026-08-16, the review gate).

**Fleet sizing acts by odometer.** When `continuingCount > targetCount`, `AbandonVehicles` sorts the eligible vehicles by `Odometer.m_Distance` and abandons the **highest-mileage** ones (`:314-360`, taking from the end of the sorted list at `:352`); when the count is short and abandoned vehicles exist, `CancelAbandon` un-abandons the **lowest-mileage** ones (`:362-408`). Both go through a `NativeQueue<VehicleAction>` drained by a single-threaded `VehicleActionJob` that ORs or clears `AbandonRoute` on whichever of the two payload components the vehicle has (`:604-652`).

**A missing vehicle becomes a request, and the request gives up after two failures.**

```
if totalCount < targetCount:
    set TransportLineFlags.RequireVehicles
    totalCount += DispatchedRequest.Length
    if still short: RequestNewVehicleIfNeeded(...)
```
(`:220-232`.) `RequestNewVehicleIfNeeded` returns the existing request's viability when one is outstanding — `serviceRequest.m_FailCount < 2` — and otherwise creates an entity of the archetype `{ ServiceRequest, TransportVehicleRequest, RequestGroup }` with `TransportVehicleRequest(route, 1 - vehicleCount/targetCount)` and `RequestGroup(8u)` (`:550-560`, archetype at `:803`). **The priority is the shortfall fraction**, so an empty line outbids a nearly-full one. `TransportVehicleRequest { m_Route, m_Priority }` is `src/Game/Game.Simulation/TransportVehicleRequest.cs:6-11`.

When the request has failed twice, `TransportLineFlags.NotEnoughVehicles` goes on and the line raises `TransportLineData.m_VehicleNotification` at `IconPriority.Problem`; the removal branch is a plain `else` (`:241-245`), so both are cleared on the next pass whenever the line is no longer blocked on a twice-failed request rather than on a vehicle's arrival, and the raise carries a `waypoints.Length != 0` guard (`:233`) (corrected 2026-08-16, the mechanical pass). `DispatchedRequest { m_VehicleRequest }` is the buffer of in-flight requests (`src/Game/Game.Routes/DispatchedRequest.cs:3-6`), pruned each tick of requests whose entity is gone (`:530-548`).

**Unbunching is one expression evaluated at each boarding.**

```
CalculateDepartureFrame(line, lineData, modifiers, targetStopTime, lastDepartureFrame, simulationFrame):
    elapsed  = (simulationFrame - lastDepartureFrame) / 60
    if elapsed < 0: return simulationFrame
    requested = ApplyModifier(lineData.m_DefaultVehicleInterval, modifiers, VehicleInterval)
    headway   = line.m_VehicleInterval
    wait      = min(requested, 2*headway*headway/(elapsed + headway) - headway) * line.m_UnbunchingFactor
    wait      = max(wait + targetStopTime, 1)
    return simulationFrame + (uint)(wait * 60)
```
(`RouteUtils.cs:495-510`, the wait term at `:504`.) **The whole of bunching control is that hyperbola**: a vehicle arriving early (small `elapsed`) is held for close to `headway * unbunchingFactor`, a vehicle arriving late (large `elapsed`) gets a term that goes negative and is floored to one second by the `max`. The `60` is the frames-per-second divisor this whole area uses to turn simulation frames into seconds — `simulation-time-and-units` owns what a frame is — and the `1` is the minimum dwell; both are C# literals and ship.

The departure frame is only computed this way for a vehicle flagged `EnRoute` on either payload component; a vehicle not yet `EnRoute` — the test is the flag, not a first boarding, both components defaulted to zero when absent — gets a flat `simulationFrame + 60`, and that arm leaves `VehicleTiming.m_LastDepartureFrame` unwritten, since the assignment is embedded in the ternary's other arm (`src/Game/Game.Simulation/TransportBoardingHelpers.cs:368-369`; corrected 2026-08-16, the mechanical pass).

`VehicleTiming.m_AverageTravelTime` is updated at the same moment: `UpdateAverageTravelTime(old, departureFrame, arrivalFrame)` returns `(arrival - departure)/60` on the first sample and `lerp(old, sample, 0.5f)` after — **a one-sample-half exponential average** (`RouteUtils.cs:476-488`), skipped entirely when `departureFrame == 0`.

### Depots and fleets: the vehicle-to-line assignment loop, end to end

Three systems, in registration order within `GameSimulation`: `TransportDepotAISystem` (`SystemOrder.cs:523`), `TransportVehicleDispatchSystem` (`:556`), `TransportLineSystem` (`:587`).

**The depot prefab declares seven things.** `TransportDepot : ComponentBase, IServiceUpgrade` carries `m_TransportType`, `m_EnergyTypes`, `m_SizeClass`, `m_VehicleCapacity`, `m_ProductionDuration`, `m_MaintenanceDuration`, `m_DispatchCenter` (`src/Game/Game.Prefabs/TransportDepot.cs:19-31`) and copies all seven into `TransportDepotData` (`:64-80`). Two things happen in that `Initialize` that a reader will not guess: **an `Undefined` size class is rewritten in C#** to `Small` for `TransportType.Taxi` and `Large` otherwise (`:74-77`), and the depot gets `UpdateFrameData(2)` (`:79`).

**Upgrades combine into the parent, additively for the numbers and by OR for the masks.** `TransportDepotData : ICombineData<TransportDepotData>` implements `m_EnergyTypes |= other`, `m_DispatchCenter |= other`, `m_VehicleCapacity += other`, `m_ProductionDuration += other`, `m_MaintenanceDuration += other` — and **does not combine `m_TransportType` or `m_SizeClass` at all** (`src/Game/Game.Prefabs/TransportDepotData.cs:23-30`). That is exactly why an upgrade prefab declares `m_TransportType = None`: it contributes only the combinable fields. Read live at 1.6.0f1, the pattern holds across every upgrade on this install — `BusDepot01 Extra Garage` is `None/None/Large` with capacity 10 and nothing else, `BusDepot01 Electric Bus Maintenance` is `None/Electricity/Large` with capacity 0, and `TaxiDepot01 Dispatch Center` is `None/None/Large` with `m_DispatchCenter = true`. **"Upgrade the depot to run electric buses" is that `|=` on `m_EnergyTypes`, and nothing else.**

**Per-tick depot behaviour** (`TransportDepotAISystem.Tick`, `src/Game/Game.Simulation/TransportDepotAISystem.cs:256-470`; `GetUpdateInterval` returns 256 and `GetUpdateOffset` returns 32, `:1048-1056`):

1. `vehicleCapacity = BuildingUtils.GetVehicleCapacity(min(efficiency, immediateEfficiency), m_VehicleCapacity)` — and that helper is `select(0, clamp((int)(efficiency * capacity), 1, capacity), efficiency > 0.001 && capacity > 0)`, so **any efficiency above 0.001 guarantees at least one vehicle** (`:258-259`, `src/Game/Game.Buildings/BuildingUtils.cs:376-379`).
2. Walk `OwnedVehicle`. A `DummyTraffic` vehicle is skipped entirely. A parked one with a non-zero odometer has its odometer cleared (`:301-321`) — and (corrected 2026-08-16, the authoring stage's decompile read) the `saturate(odometer / m_MaintenanceRange)` conversion in that block is dead: the three vehicle-data lookups key on the **depot's own** `PrefabRef` (`Tick` receives the building's, `:251`/`:256`, read at `:303`/`:310`/`:317`), which no depot prefab satisfies, so the tick clears the odometer without feeding the backlog. The conversion that actually runs is `Game.Vehicles.ReferencesSystem`'s, keyed on the vehicle's own prefab when a depot-owned vehicle is deleted (`src/Game/Game.Vehicles/ReferencesSystem.cs:498-523`). A parked one whose lane or parking location no longer exists is deleted (`:322-327`). An out-of-depot one decrements the free slots and gets `Disabled` toggled as the slot count crosses zero (`:333-346`).
3. `m_MaintenanceRequirement -= 256 / (262144 * m_MaintenanceDuration) * efficiency`, floored at zero, and **free slots lose `ceil(requirement - 0.001)`** (`:348-353`). `262144` is the simulation day in frames and `256` the update interval, so the divisor is "days of maintenance work". **A depot with a maintenance backlog has fewer vehicles available**, which is the mechanism behind a fleet that shrinks without the player changing anything.
4. `m_ProductionDuration > 0` runs a separate path: the depot advances a `Produced { m_Completed }` on the one vehicle that carries it, at the same `256/(262144*duration)*efficiency` rate, and on completion raises a `VehicleLaunchData` event matching its transport type (`:355-372`, `TryCreateLaunchEvent` at `:493-517`). **All 33 `TransportDepotData` carriers on this install were read, and exactly one has a non-zero `m_ProductionDuration`** — `SpaceCenter01`, `TransportType.Rocket`, vehicle capacity 1. So the production path is one prefab's mechanism rather than a general depot behaviour, and the `VehicleLaunch` event family exists for it. The query that reproduces the census is `ecs_query` on `Game.Prefabs.TransportDepotData` plus a batched read of `m_ProductionDuration`.
5. Drain `ServiceDispatch`: spawn at most one vehicle per tick; a surviving surplus request burns one free slot per loop pass before it is dropped, so a tick with any surplus ends at zero free slots (`:378-416`; corrected 2026-08-16, the review gate).
6. **Cull surplus parked vehicles at random**: `while (parkedVehicles.Length > max(0, m_VehicleCapacity - outCount)) delete a uniformly-chosen one` (`:417-424`). Note this uses the **raw prefab capacity**, not the efficiency-scaled one — a depot at low efficiency does not delete its parked fleet.
7. `m_AvailableVehicles = clamp(freeSlots, 0, 255)` as a `byte`, then set or clear `TransportDepotFlags.HasAvailableVehicles`, and set `HasDispatchCenter` when `m_DispatchCenter && efficiency > 0.001` (`:452-469`).
8. With slots free, `RequestTargetIfNeeded` creates a **reversed** service request: a `TaxiRequest` at `RequestGroup(16u)` for a taxi depot, otherwise a `TransportVehicleRequest(depot, availableVehicles / vehicleCapacity)` at `RequestGroup(8u)` (`:472-491`).

`Game.Buildings.TransportDepot { m_TargetRequest, m_Flags, m_AvailableVehicles, m_MaintenanceRequirement }` is `src/Game/Game.Buildings/TransportDepot.cs:6-15`; `TransportDepotFlags` is `HasAvailableVehicles = 1`, `HasDispatchCenter = 2` (`src/Game/Game.Buildings/TransportDepotFlags.cs:6-10`).

**The two halves meet in `TransportVehicleDispatchSystem`** (interval 16, `src/Game/Game.Simulation/TransportVehicleDispatchSystem.cs:677-680`), which is a two-sided pathfinding matcher rather than a search:

- A **line's** request (forward) runs `FindVehicleSource`: origin `SetupTargetType.TransportVehicle`, destination `SetupTargetType.RouteWaypoints` with the route as `m_Entity`, weights `(1,1,1,1)`, `m_MaxSpeed = 277.77777f`, `m_WalkSpeed = 5.555556f`, `m_IgnoredRules` the five-rule union `ForbidCombustionEngines | ForbidHeavyTraffic | ForbidPrivateTraffic | ForbidSlowTraffic | AvoidBicycles`, and `PathfindFlags.IgnoreExtraEndAccessRequirements`; the path methods come from `RouteUtils.GetPathMethods` on the line prefab's `RouteConnectionData` (`:377-407`).
- A **depot's** request (reversed) runs `FindVehicleTarget`, which derives the methods through a defaultless hardcoded switch on the depot's own `TransportDepotData.m_TransportType` (`:411-470`; corrected 2026-08-16, the mechanical pass): the three rail arms set `PathMethod` and `TrackTypes` directly with no synthetic struct, the rest call `VehicleUtils.GetPathMethods` on a synthetic `CarData`/`WatercraftData`/`AircraftData` carrying only the depot's size class, and an unlisted transport type keeps the pre-switch initialisers — the full-complement idiom, i.e. zero methods, a pathfind that can match nothing.
- The match is applied by `DispatchVehiclesJob`, which appends a `ServiceDispatch(request)` to the source's buffer, or sets `ServiceRequestFlags.SkipCooldown` on it when it has none (`:532-557`).

**So a vehicle reaches a line the same way a service vehicle reaches an incident**: through `ServiceRequest` + a payload request component, matched by the pathfinder, dispatched into a `ServiceDispatch` buffer. `city-services-and-coverage` owns that request machinery; what is this topic's is that `TransportVehicleRequest` and `TaxiRequest` are two more members of its family.

**Which vehicle prefab gets spawned is `TransportVehicleSelectData`'s.** `SelectVehicle` / `CreateVehicle` match on `(TransportType, EnergyTypes, SizeClass, PublicTransportPurpose, Resource cargoResources)` plus theme, with a per-mode switch and a reservoir-style random pick, returning a primary and optionally a secondary prefab and accumulating a passenger and cargo capacity range (`src/Game/Game.Prefabs/TransportVehicleSelectData.cs:134-166`, the switch at `:341-714`). **The energy-type filter is `(data.m_EnergyType != None && (data.m_EnergyType & energyTypes) == 0) -> reject`** (e.g. `:396`, `:449`, `:534`), and the depot's combined `m_EnergyTypes` is what is passed in — which is the other half of the electric-bus upgrade. Rail modes take the `controller: true` archetype and build a consist; everything else takes `controller: false` (`:168`, `:179`).

`PublicTransportPurpose` is a four-member flag enum — `TransportLine`, `Evacuation`, `PrisonerTransport`, `Other` (`src/Game/Game.Prefabs/PublicTransportPurpose.cs:6-12`) — carried on `PublicTransportVehicleData.m_PurposeMask` and used as a filter at every selection site. **It is what separates the transit fleet from the evacuation and prisoner fleets sharing the same components**, and read live on this install one of the three bus prefabs carries `Evacuation` rather than `TransportLine`, so it can never be assigned to a line.

### Maintenance, refuelling and the energy model

The whole model is four moving parts and no fuel gauge exists.

1. **`Odometer { m_Distance }`** accumulates on every transit vehicle (`src/Game/Game.Vehicles/Odometer.cs:6-9`); the `PublicTransport` and `CargoTransport` prefab components both add it (`src/Game/Game.Prefabs/PublicTransport.cs:51`, `src/Game/Game.Prefabs/CargoTransport.cs:33`).
2. **The threshold is `m_MaintenanceRange`** on `PublicTransportVehicleData`, `CargoTransportVehicleData` or `TaxiData` — authored in kilometres on the class and multiplied by `1000f` into the component (`src/Game/Game.Prefabs/PublicTransport.cs:62`, `src/Game/Game.Prefabs/CargoTransport.cs:52`, `src/Game/Game.Prefabs/Taxi.cs:37`). **A range of zero, or anything at or below `0.1`, disables the mechanic for that prefab entirely** — every test is `m_MaintenanceRange > 0.1f` (`src/Game/Game.Simulation/TransportCarAISystem.cs:327`, `:332`).
3. **Crossing it sets `RequiresMaintenance`**, but only while `Refueling` is clear (`TransportCarAISystem.cs:327-335`) — except on the taxi, whose `TaxiFlags` declares no `Refueling` member and whose test carries no such clause (`src/Game/Game.Simulation/TaxiAISystem.cs:319`; corrected 2026-08-16, the mechanical pass).
4. **At the next stop, the owning station decides.** `flag = (station.m_CarRefuelTypes & carData.m_EnergyType) != 0` — the train and watercraft AIs run the identical line against their own mask (`TransportCarAISystem.cs:1204`, `src/Game/Game.Simulation/TransportTrainAISystem.cs:923`, `src/Game/Game.Simulation/TransportWatercraftAISystem.cs:742`), while the aircraft AI (corrected 2026-08-16, the authoring stage's decompile read) tests `m_AircraftRefuelTypes & EnergyTypes.Fuel` with the energy type hardcoded, because `AircraftData` carries no energy-type field (`src/Game/Game.Simulation/TransportAircraftAISystem.cs:773-775`). With `flag` set, `RequiresMaintenance` is cleared, the vehicle stays `EnRoute`, and boarding begins with `Refueling` set (`:1217-1223`, `TransportBoardingHelpers.cs:374-390`). With `flag` clear **and** `RequiresMaintenance` set, `EnRoute` is cleared and **`CurrentRoute` is removed from the vehicle outright** (`TransportCarAISystem.cs:1206-1216`) — it leaves the line and returns to its depot; the tick then clears its odometer without feeding the backlog (the dead lookup in step 1), and the odometer-keyed conversion runs in `Game.Vehicles.ReferencesSystem` when a depot-owned vehicle is deleted (corrected 2026-08-16, the review gate).

`TransportStation : ComponentBase, IServiceUpgrade` declares the four masks — `m_CarRefuelTypes`, `m_TrainRefuelTypes`, `m_WatercraftRefuelTypes`, `m_AircraftRefuelTypes` — plus `m_ComfortFactor` (`src/Game/Game.Prefabs/TransportStation.cs:16-24`), and `Initialize` **ORs the four masks into whatever the component already holds while `m_ComfortFactor` is plainly assigned** (`:52-57`; corrected 2026-08-16, the review gate), which is what lets two ComponentBases on one prefab merge their masks; an upgrade's values reach the building instead through `TransportStationData.Combine` — masks OR, the two factors add — applied by `UpgradeUtils.CombineStats` in `TransportStationAISystem` (`src/Game/Game.Prefabs/TransportStationData.cs:21-29`, `src/Game/Game.Simulation/TransportStationAISystem.cs:74`).

`EnergyTypes` is a three-value flag byte plus `None`: `Fuel = 1`, `Electricity = 2`, `FuelAndElectricity = 3`, `None = 0` (`src/Game/Game.Vehicles/EnergyTypes.cs:3-9`). **That enum is the entire energy model.** There is no fuel level, no charge, no consumption rate: energy type is a compatibility mask between a vehicle prefab, a depot and a station, and distance-since-maintenance is the only thing that accumulates.

Read live at 1.6.0f1, the depot side of that mask: bus depot `Fuel`, taxi depot `Fuel`, ferry depot `Fuel`, tram depot `Electricity`, subway yard `Electricity`, rail yard `FuelAndElectricity` — and the electric-bus and electric-taxi upgrades each contribute `Electricity` and nothing else.

### Prefab-class field initializers in this topic, and how far they survive

**Ruled (2026-08-08, the zoning-buildings-and-land-value pass under delegated authority, with a same-day addendum; conflicts.md).** A **field initializer on a `PrefabBase`/`ComponentBase` subclass is a Unity-serialized default the shipped asset overrides, not a C# constant**, and it ships as **no number** — plus one trap, stated once, wherever the reference's map or traps send a reader into a file carrying them: these are Unity-serialized defaults, and nothing in the C# marks which survived. The test is what consumes the value: a value the code compiled in ships as a number; a value Unity deserialisation can replace is a prefab value whatever file declares it.

This topic's prefab classes carry them densely, and the live diff is decisive.

`TransportPathfind : ComponentBase` declares three initialized `PathfindCostInfo` fields and copies all three into `PathfindTransportData` in `Initialize` (`src/Game/Game.Prefabs/TransportPathfind.cs:10-14`, `:25-34`). Read live at 1.6.0f1 across the six line-mode pathfind prefabs (`Bus`, `Tram`, `Subway`, `Train`, `Ship`, `Airplane Pathfind`), **all six are identical to each other and two of the three fields differ from the initializer**:

| field | class initializer (`TransportPathfind.cs`) | all six line pathfind prefabs (live) | `Road Pathfind` (live) |
| --- | --- | --- | --- |
| `m_OrderingCost` | `(5, 0, 0, 5)` | `(5, 0, 0, 5)` | `(20, 0, 0, 5)` |
| `m_StartingCost` | `(5, 0, 10, 5)` | `(5, 0, 10, **200**)` | `(5, 0, 10, 200)` |
| `m_TravelCost` | `(0, 0, **0.02**, 0)` | `(0, 0, **0**, 0)` | `(0, 0, 10, 0.2)` |

**Two consequences the reference must not lose, and neither is a number.** The comfort component of `m_StartingCost` is **larger** on every shipped prefab than the class declares, and the three other components of the same field survive unchanged — so a reader citing the class gets a plausible wrong number in one slot out of four rather than an obviously wrong one, which is the ruling's exposure at its worst. (The size of the gap stays in this file; the reference states the direction and names the field.) And **`m_TravelCost` is zeroed on every transit line's pathfind prefab**, so a reader citing the initializer believes a transit ride accrues money per metre when on this install it accrues nothing at all — see the routing finding below for what that means.

The same shape across the rest of this topic's classes, class initializer against live:

### What a transit leg costs the pathfinder, and where the cost is not

Three `PathSpecification` builders own the whole transit half of the routing graph, and each is short enough to ship whole.

**The stop edge** — `PathUtils.GetTransportStopSpecification` (`src/Game/Game.Pathfind/PathUtils.cs:1527-1567`) builds a zero-length edge with `m_MaxSpeed = 1` and `EdgeFlags.FreeBackward`, adds `Forward` when the stop is `Active`, `AllowEnter` when it is `AllowEnter`, `Backward` when the caller is a stop rather than a waypoint, and `AllowExit` when an access restriction exists. Then:

```
stopDuration = RouteUtils.GetStopDuration(lineData, stop)
wait         = max(line.m_VehicleInterval * 0.5, (int)waitingPassengers.m_AverageWaitingTime) - stopDuration
startingCost.x = max(0, startingCost.x + wait)          // time
startingCost.z *= (int)line.m_TicketPrice                // money
startingCost.w *= 1 - stop.m_ComfortFactor               // comfort
```
(`:1560-1565`.) **Three things a reader acts on.** The expected wait is `max(half the headway, the measured average wait)` — a floor of half the headway that no amount of good measurement removes. The money term is a **multiplication by the ticket price**, so a zero-price line costs nothing in money no matter what the prefab's cost says. The comfort term is a multiplication by `1 - comfort`, so a perfectly comfortable stop costs nothing in comfort.

**The line edge** — `PathUtils.GetTransportLineSpecification` (`:1774-1803`):

```
m_Length   = routeInfo.m_Distance
m_MaxSpeed = max(1, routeInfo.m_Distance) / max(1, routeInfo.m_Duration)
m_Density  = 1
Forward set only when both distance and duration are strictly positive
methods    = PublicTransportDay/Night per the RouteInfoFlags, and/or CargoTransport
costs     += m_TravelCost * routeInfo.m_Distance
```
**The edge's speed is the line's own measured distance-over-duration**, which is why the `RouteInfo` scaling in `TransportLineSystem` is the whole of how transit responds to congestion. And because `m_TravelCost` reads `(0,0,0,0)` live on every transit pathfind prefab, **riding a line accrues nothing per metre in any of the four weights on this install** — the entire cost of a transit leg is the per-stop starting cost.

**The taxi stop edge** — `GetTaxiStopSpecification` (`:1570-1600`) is the same shape with `PathMethod.Taxi`, `EdgeFlags.SecondaryEnd`, `startingCost.x += (int)waitingPassengers.m_AverageWaitingTime` (no headway floor, since a taxi has no headway) and `startingCost.z *= (int)taxiStand.m_StartingFee`.

**The taxi drive edge** — `GetTaxiDriveSpecification` (`:1095-1130`) is a car-lane edge with `PathMethod.Taxi`, `m_TravelCost.m_Value.z *= 0.03f` before being scaled by length (`:1108-1109`), then the ordinary `PathfindCarData` turn, U-turn, curve-angle and lane-cross terms. **The `0.03` is the per-metre-to-fare conversion**, and it equals `RouteUtils.TAXI_DISTANCE_FEE` — see the const-inlining finding. Live, `Road Pathfind.m_TravelCost` is `(0, 0, 10, 0.2)`, so a taxi ride does accrue money per metre where a bus ride does not.

`PathfindTransportData { m_OrderingCost, m_StartingCost, m_TravelCost }` is `src/Game/Game.Prefabs/PathfindTransportData.cs:6-13`. `m_OrderingCost` is consumed at one pathfind edge, the parking-lane taxi-availability edge, where `GetTaxiAvailabilityDelay(parkingLane)` is added to its time component first (`:1265-1267`, the helper at `:1238`); `ResourceAvailabilitySystem` reads the same two costs a second time to estimate a taxi's response time (`src/Game/Game.Simulation/ResourceAvailabilitySystem.cs:773`), and a whole-tree grep for `OrderingCost` finds no third consumer (2026-08-16, the mechanical pass).

**`PathMethod`'s transit members** are `PublicTransportDay`, `PublicTransportNight`, `CargoTransport`, `CargoLoading`, `Taxi` and `Boarding`, out of the sixteen-member mask `roads-and-traffic` records in full (`src/Game/Game.Pathfind/PathMethod.cs:6-23`). `RouteUtils.GetTaxiMethods`, the resident overload of `GetPublicTransportMethods`, and (added 2026-08-16, the mechanical pass) `GetPathMethods`' own default arm — reached by any `RouteConnectionType` outside `{Pedestrian, Road, Air, Track}` (`RouteUtils.cs:537-538`) — are the three selectors that can refuse, and each returns **the complement of the whole mask**: `PathMethod` fills all sixteen bits of its `ushort`, so the complement is literally `(PathMethod)0` — when the resident carries `ResidentFlags.IgnoreTaxi` or `ResidentFlags.IgnoreTransport` (`RouteUtils.cs:562-570`, `:581-594`), or on the default arm always. The plain `GetPublicTransportMethods(float timeOfDay, …)` overload has no such branch and always returns a day or night method (`:571-579`). That inverted-complement idiom is the game's way of writing "no method"; a reader who reads it as a wide mask has it exactly backwards.

### The line's own route is planned congestion-blind and deterministically

`RoutePathSystem` (registered at `SystemUpdatePhase.ModificationEnd`, `src/Game/Game.Common/SystemOrder.cs:254`) issues one pathfind per route segment. Its parameters are (`src/Game/Game.Routes/RoutePathSystem.cs:552-570`):

```
m_MaxSpeed      = 277.77777f        // 1000 km/h, the same sentinel the dispatch systems use
m_WalkSpeed     = 5.555556f
m_Weights       = (1, 1, 1, 1)
m_PathfindFlags = Stable | IgnoreFlow
m_IgnoredRules  = HasBlockage | ForbidCombustionEngines | ForbidHeavyTraffic
                | ForbidPrivateTraffic | ForbidSlowTraffic | AvoidBicycles
                (+ ForbidTransitTraffic unless the route is a Car road route)
```

**Three consequences, all of them mechanism.** `PathfindFlags.Stable` removes the per-edge `[0.5, 1]` random multiplier `roads-and-traffic` records, so **a line's route is reproducible and two identical lines take the same path**. `PathfindFlags.IgnoreFlow` makes `PathUtils.CalculateSpeed` skip the `m_FlowOffset` reduction, so **the planned duration is a free-flow duration**. And the six-rule union means **a line's route ignores blockages and every district traffic restriction** — including `ForbidTransitTraffic` on anything but a car road route, which is the branch at `:565-568`.

Congestion therefore reaches transit only through the two measured channels: `VehicleTiming.m_AverageTravelTime` per stop, and the `RouteInfo.m_Duration` scaling built from it. A mod that wants transit to route around congestion changes the flags here, not the weights.

For a segment carrying `VerifiedPath`, the request is additionally forced directional — `ForceForward` on segment index 1 and `ForceBackward` otherwise — and its targets are the owning building plus each of its `InstalledUpgrade`s rather than a waypoint pair (`:571-592`).

**`TransportLineSystem` feeds the global heuristic, and that is the one hard dependency between this topic and every pathfind in the game.** `m_MaxTransportSpeed` is a two-element persistent array — passenger, cargo — reset to zero each tick and raised by an interlocked compare-exchange to the maximum per-leg `distance / duration` over every line of the matching kind, active or not — the write site at the tail of `RefreshLineSegments` carries no activity gate (corrected 2026-08-16 from "every active line", the authoring stage's decompile read) (`TransportLineSystem.cs:491`, `:498-527`). `PathfindQueueSystem` reads it once per worker-job schedule (`src/Game/Game.Pathfind/PathfindQueueSystem.cs:651`, against the accessor at `TransportLineSystem.cs:877-882`). `SetDefaults` seeds both slots at `277.77777f` (`:900-904`) and both are serialized (`:884-898`). **So the fastest transit line widens or narrows the search bounds for every query whose methods include public or cargo transport** — the value reaches every job but is consulted only under those method masks (`PathfindJobs.cs:236-247`; corrected 2026-08-16, the review gate). A city with no lines does not fall back to the seeded sentinel (corrected 2026-08-16, the mechanical pass): `OnUpdate` zeroes both slots at `:818-819`, before and outside the `IsEmptyIgnoreFilter` guard at `:820`, and the pathfinder clamps the zero with `1f / math.max(0.01f, maxSpeed)` (`src/Game/Game.Pathfind/PathfindJobs.cs:239/:245`) — 0.01 m/s, the slow extreme, not the fast one; `SetDefaults`' `277.77777f` is gone after the first tick.

### Waiting, boarding, capacity and the fare

**`WaitingPassengers { m_Count, m_OngoingAccumulation, m_ConcludedAccumulation, m_SuccessAccumulation, m_AverageWaitingTime }`** (`src/Game/Game.Routes/WaitingPassengers.cs:6-17`) is a five-field estimator, not a counter, and only `m_Count` means what its name says.

`WaitingPassengersSystem` (`SystemOrder.cs:594`, interval 256 at `src/Game/Game.Simulation/WaitingPassengersSystem.cs:252-255`) runs three jobs:

1. **Clear** `m_Count` and `m_OngoingAccumulation` to zero on every waypoint (`:28-37`).
2. **Count**: for each resident who has reached a transport stop, or each queue entry with a positive target radius, add `1 + groupCreatures.Length` to `m_Count` and `resident.m_Timer * that * (2f/15f)` to `m_OngoingAccumulation`, batched per stop and applied with `Interlocked.Add` (`:69-146`). **`2f/15f` is the conversion from the resident's timer units to seconds**, a literal compiled into the job rather than a named `const`, and it ships as part of the formula.
3. **Tick** (`:167-192`):

```
1 chance in 64 per tick: m_SuccessAccumulation++ (capped at 65535)
divisors = max(1, (m_Count, m_SuccessAccumulation))
quotients = (m_OngoingAccumulation, m_ConcludedAccumulation) ceil-divided by divisors
avg = min(65535, cmax(quotients) rounded down to a multiple of 5)
if avg != m_AverageWaitingTime: stamp PathfindUpdated on the waypoint
decay = (m_SuccessAccumulation + random(0..255)) >> 8
m_ConcludedAccumulation -= decay * quotients.y   (floored at 0)
m_SuccessAccumulation   -= decay
m_AverageWaitingTime     = avg
```

**So the published wait is the larger of two estimates — time-per-waiting-passenger and time-per-successful-boarding — quantised to five seconds, and the quantisation is what stops it re-stamping `PathfindUpdated` on every tick.** `m_ConcludedAccumulation` is fed by `ResidentAISystem` when a passenger boards (`resident.m_Timer * count * 2/15`, `src/Game/Game.Simulation/ResidentAISystem.cs:3793-3797`), when a wait times out (a flat `5000 * count * 2/15`, `:3980-3986`), and as a direct estimate in seconds (`:3990-3994`). The `1-in-64` free success increment is what keeps the average decaying on a stop nobody uses.

**Boarding capacity is enforced on the boarding resident, not on the vehicle.** `ResidentAISystem.GetFreeSpace` computes, per vehicle, `capacity - (passengers already aboard and flagged InVehicle, each counting itself plus its pending group members)` where capacity comes from `PublicTransportVehicleData.m_PassengerCapacity`, `TaxiData.m_PassengerCapacity` or `PersonalCarData.m_PassengerCapacity` — **falls back to `1000000` when a vehicle with a `Passenger` buffer carries none of the three, and returns `0` for a vehicle with no `Passenger` buffer at all** (`:3676-3725`, the fallback at `:3717`, the zero at `:3723-3724`; the second arm added 2026-08-16, the mechanical pass). `TryFindVehicle` scores each car of a consist with a leader's score capped at the space the group needs — among cars that fit, the nearest wins and room only separates cars that do not fit — while a following member scores a 0-3 preference for the leader's car and a car with room and is never refused; the whole-vehicle verdict is per capacity class — `PublicTransportVehicleData` (and the no-data fallback) accepts on total free space, `TaxiData` and `PersonalCarData` only on a completely empty vehicle (`:3616-3673`, the saturation at `:3633`, the class tests at `:3663-3671`; corrected 2026-08-16, the review gate).

**`PublicTransportFlags.Full` is not the line capacity flag.** It is set in exactly one place, only for a vehicle already flagged `Evacuating` or `PrisonerTransport` (`src/Game/Game.Simulation/TransportCarAISystem.cs:314-325`), and cleared in two — the matching clear there, and `ParkCar`'s state mask `m_State &= Evacuating | PrisonerTransport | RequiresMaintenance` (`:542`), which strips it off every parking car-type transit vehicle (corrected 2026-08-16, the mechanical pass). Its readers are the evacuation and prisoner dispatch and pathfind setups (`src/Game/Game.Simulation/EvacuationDispatchSystem.cs:231`, `PrisonerTransportDispatchSystem.cs:230`, `FirePathfindSetup.cs:335`, `PolicePathfindSetup.cs:356`). **A full bus on an ordinary line never carries `Full`**; it simply fails `GetFreeSpace` at the door.

**Two more door-side gates on `PublicTransport`.** `m_MaxBoardingDistance` and `m_MinWaitingDistance` are reset at each `BeginBoarding` to `0` and `float.MaxValue` (`src/Game/Game.Simulation/TransportBoardingHelpers.cs:388-390`); a resident further from the vehicle than `m_MaxBoardingDistance` does not board and instead lowers `m_MinWaitingDistance` (`ResidentAISystem.cs:3762-3768`). `PublicTransportFlags.RequireStop` is a passenger's request that the vehicle stop, set at two sites — a rider wanting off (`ResidentAISystem.cs:2153`) and a waiting resident asking a testing vehicle to halt (`:2930`) (widened 2026-08-16, the mechanical pass).

**The line fare is charged at boarding, from the household, to the city** (corrected 2026-08-16, the review gate). `FinishEnterVehicle` snapshots `GetTicketPrice(vehicle)` — the walk through `CurrentRoute` to `TransportLine.m_TicketPrice`, 0 when either is missing (`:3046-3057`, the sole call site at `:3003-3007`) — and the boarding job moves that price out of the household's `Resource.Money` into `PlayerMoney` and enqueues a `ServiceFeeSystem.FeeEvent { m_Amount = 1, m_Cost = ticketPrice, m_Resource = PlayerResource.PublicTransport, m_Outside = false }` (`:3922-3939`). `ExitVehicle`'s own `ticketPrice` is the taxi meter alone — `Taxi.m_CurrentFee`, read only for a `Leader` in a vehicle carrying `Taxi`, negated when `FromOutside` (`:1562-1571`, its money move at `:3565-3584`). **So the fare is per ride rather than per distance, it is a `ushort`, and a vehicle carrying no line at the door rides free.** On a multi-car rail consist only riders boarding the head car pay: `GetTicketPrice` reads `CurrentRoute` off the boarded car, every car including the head sits in the `LayoutElement` buffer `TryFindVehicle` picks from, and none of the seven `CurrentRoute` add sites targets a layout member (`TransportVehicleSelectData.cs:195-302`, `ResidentAISystem.cs:3620-3653`; added 2026-08-16, the review gate).

`RouteUtils.GetBoardingVehicle` and `ShouldExitVehicle` are the two decision helpers (`RouteUtils.cs:302-388`, `:428-474`), both returning an `obsolete` out-parameter that forces the walker to re-path. `BoardingVehicleSystem` (`SystemOrder.cs:255`) nulls a stop's `m_Vehicle` whenever the named vehicle's `Target` no longer resolves to that stop (`src/Game/Game.Routes/BoardingVehicleSystem.cs:36-59`). `BoardingVehicle.m_Testing` is the same slot for a vehicle only probing the stop, and it only deserializes from `Version.boardingTest` (`BoardingVehicle.cs:24-28`).

### Cargo loading is a storage transfer, and the work it does drives the station

`TransportBoardingHelpers.TransportBoardingJob` handles both payloads through one queue of `BoardingItem { m_Begin, m_Refuel, m_Testing, m_Vehicle, m_Route, m_Stop, m_Waypoint, m_CurrentStation, m_NextStation }` (`src/Game/Game.Simulation/TransportBoardingHelpers.cs:214-234`).

`BeginBoarding` (`:339-403`) refuses when another vehicle is already `Boarding` at the stop (`:341-345`), claims `BoardingVehicle.m_Vehicle`, updates the waypoint's `m_AverageTravelTime` and `m_LastDepartureFrame`, sets `Boarding` (plus `Refueling` when the station refuels this vehicle), then clears the `LoadingResources` buffer and runs `UnloadResources` followed by `LoadResources`, accumulating a `workAmount`.

`UnloadResources` moves every `Resources` element from the vehicle — or from each `LayoutElement` car of a consist — into the target's buffer, clears the source, and enqueues a `TransportUsageEvent` **only when the target is not an outside connection** (`:449-477` dispatching to the per-buffer overload at `:478-505`, the outside-connection guard at `:486`). `LoadResources` fills from the source's `StorageTransferRequest`s whose flags are outgoing-and-`Transport` and whose `m_Target` is the next station, across three overloads (`:506-569`, `:570-601`, `:602-679`), and `GetVehicleType` at `:680` is how each moved stack is attributed to a mode.

`AddWork` climbs the stop's `Owner` chain to the first `Game.Buildings.CargoTransportStation` and adds the moved amount to its `m_WorkAmount` (`:405-423`; the component is one float, `src/Game/Game.Buildings/CargoTransportStation.cs:6-9`). **That is what makes a cargo terminal's workload a function of tonnage moved rather than of vehicles arrived**, and `CargoTransportStationData.m_WorkMultiplier` is the per-prefab scale (`src/Game/Game.Prefabs/CargoTransportStationData.cs:6-9`, authored at `src/Game/Game.Prefabs/CargoTransportStation.cs:35`) — applied not at `AddWork` but where the amount is consumed, by `AreaLotSimulationSystem` (`src/Game/Game.Simulation/AreaLotSimulationSystem.cs:180`, `:239`) and as a gate in `AreaPathfindSetup` (`src/Game/Game.Simulation/AreaPathfindSetup.cs:75`) (clarified 2026-08-16, the authoring stage's decompile read).

`EndBoarding` releases the stop and runs one more `LoadResources` with no `LoadingResources` buffer inside the claim check `m_Vehicle == data.m_Vehicle` (`:427-434`, the release at `:429-430`), then clears `Boarding` and `Refueling` at method scope outside that check, guarded only by a `HasComponent` test — a vehicle whose claim was taken over still has both flags cleared (`:435-446`; re-scoped 2026-08-16, the review gate). `LoadingResources` is the pending-load manifest, and (corrected 2026-08-16, the mechanical pass) its real reader is the simulation, not the UI: the transit vehicle AI systems read it back to materialise `Economy.Resources` into `DummyTraffic` vehicles, bounded by `m_MaxResourceCount` and `m_CargoCapacity` (`src/Game/Game.Simulation/TransportCarAISystem.cs:305-307`, `:853-880`, with train, watercraft and aircraft twins); `Economy.Resources` is the cargo itself.

`CargoTransportStation : ComponentBase, IServiceUpgrade` is where a cargo terminal declares its traded resources, its `transports` count, its four refuel masks, its loading factor and work multiplier, and an `m_TransportInterval` (`src/Game/Game.Prefabs/CargoTransportStation.cs:19-37`); it adds `Game.Companies.StorageCompany`, `TradeCost`, `StorageTransferRequest` and `Economy.Resources` to the building, and `TransportCompany` + `OwnedVehicle` when `transports > 0`, plus a second `OwnedVehicle` add gated only on `m_WorkMultiplier > 0f`, outside both that guard and the `ServiceUpgrade` one (`:48-72`, the pair at `:62-66`, the independent add at `:68-71`; corrected 2026-08-16, the review gate). **A cargo terminal with zero transports is a warehouse with a stop on it** — no `TransportCompany`, though a positive work multiplier still adds `OwnedVehicle` — which is the mechanism behind the wiki's "companies can use it as a storage point even with no cargo lines".

### Noise and pollution: the emission model has no energy-type branch

The per-vehicle emission model is one lerp; the car and train systems carry it whole while the watercraft and aircraft ones drop the lane-length normalisation and multiply `.x` by raw distance, and (corrected 2026-08-16, the mechanical pass) the aircraft system's `HelicopterData` and `AirplaneData` `ApplySideEffects` overloads only zero the accumulators and emit nothing (`src/Game/Game.Simulation/AircraftNavigationSystem.cs:1127-1137`) — its `AircraftData` overload (`:1104-1125`) is the one that emits. When `laneDuration == 0` the speed input is `VehicleUtils.GetMaxDriveSpeed(prefabData, carLane)` — `min(scaled lane speed limit, the prefab's cornering limit for the lane's curviness)` (`src/Game/Game.Vehicles/VehicleUtils.cs:618-623`). The car-and-train shape:

```
ratio       = saturate((achievedSpeed / prefab.m_MaxSpeed)^2)
sideEffects = lerp(VehicleSideEffectData.m_Min, VehicleSideEffectData.m_Max, ratio)
sideEffects *= (min(1, distance/laneLength), duration, duration)
```
(`src/Game/Game.Simulation/CarNavigationSystem.cs:2172-2181`, `src/Game/Game.Simulation/TrainNavigationSystem.cs:853-861`, and the watercraft and aircraft variants — raw-distance `.x`, no clamp, the aircraft ratio over `m_GroundMaxSpeed` — at `src/Game/Game.Simulation/WatercraftNavigationSystem.cs:1096-1114` and `src/Game/Game.Simulation/AircraftNavigationSystem.cs:1104-1125`). `VehicleSideEffectData { m_Min, m_Max }` packs `(roadWear, noisePollution, airPollution)` per axis (`src/Game/Game.Prefabs/VehicleSideEffectData.cs:7-12`, built at `src/Game/Game.Prefabs/VehicleSideEffects.cs:26-33`). The `.x` becomes lane wear and the `.yz` become `Game.Net.Pollution` — `roads-and-traffic` and `environment-and-pollution` own both consumers, and neither is re-derived here.

**`CalculateNoise` reads the air-pollution axis, and its result is audio rather than pollution.** It uses the same squared speed ratio, drops the distance scaling, and lerps `m_Min.z` to `m_Max.z` times the lane duration (`CarNavigationSystem.cs:2145-2157`) — and `.z` is the axis `VehicleSideEffects.Initialize` fills from `m_AirPollution`, while `.y` is the one it fills from `m_NoisePollution` (`src/Game/Game.Prefabs/VehicleSideEffects.cs:30-31`). Its one caller enqueues the result as a `TrafficAmbienceEffect.m_Amount` (`CarNavigationSystem.cs:465-469`), which is the ambient traffic **sound** layer. So a vehicle's authored air-pollution factor is what drives how loud it makes the ambience, and its authored noise-pollution factor does not. Stated flat, at the cited lines; which component of `Game.Net.Pollution`'s `float2` the `.yz` pair lands in is `environment-and-pollution`'s to settle, and this pass did not.

**`CarData.m_EnergyType`, `TrainData.m_EnergyType` and `WatercraftData.m_EnergyType` appear nowhere in any of the four emission paths.** Whether a vehicle is electric or fuelled changes nothing about what it emits in code; the difference, where there is one, is authored per prefab into `VehicleSideEffectData`.

**And on this install the difference is authored for some pairs and not others**, which ships as a swept shape under the utilities ruling quoted above, with this query as the re-check: `ecs_query` on `Game.Prefabs.VehicleSideEffectData` plus the body-data component, then read both. The live figures, kept here:

| prefab | energy | `m_Min` (wear, noise, air) | `m_Max` |
| --- | --- | --- | --- |
| Bus01 | `Fuel` | (1, 0.25, 0.2) | (2, 200, 1) |
| Bus02 | `Electricity` | (1, 0.25, 0.2) | (2, 200, 1) |
| Taxi01 | `Fuel` | (0.5, 0.25, 0.1) | (1, 10, 0.5) |
| Taxi02 | `Electricity` | (0.5, **0**, **0**) | (1, 5, **0**) |
| TramEngine01 | `Electricity` | (0.5, 0, 0) | (1, 5, 0) |
| EU_TrainPassengerEngine01 | `Electricity` | (1, 0, 0) | (2, 10, 0) |

**The electric taxi is authored quieter and cleaner than the fuel taxi; the electric bus is authored byte-identical to the fuel bus.** Stated flat, surprise first: a mod that expects the electric bus to emit less has to author that itself, and a mod that patches the emission code to branch on energy type has patched the wrong layer, because the code has no branch to change.

### Usage tracking covers three modes and silently drops every other one

`TransportUsageTrackSystem` (`SystemOrder.cs:595`, with `TransportRequirementSystem` ordered after it at `:596`) drains a queue of `TransportUsageEvent { m_Building, m_TransportType, m_TransportedPassenger, m_TransportedCargo }` (`src/Game/Game.Simulation/TransportUsageEvent.cs:6-15`) into `TransportUsageData`, a struct of six `long`s — train, ship and airplane, each × cargo and passenger — where `GetTotalPassenger()` sums the three passenger fields and `GetTotalCargo()` the three cargo ones, and neither has a term for any other mode (`src/Game/Game.Simulation/TransportUsageData.cs:20-42`).

The accumulator is a `switch` on `m_TransportType` with three cases — `Airplane`, `Ship`, `Train` — and **no default** (`src/Game/Game.Simulation/TransportUsageTrackSystem.cs:47-60`). An event whose type is `Bus`, `Tram`, `Subway`, `Ferry`, `Taxi`, `Post` or anything else leaves all six locals at zero and is still written into the per-prefab and per-unlock-filter maps as a row of zeroes (`:63-108`). Stated as behaviour: **the transported-passenger and transported-cargo counters cover rail, sea and air only.**

Passengers are enqueued at exactly two sites, both in `ResidentAISystem` and both with `m_TransportedPassenger = 1` (`:3600-3606`, `:3842-3848`) — and (corrected 2026-08-16, the mechanical pass) both sites are themselves gated on `transportType` being `Airplane`, `Train` or `Ship` **and** on the destination not being an outside connection, with the second site zeroing the type first for an `Evacuating` or `PrisonerTransport` run (`:3838-3841`), so no passenger event for another mode ever exists. Cargo is enqueued per unloaded resource stack in `TransportBoardingHelpers` (`:493-501`, `:645-653`), gated **only** on the destination not being an outside connection — so bus and truck cargo events do fire, and it is the accumulator's defaultless three-case switch that lands them as rows of zeroes.

These counters are what `TransportRequirementData { m_BuildingPrefab, m_TransportType, m_FilterID, m_MinimumTransportedPassenger, m_MinimumTransportedCargo }` gates an unlock on (`src/Game/Game.Prefabs/TransportRequirementData.cs:5-16`, authored by `TransportRequirementPrefab : UnlockRequirementPrefab`, `src/Game/Game.Prefabs/TransportRequirementPrefab.cs:24-34`). That makes the three-mode coverage a progression fact as well as a statistics one; the unlock half is `city-state-and-progression`'s.

### The gate-bypass penalty, and what a resolved bypass path costs a building

`RoutePathReadySystem` (`SystemOrder.cs:94`, `SystemUpdatePhase.Modification1`) does two things beyond copying ready positions onto `PathTargets` (`src/Game/Game.Routes/RoutePathReadySystem.cs:108-133`).

**One: a route segment whose path starts or ends inside a building the route already owns raises the gate-bypass warning** on that building and on any of its `InstalledUpgrade`s that match (`:145-172`).

**Two: the penalty runs the other way from what its pairing with `HiddenRoute` suggests** (corrected 2026-08-16, the authoring stage's decompile read; the block sits inside `UpdateVerifiedPathNotifications`, so it runs for routes with `VerifiedPath` segments — the verification routes that deliberately try to path into the owning building):

```
noPathAnywhere = no RouteSegment of the route has PathInformation.m_Distance >= 0
if noPathAnywhere: add HiddenRoute; efficiency = 1                        // clean: no bypass exists
else:              efficiency = 1 + RouteConfigurationData.m_GateBypassEfficiency   // a path into the building resolved: the gate is bypassed
BuildingUtils.SetEfficiencyFactor(efficiencies, EfficiencyFactor.GateBypass, efficiency)
```
(`:174-205`; the operative line is `math.select(1f + m_GateBypassEfficiency, 1f, flag)` at `:203`, and `HiddenRoute` moves at `:193`/`:197`.) `EfficiencyFactor.GateBypass` is a member of the building-efficiency enum (`src/Game/Game.Buildings/EfficiencyFactor.cs:36`) that `city-services-and-coverage` owns; what belongs here is that **a verification route that *does* resolve a path is what sets the penalty** — the bypass existing is the failure case, and a route reaching nothing is the clean state — and that `RouteConfigurationData.m_GateBypassEfficiency` is the singleton field carrying the magnitude (`src/Game/Game.Prefabs/RouteConfigurationData.cs:25`). Read live at 1.6.0f1 the sole `Route Configuration` prefab carries `-0.5`, matching its class initializer (`src/Game/Game.Prefabs/RouteConfigurationPrefab.cs:28`) — one of the few in this topic that does.

`RouteConfigurationData` also holds the six per-medium route-visualisation prefabs, `m_MissingRoutePrefab`, `m_PathfindNotification` and `m_GateBypassNotification` (`:7-25`). **It is the singleton a mod reads to reach any of the game's own route visuals**, through `GetSingleton<RouteConfigurationData>()`.

### `RouteUtils`' seven public constants are inlined, and the decompile shows literals at every use

`RouteUtils` declares seven `public const float`s (`src/Game/Game.Routes/RouteUtils.cs:23-35`):

| name | value | where the same literal appears |
| --- | --- | --- |
| `WAYPOINT_CONNECTION_DISTANCE` | `10f` | `src/Game/Game.Routes/WaypointConnectionSystem.cs:217`, `:607` |
| `ROUTE_VISIBLE_THROUGH_DISTANCE` | `100f` | — |
| `TRANSPORT_DAY_START_TIME` | `0.25f` | `RouteUtils.cs:576`, `:588`; `src/Game/Game.Simulation/TransportLineSystem.cs:824` |
| `TRANSPORT_DAY_END_TIME` | `11f / 12f` | the same three sites |
| `DEFAULT_TRAVEL_TIME` | `1f / 48f` | the `predictionOffset` default parameter at `RouteUtils.cs:571`, `:581` |
| `MAX_BOARDING_GRACE_PERIOD` | `30f` | — |
| `TAXI_DISTANCE_FEE` | `0.03f` | `src/Game/Game.Pathfind/PathUtils.cs:1108` |

**A whole-decompile grep for each of the seven names returns only its own declaration.** That is a decompilation artifact rather than dead code: a C# `const` is inlined by the compiler at every use site, so ILSpy renders the literal and the symbol vanishes. **The names are the only documentation these numbers have** — `0.03f` in a taxi cost expression means nothing until you know it is `TAXI_DISTANCE_FEE`. And **the value cannot be changed at runtime**: patching the field, or reflecting on it, changes nothing, because every consumer compiled the number in. A mod that wants a different day/night boundary patches `TransportLineSystem.OnUpdate` and `RouteUtils.GetPublicTransportMethods` separately.

These seven are `const` and therefore ship as numbers under the ruling: the consuming code compiled them in and no asset can replace them. `roads-and-traffic` records the same shape for `RoadSafetySystem.UPDATES_PER_DAY` and `TrafficFlowSystem.UPDATES_PER_DAY`; `TransportLineSystem.UPDATE_INTERVAL = 256u` (`TransportLineSystem.cs:772`) against `GetUpdateInterval`'s literal `256` (`:792`) is this topic's third instance, and 256 × 1024 = 262144, the simulation day, exactly as the sibling's pairs work out.

### Verdicts against the wiki's transportation prose

The wiki makes very few checkable mechanism claims about this topic, and they all sit in the `Transportation` page's prose rather than in its tables. Every one that could be checked was, and the decompile or the running game owns each.

`Verdict:` **"Each depot can support a predetermined number of vehicles and this can be extended with suitable building upgrades"** (https://cs2.paradoxwikis.com/Transportation) — **confirmed, and the decompile supplies the mechanism the wiki lacks**: the number is `TransportDepotData.m_VehicleCapacity` and the extension is `ICombineData<TransportDepotData>.Combine`'s `m_VehicleCapacity += otherData.m_VehicleCapacity` over the building's `InstalledUpgrade`s (`src/Game/Game.Prefabs/TransportDepotData.cs:23-30`), scaled at read time by `BuildingUtils.GetVehicleCapacity(efficiency, capacity)` (`src/Game/Game.Buildings/BuildingUtils.cs:376-379`).

`Verdict:` **"To use electric buses in your city you will need to update the bus depot to maintain them"** and **"The taxi service can be expanded by replacing some taxis with electric taxis … by upgrading the Taxi Depot"** (same page) — **confirmed, and it is one `|=` and one filter.** The upgrade prefab contributes `EnergyTypes.Electricity` through the same `Combine` (`TransportDepotData.cs:25`), and `TransportVehicleSelectData` rejects any candidate prefab whose `m_EnergyType` does not intersect the depot's combined mask (`src/Game/Game.Prefabs/TransportVehicleSelectData.cs:396`, `:449`, `:534`). Read live on this install, `BusDepot01 Electric Bus Maintenance` carries `m_EnergyTypes = Electricity` and a vehicle capacity of zero — it contributes the mask and nothing else.

`Verdict:` **"before upgrading the Taxi Depot, taxis can only pick up passengers from the taxi stand. With the dispatch center upgrade, there are no limits for picking up fares in the city"** (same page) — **confirmed at the line that enforces it.** `TaxiRequestType` is `Stand`, `Customer`, `Outside` and a `None = byte.MaxValue` sentinel that a city depot's own reversed request carries (`TransportDepotAISystem.cs:480`; corrected 2026-08-16, the mechanical pass), and every `Customer` request is skipped when the candidate depot lacks `TransportDepotFlags.HasDispatchCenter` (`src/Game/Game.Simulation/TransportPathfindSetup.cs:269-273`, again at `:328-333`, and the same test decides the seeker's own eligibility at `:574`). The flag is set only while `m_DispatchCenter` is true **and** the depot's efficiency exceeds `0.001` (`src/Game/Game.Simulation/TransportDepotAISystem.cs:462-469`) — so a dispatch centre in a depot with no efficiency stops working, which the wiki does not say.

`Verdict:` **"Ticket price affects citizens' pathfinding calculations. Citizens weigh time, traveling comfort, and money … money can sway them between public transportation and private vehicle usage"** (same page) — **confirmed, and the mechanism is a multiplication rather than an addition**: `transportPathfindData.m_StartingCost.m_Value.z *= (int)transportLine.m_TicketPrice` at the stop edge (`src/Game/Game.Pathfind/PathUtils.cs:1564`). The consequence the wiki misses follows from the operator: **at a ticket price of zero the money term is exactly zero**, whatever the pathfind prefab declares, so a free line is free in the model and not merely cheap.

`Verdict:` **"If a line becomes extremely popular … increasing the number of vehicles can alleviate the pressure and shorten passenger wait times at stops and stations which in turn affect their pathfinding calculations as well"** (same page) — **confirmed twice over, through two independent channels.** More vehicles lowers `TransportLine.m_VehicleInterval` directly (`CalculateVehicleInterval(lineDuration, vehicleCount)`, `src/Game/Game.Simulation/TransportLineSystem.cs:911-914`), and the stop edge's time cost is `max(m_VehicleInterval * 0.5, m_AverageWaitingTime) - stopDuration` (`PathUtils.cs:1561-1562`); and shorter real waits lower `WaitingPassengers.m_AverageWaitingTime`, which is the other half of that same `max`. **The half-headway floor is the part a reader needs and the wiki does not give**: it caps how much a shorter measured wait can lower the routing cost, but not how much more vehicles can, since they shrink the headway the floor is half of (corrected 2026-08-16, the review gate).

`Verdict:` **"Air transport lines don't require any additional infrastructure other than the airports themselves"** (same page) — **confirmed, and the reason is that the outside connection is the depot.** All 33 `TransportDepotData` carriers on this install were read and none is an `Airplane` or `Ship` depot building; the only carriers for those two transport types are `Airplane Outside Connection` and `Ship Outside Connection - Twoway`. The airport is a `TransportStation` — comfort, loading factor and refuel masks — not a depot.

`Verdict:` **"Taxis operate on a similar logic to personal vehicles … Taxis are an extremely flexible public transport option as they don't require lines to operate"** (same page) — **confirmed structurally**: `TransportType.Taxi` has no `TransportLineData` prefab on this install, and `TransportStop.GetArchetypeComponents`' taxi branch is the only one that puts the line's own components on the stop object instead (`src/Game/Game.Prefabs/TransportStop.cs:66-83`).

`Verdict:` **"Ferries carry 100 passengers"** and **"Cargo ships can carry 1000 tons of cargo"** (same page) — **both re-derive first-party** as `PublicTransportVehicleData.m_PassengerCapacity` and `CargoTransportVehicleData.m_CargoCapacity` on this install, the second in game units where a tonne reads as 1,000. **Neither ships**, under the ruling at the head of this file; they are recorded only because a wiki number matching a first-party read is worth knowing when the next version's does not.

`Verdict:` **"electric taxis, reducing noise and air pollution caused by the service"** against **"environmentally friendly electric buses"** (same page) — **the first is borne out by the shipped data and the second is not**, and the reason is that neither is a code behaviour at all: the emission model has no energy-type branch, so the wiki's two sentences describe authored prefab values, and on this install the taxi pair is authored differently while the bus pair is authored identically. The emission finding above carries the evidence and the query; what is settled here is that the wiki's phrasing invites a reader to look for a rule in code and there is none to find.

`Verdict:` **the wiki's `Vehicle` page's one substantive sentence** — "Each Vehicle has specific attributes including passenger or cargo capacity, noise pollution rating, and speed that vary depending on the type and classification of vehicle" (https://cs2.paradoxwikis.com/Vehicle) — **is correct and is the whole of what that page contains.** The decompile names the fields it gestures at: capacity on `PublicTransportVehicleData` / `CargoTransportVehicleData` / `TaxiData`, the emission pair on `VehicleSideEffectData`, speed on `CarData` / `TrainData` / `WatercraftData` / `AircraftData`. Its taxonomy is incomplete and its links are red; nothing on it is worth a citation.

## Bridge

**Changing what a mode is means changing prefab data, not code.** Vehicle capacity, speed, maintenance range, cargo capacity, depot vehicle capacity, headway, stop duration, comfort and loading factors all live on `*Data` components written during prefab initialisation — `TransportLineData` from `TransportLinePrefab.LateInitialize` (`src/Game/Game.Prefabs/TransportLinePrefab.cs:101-129`), `TransportDepotData` from `TransportDepot.Initialize` (`src/Game/Game.Prefabs/TransportDepot.cs:64-80`), `PublicTransportVehicleData` from `PublicTransport.Initialize` (`src/Game/Game.Prefabs/PublicTransport.cs:59-67`), `CarData`/`TrainData` from `VehicleInitializeSystem` (`src/Game/Game.Prefabs/VehicleInitializeSystem.cs:356-400`). So the technique is `prefabs-and-assets`' — a system in the prefab-initialisation phase that queries the data component and overwrites it — and **not** patching, because the value the game reads is the component and never the class field. The field-initializer ruling above is why a reader must be told this: Harmony-patching `PublicTransport.Initialize` to change `m_PassengerCapacity = 30` is both harder and wrong, since the asset overrides the literal anyway.

**Adding or editing a line at runtime is `ecs-in-this-game`'s, and the four-archetype shape is what makes it hard.** A line is a route entity plus N waypoints plus N segments, each built from a separate `EntityArchetype` on `RouteData`, and the two directions of the waypoint↔stop link are maintained by `WaypointConnectionSystem` rather than by whoever creates the entity. The supported creation path is the tool's — `RouteToolSystem` at `SystemUpdatePhase.ToolUpdate` and `ApplyRoutesSystem` at `ApplyTool` (`src/Game/Game.Common/SystemOrder.cs:704`, `:719`), consuming `WaypointDefinition`, which is `placement-definitions`' subject and is the shape `ExtraDetailingTools` reuses. A mod building entities directly has to reproduce the archetype selection and the reference maintenance itself, and the corpus contains no example of anyone doing so.

**Making transit re-derive is the same three-trigger ladder `roads-and-traffic` teaches, and this topic uses the cheapest rung constantly.** `Game.Common.PathfindUpdated` on a waypoint or segment re-derives that transit edge's pathfind specification without touching anything else, and vanilla stamps it from `TransportLineSystem` (interval or ticket change, `TransportLineSystem.cs:261`; `RouteInfo` change, `:487`), `TransportStopSystem` (comfort, loading or active change, `src/Game/Game.Simulation/TransportStopSystem.cs:88-98`) and `WaitingPassengersSystem` (average wait crossing a five-second step, `src/Game/Game.Simulation/WaitingPassengersSystem.cs:184-187`). **A mod changing a line's price, its stops' comfort or its published wait must stamp the same tag, or the routing graph keeps the old cost.** `mod-lifecycle-and-ordering` decides the phase; `ecs-in-this-game` owns the `EntityCommandBuffer` write.

**Putting a vehicle on a line, or taking one off, is a request rather than a write.** The supported route is `TransportVehicleRequest` + `ServiceRequest` + `RequestGroup` on a fresh entity of the archetype `TransportLineSystem` builds (`TransportLineSystem.cs:803`), matched by `TransportVehicleDispatchSystem` and delivered into a `ServiceDispatch` buffer. Writing `CurrentRoute` and the `RouteVehicle` buffer by hand skips the depot's slot accounting and the odometer/maintenance loop. `city-services-and-coverage` owns the request family's shape; `ecs-in-this-game` owns the archetype creation.

**Reaching the transit half of the routing graph is `patching`'s, and the seams are narrow.** The five `PathUtils.Get*Specification` methods consuming `PathfindTransportData` — the transport stop, transport line, taxi stop, taxi drive and taxi access builders (corrected 2026-08-16, the mechanical pass, from "three") — are `public static` and pure, but every call site sits in a `[BurstCompile]` job in `RoutesModifiedSystem` and `LanesModifiedSystem`, so a prefix or transpiler on them is inert with Burst on and the seam is the managed `OnUpdate` that schedules those jobs — `patching`'s replace-the-job rule (corrected 2026-08-16, the review gate); `RoutePathSystem.SetupPathfind` is `private` and is where the `Stable | IgnoreFlow` decision lives. `SetupTargetType` is the closed hardcoded switch `roads-and-traffic` records — `TransportVehicle` and `RouteWaypoints` are its two transit members and a mod may not add a third. `mod-lifecycle-and-ordering` decides when the patch lands.

**Reading transit state for a UI or an info view** is a `localization` / `units-and-formatting` job over components this topic names: `TransportLine.m_VehicleInterval` and `m_TicketPrice`, `RouteInfo.m_Duration`/`m_Distance`, `WaitingPassengers.m_Count`/`m_AverageWaitingTime`, `Game.Buildings.TransportDepot.m_AvailableVehicles`/`m_MaintenanceRequirement`, `Odometer.m_Distance`, and the `Passenger` buffer's length. `units-and-formatting` matters more here than usual: **speed is m/s on the component and km/h in the UI, turning angles are radians on the component and degrees on the class, maintenance range is metres on the component and kilometres on the class, and the ticket price is a `ushort`.** The one derived figure a reader will look for and not find as a component is line usage — the game recomputes it per read in `TransportUIUtils`, and the dead ends record the walk.

**Anything this topic persists is `save-serialization`'s, and the version gates are dense.** Several components here deserialize a field only past a named format version — `Route.m_OptionMask` past `Version.routePolicies`, `RouteInfo.m_Flags` past `Version.transportLinePolicies`, `TransportLine.m_Flags` past `Version.transportLineFlags` and `m_TicketPrice` past `Version.transportLinePolicies`, `TransportStop.m_AccessRestriction` past `Version.pathfindAccessRestriction` and `m_LoadingFactor` past `Version.transportLoadingFactor`, `WaitingPassengers`' last three fields past `Version.passengerWaitTimeCost` and `passengerWaitTimeCost2`, `BoardingVehicle.m_Testing` past `Version.boardingTest`, `Game.Buildings.TransportDepot`'s three later fields past their own gates. Two prefab components also branch on `FormatTags.BpPrefabData` and fall back to `SizeClass.Large` without it (`src/Game/Game.Prefabs/TransportLineData.cs:63-71`, `src/Game/Game.Prefabs/TransportDepotData.cs:64-72`). And the buffers split cleanly: `LayoutElement`, `VehicleModel` and `RouteModifier` are `ISerializable` and survive; `RouteWaypoint`, `RouteSegment`, `ConnectedRoute`, `SubRoute`, `RouteVehicle`, `Passenger`, `OwnedVehicle` and `GuestVehicle` are `IEmptySerializable` and are rebuilt on load by the matching `Game.Serialization` systems in `SystemUpdatePhase.Deserialize` — `RouteWaypointSystem`, `RouteSegmentSystem`, `RouteVehicleSystem`, `ConnectedRouteSystem` and `SubRouteSystem` for the route side (`src/Game/Game.Common/SystemOrder.cs:809`, `:830-833`), `PassengerSystem`, `OwnedVehicleSystem` and `GuestVehicleSystem` for the vehicle side (`:819-822`; corrected 2026-08-16, the review gate).

**Boundaries with sibling topics, stated so the reference does not cross them.**

- **`roads-and-traffic`** owns the network under a line, the pathfinding queue and cost model, the `PathNode`/lane/composition machinery, intercity *traffic* (`TrafficSpawnerAISystem`, `RandomTrafficDispatchSystem`) and the outside-connection *delay* (`OutsideConnectionDelaySystem`). That sibling's file states the same seam from its side and the two agree.

## Dead ends

**The wiki's `Transportation` page carries no per-mode vehicle-spec table, and the premise that it did is worth correcting explicitly.** Fetched 2026-08-16 through `action=raw`; page ID 443, last edited 2026-06-16, whose edit comment shows the change was an icon swap and an empty ferry table rather than any re-verification. Every `====Buildings:====` table on it is a **building** table — cost, upkeep/month, XP, DLC, description, notes — and the column sets are not even uniform between modes (taxi, passenger ship, cargo train and cargo ship tables have no DLC column; taxi's header reads `Upkeep` rather than `Upkeep/month`; the two plane tables add an `Effects` column). **There is no wiki page for outside connections, in any capitalisation.** `Outside connections`, `Outside Connections` and `Outside connection` all report `missing` against the API, verified against a full main-namespace enumeration (`list=allpages&aplimit=500`, one batch, roughly 350 pages). The `Transportation` page links to `[[Outside Connections]]` four times and every one is red. **The install's packaged content was not opened and would have been the wrong road.** `docs/SOURCES.md` entry 5 establishes that base-game prefabs are Unity serialized objects in `Cities2_Data/resources.assets` with no field names, needing a parser driven by the decompiled class's field order. **No live transit line existed on the throwaway save; the missing reads were closed the same day against a second save.** On the throwaway save, `ecs_query` on `Game.Routes.Route` + `Game.Routes.TransportLine` returned four entities and all four are the route tool's own template entities. **Searching `Game.Routes` for a line-capacity, line-usage or occupancy component finds nothing, and the reason is worth carrying rather than just recording.** There is no per-line "usage %" component. The figure the panel shows is computed in the UI layer at read time by `TransportUIUtils`, which walks the line's `RouteVehicle` buffer, descends into each vehicle's `LayoutElement` consist, and per unit adds the `Passenger` buffer's **length** against `PublicTransportVehicleData.m_PassengerCapacity`, or the `Economy.Resources` amounts against `CargoTransportVehicleData.m_CargoCapacity` or `WorkVehicleData.m_MaxWorkAmount`; usage is then `capacity > 0 ? cargo / capacity : 0` (`src/Game/Game.UI.InGame/TransportUIUtils.cs:52`, the walk at `:100-146`, the payload struct at `src/Game/Game.UI.InGame/UITransportLineData.cs:34-49`). **So line usage is derived, never stored**, and a mod that wants it reproduces that walk. The only persisted counters in the whole topic are `WaitingPassengers`' five fields per waypoint and `TransportUsageData`'s six longs per building prefab.

**There is no aggregate "transport network" system.** No baked line table, no cached transfer matrix, no route index. Every line is ticked independently by `TransportLineSystem` at interval 256 and every segment path is an ordinary pathfind request thrown away and re-issued. `Game.Prefabs.ProductionChainDataSystem`'s analogue does not exist here either.

Nothing else in the namespace bears on lines, stops, cargo or the vehicle.
