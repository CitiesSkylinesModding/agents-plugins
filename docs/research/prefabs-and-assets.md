## Findings

### The three things the word "prefab" names

This is the number-one conceptual trap, and the wiki is the only source that states it. Its TL;DR, quoted from https://cs2.paradoxwikis.com/PrefabSystem: "**Baseline (true vanilla)** = `PrefabBase` authoring fields (via `PrefabSystem.TryGetPrefab(...)`) | **What mods usually edit** = prefab-entity `*Data` components. | **What gameplay uses right now** = instance-side runtime components (often game computed / cached / serialized)".

**Verdict: verified in full, and one file in the decompile shows all three layers at once.** `Game.Prefabs.DeathcareFacility` (`src/Game/Game.Prefabs/DeathcareFacility.cs`) is 73 lines and contains the entire triad:

| Layer             | What it is in C#                                                                                                                                      | In that file                                                                                                                                                                                                   |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Authoring**     | a `ComponentBase : ScriptableObject` (`src/Game/Game.Prefabs/ComponentBase.cs:13`), managed, one object per prefab, holds the values a designer typed | `class DeathcareFacility : ComponentBase` with `m_HearseCapacity = 5`, `m_StorageCapacity = 100`, `m_ProcessingRate = 10f`, `m_LongTermStorage` (`:17-25`)                                                     |
| **Prefab entity** | an ECS entity carrying `*Data` components, one per registered prefab                                                                                  | `GetPrefabComponents` requests `DeathcareFacilityData` and `UpdateFrameData` (`:27-31`); `Initialize` copies the four authoring fields into `DeathcareFacilityData` (`:62-72`)                                 |
| **Instance**      | the placed building's own entity, whose archetype the prefab declares                                                                                 | `GetArchetypeComponents` puts `Game.Buildings.DeathcareFacility` on every instance, plus `Efficiency`, `OwnedVehicle`, `ServiceDispatch`, `ServiceDistrict`, and `Patient` when storage is non-zero (`:33-49`) |

The two `DeathcareFacility` types are different in kind, not just in namespace: `Game.Prefabs.DeathcareFacility` is a managed `ScriptableObject` and cannot appear in a query at all; `Game.Buildings.DeathcareFacility` is `IComponentData` with `m_TargetRequest`, `m_Flags`, `m_ProcessingState`, `m_LongTermStoredCount` (`src/Game/Game.Buildings/DeathcareFacility.cs:6-13`) — runtime state, none of it a copy of an authoring value. `Game.Prefabs.DeathcareFacilityData` is the third type, with `m_HearseCapacity`, `m_StorageCapacity`, `m_ProcessingRate`, `m_LongTermStorage` (`src/Game/Game.Prefabs/DeathcareFacilityData.cs:6-14`) — the authoring values, blittable, on the prefab entity.

**The field name does not survive the copy, which is the trap inside the trap.** The wiki's second worked example is workplaces, and the three layers spell the same quantity three different ways: authoring `Game.Prefabs.Workplace.m_Workplaces` (`src/Game/Game.Prefabs/Workplace.cs:17`), prefab-entity `Game.Prefabs.WorkplaceData.m_MaxWorkers` (`src/Game/Game.Prefabs/WorkplaceData.cs:11`, written from the authoring field at `Workplace.cs:54-65`), instance `Game.Companies.WorkProvider.m_MaxWorkers` (`src/Game/Game.Companies/WorkProvider.cs:8`). A reader who greps for `m_MaxWorkers` finds the second and third and never learns the first exists. **Verdict: the wiki's quick-reference table names all three correctly** (https://cs2.paradoxwikis.com/PrefabSystem).

**Which layer a given API takes, from the decompile.**

- `PrefabSystem.TryGetPrefab(...)` and `GetPrefab<T>(...)` return the **authoring** object (`src/Game/Game.Prefabs/PrefabSystem.cs:643-687`).
- `PrefabSystem.GetEntity(prefab)` / `TryGetEntity` go the other way, authoring object to **prefab entity** (`:705-713`).
- `PrefabRef.m_Prefab` on an **instance** points at the **prefab entity**, never at the authoring object (`src/Game/Game.Prefabs/PrefabRef.cs:6-8`). It has an implicit conversion to `Entity` (`:25-28`), so `prefabRefLookup[instance]` used where an `Entity` is expected silently yields the prefab entity — convenient, and one more way to lose track of which layer you hold.
- `PrefabData.m_Index` on the **prefab entity** is an index into `PrefabSystem`'s managed `List<PrefabBase>` (`src/Game/Game.Prefabs/PrefabData.cs:9`, list at `PrefabSystem.cs:44`, indexed at `:645`). That int is the entire bridge from ECS back to managed authoring data.
- `ComponentBase.prefab` is the back-pointer from an authoring component to its owning authoring prefab (`ComponentBase.cs:21`).

**The wiki's own `SystemAPI.Query` warning is the practical form of this** (https://cs2.paradoxwikis.com/PrefabSystem): `.WithAll<DeathcareFacility>()` is wrong and `.WithAll<Game.Buildings.DeathcareFacility>()` is right. **Verdict: verified, and the exposure is far wider than that one type.** A file-name comparison of `src/Game/Game.Prefabs/` (1274 files) against every other `src/Game/Game.*` namespace (3051 files) returns **111 short names declared in both**. 98 of the 111 are `Game.Prefabs` authoring `ComponentBase` classes shadowing an ECS component elsewhere — `Workplace`, `Hospital`, `School`, `Park`, `FireStation`, `PoliceStation`, `Prison`, `GarbageFacility`, `PostFacility`, `TelecomFacility`, `TransportStation`, `Taxi`, `Hearse`, `Resident`, `Pet`, `Wildlife` and 82 more. In every one of those cases the `Game.Prefabs` type is not a component, so naming it in a query is a compile error rather than a silent wrong answer — the failure is loud.

The six that are silent are `WaterSourceData`, `IComponentData` on both sides (`Game.Prefabs/WaterSourceData.cs:5`, `Game.Simulation/WaterSourceData.cs:6`), `CompanyInitializeSystem`, a `GameSystemBase` on both sides and so a valid type argument to `GetOrCreateSystemManaged<T>` or `UpdateBefore<T>` either way (`Game.Prefabs/CompanyInitializeSystem.cs:14`, `Game.Citizens/CompanyInitializeSystem.cs:21`), and the four `Sub*` buffers — the same trap in its purest form — a buffer that exists once on the prefab entity and once on the instance, with the same short name:

### The four archetype declaration hooks, and what each populates

`ComponentBase` declares exactly two abstract members and nothing else is required of an authoring component (`src/Game/Game.Prefabs/ComponentBase.cs:87-89`):

```csharp
public abstract void GetPrefabComponents(HashSet<ComponentType> components);
public abstract void GetArchetypeComponents(HashSet<ComponentType> components);
```

Counted over `src/Game/Game.Prefabs/`: **500 `GetPrefabComponents` implementations, 373 `GetArchetypeComponents`, 42 `GetUpgradeComponents`, and 6 each of `GetBuildingPrefabComponents` / `GetBuildingArchetypeComponents`.** Four hook families, each with a different consumer.

**1. `GetPrefabComponents` populates the prefab entity, and `PrefabSystem.AddPrefab` is the only consumer.** `AddPrefab` walks every attached `ComponentBase`, unions their output, adds `UnlockRequirement` + `Locked` when the prefab is unlockable, adds `Created` and `Updated` unconditionally, and calls `EntityManager.CreateEntity` once (`src/Game/Game.Prefabs/PrefabSystem.cs:130-145`). The base seeds it with `PrefabData` and `LoadedIndex`, plus `ModPrerequisiteData` when the prefab came from an asset carrying a platform id (`src/Game/Game.Prefabs/PrefabBase.cs:362-370`).

**2. `GetArchetypeComponents` populates the instance archetype — but nothing consumes it directly.** `PrefabBase` seeds it with `PrefabRef` alone (`PrefabBase.cs:372-375`). The set is materialised from `LateInitialize`, and **six independent families route it through a `RefreshArchetype` method, each writing the resulting `EntityArchetype` into a different prefab-data component** — while ten other bases (`NetPrefab`, `NetLanePrefab`, `RoutePrefab`, `AreaPrefab`, `ZoneBlockPrefab`, `AggregateNetPrefab`, `NetGeometryPrefab`, `EffectPrefab`, `LifePathEvent`, `RadioEvent`) declare no `RefreshArchetype` and build theirs inline in their own `LateInitialize`:

| Prefab base class        | Destination                        | Where                                                   |
| ------------------------ | ---------------------------------- | ------------------------------------------------------- |
| `ArchetypePrefab`        | `ArchetypeData.m_Archetype`        | `src/Game/Game.Prefabs/ArchetypePrefab.cs:26-40`        |
| `ObjectPrefab`           | `ObjectData.m_Archetype`           | `src/Game/Game.Prefabs/ObjectPrefab.cs:31-46`           |
| `BrushPrefab`            | `BrushData.m_Archetype`            | `src/Game/Game.Prefabs/BrushPrefab.cs:36-52`            |
| `ChirpPrefab`            | `ChirpData.m_Archetype`            | `src/Game/Game.Prefabs/ChirpPrefab.cs:32-46`            |
| `EventPrefab`            | `EventData.m_Archetype`            | `src/Game/Game.Prefabs/EventPrefab.cs:32-46`            |
| `NotificationIconPrefab` | `NotificationIconData.m_Archetype` | `src/Game/Game.Prefabs/NotificationIconPrefab.cs:54-68` |

All six are siblings deriving straight from `PrefabBase`, and all six add `Created` and `Updated` to the archetype unconditionally. Three subclasses override the object one: `BuildingPrefab` adds `InstalledUpgrade`, `Game.Net.SubNet` and `SubRoute` first when the prefab entity already carries a `BuildingUpgradeElement` buffer (`src/Game/Game.Prefabs/BuildingPrefab.cs:58-79`), `MovingObjectPrefab` (`MovingObjectPrefab.cs:31-45`) and `TrainPrefab` (`TrainPrefab.cs:79-128`).

**`NetPrefab` — one of the ten inline builders — is the case worth reading, because it calls the hook twice with different seeds.** `LateInitialize` builds two sets, one pre-seeded with `Node` and one with `Edge`, runs every component's `GetArchetypeComponents` against both, and writes `NetData.m_NodeArchetype` and `NetData.m_EdgeArchetype` (`src/Game/Game.Prefabs/NetPrefab.cs:31-53`). Its own override then _reads the set it was handed_ and branches: `ConnectedEdge` if `Node` is present, `ConnectedNode` if `Edge` is (`:18-29`). So `GetArchetypeComponents` is not a pure emit — the contents of the set at call time carry meaning, and an override may be invoked more than once per prefab with different contents. `NetPrefab` is not alone in multi-seeding: `NetLanePrefab` runs the hook eight times and `RoutePrefab` four, and among the `RefreshArchetype` overrides the moving-object one runs two passes and the train one four.

**3. `IServiceUpgrade.GetUpgradeComponents` populates the components an upgrade contributes to its _host_ building.** The interface is two members (`src/Game/Game.Prefabs/IServiceUpgrade.cs:7-11`), 42 authoring components implement it, and the only call sites in the whole of `src/Game/` are four in `src/Game/Game.Buildings/ServiceUpgradeSystem.cs:146/174/189/219`. `Workplace` shows the shape: `GetArchetypeComponents` adds `WorkProvider` and `Employee` only when the component is _not_ a service upgrade (`src/Game/Game.Prefabs/Workplace.cs:36-43`), and `GetUpgradeComponents` adds the same pair whenever the workplace count is non-zero (`:45-52`), so the components land on the building rather than on the upgrade sub-entity.

**4. `IZoneBuildingComponent` adds a zone-and-level-parameterised pair.** `void GetBuildingPrefabComponents(HashSet<ComponentType>, BuildingPrefab, byte level)` and the archetype twin (`src/Game/Game.Prefabs/IZoneBuildingComponent.cs:8/10`). These are not called by the prefab machinery at all: `SpawnableBuilding` and `SignatureBuilding` call them from inside their own two hooks, forwarding to the zone prefab (`src/Game/Game.Prefabs/SpawnableBuilding.cs:44-65`, `SignatureBuilding.cs:37/48`), and `ZonePrefab` fans out to every `IZoneBuildingComponent` it carries (`src/Game/Game.Prefabs/ZonePrefab.cs:48-75`). So a growable building's archetype is partly decided by the _zone prefab it belongs to_ and by its level, not only by its own components.

**Corpus: 19 `GetPrefabComponents` overrides and 11 `GetArchetypeComponents` overrides, across seven repositories** — `CS2-NetworkTools`, `CS2-Platter`, `FindIt-CSII`, `Recolor`, `RoadBuilder-CSII`, `Traffic`, `Water_Features`. Nobody in the corpus implements `IServiceUpgrade` or `IZoneBuildingComponent`.

The clearest pair is `CS2-Platter/Platter/Prefabs/ParcelPrefab.cs:37-52`: `GetPrefabComponents` adds `ParcelData` and `PlaceableObjectData` to the prefab entity, `GetArchetypeComponents` adds `Parcel` and `ParcelSubBlock` to every instance, and each override calls `base` first. `Traffic/Code/Helpers/FakePrefab.cs:14-24` is the minimum viable custom prefab, adding the same one component to both sets. `Water_Features/Water_Features/Prefabs/WaterSourcePrefab.cs:51/57` and `Recolor/Recolor/Domain/Palette/Prefabs/PalettePrefab.cs:45-56` override only the prefab-entity hook, which is legal because `PrefabBase` already implements both; `Recolor`'s is conditional, adding `PaletteFilterEntityData` and `PaletteFilterTypeData` only when the palette declares filters.

**`FindIt-CSII/FindIt/Domain/FindItGenerated.cs:9-18` is a `ComponentBase` whose two overrides are both empty.** It contributes no ECS component at all and exists purely as a managed marker readable through `prefab.Has<FindItGenerated>()`. Vanilla does the same with `ObsoleteIdentifiers` (`src/Game/Game.Prefabs/ObsoleteIdentifiers.cs:12-18`). That is a supported shape: an authoring component that carries data for the mod's own code and nothing for the ECS.

### `PrefabSystem`'s lookup surface, and the two ways it lies

`PrefabSystem` is created by hand in `GameManager.CreateWorld()` before any mod loads (`src/Game/Game.SceneFlow/GameManager.cs:2363-2374`, and see `mod-lifecycle-and-ordering.md`, "Where mod loading sits in the boot sequence"), so it always exists. It holds five managed dictionaries and two lists (`src/Game/Game.Prefabs/PrefabSystem.cs:44-62`); everything below is a read of one of them.

**By `PrefabID` — the string-keyed lookup, and the only total one.** `TryGetPrefab(PrefabID id, out PrefabBase prefab)` consults `m_PrefabIndices` (`:939-948`). No cast, no lie. This is the corpus's workhorse: **123 `new PrefabID(...)` constructions and 174 `TryGetPrefab` calls across the 20 repositories.** `Anarchy/Anarchy/ExtendedRoadUpgrades/UpgradesManager.cs:146` is the readable form, `new PrefabID("FencePrefab", upgradeMode.ObsoleteId)`; `Recolor/Recolor/Domain/Palette/Prefabs/PalettePrefab.cs:111/136` uses `nameof(ThemePrefab)` and friends rather than a literal, which is the safer spelling.

**By entity, `PrefabData` or `PrefabRef` — and here `TryGetPrefab<T>` returns `true` while handing back `null`.**

```csharp
public bool TryGetPrefab<T>(PrefabData prefabData, out T prefab) where T : PrefabBase
{
    if (prefabData.m_Index >= 0)
    {
        prefab = m_Prefabs[prefabData.m_Index] as T;
        return true;
    }
    prefab = null;
    return false;
}
```

(`PrefabSystem.cs:658-667`, with the entity and `PrefabRef` overloads at `:669-687` delegating to it.) The `as T` cast is unchecked and its result is never tested. **`true` means "this entity is a live prefab", not "you got a `T`".** The two-argument `GetPrefab<T>` overloads have the same shape and simply return null (`:643-656`).

**`RoadBuilder` found this and shipped a workaround, which the seed survey then misread as a game API.** `survey-mods-techniques.md:208` lists `TryGetSpecificPrefab<T>(PrefabRef)` among the "prefab lookup surface used", alongside real `PrefabSystem` members. **Verdict: `TryGetSpecificPrefab` does not exist in the game at 1.6.0f1.** A grep over the whole decompile returns zero hits. It is four extension methods in `RoadBuilder-CSII/RoadBuilder/Utilities/Extensions.cs:242-260`, each of them exactly `prefabSystem.TryGetPrefab(x, out prefab) && prefab is not null`. The mod calls it at ten sites and never calls the raw API. That null test is the fix for the bug above, and it is the only place in the corpus where anyone guards against it.

**By `EntityQuery` singleton.** `GetSingletonPrefab<T>(EntityQuery)` and `TryGetSingletonPrefab<T>` (`:689-703`); the `Try` form gates on `IsEmptyIgnoreFilter`, so a shared-component filter on the query does not narrow the gate — the same trap `ecs-in-this-game.md` records for `RequireForUpdate`.

**Authoring object to prefab entity.** `GetEntity(PrefabBase)` is a bare `m_Entities[prefab]` (`:705-708`) and throws `KeyNotFoundException` for a prefab that was never added or was removed. `TryGetEntity` is the safe form (`:710-713`). **Corpus: 101 `GetEntity(` against 65 `TryGetEntity(`,** so the throwing form is the majority — usually right after an `AddPrefab` that returned true.

**Reading the authoring layer once you have the object.** `PrefabBase.TryGet<T>` matches the type _or any subclass of it_ and also matches the prefab object itself (`PrefabBase.cs:274-301`); `TryGetExactly<T>` matches only the exact type, again including the prefab itself (`:303-328`). `Has<T>` / `Has(Type)` follow `TryGetExactly`'s rule (`:237-256`), `HasSubclassOf` follows `TryGet`'s (`:258-272`). `ComponentBase.GetComponent<T>()` is `prefab.TryGet<T>` and throws `NullReferenceException` when the component has no owning prefab (`ComponentBase.cs:39-50`).

**The wiki's headline recommendation has exactly one corpus practitioner, and that mod's own comment states the same rule independently.** The maxim is "vanilla baseline = the original default values included with the game. Prefab `*Data` values (what mods usually edit) may match vanilla by chance, but **shouldn't be trusted as baseline**" (https://cs2.paradoxwikis.com/Prefab_-_Quick_Start), and every worked example on both pages opens with `prefabBase.TryGetExactly(out Game.Prefabs.DeathcareFacility authoring)` before scaling from `authoring.m_ProcessingRate`.

**Verdict: verified in mechanism and corroborated in practice.** The mechanism holds because nothing that writes a prefab entity touches the authoring object — `ComponentBase.Initialize` copies one way and there is no reverse path — so the authoring field really is the durable original. The practice is `Tree_Controller/Tree_Controller/Systems/ModifyVegetationPrefabsSystem.cs`, whose two public methods are the wiki's pattern in miniature. `SetVegetationCostsToZero` writes `PlaceableObjectData.m_ConstructionCost = 0` on every matching prefab entity (`:31-44`, the write at `:38`); `ResetVegetationCosts` restores it by reading the authoring value back —

```csharp
if (EntityManager.TryGetComponent(entity, out PlaceableObjectData placeableObjectData)
   && m_PrefabSystem.TryGetPrefab(entity, out PrefabBase prefab)
   && prefab.TryGet(out PlaceableObject placeableObject))
{
    placeableObjectData.m_ConstructionCost = placeableObject.m_ConstructionCost;
    EntityManager.SetComponentData(entity, placeableObjectData);
}
```

(`:49-64`, the restore at `:54-58`) — with the comment "The PlaceableObject prefab component on the PrefabBase is the 'Source of Truth' and should contain the original values for that prefab." That is the wiki's maxim, discovered independently and written down in a mod. It also shows why a `TryGetExactly` grep misses the pattern: the corpus reaches the authoring layer through `TryGet`, not `TryGetExactly`.

**Two other reasons to read the authoring layer show up in the corpus, and one is not about baselines at all.** `Recolor/Recolor/Systems/SelectedInfoPanel/SIPColorFieldsSystem.OtherPrivateMethods.cs:364-384` reads `Game.Prefabs.ColorProperties` off the authoring object to find which colour channel may be modified externally — information that has **no `*Data` counterpart on the prefab entity**, so the authoring object is the only place it exists. `FindIt` reads `UIObject`, `ThemeObject`, `AssetPackItem`, `ContentPrerequisite`, `EditorAssetCategoryOverride`, `SpawnLocation`, `ObjectSubLanes`, `ObjectSubObjects` and `LodProperties` off authoring objects throughout its indexer (`FindIt-CSII/FindIt/Systems/PrefabIndexingSystem.cs:225/307/349-350/410/596/601/612`), because it is building a catalogue of assets rather than reading simulation state.

Counts: `TryGetExactly` appears twice in the whole corpus (`CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:155`, `RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderNetSectionsSystem.cs:110`), `.TryGet<` 48 times in 5 repositories, `.GetComponent<` 34 times in 6, `.Has<` 42 in 5, `HasSubclassOf` zero.

**`Recolor` is also the second independent witness to the `TryGetPrefab<T>` bug**, and it guards inline rather than through a helper: `!m_PrefabSystem.TryGetPrefab(subMeshBuffer[0].m_SubMesh, out PrefabBase prefabBase) || prefabBase is null || ...` (`SIPColorFieldsSystem.OtherPrivateMethods.cs:367-370`). Two of twenty repositories know about it; the other eighteen call the API bare.

Rots: the `PrefabSystem` member names and their signatures — re-read `src/Game/Game.Prefabs/PrefabSystem.cs:643-753`.

### `PrefabSystem`'s mutation surface

Five methods change the registry, and five more change the prefab entity.

**`AddPrefab(PrefabBase, string parentName = null, PrefabBase parentPrefab = null, ComponentBase parentComponent = null)` returns `bool` and swallows every exception** (`PrefabSystem.cs:88-189`). It returns false in four cases: a null prefab, an already-registered prefab (`m_Entities.ContainsKey`), a prefab whose content prerequisite is unavailable, and any thrown exception, which is caught and logged as `Error when adding prefab: {0}` (`:184-187`). The three optional parameters exist only to make the warning message name the parent that pulled the prefab in.

The availability gate is worth stating on its own: `IsAvailable(prefab)` is true only when both the asset's own platform id and any `ContentPrerequisite` component resolve to available content (`:484-520`), and a `ContentPrefab` is minted per mod id on demand as `"Mod:" + modId` with a `ModRequirement` component (`:330-340`). So a prefab that names a DLC or another mod as a prerequisite silently does not register when that content is absent — `AddPrefab` returns false and logs `Dependency not available in {0}/{1}: {2}` only when a parent was passed.

**`RemovePrefab` is a swap-with-last, and it rewrites another prefab's index.** It tags the entity `Deleted`, unregisters every `PrefabID` the prefab owns, then moves the _last_ prefab in `m_Prefabs` into the freed slot, rewriting that prefab's `PrefabData.m_Index` and every one of its index entries (`:225-253`). The removed entity's own index is set to the sentinel `-1000000000` (`:254`). **A cached `PrefabData` or a cached `m_Index` int is invalidated by any removal, anywhere** — not only of the prefab it names.

**`UpdatePrefab(PrefabBase prefab, Entity sourceInstance = default)` does no work.** Its whole body is `m_UpdateMap[prefab] = sourceInstance` (`:306-309`). The work happens in the next `OnUpdate` (below). `AddOrUpdatePrefab` picks between the two on `m_Entities.ContainsKey` (`:294-304`).

**`DuplicatePrefab(template, name)` is three lines and the third one matters**: `Clone`, then `Remove<ObsoleteIdentifiers>()`, then `AddPrefab` (`:269-275`). See the cloning finding below for why the removal is not optional.

**The prefab-entity accessors all index `m_Entities[prefab]` directly** and therefore throw for an unregistered prefab: `HasComponent<T>`, `HasEnabledComponent<T>`, `GetComponentData<T>`, `TryGetComponentData<T>`, `GetBuffer<T>`, `TryGetBuffer<T>`, `AddComponentData<T>`, `RemoveComponent<T>` (`:715-753`). The `Try` prefix on two of them refers to the _component_, not to the prefab. These are conveniences over `EntityManager`; the wiki's samples reach for `EntityManager.GetComponentData<T>(prefabEntity)` instead and both are equivalent (https://cs2.paradoxwikis.com/PrefabSystem).

**`AddUnlockRequirement(unlocker, unlocked)` is the one domain-specific mutator**, appending to the `UnlockRequirement` buffer and warning when either side is not unlockable (`:601-641`). Unlockability is computed recursively over the prefab's dependency graph and memoised (`:522-599`).

Rots: the sentinel `-1000000000` at `:254` and the mutator names.

### Prefab data initialisation: two layers, one phase, and a wrong claim in a sibling file

**Layer one is managed and per-component.** `PrefabInitializeSystem` queries `{Created, PrefabData}` with `RequireForUpdate` (`src/Game/Game.Prefabs/PrefabInitializeSystem.cs:56-62`) and runs three passes over the batch (`:65-113`):

1. Collect every newly created prefab entity and its authoring object.
2. For each, call `ComponentBase.Initialize(EntityManager, Entity)` on every attached component, then `GetDependencies` — and **any dependency prefab not already known is added to the registry mid-loop and initialised in the same pass**, through a queue that is drained until empty (`:94-103`, `:138-146`). This is how a prefab pulls its referenced prefabs in without anyone registering them.
3. For each, call `LateInitialize` on every component, then hand the accumulated dependency list to `UnlockableBase` (`:151-213`).

Both passes wrap each component in a try/catch that logs `Error when initializing prefab: {0} ({1})` and continues (`:126-135`, `:176-185`), suppressing the UI error in editor mode. **A component whose `Initialize` throws leaves its `*Data` component present but at default values, with one log line and no other symptom.**

The split matters: `Initialize` may only touch its own prefab entity, because other prefabs may not be registered yet; `LateInitialize` may resolve cross-prefab references, because by then they are. Vanilla uses exactly that split — `DeathcareFacility.Initialize` writes its own data (`DeathcareFacility.cs:62-72`), while `PrefabBase.LateInitialize` resolves the mod-prerequisite entity (`PrefabBase.cs:377-392`) and every `RefreshArchetype` runs from `LateInitialize` because the archetype may name components other prefabs' hooks contributed.

`Recolor` is the corpus's only user of both hooks on its own prefab type: `Initialize` fills the `SwatchData` buffer from the authoring array, `LateInitialize` resolves theme, zone and asset-pack prefab names into entities and removes the filter components again when nothing resolved (`Recolor/Recolor/Domain/Palette/Prefabs/PalettePrefab.cs:59-146`).

**Layer two is the `*InitializeSystem` family, and it computes what authoring cannot state.** `SystemUpdatePhase.PrefabUpdate` carries 23 vanilla registrations (`src/Game/Game.Common/SystemOrder.cs:1004-1026`), in this order: `TextureStreamingSystem`, `GeometryAssetLoadingSystem`, `PrefabInitializeSystem`, `MeshSystem`, `AnimatedPrefabSystem`, `UIInitializeSystem`, `TerrainInitializeSystem`, `NetInitializeSystem`, `ObjectInitializeSystem`, `ZoneSystem`, `AreaInitializeSystem`, `CompanyInitializeSystem`, `ResourceSystem`, `ZonePrefabInitializeSystem`, `BuildingInitializeSystem`, `LotInitializeSystem`, `RouteInitializeSystem`, `InfoviewInitializeSystem`, `VehicleInitializeSystem`, `EffectInitializeSystem`, `VehicleCapacitySystem`, `NotificationIconPrefabSystem`, `TriggerPrefabSystem`. `PrefabInitializeSystem` is third, so **every `*InitializeSystem` runs after the managed `Initialize`/`LateInitialize` pass in the same frame.**

These are ordinary ECS systems reading prefab-entity components and writing derived ones. `ObjectInitializeSystem` gates on `{PrefabData, ObjectData}` with `Any = {Created, Deleted}` (`src/Game/Game.Prefabs/ObjectInitializeSystem.cs:426-444`) and derives `ObjectGeometryData` — size, bounds and roughly twenty `GeometryFlags` bits — from the prefab's meshes and its other components (`:563-658`, `:1291-1422`). Nothing an authoring component wrote is recomputed; what is computed is everything that depends on geometry or on another prefab.

**Verdict: `mod-lifecycle-and-ordering.md:250` states that `PrefabUpdate` "runs whenever `PrefabSystem` has pending prefab updates". That is wrong, and the correction changes what a mod may assume.** `PrefabSystem.OnUpdate` is unconditional:

```csharp
bool num = UpdatePrefabs();
m_UpdateSystem.Update(SystemUpdatePhase.PrefabUpdate);
if (num) { ...FinalizeReplaces(); }
```

(`PrefabSystem.cs:756-764`.) `PrefabSystem.OnCreate` registers no `RequireForUpdate` and never sets `Enabled = false` (`:70-86`), and `GameSystemBase` adds no gate of its own (`src/Game/Game/GameSystemBase.cs:18-31`). So **`PrefabUpdate` is driven once per `MainLoop` frame, always**, and only the pending-update _replacement_ work and `FinalizeReplaces` are conditional. The gating is per system: `PrefabInitializeSystem` and its 22 neighbours each carry their own `RequireForUpdate` on a `Created`-shaped query, which is why nothing runs on a quiet frame. A mod registering into `PrefabUpdate` gets an `OnUpdate` every frame and must gate it the same way.

**Corpus: three repositories write a prefab-data initialisation system, and all three copy the vanilla query shape.** `CS2-Platter/Platter/Systems/Parcels/P_ParcelInitializeSystem.cs:74-90` builds `WithAll<PrefabData, Created>().WithAllRW<ParcelData, ObjectGeometryData, PlaceableObjectData>()` and gates on it; its sibling `Systems/Blocks/P_UnzonedInitializeSystem.cs:38` is the same shape. Both are anchored into `PrefabUpdate` _after_ the vanilla system whose output they overwrite — `UpdateAfter<P_ParcelInitializeSystem, ObjectInitializeSystem>(SystemUpdatePhase.PrefabUpdate)` and `UpdateAfter<P_UnzonedInitializeSystem, ZoneSystem>(...)` (`CS2-Platter/Platter/PlatterMod.cs:181-183`). That is the whole technique: let vanilla derive what it derives, then correct it. Its body writes `ObjectGeometryData` (flags, size, pivot, bounds, layers), `PlaceableObjectData` and its own `ParcelData` (`P_ParcelInitializeSystem.cs:107-164`), carries a 20-line comment justifying each `GeometryFlags` bit (`:29-60`), and finishes with `EntityManager.AddComponent<Updated>(m_ParcelPrefabQuery)` (`:104`).

`Recolor/Recolor/Mod.cs:152` registers `AddPalettePrefabsSystem` with a plain `UpdateAt<...>(SystemUpdatePhase.PrefabUpdate)`, no anchor.

Rots: the 23-system `PrefabUpdate` list and its order (`SystemOrder.cs:1004-1026`), and the `GeometryFlags` member names.

### Editing a prefab: what reaches placed instances, what does not, and the three remedies

The wiki's workers section is the clearest statement of the problem anywhere (https://cs2.paradoxwikis.com/Prefab_-_Quick_Start): "Worker limits are runtime instance components (ex: `Game.Companies.WorkProvider.m_MaxWorkers`) and instance-entities don't just hot-update when you edit the prefab `*Data` items. So: Editing `WorkplaceData` is safe for all new buildings […] For Existing buildings to change values, something needs to trigger the game job to update the runtime instance […] restarting the game usually doesn't force that refresh."

**Verdict: verified, and the decompile names the exact job and the exact gate.** `CityServiceWorkplaceInitializeSystem` is the system that writes `WorkProvider.m_MaxWorkers` from `WorkplaceData` (`src/Game/Game.Buildings/CityServiceWorkplaceInitializeSystem.cs:97-121`, the write at `:110` and the add at `:116-120`). Its query is two descs (`:219-250`): `{CityServiceUpkeep, Created}` excluding `{ServiceUpgrade, Deleted, Temp}`, or `{ServiceUpgrade}` with `Any = {Created, Deleted}` excluding `{Temp, OutsideConnection}`. It is registered at `SystemUpdatePhase.Modification5` (`src/Game/Game.Common/SystemOrder.cs:235`).

Read that query against the wiki's Option 1: **`Created` on the building is "rebuild it", and `Created`-or-`Deleted` on a `ServiceUpgrade` is "add or remove an extension".** Those are precisely the two player actions the wiki lists, and the query is why they work. Note what is absent: **`Updated` is not in either desc.** So tagging the building `Updated`, or replacing the prefab outright (which tags every instance `Updated`, below), does not re-run it.

**But the general claim "prefab edits do not reach placed instances" is false, and the true shape is a two-way split.** Most simulation code re-reads prefab-entity data every pass through a `ComponentLookup` indexed by `PrefabRef.m_Prefab`. `BuildingUpkeepSystem` holds `ComponentLookup<ConsumptionData> m_ConsumptionDatas` and does `ConsumptionData consumptionData = m_ConsumptionDatas[prefab];` inside the job (`src/Game/Game.Simulation/BuildingUpkeepSystem.cs:128/182`). A grep for `.m_Prefab]` across `src/Game/Game.Simulation/*.cs` returns **292 indexed reads, 210 of them written as `prefabRef.m_Prefab]`**. For every one of those, a write to the prefab entity is live on the next simulation pass, for every placed instance, with nothing to trigger.

So the rule to carry is per-field, not per-topic:

- **A value the simulation reads from the prefab entity each pass changes immediately.** This is the common case.
- **A value copied into an instance component once, at creation, stays stale until something re-runs the copy.** `WorkProvider.m_MaxWorkers` is the canonical one.
- **A change to the instance _archetype_ never reaches an existing instance at all.** The archetype is fixed when the entity is created from `ObjectData.m_Archetype`; adding a type to `GetArchetypeComponents` afterwards does nothing to what is already placed. The only vanilla reconciliation is `ReplacePrefabSystem.CheckInstanceComponents`, which compares an instance's actual archetype against the prefab's current `GetArchetypeComponents` output and adds or removes the difference (`src/Game/Game.Prefabs/ReplacePrefabSystem.cs:1607-1638`) — but it is called from exactly one place, over a hard-coded set of three types, `Stack`, `MeshColor` and `MeshGroup`, and only when the prefab's mesh changed (`:906-915`).

**The split is not even uniform within one field.** `WorkProviderSystem` (GameSimulation, `SystemOrder.cs:373`) recomputes `m_MaxWorkers` from `WorkplaceData` every pass for school buildings (`src/Game/Game.Simulation/WorkProviderSystem.cs:165`, `UpdateSchoolMaxWorkers` at `:193-197`, gated on `chunk.Has<Game.Buildings.School>()` at `:130`) and folds in installed-upgrade stats at `:171`, while leaving the field alone for every other building kind. So "does my edit reach placed buildings" is answered by reading the systems that touch the field, not by a rule.

**The wiki's three remedies, quoted** (https://cs2.paradoxwikis.com/Prefab_-_Quick_Start): "Option 1 Player action (easiest) — rebuild building; add/remove extension building or upgrade items (ex: cold storage). These actions trigger the game's own job to run -> reads the `WorkplaceData` you altered -> refreshes the employee `m_MaxWorkers` -> building panel shows increase number." "Option 2 Custom code — If you can find the specific game job using iLSpy, copy the same method used to complete Option 1, then run it when you like (ex: Options UI slider to trigger it)." "Option 3 Harmony patch code — Sometimes easier than option 2 as there are 1000's of code lines to research and you might not find a lucky hook. Could be brittle on game patch days."

**Verdict: Option 1's mechanism is confirmed by the query above.** Options 2 and 3 are advice rather than claims and the decompile neither supports nor contradicts them; what it adds is a fourth lever the wiki does not mention, and a warning about it.

**The fourth lever: tag the prefab entity `Updated`.** Three systems under `src/Game/Game.Prefabs/` query for `Updated`: `AreaInitializeSystem`, `UnlockSystem` and `VehicleCapacitySystem`. The last is the useful one — `{VehicleData, PrefabData}` with `Any = {Updated, Deleted}` (`src/Game/Game.Prefabs/VehicleCapacitySystem.cs:63-76`) — so re-deriving vehicle capacity after a prefab-data edit is a one-line `EntityManager.AddComponent<Updated>(prefabEntity)`. `CS2-Platter` uses exactly this shape after writing its own prefab data (`P_ParcelInitializeSystem.cs:104`). The warning is that the coverage is three systems out of the twenty-three in `PrefabUpdate`, so `Updated` is not a general "recompute everything downstream" signal and reaching for it as one produces a partial refresh that looks like a bug elsewhere.

**The wiki's own caution on mutating instance components, quoted in full** (https://cs2.paradoxwikis.com/Prefab_-_Quick_Start): "Only if you fully understand: which systems read them, what caches exist, what invariant you might violate […] Consider: mutating runtime components that are calculated by the game is riskier with side effects. In the example of max workers, asking the player to rebuild the building to refresh values is easier and safe (all their new buildings are already handled by changing `WorkplaceData` in the easier method)."

Rots: `CityServiceWorkplaceInitializeSystem`'s query shape and its `Modification5` registration; the three `Updated`-consuming prefab systems; the 292/210 lookup counts.

### Editing vanilla prefab entities in bulk, and adding your own component to them

The prefab entity is an ordinary entity, so a mod edits vanilla prefabs with an ordinary query. `Tree_Controller/Tree_Controller/Systems/ModifyVegetationPrefabsSystem.cs` is the cleanest example in the corpus and it does both halves of that:

- **Edit.** `SystemAPI.QueryBuilder().WithAllRW<PlaceableObjectData>().WithAll<Vegetation>().WithNone<Deleted, Overridden>()` (`:77-81`), walked on the main thread with `ToEntityArray(Allocator.Temp)` and written with `EntityManager.SetComponentData` (`:31-44`). The change is live for every subsequent placement because the placement pipeline reads `PlaceableObjectData` off the prefab entity each time — the "live read" class above, and the reason a cost edit needs no refresh trigger while a worker-count edit does.
- **Add a component to vanilla prefab entities.** `OnUpdate` queries `{PlantData}` with `None = {Deleted, Vegetation}` (`:83-86`) and adds the mod's own `Vegetation` tag to each, through `ToolOutputBarrier.CreateCommandBuffer()` (`:92-101`, the barrier at `:95` and the add at `:99`), gated by `RequireForUpdate(m_PlantDataWithOutVegetationQuery)` (`:88`) so it stops firing once every plant prefab is tagged. The system is registered at `SystemUpdatePhase.ToolUpdate` (`Tree_Controller/Tree_Controller/TreeControllerMod.cs:131`), and the source carries a comment explaining that choice of barrier — the public methods are callable from anywhere and therefore cannot use it (`:26`).

The pattern generalises: a mod that wants to select vanilla prefabs by a criterion the game does not express as a component adds its own tag to the prefab entities once, then queries on the tag. `Vegetation` is not an archetype-hook component — it never reaches an instance — it exists only to make a query cheap.

It is also worth noting where that runs from: `OnGameLoadingComplete` calls the cost edit when the user's setting says so (`ModifyVegetationPrefabsSystem.cs:104-112`, the call at `:110`), and the options page calls both methods directly when the setting is toggled mid-session (`Tree_Controller/Tree_Controller/Settings/TreeControllerSettings.cs:441-448`). So the edit-and-restore pair is driven by a user control rather than by the phase walk, which is why it needs the authoring baseline at all: without it, a second toggle would restore zero.

Rots: `PlaceableObjectData.m_ConstructionCost` and the `Vegetation` / `PlantData` component names.

### Synthesising a new prefab type

The recipe, all four steps cited:

1. **Instantiate.** `PrefabBase.Create<T>(string name)` is `ScriptableObject.CreateInstance<T>()` plus a name assignment (`src/Game/Game.Prefabs/PrefabBase.cs:417-422`); `Create(Type, string)` is the reflective form and throws `ArgumentException` for a type that is not a `PrefabBase` (`:424-433`). **The corpus does not use either** — zero `PrefabBase.Create` calls in 20 repositories against 52 `ScriptableObject.CreateInstance<...>` calls, which is the same thing written out (`CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:226/233`, `FindIt-CSII/FindIt/Systems/AutoVehiclePropGeneratorSystem.cs:99`, `Anarchy/Anarchy/ExtendedRoadUpgrades/UpgradesManager.cs:153`).
2. **Set the authoring fields** on the object directly.
3. **Attach authoring components.** `AddComponent<T>()` creates a `ScriptableObject` of that type, names it after the type, sets its `prefab` back-pointer and appends it (`PrefabBase.cs:190-202`) — and **throws `InvalidOperationException("Component already exists")` when one is already present** (`:192-195`), which is why `AddOrGetComponent<T>()` exists (`:152-168`). `AddComponentFrom(from)` is the copying form: `AddOrGetComponent` on the source's exact type, then `JsonUtility.FromJsonOverwrite(JsonUtility.ToJson(from), target)` (`:175-188`). **Corpus: 19 `AddComponentFrom` calls.** A frequent idiom is to build a detached authoring component and copy it in rather than mutating in place — `CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:241-244` creates a `PlaceableObject`, zeroes its cost and XP, and hands it to `AddComponentFrom`.
4. **Register.** `prefabSystem.AddPrefab(prefabBase)`, checked for `false`.

**Corpus: 60 `AddPrefab(` call sites across 10 repositories** — `RoadBuilder-CSII` and `ExtraAssetsImporter` 6 each, `FindIt-CSII` 4, `Recolor` 3, and one each in `Water_Features`, `Traffic`, `ExtraDetailingTools`, `CS2-Platter`, `CS2-NetworkTools`, `Anarchy`. `CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:220-349` is the fullest example, minting sized `ParcelPrefab`/`ParcelPlaceholderPrefab` pairs, a `UIAssetCategoryPrefab` toolbar tab, a cloned `ZonePrefab` and a single selector prefab.

**Custom `PrefabBase` subclasses in the corpus**, all deriving from a vanilla base rather than from `PrefabBase` where they need vanilla behaviour: `ParcelPrefab : StaticObjectPrefab` and `ParcelPlaceholderPrefab`, `ParcelSelectorPrefab` (Platter); `RoadBuilderPrefab : RoadPrefab, INetworkBuilderPrefab`, `LaneGroupPrefab : PrefabBase`, `FenceBuilderPrefab`, `PathBuilderPrefab`, `TrackBuilderPrefab` (RoadBuilder); `PalettePrefab : PrefabBase` and `PaletteSubCategoryPrefab` (Recolor); `WaterSourcePrefab` (Water Features); `ToolPrefab` (Network Tools); `FakePrefab : PrefabBase` (Traffic).

### Cloning a vanilla prefab, and the reference hygiene a clone needs

**`PrefabBase.Clone(string newName = null)` is the sanctioned route** (`src/Game/Game.Prefabs/PrefabBase.cs:399-415`). It instantiates the same concrete type, JSON-round-trips the prefab's own fields with `"components"` and `"m_NameOverride"` stripped from the payload, names the result `newName ?? name + " (copy)"`, and then rebuilds the component list by calling `AddComponentFrom` for each source component. Two consequences follow from that body and both matter:

- **The clone's `components` are fresh objects, not shared with the original.** `AddComponentFrom` creates a new `ScriptableObject` of the source type and JSON-overwrites it (`:175-188`). Mutating a clone's component cannot reach back into the original's.
- **The clone has no asset.** `PrefabBase.asset` is a property (`:64`), not a serialized field, so the JSON round trip does not carry it. That makes the clone `isBuiltin == false`, `isSubscribedMod == false`, `isPackaged == false` and therefore `isReadOnly == false` (`:36-62`), and it makes its `PrefabID` hash invalid, because `PrefabID`'s constructor only computes a hash from `prefab.asset` (`src/Game/Game.Prefabs/PrefabID.cs:15-36`). The clone's identity is therefore `(TypeName, name)` with no hash, and picking a fresh name is not optional.

**`PrefabSystem.DuplicatePrefab` adds the step `Clone` leaves out**: `Remove<ObsoleteIdentifiers>()` before `AddPrefab` (`src/Game/Game.Prefabs/PrefabSystem.cs:269-275`). Without it the clone inherits the original's obsolete identifiers, and `AddPrefab` registers each of them as an alias pointing at the clone (`:164-178`) — or, if the original registered them first, logs `Duplicate prefab ID: {0} ({1})` and drops them. Either way a save referring to the original by an obsolete id can resolve to the clone. **Corpus: 2 `DuplicatePrefab` calls against 0 direct `Clone` calls written as `.Clone(`**; `CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:295` calls `originalUnzonedPrefab.Clone("PlatterUnzoned")` through a cast, then `AddPrefab`s it at `:299` — without the `ObsoleteIdentifiers` removal.

**`Anarchy` is the best-commented clone in the corpus and also carries a reference-hygiene hazard.** `Anarchy/Anarchy/ExtendedRoadUpgrades/UpgradesManager.cs:144-207` builds each custom road-upgrade mode by hand rather than through `Clone`: instantiate a `FencePrefab`, copy the vanilla "Grass" prefab's components one by one with `AddComponentFrom`, then explicitly `Remove<UIObject>()` and build a _fresh_ `UIObject` with only the fields it wants. Its five-line comment states the rule better than any other source: "To avoid impacting the Grass prefab we need to replace the UIObject with a fresh instance. Every property besides name and icon can be copied over. There is probably a better way of doing this, but I need to be sure that we're not keeping any unintended reference to the source object so I'd rather manually copy over only the thing I need instead of relying on automatic cloning" (`:169-173`).

The hazard is one line above the copy. The loop reads:

```csharp
foreach (ComponentBase componentBase in grassUpgradePrefab.components)
{
    componentBase.prefab = fencePrefab;
    fencePrefab.AddComponentFrom(componentBase);
}
```

(`:159-163`.) That assignment mutates the **source** prefab's components, repointing each one's owning-prefab back-reference at the clone. It is unnecessary — `AddComponentFrom` reads only the JSON of `from` and never its `prefab` field (`PrefabBase.cs:182-188`) — and it leaves the vanilla Grass prefab holding components that believe they belong to a mod prefab, so `ComponentBase.GetComponent<T>()` called on any of them resolves against the wrong prefab (`ComponentBase.cs:39-50`). The game detects the same condition and logs it, but only inside `PrefabBase.OnEnable`, which has already run by this point: "Component on prefab {0} is referenced from another prefab: {1}" (`PrefabBase.cs:137-140`). Nothing re-checks it later. Recorded as an observed hazard rather than a reported bug — nothing in the corpus or the decompile shows a symptom, and I did not run the game.

**`FindIt` shows the hygienic alternative to cloning: derive selectively.** `FindIt-CSII/FindIt/Systems/AutoVehiclePropGeneratorSystem.cs:92-180` turns every vehicle prefab into a static prop by creating a fresh `StaticObjectPrefab`, sharing the mesh array by reference (`newPrefab.m_Meshes = original.m_Meshes`, `:113`), and copying exactly four components with `AddComponentFrom` — `UIObject`, `ThemeObject`, `AssetPackItem`, `ContentPrerequisite` (`:115-133`). The hygiene detail is `.m_Group = null` on the copied `UIObject` (`:117`): without it the derived prefab would join the original's toolbar group. It also adds `ObsoleteIdentifiers` deliberately, to migrate names it used in an earlier release (`:173-177`), and reads `original.asset?.database == AssetDatabase<ParadoxMods>.instance` to categorise per source mod (`:149-152`).

So the corpus has three cloning strategies and they are not equivalent: `Clone` (whole object, then strip), hand-copy every component (Anarchy), and derive by cherry-picking (FindIt). The last is the only one that cannot inherit something you did not think about.

Rots: `PrefabBase.Clone`'s two stripped JSON keys (`"components"`, `"m_NameOverride"`, `PrefabBase.cs:405-406`), and the `isBuiltin`/`isReadOnly` property chain.

### Regenerating a prefab in place: the entity is replaced, and what that leaves stale

**`PrefabSystem.UpdatePrefab` does not update anything; it destroys and re-creates.** The pending map is drained by `UpdatePrefabs()` at the top of `PrefabSystem.OnUpdate` (`src/Game/Game.Prefabs/PrefabSystem.cs:766-825`), and for each entry it:

1. Tags the **old prefab entity** `Deleted` (`:782`).
2. Rebuilds the prefab-component set from scratch by re-running every attached component's `GetPrefabComponents`, and creates a **brand-new entity** (`:783-798`).
3. Copies the old `PrefabData` — so the new entity keeps the same `m_Index`, and `m_Prefabs` needs no change (`:799`).
4. Carries the unlocked state across, by disabling `Locked` on the new entity when it was disabled on the old (`:800-803`).
5. Rewrites `m_Entities[key]` to the new entity (`:804`).
6. Calls `ReplacePrefabSystem.ReplacePrefab(oldEntity, newEntity, sourceInstance)` (`:805`).

Each iteration is individually try/caught, logging `Error when updating prefab: {0}` and continuing, with the UI error suppressed in editor mode (`:808-817`).

**The prefab entity's identity changes. That is the whole story of what goes stale.** `ReplacePrefabSystem` covers the ECS side thoroughly: its query is a 14-way `Any` over `PrefabRef`, `SubObject`, `SubNet`, `SubArea`, `PlaceholderObjectElement`, `ServiceUpgradeBuilding`, `BuildingUpgradeElement`, `Effect`, `ActivityLocationElement`, `CharacterElement`, `SubMesh`, `LodMesh`, `UIGroupElement` and `TutorialPhaseRef` (`src/Game/Game.Prefabs/ReplacePrefabSystem.cs:1551-1570`), and `ReplacePrefabJob` rewrites every `m_Prefab` field it finds from old to new, tagging each touched instance `Updated` and queueing it (`:1223-1254`). `EditorContainer.m_Prefab` is patched in the same pass (`:1245-1253`). A second job then tags any entity whose `PrefabRef` points at a _touched instance_ with `Updated` too, so owners see their children changed (`:1140-1172`). `BuildingUpgradeElement` buffers are copied across by hand (`:1727-1732`), system-held references are patched through `PrimaryPrefabReferencesSystem.PatchSystemReferences` (`:1724-1725`), and mesh batches are rebuilt when the prefab carried `MeshData` (`:1647-1670`, `:897-916`). Finalisation runs from `PrefabSystem.OnUpdate` after the phase, but only when something was actually replaced (`PrefabSystem.cs:760-763`).

**What that sweep cannot reach is any `Entity` value held in managed memory.** That is the whole residue, and `RoadBuilder` is the corpus's proof. `RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderSystem.cs:241-276`, its `UpdatePrefab`, does three things:

```csharp
var entity = prefabSystem.GetEntity(prefab);
EntityManager.AddComponent<DiscardedRoadBuilderPrefab>(entity);
prefabSystem.UpdatePrefab(prefab, entity);
// then: find and remove the entity from ToolbarUISystem's private m_LastSelectedAssets dictionary
// then: scan every UIGroupElement buffer and RemoveAt the stale reference
```

`m_LastSelectedAssets` is a `Dictionary<Entity, Entity>` private to a vanilla system, reached by reflection one frame after `OnCreate` because the system does not exist yet during the mod's own (`:63`). Nothing in the ECS sweep can see it, and a stale entry there points at an entity that is about to carry `Deleted`. The `UIGroupElement` scan (`:261-275`) is the mod's own choice rather than a gap in the sweep — that buffer _is_ patched by `ReplacePrefabJob` — and it removes the entry outright so the regenerated road leaves and re-enters the toolbar rather than appearing twice.

Two more details from the same file are the practical cost of this technique. **It must be throttled**: `OnUpdate` refuses to drain its queue while a drag is in progress or within 0.66 seconds of the last request (`:66-91`), and generation is queued rather than immediate (`:150-155`). And **the mod tags the outgoing entity with a marker of its own**, `DiscardedRoadBuilderPrefab` (`:245`), which its other queries then exclude (`:334`) — because between the call and the next `PrefabSystem.OnUpdate` both the old and the new prefab entity exist.

`survey-mods-techniques.md:192-204` calls this "the corpus's most hard-won prefab code" and it is right. **Verdict on the survey's explanation, though: it says the two clean-up steps "exist because `PrefabSystem.UpdatePrefab` leaves the toolbar and UI-group buffers holding stale references", and only the first half holds.** The toolbar dictionary is genuinely unreachable by the sweep; `UIGroupElement` is in `ReplacePrefabSystem`'s query list at `ReplacePrefabSystem.cs:1567` and _is_ repointed.

`RoadBuilder-CSII/RoadBuilder/Utilities/NetworkPrefabGenerationUtil.cs:36-128` is the generation half: it rebuilds `m_Sections`, `m_NodeStates`, `m_EdgeStates`, `m_AggregateType` and `m_InvertMode`, destroys and rebuilds `prefab.components`, and mints an id as `{typeInitial}{Guid}-{PlatformManager.instance.userSpecificPath}`.

Rots: `ReplacePrefabSystem`'s 14-component query list, and the three types `CheckInstanceComponents` reconciles (`Stack`, `MeshColor`, `MeshGroup`).

### Prefab identity, and where the collisions come from

**A `PrefabID` is three fields: `m_Type`, `m_Name`, `m_Hash`** (`src/Game/Game.Prefabs/PrefabID.cs:9-13`). `Equals` compares all three (`:45-52`), `GetHashCode` deliberately ignores the type (`:54-57`), and `ToString` renders `Type:Name (Hash)` or `Type:Name` (`:70-77`).

Three facts about how it is built decide everything else (`:15-36`):

- **`m_Type` is `prefab.GetType().Name` — the short name, with no namespace.** `Game.Prefabs.ParcelPrefab` and `Platter.Prefabs.ParcelPrefab` produce byte-identical ids.
- **`m_Hash` comes from the asset, or is invalid.** For an asset carrying a platform id, the hash is computed from that string; otherwise it is `asset.id.guid`; and when `asset` is null — which is every prefab a mod creates at runtime — the hash stays default and the id is `(Type, Name)` alone.
- The `m_Hash` field only round-trips through a save when the format carries `FormatTags.PrefabIDHash` (`:100-104`), so older saves resolve on `(Type, Name)`.

**A mod-created prefab is therefore identified by nothing but its class's short name and the string you assigned.** That is the whole namespace of collisions, and `AddPrefab` handles one the worst possible way: it logs `Duplicate prefab ID: {0}` and **skips only the index registration**, while still appending the prefab to `m_Prefabs`, creating its entity, and returning `true` (`src/Game/Game.Prefabs/PrefabSystem.cs:152-159`, `:179-181`). The loser of a collision is a fully live prefab that `TryGetPrefab(PrefabID)` can never find. Two mods that both create a `StaticObjectPrefab` named `"Bench"` produce exactly that, with one warning line.

Corpus practice is consistent about avoiding it without ever saying why: names are prefixed with the mod's own token. `Traffic.FakePrefab` (`Traffic/Code/Systems/ModDefaultsSystem.cs:32`), `PlatterUnzoned` and `PlatterCat` (`CS2-Platter/Platter/Systems/P_PrefabsCreateSystem.cs:295/262`), `WaterSource ` as a declared prefix constant (`Water_Features/Water_Features/Systems/AddPrefabsSystem.cs:33`).

**A legacy alias exists and a mod will not encounter it by accident.** `TryGetLegacyModPrefabID` registers a second id for any prefab whose asset carries a numeric, positive platform id, hashing the parsed integer rather than the string (`PrefabSystem.cs:277-292`, registered at `:160-163`). This is the pre-Paradox-Mods identifier shape for subscribed content.

**`ObsoleteIdentifiers` is the rename-migration mechanism**, and it is an authoring component with two empty hooks and one field, `PrefabIdentifierInfo[] m_PrefabIdentifiers` (`src/Game/Game.Prefabs/ObsoleteIdentifiers.cs:10`, entry type at `src/Game/Game.Prefabs/PrefabIdentifierInfo.cs:6-28`). `AddPrefab` registers every entry as an additional index into the same prefab (`PrefabSystem.cs:164-178`), so a save written against the old name still resolves. `PrefabIdentifierInfo.GetPrefabID` throws `Exception("Invalid hash in ObsoleteIdentifier")` on a malformed hash string (`:22-25`), and `PrefabBase.MarkCurrentPrefabObsolete()` is the helper that appends the current identity to the array (`PrefabBase.cs:80-102`), called automatically on deserialising a version-0 prefab asset (`:104-111`).

**Corpus: 14 `ObsoleteIdentifiers` references, in two repositories.** `ExtraAssetsImporter/MOD/AssetImporter/PrefabImporterBase.cs:248-275` builds an entry per legacy naming scheme, switching on a user-visible compatibility setting so a player upgrading from an older release keeps their placed assets; `FindIt-CSII/FindIt/Systems/AutoVehiclePropGeneratorSystem.cs:172-176` maps each generated prop back to the names an earlier version gave it.

**On declaring a mod prefab class inside `namespace Game.Prefabs`.** Two mods do it: `CS2-Platter/Platter/Prefabs/ParcelPrefab.cs:6` (and its two siblings) and `CS2-NetworkTools/NetworkTools.Mod/Prefabs/ToolPrefab.cs:6`. Neither comments on why. **Verdict: `survey-mods-techniques.md:183` explains it as "prefab identity is `(TypeName, name)` via `PrefabID`, and this placement is a deliberate identity/serialization choice", and the first clause is right while the conclusion does not follow.** Because `PrefabID` stores only `GetType().Name`, the namespace is invisible to prefab identity, so moving the class into `Game.Prefabs` changes nothing about how it is found or saved. A grep for the literal `"Game.Prefabs` across the decompile returns nothing but the generated `AssemblyTypeRegistry`, so no namespace-based lookup exists either. What the placement does buy is that `using Game.Prefabs;` alone resolves the type in the mod's own files — and what it costs is that the type now competes for a short name in the same space as 1274 game types, so a future vanilla `ParcelPrefab` becomes an ambiguous reference at compile time. The real reason those two authors did it is not recorded anywhere I could read.

Rots: the `PrefabID` field set and its serialization gate `FormatTags.PrefabIDHash`; the `-1000000000` obsolete sentinel; `ObsoleteIdentifiers` / `PrefabIdentifierInfo` member names.

### How a prefab's identity survives a save

`PrefabSystem` implements `ISerializable` and `IDefaultSerializable` (`src/Game/Game.Prefabs/PrefabSystem.cs:24`) and what it writes is a **list of `PrefabID`s, not entities** (`:827-865`). Live prefabs come first, then obsolete ones, each guarded by `EntityManager.IsComponentEnabled<PrefabData>(entity)` — the enableable flag that `ecs-in-this-game.md` records as meaning "this prefab still exists".

On load, `Deserialize` reads each id back and looks it up: found ids become `LoadedIndexData` pairs, unknown ones go into `m_LoadedObsoleteIDs` keyed by save index (`:867-911`). `UpdateLoadedIndices` then clears every prefab entity's `LoadedIndex` buffer and refills it (`:920-937`), so the buffer is a per-prefab list of the save-file indices that resolve to it — which is how a prefab that absorbed two obsolete ids ends up owning several. Obsolete prefabs get a negative `PrefabData.m_Index` decoded as `-1 - index` (`:894-896`, read back at `:969-972`), and `GetPrefabName` falls back to the obsolete id's name for display (`:979-990`). A missing id resolves to the literal `PrefabID("[Missing]", "[Missing]")` (`:950-957`).

This is the mechanism behind the save-side behaviour `ecs-in-this-game.md` records at `src/Game/Game.Serialization/ResolvePrefabsSystem.cs:511-537`, where `PrefabData` is disabled on prefabs a save references and the install no longer has.

Rots: the two-list save format and the `Version.obsoletePrefabFix` gate at `:874`.

### Loading an asset from code

**`Colossal.IO.AssetDatabase` is the layer under the prefab system, and `AssetDatabase.global` is the aggregate.** Four statics exist: `global` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/AssetDatabase.cs:179`), `game` (`:181`), `user` (`:183`) and `packages` (`:185`), plus `GetTransient(...)` for a throwaway one (`:301-304`). `global` is a collection of registered databases (`:187`) rather than a database itself.

The read surface is `IAssetDatabase` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/IAssetDatabase.cs`): `TryGetAsset` and `GetAsset` each in four keyings — by `Uri`, by string uri, by `Hash128` guid, and by `SearchFilter<T>` — plus `GetAssets<T>(SearchFilter<T>)`, `AllAssets()`, `DeleteAsset` and `UnloadAllAssets`. The write surface is `ILocalAssetDatabase`, which adds `AddAsset<TAssetData, TData>(AssetDataPath, TData, Hash128 forceGuid = default)` and two simpler overloads, `MoveAssetTo`, `CopyAssetTo`, `Exists<T>` and `MarkForDeletion` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/ILocalAssetDatabase.cs`). `AssetDatabase.global` is not an `ILocalAssetDatabase`; `AssetDatabase.user` is.

**`PrefabAsset` is the asset kind that carries a prefab**, and `Load()` / `Load<T>()` return the `ScriptableObject` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/PrefabAsset.cs:487-492`). It saves as text by default (`kDefaultFormat = ContentType.Text`, `:328`) with a binary option (`:425-462`). `GameManager.LoadPrefabs` is nothing more than `assetDatabase.GetAssets(default(SearchFilter<PrefabAsset>))`, `item.Load() is PrefabBase`, `m_PrefabSystem.AddPrefab(...)` (`src/Game/Game.SceneFlow/GameManager.cs:1900-1949`) — the same three calls a mod would write.

**Corpus reads of the database, most of them one-liners.** The near-universal one is `AssetDatabase.global.LoadSettings(name, settings, defaults)`, in 8 of 20 repositories, which is settings rather than assets. The asset reads that matter: locating the mod's own assembly asset to derive its on-disk directory, `AssetDatabase.global.GetAsset(SearchFilter<ExecutableAsset>.ByCondition(x => x.definition?.FullName == assemblyName))` (`AreaBucket/Mod.cs:56`, `CS2-WriteEverywhere/BelzontWE/Enum/WEMemberSource.cs:44`); finding a UI module asset by name (`CS2-WriteEverywhere/BelzontWE/WriteEverywhereCS2Mod.cs:106`); enumerating every prefab asset to find those carrying a sidecar (`CS2-WriteEverywhere/BelzontWE/Utils/WEAssetsSettingsLoaderUtility.cs:31`); and testing an existing prefab's provenance with `original.asset?.database == AssetDatabase<ParadoxMods>.instance` (`FindIt-CSII/FindIt/Systems/AutoQuantityPropGeneratorSystem.cs:155`).

**`ExtraAssetsImporter` is the only mod that registers a database of its own, and it is the deepest asset work in the corpus.** It declares a descriptor type and exposes `AssetDatabase<EAIAssetDataBaseDescriptor>.instance` (`ExtraAssetsImporter/MOD/DataBase/EAIDataBaseManager.cs:27`), registers it with `AssetDatabase.global.RegisterDatabase(...)` and then populates it from its own data source (`:116-129`), and unregisters it on dispose (`:244`). A descriptor is five members: `name`, `canWriteSettings`, `dlcId`, `assetFactory`, `dataSourceProvider` (`src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/IAssetDatabaseDescriptor.cs:7-17`). Everything it imports goes in through `AddAsset<PrefabAsset, ScriptableObject>(path, prefab, Hash128.CreateGuid(name))` followed by `Save()` (`ExtraAssetsImporter/MOD/AssetImporter/ImportersUtils.cs:130-131`, `MOD/AssetImporter/PrefabImporterBase.cs:199`), and the resulting prefab is handed to `PrefabSystem.AddPrefab` from the main thread (`ImportersUtils.cs:64-70`). Its own cache-hit path is the readable version of "load an asset from code": `dataBase.TryLoadPrefab<RenderPrefab>(assetPath, out renderPrefab)`, then register it if the prefab system does not know it yet (`:60-70`). The mod also writes geometry assets (`:104`), locale assets (`:153`), image assets (`:258`) and category prefabs (`:301`) through the same API, and its extension helpers are worth naming because they fill an obvious gap in `ILocalAssetDatabase`: `GetOrAddAsset`, `TryGetOrAddAsset<TAsset>`, `LoadPrefab<T>` and `TryLoadPrefab<T>` (`ExtraAssetsImporter/MOD/ClassExtension/ILocalAssetDatabase.cs:16/58/70/75`).

Note the boundary: creating textures, meshes and surfaces is asset authoring and out of scope; the database calls that _store and retrieve_ them are not.

Rots: the `IAssetDatabase` / `ILocalAssetDatabase` member lists and the four `AssetDatabase` statics — re-read `src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/IAssetDatabase.cs` and `AssetDatabase.cs:177-185`.

### Serving files over the game's own resource scheme

**The UI reads files through `coui://<host>/<path>`, and a host is a name mapped to one or more directories on disk.** The scheme constant is `kCouiScheme = "coui"` / `kCouiProtocol = "coui://"` (`src/Colossal.UI/Colossal.UI/DefaultResourceHandler.cs:363-365`), and a request counts as local when its scheme is `coui` or `file` (`:67-77`).

**Registration is one call**: `UISystem.AddHostLocation(string hostName, string path, bool shouldWatch = true, int priority = 0)` (`src/Colossal.UI/Colossal.UI/UISystem.cs:254-273`). It appends to a `Dictionary<string, List<(string path, int priority)>>`, keeps the list sorted by priority, ignores a duplicate path, logs `Added host location {0} {1}`, and raises `onHostLocationAdded` with the watch flag. A second overload takes several paths at once (`:275-304`), and `RemoveHostLocation` exists (`:306+`).

**Resolution walks the host's paths in order and takes the first that reads.** `RequestResourceAsync` looks the host up, fails with `"Invalid host locations map."` when the host is unknown or empty, and otherwise tries each registered root until one returns without error (`DefaultResourceHandler.cs:599-623`, and identically for streams at `:625-648`). So two mods registering the same host name do not conflict — they stack, and priority decides who is asked first.

**The game registers three hosts of its own** and they are the shapes to copy: `gameui` → `EnvPath.kContentPath + "/Game/UI"` at bootstrap (`src/Game/Game.UI/UISystemBootstrapper.cs:53`); `ui-mods` → the directory of every mod's UI module asset, watched only when the module is local (`src/Game/Game.Modding/ModManager.cs:468/479`, and `UIModuleAsset.couiPath => "coui://ui-mods/" + fileName` at `src/Colossal.IO.AssetDatabase/Colossal.IO.AssetDatabase/UIModuleAsset.cs:41`); and one host per `UIHostAsset` found in the database at UI initialisation, routed to `AddDatabaseHostLocation` instead when the asset's scheme is `assetdb` (`src/Game/Game.SceneFlow/GameManager.cs:1750-1760`).

**Corpus: 5 `AddHostLocation` calls in 4 repositories, and 347 `coui://` string literals.** The two patterns are a read-only icon directory beside the mod's assembly and a watched temp directory for generated files:

- `CS2-Platter/Platter/PlatterMod.cs:162` — `AddHostLocation("platter", assemblyPath + "/Assets/")`, consumed as `coui://platter/logo.svg` (`Systems/P_PrefabsCreateSystem.cs:263`).
- `FindIt-CSII/FindIt/Mod.cs:50` — `AddHostLocation("findit", Path.Combine(Path.GetDirectoryName(asset.path), "images"), false)`, the path derived from the mod's own `ExecutableAsset`, watching disabled.
- `RoadBuilder-CSII/RoadBuilder/Mod.cs:36/40` — two hosts, `roadbuilderthumbnails` pointed at a temp folder **with watching on**, and `roadbuildericons` pointed at a shipped directory with it off. The watched one holds runtime-generated thumbnails (though watching is not what serves them, see the 2026-08-04 verdict below): `RoadBuilder-CSII/RoadBuilder/Utilities/ThumbnailGenerationUtil.cs` composes an SVG with `System.Xml.Linq` (`:110/168`), saves it into that folder (`:88`) and returns `coui://roadbuilderthumbnails/{id}.svg` (`:90`).
- `AreaBucket/Mod.cs:90` is the same call, commented out.

Host name counts across the corpus's `coui://` literals: `roadbuildericons` 249, `uil` 78, `nt` 22, `findit` 16, `we.k45` 14, `ui-mods` 7, `platter` 4, `roadbuilderthumbnails` 2, `extradetailingtools` 1. Three of those hosts are used without a visible registration: `uil` and `we.k45` come from shared libraries whose sources are absent from the checkout, and `nt` is `CS2-NetworkTools`' own but is registered neither by an `AddHostLocation` call nor by any declarative host file in the repository — presumably by its `LucaModBase<T>` framework base, which `mod-lifecycle-and-ordering.md` records as unreadable here.

**Where a `coui://` URL is consumed on the prefab side.** `UIObject.m_Icon` is a plain string (`src/Game/Game.Prefabs/UIObject.cs:18`) and `ImageSystem.GetIcon(prefab)` returns it resolved when non-empty, otherwise null (`src/Game/Game.UI/ImageSystem.cs:61-68`). `GetIconOrGroupIcon` falls back to the UI group's icon (`:81-88`). **`GetThumbnail` is the fallback chain that matters**: icon if set, else `"Media/Placeholder.svg"` when thumbnails are disabled, else `prefab.thumbnailUrl` with `?width=128&height=128` appended (`:101-115`) — and `thumbnailUrl` is `"thumbnail://ThumbnailCamera/" + GetPrefabID().ToUrlSegment()` (`src/Game/Game.Prefabs/PrefabBase.cs:32`, segment builder at `src/Game/Game.Prefabs/PrefabID.cs:59-68`). So a prefab with no `UIObject` icon gets a live render, keyed on its prefab id, through a second scheme the game's own resource handler adds on top of `coui`: `thumbnail`, alongside `screencapture` and `useravatar` (`src/Game/Game.UI/GameUIResourceHandler.cs:23-27/42-47`).

**Verdict (2026-08-03 re-sweep): the three host registrations hold against the install, which the original pass could not check.** `gameui`'s target directory exists and is the one the bootstrap names — `Cities2_Data/Content/Game/UI/`, holding `index.html`, `index.js`, `index.css` beside `Fonts/`, `Media/` and `Static/` — and the third registration's declarative half is visible beside them as `gameui.uiHost`, the `UIHostAsset` the database picks up. `ui-mods` is registered from the body of `ModManager.AddUIModule` that an uninitialised manager skips, so the host and the module's `coui` path land together or not at all (`ModManager.cs:477-482`; `mod-lifecycle-and-ordering.md` owns the timing). The `Media/` directory under the `gameui` host is also what makes `custom-tools.md`'s mode-icon claim true: a bare `Media/...` src in the frontend resolves under `coui://gameui/`, a directory no mod can register into.

**Verdict (2026-08-04 re-sweep, corpus read at 22 repositories): the watch flag was never what made a runtime-written file appear, and what it does instead is reload the whole view.**

The claim came from this file's own reading of the one corpus repository that passes `true` explicitly, for a directory of generated thumbnails (`RoadBuilder-CSII/RoadBuilder/Mod.cs:36`, above), generalised into a statement about the game — the precedence inversion `../SOURCES.md` entry 11 forbids. The decompile is the authority and it overturns the causal half.

`shouldWatch` reaches exactly one consumer. `AddHostLocation` raises `onHostLocationAdded` carrying it (`src/Colossal.UI/Colossal.UI/UISystem.cs:254-273`), and `UILiveReload.OnHostLocationAdded` is the only subscriber, building a `BufferedFileSystemWatcher` over the path when the flag is set and nothing at all when it is not (`src/Colossal.UI/Colossal.UI/UILiveReload.cs:209-231`). A view constructs that component only when its settings carry `liveReload` (`src/Colossal.UI/Colossal.UI/UIView.cs:260-263`), and `UIManager` sets `liveReload = developerMode` (`src/Colossal.UI/Colossal.UI/UIManager.cs:177-189`), which the game passes as `configuration.uiDeveloperMode` (`src/Game/Game.SceneFlow/GameManager.cs:1745`, the launch option parsed at `:370-373`). **So the game's own UI view carries a watcher under that option, and under one other thing:** `UIManager`'s constructor runs `AssetDatabase.global.LoadSettings("UIManager Settings", m_Settings, m_Settings)` on the line after seeding the field (`UIManager.cs:191`), and `liveReload` is a settable property on that settings type (`:54`), so a `SettingAsset` under that name in any registered database overrides the launch option. None ships — neither `FallbackSettings.coc`, `Settings.coc`, `SettingsManager.coc` nor `UserState.coc` in the 1.6.0f1 install names `UIManager` or `liveReload` — so a player ordinarily has no watcher, which is a default rather than a guarantee. One other view does: the fatal-error fallback sets `liveReload = true` explicitly on a `UIManager` built with `developerMode: false` (`GameManager.cs:1687-1690`, `:1719-1721`), but it runs on its own `UISystem` behind a fatal resource handler, so no mod host is registered there and a mod never meets it.

**What the watcher does is reload the view, not refresh the file.** `OnChanged` sets `ReloadType.Page` for a `.js`, `.css` or `.html` change and `ReloadType.Media` for anything else (`UILiveReload.cs:260-295`). The media path is not an image-cache sweep: `Update` first calls `UpdateURL(m_Target.liveReloadUrl)` (`:337`), which `LoadURL`s `assetdb://gameui/Static/reload.html` (`UIView.cs:55/221`, the page present in the install at `Cities2_Data/Content/Game/UI/Static/reload.html`), then after the delay calls `uiSystem.ClearCachedUnusedImages()` (`:341-343`, the public passthrough at `UISystem.cs:333-335`) and falls through to `UpdateURL(m_Target.url)` (`:367`), navigating back. The document is gone by the time the clear runs, so **"unused" spares nothing and the whole UI rebuilds** — which is why a mod writing files at runtime registers its host with watching off.

Resolution itself holds no content cache — `RequestResourceAsync` walks the host's paths and issues a fresh `UnityWebRequest` per attempt (`DefaultResourceHandler.cs:599-623`, `:692-703`) — so a file written after startup is served whenever the frontend next asks.

**But the host walk is not the entry point, and the branch in front of it collides with mod file names.** `OnResourceRequest` starts at `TryPreloadedResourceRequestAsync` (`:428`, body at `:650-690`), which sends a local request straight to `RequestResourceAsync` **unless** its host is `preloaded` or `IsImageRequest` holds — that being an extension match against an 11-entry `ImageExtensions` list, `.png .jpg .jpeg .gif .bmp .psd .tga .astc .pkm .dds .ktx`, `.svg` absent (`:25-29`, `:81-87`). For those, it first runs `Resources.LoadAsync<Texture>(Utils.CombinePaths("UI/SharedImages", Path.GetFileNameWithoutExtension(requestData.UriBuilder.Path)))` (`:675`, the path constant at `:373`) and only falls through to the host walk when `request.asset == null` (`:677-681`); a hit is served as a Unity resource user image (`:687`) and the mod's own file is never read. So a raster file served over a mod host whose base name matches a shipped shared image is shadowed by it, permanently and silently. `.svg` never takes this branch, which is why the corpus's icon hosts — overwhelmingly `.svg` — never met it. `ToFullPath` builds the disk path from `UriBuilder.Uri.LocalPath` (`:131-146`), which excludes the query, and the `coui` branch reads no query at all — `DefaultResourceHandler`'s only two `UrlQuery` reads, `fallback` and `mipBias`, are in its `assetdb` branch (`:530`, `:557`), and the subclass the game actually installs reads several more (`width`, `height`, `op`, `alloc`, `size`, `liveView`, and the whole query handed to a save-preview settings parser) on its own `thumbnail`, `screencapture` and `useravatar` schemes alone (`src/Game/Game.UI/GameUIResourceHandler.cs:137-160`, `:269`, `:309-314`, installed at `GameManager.cs:1747-1749`). So a version parameter on a fixed file name reaches the same file.

Unconfirmed: whether a rewritten file at an unchanged URL is re-fetched, which is what decides whether the version query is needed at all. The C# names an image cache but never its key — `ClearCachedUnusedImages` bottoms out in `CSharp_UISystem_ClearCachedUnusedImages` (`src/cohtml.Net/cohtml.Net/cohtmlNativePINVOKE.cs:1428`) — and the game's own frontend busts no image URL anywhere, its one URL-keyed structure being the opt-in prefetch registry in `game-ui/common/image/preload.ts` (`src-ui/source.js:39702-39723`). No source `../SOURCES.md` lists settles it. The engine's own vendor documentation is not one of them — the sibling Gameface plugin reads it and this pipeline does not — so what it does or does not cover is outside what this file can cite, and the shipped marker is worded to the limit of the sources here rather than to that. What would settle it: rewrite a file under a registered host in a running game and watch whether the view re-requests it, over that plugin's connection to the live view.

Corpus, for the record rather than as warrant: the frontend entry added on 2026-08-04 registers a host over its own data directory with watching explicitly off and a `?v={counter}` on two fixed file names it rewrites per screenshot (`HallOfFame/HallOfFame/Mod.cs:152-160`, `HallOfFame/HallOfFame/Services/ScreenshotSnapshot.cs:26-66`), contributing `halloffame` 3 and further `ui-mods` literals (`HallOfFame/HallOfFame/Settings.cs:98`, `Systems/StatsNotificationSystem.cs:96`). The host-name table above was not re-run for this checkout and stays the 20-repository sweep it says it is. ### What the install's packaged content actually holds (2026-08-03 re-sweep)

Added by ticket 15b, the first pass to open a `.cok`. This topic's material had been derived from the loader alone.

**Every `.cok` is a plain zip**, stored rather than deflated, one entry per asset beside a `.cid` sibling; a zip reader opens the 4 GB `Blob.cok` without unpacking it. What is inside splits three ways, and the split is what nothing had recorded:

- **Art only, in the big packages.** `Cities2_Data/Content/Game/Blob.cok` is 27,910 entries — 13,012 `.Material`, 8,442 `.Geometry`, 5,832 `.Surface`, 456 `.Animation`, plus textures and atlases — and **not one `.Prefab`**. The `VT*` and `MidMips*` sets are virtual-texture data and one blob each.
- **Prefabs, but only for content packs.** A `Prefabs.cok` in each of the seven DLC directories under `Cities2_Data/Content/`, plus `Content/Game/Prefabs_FreeUpdate02.cok`: 1,571 `.Prefab` entries across the eight. Each entry is a **self-describing binary key/value stream** — UTF-16LE type names and field names inline, values inline, no schema needed. `Playground04/Playground04.Prefab` reads as `Game.Prefabs.BuildingPrefab, Game` named `Playground04`, with a `components` list whose second element is `Game.Prefabs.ServiceConsumption, Game` carrying `m_Upkeep = 2000`, `m_ElectricityConsumption = 500`, `m_WaterConsumption = 0`, `m_GarbageAccumulation = 100`, `m_TelecomNeed = 0` — field order and types exactly as `src/Game/Game.Prefabs/ServiceConsumption.cs:14-22` declares them, four `int` then one `float`, with distinct tag bytes for the two. Values differ per prefab across the package (`ChirperPark01` 1000/250/0/100, `ParkCafe01` 4000/750/500/200, `BasketballCourt04` 8000/3000/10000/150), so this is real authoring data and not a template.
- **The base game's own prefabs are in neither.** No `.cok` in the install holds one. They are Unity serialized objects in `Cities2_Data/resources.assets` (221 MB), which carries **type names and no field names**: `grep -ac` over it returns 203 for `ServiceConsumption` and 257 for `BuildingPrefab`, and 0 for `m_Upkeep`, `m_ElectricityConsumption` and `m_GarbageAccumulation`. Reading a value there needs a Unity serialized-file parser driven by the field order of the decompiled class — a derivation, not a read. The same limit covers the input action asset, which `Resources.Load` pulls from the same file.

This bears on `conflicts.md`'s open pre-launch-balance entry, where it is written up as an amendment to that entry's `**Established.**` section; nothing here is a ruling.

**Source-list gap, corrected.** `docs/SOURCES.md` entry 5 described the whole `.cok` set as "the shipped prefabs, assets and their data, in the asset-database package format" and said the pipeline had not opened one. Both halves were wrong once opened: the format is a plain zip, and the prefab/art split plus the base-game exclusion is the fact a later pass needs. The entry now records all three cases and points a base-game value question at the running game instead.

## Bridge

This is a technique topic. Four mechanics areas need something specific from it, and in every case the thing they need is which of the three layers their subject lives on.

- **`zoning-buildings-and-land-value`** needs the most, because growable buildings are the one place where the archetype is decided by a _second_ prefab. `SpawnableBuilding` and `SignatureBuilding` forward both of their hooks to the zone prefab, parameterised by building level (`src/Game/Game.Prefabs/SpawnableBuilding.cs:44-65`, `SignatureBuilding.cs:37/48`), and `ZonePrefab` fans that out to every `IZoneBuildingComponent` it carries (`src/Game/Game.Prefabs/ZonePrefab.cs:48-75`). It also owns the corpus's clearest worked example of the stale-instance problem: `WorkplaceData.m_MaxWorkers` on the prefab entity against `Game.Companies.WorkProvider.m_MaxWorkers` on the building, refreshed only on `Created` or on an upgrade change (`src/Game/Game.Buildings/CityServiceWorkplaceInitializeSystem.cs:219-250`). And it needs `BuildingPrefab`'s conditional archetype — three extra component types appear only when the prefab entity already carries a `BuildingUpgradeElement` buffer (`src/Game/Game.Prefabs/BuildingPrefab.cs:58-79`), which is why adding an upgrade to a building prefab calls `RefreshArchetype` again (`:80-93`).
- **`roads-and-traffic`** needs the twin-archetype case, because a network prefab produces two different instance archetypes from one component set: `NetData.m_NodeArchetype` and `m_EdgeArchetype`, built by calling `GetArchetypeComponents` twice against differently seeded sets (`src/Game/Game.Prefabs/NetPrefab.cs:31-53`, with the seed-reading branch at `:18-29`). It also needs the `Game.Prefabs.SubNet` / `Game.Net.SubNet` and `Game.Prefabs.SubLane` / `Game.Net.SubLane` pairs, since a network prefab's sub-net buffer is a list of curves and prefab references while the instance's is a list of spawned entities, and both bind in a query. And a mod that lets the player build roads at runtime lands on the regeneration finding whole — `RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderSystem.cs:241-276` is that topic's material as much as this one's.
- **`transportation-and-vehicles`** needs the one place where tagging a prefab entity `Updated` actually re-derives something: `VehicleCapacitySystem` queries `{VehicleData, PrefabData}` with `Any = {Updated, Deleted}` (`src/Game/Game.Prefabs/VehicleCapacitySystem.cs:63-76`) and is registered in `PrefabUpdate` (`src/Game/Game.Common/SystemOrder.cs:1024`). It also has its own `RefreshArchetype` overrides, `MovingObjectPrefab` (`src/Game/Game.Prefabs/MovingObjectPrefab.cs:31-45`) and `TrainPrefab` (`TrainPrefab.cs:79-128`), so a vehicle's instance archetype is not built by the plain object path.
- **`placement-definitions`** is the seam where a prefab becomes an instance. `CreationDefinition.m_Prefab` and `m_SubPrefab` are prefab **entities** (`src/Game/Game.Tools/CreationDefinition.cs:6-8`), and the archetype the resulting instance gets is `ObjectData.m_Archetype` on that prefab entity (`src/Game/Game.Prefabs/ObjectPrefab.cs:31-46`). Everything a definition-rewriting mod does — the technique the catalog credits to Tree Controller — depends on knowing that the definition holds the middle layer, not the authoring object and not the placed entity. `PlaceableObjectData` and `ObjectGeometryData` are the two prefab-entity components the placement pipeline reads, and `CS2-Platter/Platter/Systems/Parcels/P_ParcelInitializeSystem.cs:107-164` is the readable example of a mod writing both.

Going the other way, three technique topics take material from here rather than rediscovering it:

- **`mod-lifecycle-and-ordering`** is already shipped and owns _when_ a system runs. Two corrections belong to it rather than here: `PrefabUpdate` is driven every `MainLoop` frame rather than only when updates are pending (`src/Game/Game.Prefabs/PrefabSystem.cs:756-764`), and the phase's 23 vanilla occupants are listed at `SystemOrder.cs:1004-1026`. The six prefab-registration timings tabulated above are that topic's material too, since four of the six are lifecycle hooks.
- **`save-serialization`** owns the format; it should take from here that prefab references cross a save as `PrefabID` strings rather than entities (`PrefabSystem.cs:827-865`), that unresolved ids become negative `PrefabData.m_Index` values (`:894-896`), and that `LoadedIndex` is the per-prefab list of save indices resolving to it (`:920-937`).
- **`frontend-and-injection`** owns the Cohtml side; it should take the host-location mechanism from here — `AddHostLocation`'s signature and the priority-ordered first-hit-wins resolution (`src/Colossal.UI/Colossal.UI/UISystem.cs:254-273`, `src/Colossal.UI/Colossal.UI/DefaultResourceHandler.cs:599-623`) — since that is what makes `coui://<mod>/icon.svg` resolve at all, and the `thumbnail://` fallback chain in `src/Game/Game.UI/ImageSystem.cs:101-115`.

- **~~Whether `PrefabSystem.UpdatePrefab` is safe to call on a vanilla prefab was not established.~~ Settled 2026-08-03 against the running game (source 8); this dead end is closed.** The only corpus caller regenerates its own prefabs (`RoadBuilder-CSII/RoadBuilder/Systems/RoadBuilderSystem.cs:247`), and nothing in the decompile forbade it, but nothing exercised it either.

  **The experiment.** In a loaded city, `Game.Buildings.Building` + `PrefabRef` matched 958 entities. Instance `50901:1` resolved through `PrefabRef` → `PrefabData` → `PrefabSystem.GetPrefab<PrefabBase>` to `CityPark03`, a vanilla `Game.Prefabs.BuildingPrefab` on prefab entity `12530`. `UpdatePrefab(prefab, Entity.Null)` was called on it and the drain allowed to run.

  **Result: it works, and the city is undisturbed.** Prefab entity `12530` no longer exists; the instance's `PrefabRef` now points at `50411:25`, which carries `PrefabData` and resolves back to the same `CityPark03` authoring object; the building count is still 958. So the replacement path carries vanilla instances across exactly as it carries a mod's own.

  **Two facts worth shipping came out of it.** A prefab entity does not survive its own update, so any cached `Entity` is stale afterwards and the safe form is to hold the `PrefabBase` and re-resolve. And `UpdatePrefabs()` wraps each prefab in its own `try`/`catch` that logs `Error when updating prefab: {0}` and continues (`PrefabSystem.cs:808-817`), so a failed rebuild leaves the registry on the old entity and returns nothing to the caller.

  **Both limits closed 2026-08-03, in a second run, and the second one overturned the headline.** Three prefab families were regenerated in one session — `CityPark05` (`BuildingPrefab`), `Pavement Path` (`PathwayPrefab`) and `CarTrailer01` (`CarTrailerPrefab`), chosen because the net prefab calls the archetype hook twice with `Node`/`Edge` seeds and the moving-object prefab builds two archetypes. All three behaved identically to the building: old prefab entity gone, instances remapped, counts unchanged (958 buildings, 5,564 edges, 5,544 vehicles).

  **The save/load round trip completed and the city is intact — but the save logged a critical.** `[SceneFlow] [CRITICAL] Cached ServiceUpkeepData not found Entity(50411:51)`, where `50411` is the _new_ prefab entity `UpdatePrefab` minted for `CityPark05`. Post-load the city is healthy, every count holds, `CityPark05` resolves at `50411:51`, and that prefab entity does carry its `ServiceUpkeepData` buffer — so the buffer was never the problem.

  **The problem is a vanilla managed cache keyed by prefab `Entity`.** `ServiceConsumptionGlobalMode.RestoreDefaultData` looks up `m_CachedUpkeepDatasDatas[entity]` and logs that critical on a miss (`src/Game/Game.Prefabs.Modes/ServiceConsumptionGlobalMode.cs:126-152`, the log at `:149`). The cache was populated against the _original_ prefab entity; `UpdatePrefab` destroyed it and minted a new one, so the key no longer resolves. The buffer itself is re-added by `CityServiceBuilding.Initialize` on the replacement (`src/Game/Game.Prefabs/CityServiceBuilding.cs:50-53`), which is why the ECS side looks clean.

  This is the same residue class the `RoadBuilder` finding below records — `Entity` values held in managed memory that `ReplacePrefabSystem`'s sweep cannot reach — but the example is now **vanilla and first-party** rather than one mod's own dictionary, which is a much stronger thing to ship. It also relocates the risk: the failure surfaces during a save, in a game-mode system, naming neither prefabs nor the mod that caused it.

  Still not established: how many other vanilla systems hold a prefab-entity-keyed cache, and whether any of them corrupts state rather than merely logging.
